# Email Settings

The **Email Settings** module is one screen, `EmailSettingManagement` at `/backstage/email-settings`, that manages two things which used to be one: a named master list of outbound SMTP sender profiles (`tb_email_sender_profile`), and a routing map (`email_routing`, a `tb_backstage_config` key — the **same** shared config table the [Backstage Config](/en/backstage/backstage-config) module edits) that decides which profile sends each of five outbound mail flows: sign-up/account-exists, email verification, invitation, forgot-password, and notification. The two used to be one thing — one profile row per hard-coded `purpose` enum value — until migration `20260808130000_email_profile_master_and_routing` split them apart specifically so an operator could add a new sender, or repoint a flow to a different one, from a screen instead of an enum change and a deploy (§2).

> **At a Glance**
> **Component:** `EmailSettingManagement` &nbsp;·&nbsp; **Route:** `/backstage/email-settings` &nbsp;·&nbsp; **Nav:** `permission: 'email_setting.read'`, `feature: 'email_settings'`, `groupKey: 'navGroup.backstage'` (`backstageNav.ts:44`) &nbsp;·&nbsp; **This module's own gate:** `email_setting.read` (view) / `email_setting.manage` (create/update/delete sender profiles, send a test email) — consistent on both frontend and backend for every one of its **own** endpoints (§4.1) &nbsp;·&nbsp; **The one surface that is *not* this module's own gate:** the Email Routing card, which reads and writes a `backstage_config` row through the Backstage Config module's shared endpoint — see §4.2, the mismatch this page was specifically asked to trace end to end &nbsp;·&nbsp; **e2e suite:** read-only smoke spec only (`../carmen-backstage-e2e/tests/email-settings/email-settings-smoke.spec.ts`: page renders, sidebar link present; it still targets the pre-rename `/platform/email-settings`, so its sidebar assertion on `a[href="/platform/email-settings"]` no longer matches the rendered `/backstage/email-settings` link); every behavioural claim below is sourced from `../carmen-backstage`, `../carmen-turborepo-backend` and `../micro-notification` directly &nbsp;·&nbsp; **Sub-pages:** 1

## 1. Overview

The page fetches every sender profile in one call, `emailSettingService.getAll()` → `GET /api-system/backstage/email-settings?perpage=20` (`emailSettingService.ts:11-14`), gated by `email_setting.read`, and separately loads the routing map through a shared hook, `useEmailRouting()` (`hooks/useEmailRouting.ts`), which calls `backstageConfigService.getByKey('email_routing')` — the **Backstage Config** module's own generic client, not this module's service. The hook is factored out of the routing card specifically so the card and every profile card read the identical mapping (`useEmailRouting.ts:18-24`): if each fetched its own copy, the routing panel and a profile card's "carries: Invitation, Forgot password" badge could show two different pictures of the same data on one screen.

The page lays out two peer sections (`SectionHeading`, both rendered as `<h2>`, `EmailSettingManagement.tsx:134-191`):

| Section | Component | What it edits |
| --- | --- | --- |
| Email Routing | `EmailRoutingCard` → `RoutingPanel` | The `email_routing` platform-config row — which profile each of the five flows (§3.2) sends through |
| Sender Profiles | A grid of `EmailSettingCard`, one per profile, plus an "Add Profile" placeholder card when creating | `tb_email_sender_profile` rows — name, from address, SMTP endpoint, credentials, active flag |

A component-level comment on `EmailSettingManagement.tsx:22-30` documents a deliberate visual-hierarchy fix (`#260`, commit `8fc31e7`): both section headings render at the same `<h2>` weight on purpose, because an earlier layout had the routing section with no heading of its own (bare card header) sitting visually *lighter* than "Sender profiles" below it, even though routing is the higher-level concern — the document's heading order was silently H1 → H3 → H2 → H3, skipping a level.

**Only one card can be in edit mode at a time**, tracked by a single page-level `editingPurpose: string | null` (`'routing'`, `'new'`, or a profile's `id`). Requesting to edit a second card while one is already open does not switch immediately — it raises a confirm dialog ("Discard your changes?") and only swaps `editingPurpose` on confirmation (`EmailSettingManagement.tsx:94-100, 246-259`). The page's own `useUnsavedChanges` guard fires whenever *any* card is open, for the same reason [Backstage Config](/en/backstage/backstage-config) documents for its own single-editor-at-a-time design: each card owns its own form state, so the page cannot compute per-field dirtiness without coupling to every card individually.

Saving any profile refetches the whole list (`handleSaved` → `fetchAll()`), and every profile card is keyed on `` `${setting.id}-${setting.doc_version ?? 'new'}` `` (`EmailSettingManagement.tsx:221-224`) — a save that changes `doc_version` remounts that card, resetting its form to the freshly-fetched value. This is what makes the optimistic-lock recovery path work: on a `409`, the card asks the page to refetch *without* leaving edit mode (`onSaved({ keepEditing: true })`, `EmailSettingCard.tsx:229-234`), and the remount from the new `doc_version` refreshes the form in place.

A dev-only debug panel (`DevDebugSheet`, bottom-right, same shared component [Backstage Config](/en/backstage/backstage-config) uses) renders the raw `GET /api-system/backstage/email-settings` payload — populated only when `process.env.NODE_ENV === 'development'` and rendered only when `import.meta.env.DEV` is true, so it compiles away in production regardless of the viewer's permissions. The page's own comment states this is safe to stash even with real data in it, because the API always returns `smtp_password` masked (§3.3) — it never carries a decryptable secret.

## 2. Business Context

Before migration `20260729000000_email_sender_profile`, this table did not exist at all in its current form: it was created with a `purpose` column typed to a three-value enum (`no_reply`, `support`, `billing`) and a unique index on `(purpose, deleted_at)` — one live profile per purpose, full stop. Adding a fourth kind of outbound mail meant adding an enum value and deploying. Migration `20260808130000_email_profile_master_and_routing` removed that ceiling: it renamed each existing row after the purpose it held, moved uniqueness from `purpose` to the operator-chosen `name`, dropped the `purpose` column outright, and seeded a new `tb_backstage_config` row (`key = 'email_routing'`) that pointed every one of the five mail flows at the pre-existing "No-reply" profile — so the migration itself changed nothing observable for an already-running deployment, only the storage shape underneath it. From that point on, a profile is a named, general-purpose sender an operator creates freely, and the flow-to-profile assignment lives entirely in the separate routing map (§3.2) — adding a sixth sender, or moving Invitation onto it, is a screen change, never a deploy.

**A schema fossil worth recognizing on sight:** the original `enum_email_sender_purpose` Postgres/Prisma enum type is still declared in the schema (`schema.prisma:1746-1758`) and referenced by **zero columns** — the migration dropped the *column* that used it, not the type itself. Its own doc-comment is now actively misleading: it states "a flow without its own profile falls back to `no_reply`" — true of the pre-2026-08-08 design, false of the current one, where the fallback target is whatever profile an operator has set as `default` in the `email_routing` map (§3.2), which need not be named "No-reply" at all. Do not treat this enum's comment as a description of current behavior; it documents an architecture this migration replaced.

## 3. Key Concepts

### 3.1 Two peer concerns on one screen: who can send, and who sends what

Sender profiles (§4 of the data model) and mail-flow routing (this section) are deliberately independent axes. A profile that carries zero flows still shows in the grid as fully configured, just unused (`pages.emailSettings.laneDark`, rendered by `RoutingPanel`'s `Lane` component when `carries === 0`) — deleting an unused-looking profile is still gated the same way as deleting a busy one, because "unused" is read from the routing map, which can itself still be loading or have failed to load (§4.3) when a profile card renders; `lane` is `null`, not `false`, in that window, and the card deliberately shows nothing about routing rather than a wrong "unused" claim (`EmailSettingCard.tsx`, the `lane` prop's own doc comment).

### 3.2 The five email flows — trigger, controlling setting, and where the send actually happens

`src/constants/emailFlows.ts` defines the fixed list of five flows a route can be assigned to (`EMAIL_FLOWS`, used to render both `RoutingPanel`'s lanes and each `FlowChip`'s label/menu). The list is a UI-facing *catalog* of destinations; the actual trigger, link-lifetime setting, and send call for each flow live in the backend, split across two services in `../carmen-turborepo-backend`:

| Flow | Triggered by | Controlling `backstage_config` key | Sent from |
| --- | --- | --- | --- |
| **register** | `AuthService.signupRequest()` (micro-business, `auth.service.ts:1807-1905`) — the self-service sign-up request endpoint, which always answers `200` regardless of outcome so it cannot be used to enumerate existing accounts. **Two different messages share this one flow**, chosen by the address's existing-account state: a new/reclaimable address gets `sendSignupLinkEmail()` ("Confirm your email to finish signing up," `auth.service.ts:3487-3514`); an already-owned or username-conflicting address gets `sendAccountExistsEmail()` ("You already have a Carmen Blue account" — the message that closes the enumeration oracle while still helping a real user, `auth.service.ts:3522-3538`). Both funnel through a shared helper, `sendBackstageEmail(..., 'register')` (`auth.service.ts:3549-3578`; named `sendPlatformEmail` before the 2026-10 rename). | `signup` — `verify_base_url`/`link_expiry_hours`, read via `readSignupConfig()` (`auth.service.ts:306-308`) | micro-business, via RPC `Notifications.platformEmailSend` to micro-notification |
| **verify_email** | `AuthService.resendVerificationEmail()` (`auth.service.ts:1742-1797`) — a separate, **legacy** endpoint for an account that already exists in `tb_user` with `email_verified_at: null` (created directly, or predating the sign-up flow's 2026 reversal); simultaneously live alongside `register` above, not superseded by it. Sends `sendEmailVerification()` ("Verify your email address," `auth.service.ts:3429-3478`). | `email_verification` — `base_url`/`expiry_hours`, read via `readEmailVerificationConfig()` (`auth.service.ts:315-321`, called at 1777) | micro-business, via the same RPC call |
| **forgot_password** | `AuthService.forgotPassword()` (`auth.service.ts:2076-2207`), which calls `sendPasswordResetEmail()` **fire-and-forget** (no `await`, call at line 2170) so a mail-send failure never fails the forgot-password request itself (`sendPasswordResetEmail`, `auth.service.ts:3339-3412`, comment around 3394-3399 explains the deliberate non-throw). Sends "Password Reset Request" with both a link and a short code. | `password_reset` — `base_url`/`expiry_hours`, read via `readPasswordResetConfig()` (`auth.service.ts:328-334`) | micro-business, via the same RPC call |
| **invitation** | `UserInvitationService` (micro-cluster, `user-invitation.service.ts`) — three distinct call sites, all this one flow: `sendInvitationEmail()` (lines 296-355, RPC call at 329) sends the invite link itself, called from `createInvitation()` and `resendInvitation()`; `notifyAccountCreatedFromInvitation()` (lines 1245-1290, RPC call at 1267) sends an account-created confirmation when an invited user completes sign-up via `acceptWithSignup()`; `notifyAddressConflict()` (lines 1327-1435, RPC call at 1403) sends a conflict notice when acceptance collides with an existing account. | `invitation` — `base_url`/`expiry_days` half of the two-card `invitation` key documented on [Backstage Config](/en/backstage/backstage-config)'s landing page §3.2 | micro-cluster, via the same RPC call |
| **notification** | **Only external callers, through `micro-notification`'s REST `POST /v1/emails`.** Re-checked 2026-10-27: no service in the Carmen monorepo, `micro-report`, `micro-cronjobs` or `micro-data` passes `flow: 'notification'` — the six in-monorepo call sites of `Notifications.platformEmailSend` (`packages/notification-contract/src/rpc.ts:62`) are three in `auth.service.ts` (lines 3368 `forgot_password`, 3452 `verify_email`, 3558 the shared `sendBackstageEmail()` helper both `register` messages use) and three in `user-invitation.service.ts` (lines 329, 1267, 1403), all for the other four flows. What changed is that `micro-notification` (now its own repo, `../micro-notification`) gained a public REST `/v1` surface (commits `b52f85e`, `402bf79`, `2627aad`, 2026-10-05): `POST /v1/emails` (`src/v1/v1.controller.ts`, scope `emails:send`) accepts **only** `flow: 'notification'` (any other flow is a 400 on `path: ['flow']`), requires a single bare recipient address whose domain is in the calling API client's mandatory `allowed_email_domains` allowlist (403 `RECIPIENT_DOMAIN_NOT_ALLOWED` otherwise — no open relay), and then sends through the same routing resolver as every other flow. API clients (id, SHA-256 of key, scopes, domain allowlist) are configured in that service's `NOTIFICATION_API_CLIENTS` env value (`src/v1/api-client.config.ts`). So the routing panel's "Notification" lane is live for systems outside the monorepo; nothing inside it uses it. | *(none — the `signup`/`email_verification`/`password_reset`/`invitation` link settings do not apply)* | micro-notification itself (REST caller → `PlatformEmailService.send`) |

**The `notification` flow above is a different thing from the `notification_email` backstage-config key** documented on [Backstage Config](/en/backstage/backstage-config)'s own page (§3.2 there) — that key is a separate, unrelated `tb_backstage_config` row (recipient list + subject prefix for internal report/notification mail), which that module's own research found had no confirmed reader. Do not conflate them: this page's `notification` flow is an **email-routing lane** whose only sender is the external `/v1/emails` route; the Backstage Config page's key is a **config key** with no confirmed reader. Neither confirms nor depends on the other.

### 3.3 How a flow becomes an SMTP send — and what happens when it cannot

Every flow above ends at the same resolver, `PlatformEmailService.resolveProfile()` (`../micro-notification/src/platform-email/platform-email.service.ts:186-212` — the service moved out of the monorepo into its own repo; the class and folder keep their `Platform*` names): it reads the live `email_routing` row from `tb_backstage_config`, validates it against a Zod schema, looks up `routing[flow] ?? routing.default`, and loads that `tb_email_sender_profile` row **only if** it is not soft-deleted and `is_active` is `true`. If the row is missing, deleted, or inactive, `send()` reports `{ sent: false, reason: 'no-config' }` and logs a warning naming the flow and the dangling profile id — it never falls back to any other profile or to environment variables.

**There is no environment-variable fallback anywhere in this file**, despite a doc-comment on the sibling method `resolveSmtpConfig()` claiming otherwise ("A failed lookup does not short-circuit; it falls through to env exactly as `send()` does," `platform-email.service.ts:268`). The only `process.env` read in the entire file is the database connection string (`SYSTEM_DATABASE_URL`, line 165); `send()` returns `no-config` on an unresolved lookup exactly as described above, with no env read at all. `resolveSmtpConfig()` itself is additionally dead code today — grepped across all of `../micro-notification/src`, it has **zero callers** (only its own definition at line 272); only `send()`, `sendTest()`, and `sendWithConfig()` are wired to the `@MessagePattern` handler that micro-business and micro-cluster actually call. Its doc-comment describes a future integration ("made public so the internal-notification path shares one SMTP source") that does not exist in the current codebase — treat the comment as an aspiration, not a description of what runs today.

**A fresh, never-configured deployment starts with an unusable placeholder.** The `email_routing` key's registry default (`apps/micro-cluster/src/cluster/backstage-config/backstage-config.schema.ts:340-345`, same registry [Backstage Config](/en/backstage/backstage-config) documents; the comment above it, line 335, still says "micro-notification falls back to the old env vars while no row exists", which the resolver contradicts — it returns `no-config` and reads no env vars) is `{ default: '00000000-0000-0000-0000-000000000000' }` — an all-zero UUID that matches no real profile, by design (the registry's own comment says there is no meaningful default because profile ids differ per environment). In practice this default is never reached on an upgraded deployment: migration `20260808130000_email_profile_master_and_routing` seeds a real mapping pointing every flow at the pre-existing "No-reply" profile at migration time (§2). A genuinely fresh environment with no such profile to seed from would sit on the placeholder default — every flow returns `no-config` — until an operator creates at least one profile and saves a routing map with a real `default`.

### 3.4 Password handling

`smtp_password` is stored encrypted (`enc:v1`, AES-256-GCM, `decryptSecret`/`encryptSecret` from `@repo/secret-crypto`) and is **never** returned in plaintext by any endpoint — `findAll`/`findOne`/`create`/`update` all mask it to a fixed `••••••` string before responding (`email-sender-profile.service.ts:41-43`). The frontend's `PasswordField` component treats the mask as "no change, do not resend": the save payload omits `smtp_password` entirely unless the operator has actively typed a new value (`PasswordField.tsx:40-43`), and an empty string is likewise treated as "unchanged," not "clear" — the field's own comment states this is deliberate, so that clearing a text box by accident can never blank out a working credential (`PasswordField.tsx:13-15`). The backend's own `passwordPatch()` (`email-sender-profile.service.ts:51-56`) *would* accept an explicit `null`/`''` to clear the stored password, but nothing in this screen's UI can produce that value — clearing a profile's password is not reachable from the Email Settings screen today, only replacing it with a new one.

### 3.5 Sending a test email

Each configured profile's non-editing state shows a "Send test email" action, opening `TestEmailDialog`, which defaults the recipient to the caller's own address when it looks like an email (`user.email.includes('@')`, since `AuthContext` can populate `user.email` from a username rather than an address) and otherwise leaves the field blank for the operator to fill in. The send goes through this module's own endpoint, `POST /api-system/backstage/email-settings/:id/test` (`email_setting.manage`, not `.read` — sending mail, even a test, requires the write permission), which is proxied to micro-notification's `sendTest()` — the only path in this service that loads a profile **without** checking `is_active`, so a deactivated profile can still be smoke-tested before being turned back on. Failure reasons (`smtp-error`, `decrypt-failed`, `lookup-failed`, `no-config`) are mapped to distinct, actionable toast messages (`TestEmailDialog.tsx:27-33`) rather than one generic failure string.

## 4. Roles and Permissions

### 4.1 This module's own gate — consistent everywhere

| Surface | Permission | Source |
| --- | --- | --- |
| Sidebar entry, `/backstage/email-settings` route | `email_setting.read` + feature `email_settings` | `backstageNav.ts:44`; `App.tsx:537-543` |
| Every Sender Profile card's Edit/Configure, Send test email, Unset buttons | `email_setting.manage` (`canManage`) | `EmailSettingManagement.tsx:48`, passed down as the `canManage` prop |
| `GET`/`POST`/`PUT`/`DELETE`/`POST .../test` on `/api-system/backstage/email-settings*` | `email_setting.read` (list/get) or `email_setting.manage` (create/update/delete/test) | `backstage_email-settings.controller.ts:77, 118` (read) and `:155, :193, :237, :274` (manage) |

Every one of this module's **own** REST routes matches its frontend gate exactly — list/get on `.read`, every write (including the test-send) on `.manage`. There is no asymmetry inside this table.

### 4.2 The one surface that is not this module's own gate — the Email Routing card, traced end to end

This was flagged forward by the [Backstage Config](/en/backstage/backstage-config) module's own task as a mismatch to verify, not assert. Tracing it end to end, on both the read and write sides:

**Read side.** `useEmailRouting()` calls `backstageConfigService.getByKey('email_routing')` → `GET /api-system/backstage/configs/email_routing`, which the Backstage Config module's controller gates on **`backstage_config.read`** (`backstage_configs.controller.ts:210-212`) — not `email_setting.read`. This call runs unconditionally whenever the Email Settings page mounts, for **every** viewer, regardless of whether they can manage anything. A session holding `email_setting.read` alone (enough to reach this page at all) but lacking `backstage_config.read` sees the Sender Profiles grid load normally — that call is gated correctly, on this module's own key — while the Email Routing card above it permanently shows a load error (`loadError`, `EmailRoutingCard.tsx:166-167`), because the one API call it depends on is gated by a resource this module's own screen never checks for.

**Write side.** `EmailRoutingCard.handleSave()` calls `backstageConfigService.update('email_routing', payload)` → `PUT /api-system/backstage/configs/email_routing` (`EmailRoutingCard.tsx:124`). Reaching a *live* Save button at all requires clearing **two** gates on the frontend, not one: `canManage` — `hasPermission('email_setting.manage')`, computed once on the page (`EmailSettingManagement.tsx:48`) — **and** `!routingError` (`EmailSettingManagement.tsx:140-143`), which is only false once the read call in §4.2's "Read side" above has already succeeded. `EmailRoutingCard` itself contains no permission check of its own, trusting the page entirely, but the page's own read-error guard means the button structurally cannot render for a session whose `GET` already 403'd. The **backend** endpoint the eventual Save actually hits requires `backstage_config.manage` (`backstage_configs.controller.ts:252-254`, the `PUT` route's `@RequireBackstagePermission` decorator, enforced by `BackstagePermissionGuard` *before* the handler body runs) — and `writeKeyDenial()`, the handler's own per-key second gate, adds nothing further for `email_routing`; it only tightens `license` and `backstage_migration` (documented on [Backstage Config](/en/backstage/backstage-config) §3.3). `email_routing` is not one of those two, so `backstage_config.manage` alone is what the endpoint checks.

**The two keys do not agree — but the trap only reaches one specific combination, not "`email_setting.manage` without `backstage_config.manage`" in general.** Because the button is gated on `!routingError` (read side), a session needs `backstage_config.read` to succeed *before* it can ever see a Save button on this card at all. The live-looking trap therefore requires **`backstage_config.read` present and `backstage_config.manage` absent**, on top of this module's own `email_setting.read`/`.manage`: the panel loads normally, the button renders, the editor opens, every flow chip can be reassigned — and clicking Save 403s, rejected by `BackstagePermissionGuard` before `writeKeyDenial()` or any application code ever runs, because the resource the endpoint decorator names is `backstage_config`, not `email_setting`. A session that has `email_setting.manage` but **no** `backstage_config.*` at all never reaches this trap — it fails at the read gate first (§4.2 "Read side"), and the button never appears for it to click. There is no reachable combination in the other direction either: a session holding only `backstage_config.*` and nothing in `email_setting.*` cannot even load `/backstage/email-settings` in the first place, since the route itself requires `email_setting.read` (`App.tsx:540`).

**This confirms, rather than contradicts, the Backstage Config module's own forward-flagged account**, with one correction to how the write-side trap is reached. That module described the identical shape from its own side (§3.5 of its landing page) and explicitly left verification to this task. Reading both sides independently: `email_setting.manage` is necessary but not sufficient to save the routing map from this screen — but it is not sufficient in a very specific way, because the read gate (`backstage_config.read`) has to succeed first for the Save button to exist at all. `backstage_config.manage` is the one gate that, missing on its own with `backstage_config.read` present, produces a working-looking editor that cannot save.

### 4.3 Three sessions, three different outcomes

The read gate's veto over the button (§4.2) means "grant `email_setting.*` alone" does **not** reproduce a write trap — it only reproduces a read failure. The three combinations worth testing separately:

| Session holds | What happens on this screen |
| --- | --- |
| `email_setting.read`/`.manage` only — no `backstage_config.*` | Sender Profiles grid loads and is fully editable (gated correctly on this module's own key). Email Routing's `GET` 403s, `routingError` is set, and the Edit Routing button **never renders** — a permanent load error, not a write trap. |
| `email_setting.read`/`.manage` **plus** `backstage_config.read`, but **not** `backstage_config.manage` | Email Routing's `GET` succeeds, the panel loads normally, and the Edit Routing button renders (`canManage` and `!routingError` both true). The editor opens, every flow can be reassigned — and Save 403s. **This is the actual write-side trap**, and it requires `backstage_config.read` specifically, not just "some `backstage_config` permission." |
| `email_setting.read`/`.manage` plus `backstage_config.read`/`.manage` | Works as designed — the only combination that does. |

**Answered from the seed (2026-10-27):** the middle row needs a role that holds `email_setting.manage` and `backstage_config.read` but not `backstage_config.manage`. No built-in role has that shape. In `seed.backstage-role-permission.data.ts`, Backstage Admin holds `email_setting.*` and `backstage_config.*` (lines 23 and 32), so it is the "works as designed" row; Support Manager holds only `email_setting.read` and `backstage_config.read` (lines 74-75) — it reaches the page and sees the routing map read-only, with no Edit buttons because `canManage` is false; Support Staff and Security Officer hold neither. The write-side trap is therefore reachable only through a custom role assembled in the Backstage Roles screen, never through a seeded one. The PUT endpoint also now rejects a body that omits any schema field with 422 (a `PATCH` on the same path merges instead, `backstage_configs.controller.ts:252, 309`); the routing card always sends its full draft object, so it is unaffected.
