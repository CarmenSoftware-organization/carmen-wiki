# License Catalog

The **License Catalog** module is one screen, `LicenseCatalog`, rendered behind two separate routes and switched by a `tab` prop: `/license-features` (the **Features** tab, `FeatureCatalogPanel`) and `/license-modules` (the **Modules** tab, `GroupCatalogPanel`). This is a documentation merge, not a product merge — the two tabs kept their own historical nav rows, permission pairs, and feature-flag keys throughout, and this page documents both under one module because they answer one question together: *what does Carmen Blue sell, and how is it packaged?* **Features** is the raw catalog of sellable capabilities, generated from the permission map and editable only for `state` (sellable / not-yet-sellable / hidden). **Bundles** is the admin-curated set of named packages — spanning any features from any part of the catalog — that a subscription actually picks from on the [Licenses](/en/backstage/licenses) module's sales screen. A third route, `/license-modules/{new,:id/edit}`, renders a distinct component, `LicenseFeatureGroupEdit`, for creating and editing one bundle.

> **Wording change, 2026-10-27:** the SPA now calls a license feature group a **Module** (sidebar "License Modules", tab "Modules", editor "New module") and calls the old root of the feature tree a **Feature area** (`../carmen-backstage` commit `e848573c`, i18n text only). Tables, API paths, i18n keys, code names and the component's `tab: 'bundles'` value are unchanged, so this page and its sub-pages keep saying *bundle* / *group* when they mean code or data, and say *Modules tab* when they mean the screen. The sale-side "Module" (Procurement, Inventory, Recipe, GL, AP, AR, Asset, Income) is exactly one `tb_license_feature_group` row.

## 1. Overview

- **`/license-features` → `LicenseCatalog` (`tab="features"`) → `FeatureCatalogPanel`** — the read-oriented catalog screen. Every non-deleted feature row, including hidden ones, grouped into a "shelf" per root module with an n-tier indent for children and grandchildren. The only edit surface is a per-row state toggle (`active` / `inactive` / `hide`); rows themselves belong to a backend generator (`scripts/generate-license-catalog/run.ts`), not this screen.
- **`/license-modules` → `LicenseCatalog` (`tab="bundles"`) → `GroupCatalogPanel`** — the curated-module (bundle) list: one row per named group, a Features-composition bar sharing a page-wide divisor, a subscription-count column, active/inactive status, and row actions to edit or delete.
- **`/license-modules/new`, `/license-modules/:id/edit` → `LicenseFeatureGroupEdit`** — a standalone route (not a tab inside `LicenseCatalog`) for creating or editing one bundle: its identity, its sort position on the sales form, its active/inactive status, and the set of features it grants.

Both tab routes and both `LicenseFeatureGroupEdit` routes are guarded by `PrivateRoute` with a `requiredPermission` and a `feature` flag (`App.tsx:319-350`); see §4 for the full matrix, including the one route (`:id/edit`) that requires only the read key.

## 2. Business Context

Selling Carmen Blue inventory features to a business unit happens in two decoupled steps, and this module owns both of them:

1. **Deciding what is sellable at all.** Every route in the product maps to a permission resource, and every permission resource that should be *sellable* — not just access-controlled — gets a matching row in `tb_license_feature`, generated automatically from the permission map (`permission.route-map.ts` + `seed.permission.data.ts`). A platform admin cannot add a feature by hand; the only lever this screen gives them is turning an existing one off (`inactive` — stop selling new instances of it) or all the way off (`hide` — take the menu away from everyone who already has it).
2. **Packaging what is sellable into something a salesperson picks from once.** Ticking over a hundred individual feature checkboxes for every new contract does not scale and does not match how Carmen Blue actually sells — customers buy a plan, not a checklist. **Bundles** (`tb_license_feature_group`) are the admin-curated answer: a named, orderable, freely-cross-module set of feature keys that a [Licenses](/en/backstage/licenses) subscription references as a whole (`tb_subscription_bu_group`), not by unpacking it into individual feature rows on the contract.

The two steps are deliberately separate roles: deciding what *can* be sold (this module) and deciding what a specific customer *did* buy (the [Licenses](/en/backstage/licenses) module) are different jobs, gated by entirely different permission resources.

## 3. Key Concepts

### 3.1 One component, two tabs, three deliberate decisions

`LicenseCatalog.tsx`'s own comments name three choices a tester would otherwise file as bugs:

- **Switching tabs navigates — it does not swap state.** `TabStrip`'s `onChange` calls `navigate(TAB_PATH[next])`, which changes the route, remounts `LicenseCatalog`'s child panel, and triggers a fresh fetch. Nothing is cached across tabs. This is intentional: both panels fetch once and are already structurally capped in size (the feature catalog and the group list are both curated, not usage-scaled data), so the cost of a fresh fetch on every tab switch is negligible, and the alternative — an in-memory cache spanning two differently-permissioned routes — is complexity nobody asked for.
- **The page header's title never changes; only the subtitle does.** `PageHeader`'s `title` is always `t('pages.licenseCatalog.title')` ("License Catalog"), regardless of which tab is active — only `subtitle` switches between `pages.licenseFeatureGroups.subtitle` and `pages.licenseFeatures.subtitle`. A title that changed per tab would make the merge unreadable as *one place*; that is the entire reason this is documented as one module and not two.
- **The tab strip disappears when only one tab is reachable.** `tabs` is computed by filtering `TAB_ORDER` through both `hasPermission(gate.permission)` **and** `flagOf(gate.feature) === 'active'` for each tab's own gate (`TAB_GATE`, §4) — a client-side re-check of exactly what the route guard already enforced — and the strip renders only when `tabs.length > 1`. A session that can reach only one of the two tabs sees a single, un-tabbed screen with no dead control pointing at a tab it cannot open.

### 3.2 The catalog is a generator-owned n-tier tree, not a flat list

`tb_license_feature` rows come **only** from `scripts/generate-license-catalog/run.ts`; `licenseFeatureService` has no create or delete by design — the only thing an operator owns is `state`. Since the 2026-09-03 "license feature tree" work (`docs/superpowers/specs/2026-09-03-license-feature-tree-design.md`, phases A–C, all shipped same day), `parent_key` is **the longest prefix that actually exists in the catalog**, not simply the text before the first dot — so a key can sit three levels deep (`accounting.config.ap`, parent `accounting.config`, root `accounting`). `moduleOf()` (`featureSelection.ts:26`) still only ever returns the **root** module and remains valid for that one purpose; walking the full ancestor chain requires `ancestorsOf()`/`descendantKeys()`/`flattenDescendants()` (`utils/featureTree.ts`), not string-splitting on the first dot.

**A source comment in this codebase is stale — verify counts against generator data, not against it.** `FeatureCatalogPanel.tsx`'s own doc-comment and `ModuleShelf.tsx`'s describe "76 rows" / "10 modules + 66 children" — both predate the 2026-09-03 tree work. Counting `"key":`/`"parent_key": null` entries directly in `seed.license-feature.data.ts` (the generator's own output, `../carmen-turborepo-backend` HEAD `c9d788829`, 2026-10-27) gives **112 rows across 13 root feature areas** — `accounting`, `ai`, `configuration`, `dashboard`, `interface`, `inventory_management`, `operation_plan`, `procurement`, `product_management`, `report`, `store_operations`, `system_admin`, `vendor_management` — of which **105 are seeded `active`** (sellable today) and **7 are seeded `inactive`** (all `accounting.*` keys registered ahead of their real endpoints, per Phase C of the design doc — seeded not-active specifically so a feature with no route behind it cannot sell on day one, the same class of bug the generator's own code comments say happened once already with `report.schedule`). The count moved from 107/12/100/7 (the 2026-09-22 baseline) to 112/13/105/7 by +5 keys net, diffed against the 2026-09-22 seed file: a new **`ai` root** (`ai`, `ai.mcp` — the MCP-token licence, moved under `ai` by migration `20261014230000_move_mcp_license_under_ai`), `configuration.customer`, and an interface-brand reshuffle — `interface.accounting.external` became `interface.export.external` under a new `interface.export` category (migration `20261018120000_move_external_interface_under_export`, which renames the catalog row and rewrites every group item so no BU loses the licence), and `interface.pos.micros` was replaced in the seed by two keys, `interface.pos.micros3700` and `interface.pos.simphony` (commit `2cfc4c04f`; no SQL migration rewrites existing `interface.pos.micros` group items — see the ticket note in the report). Before that, the count had moved from 89/11/79/10 (the 2026-09-06 baseline) by +19/−2 keys, diffed directly against the 2026-09-05 seed file: the **`interface` module** (as first added: 12 keys — `interface`, three category rows `interface.{accounting,pos,pms}`, and eight brand leaves; **today 14 keys**: `interface`, four categories `interface.{accounting,export,pos,pms}`, and nine leaves — `accounting.{carmen_gl,blueledgers}`, `export.external`, `pos.{infrasys,micros3700,simphony,square}`, `pms.{opera,protel}`), added 2026-09-08 when interface entitlement became a licence feature; five `configuration.*` keys (`chart_of_account_mapping`, `email_profile`, `email_template`, `cost_center`, `cost_center_group`); two `accounting.gl.*` keys (`budget`, `jv_template`, for the new GL budget/JV-template endpoints); and the rename `system_admin.period` → `system_admin.inventory_period` (2026-09-16, `20260916140000_rename_period_to_inventory_period` — the same migration renamed the permission resource and the `period.*` `api_name`s, and a follow-up `20260916150000` fixed `tb_license_feature_group_item.feature_key`, which the first migration had missed because that join is a soft string reference with no FK, leaving every BU's group pointing at a key that no longer existed and `LicenseInterceptor` answering `403 LICENSE_REQUIRED` on every `/inventory-periods` call). `system_admin.query_dataset` was removed. The `interface.*` keys, `ai`/`ai.mcp` and two `configuration.*` keys (`email_profile`, `email_template`; `chart_of_account_mapping` is no longer in the set) arrive through a **new generator source set, `LICENSE_ONLY_RESOURCES`** (`permission.route-map.ts:472`): keys that are real and already sold but have **no permission and no route** behind them, which the generator emits as `active` and exempts from `assert_planned_sets_agree()`. They could not go through the pre-existing `PLANNED_LICENSE_RESOURCES` set, because that set forces `inactive` (a group could keep such a key but never add it, so nobody could ever sell an interface to a new BU) and additionally requires membership in `PLANNED_RESOURCES`, which would lie to `check-endpoint-permission`. No `interface.*` key appears in `license-catalog.generated.ts`'s route→feature map, so `LicenseInterceptor` never gates an interface route — enforcement is by the inventory frontend reading `GET /api/license` ([Licenses](/en/backstage/licenses) §3.6). See [Data Model](/en/backstage/license-catalog/data-model) §3 for the full shape and the hide-at-a-middle-tier hazard this tree structure creates.

### 3.3 `state` here is not the same concept as `state` on the Feature Flags screen

`FeatureCatalogPanel.tsx` defines its own `LICENSE_STATE_LABEL`/`LICENSE_STATE_HINT` key sets specifically so nobody reuses the ones from `/backstage/features` (the unrelated **Feature Flags** module, `feature_flag.manage`) — the two screens share the string values `active`/`inactive`/`hide` but mean different things by them. On Feature Flags, `hide` makes a whole screen and route vanish from the SPA. Here, `hide` means "no business unit may newly acquire this, and every BU that already holds it loses the menu item" — a commercial decision, not a routing one.

### 3.4 Bundles are curated, not derived from the module tree — and since 2026-09-10 they have a kind

A bundle (`tb_license_feature_group`) is a hand-picked, free-form set of feature keys — it can span `inventory.count` and `report.daily` in one group, unlike a "module" which is always a contiguous branch of the tree (§3.2). Since migration `20260910000000_license_feature_group_kind` every bundle also carries `kind`: `standard` (sold on the main subscription — the default) or `interface` (sold one-per-licence on an interface licence, `INF`). The kind is chosen with a segmented control on the create form and is **locked afterward** — the edit form shows it read-only with the hint "Set when the group is created — changing it would move sold entitlements between license kinds", and the backend's update DTO does not accept it. The Bundles list marks `interface` bundles with a badge and exports the kind in CSV. The kind is not derived from the keys inside (the backfill on 2026-09-10 did derive it once, marking as `interface` every group whose live items were *all* `interface`/`interface.*`, but mixed and empty groups stayed `standard`) — the column is the source of truth, and the backend refuses with 400 both an `interface` group on a subscription and a `standard` group on an interface licence. The design reasoning — why a column and not a code prefix or key inspection — is in `../carmen-backstage/docs/superpowers/specs/2026-09-09-interface-license-split-design.md` §2. Two rules govern what a bundle can actually hold: **the server enforces "a selected child drags its full ancestor chain in with it"** on every `PUT .../features` call (walking `parent_key` to full depth before validating, not just once at the first level) — so a bundle can never be saved holding a feature but missing one of its parent modules, which the license evaluator would otherwise treat as an incomplete grant. The picker UI (`FeatureSelectionCard`, used **only** by [UI Screens](/en/backstage/license-catalog/ui-screens) §5 now — it was removed from the sales/subscription flow entirely in License Catalog's own Phase 4, per the same design doc) enforces the identical rule client-side, but the server-side check is the real gate, since `PUT` can be called directly.

## 4. Roles and Permissions

This module has no dedicated Permissions sub-page — both permission pairs are small enough to document here in full.

### 4.1 Frontend route gate matrix

All routes resolve through `PrivateRoute`, which checks `requiredPermission` first (failure → `<Forbidden>`, in place) and the `feature` flag strictly afterward (failure → `NotFound` on `hide`, `ComingSoon` on `inactive`) — see [Backstage Roles — Permissions](/en/backstage/rbac/permissions) for the shared resolver.

| Route | Permission | Feature flag | Component | Source |
|---|---|---|---|---|
| `/license-features` | `license_feature.read` | `license_features` | `LicenseCatalog` (`tab="features"`) | `../carmen-backstage/src/App.tsx:319-326` |
| `/license-modules` (legacy `/license-feature-groups/*` redirects here via `LegacyLicenseModuleRedirect`, `App.tsx:656`) | `license_feature_group.read` | `license_feature_groups` | `LicenseCatalog` (`tab="bundles"`) | `App.tsx:327-334` |
| `/license-modules/new` | `license_feature_group.manage` | `license_feature_groups` | `LicenseFeatureGroupEdit` | `App.tsx:335-342` |
| `/license-modules/:id/edit` | **`license_feature_group.read`** | `license_feature_groups` | `LicenseFeatureGroupEdit` | `App.tsx:343-350` |
| Sidebar "License Modules" (nav key `nav.licenseFeatureGroups`) | `license_feature_group.read` | `license_feature_groups` | — | `../carmen-backstage/src/components/nav/backstageNav.ts:25` |
| Sidebar "License Features" | `license_feature.read` | `license_features` | — | `backstageNav.ts:26` |

**The edit route requires only the read key, matching the pattern the [Licenses](/en/backstage/licenses) module documents for its own purchase-form edit routes.** A `license_feature_group.read`-only session can open `/license-modules/:id/edit` and see a bundle's full detail; `LicenseFeatureGroupEdit.tsx:104`'s own `canManage = hasPermission('license_feature_group.manage')` is what actually decides whether any field renders editable, whether the feature picker is `readOnly`, and whether the sticky save bar renders at all (`{canManage && (...)}` — a `read`-only session sees no save bar, not a disabled one).

In-page gates, both on `license_feature_group.manage`: the **New module** button and empty-state action and the row-actions dropdown's **Edit**/**Delete** items (all `<Can permission="license_feature_group.manage">` in `GroupCatalogPanel.tsx`) — a `.read`-only session sees the list and the composition bars, but no way to create, edit, or delete a bundle from the list screen itself (it can still reach `:id/edit` by URL and see the read-only detail, per the paragraph above).

### 4.2 Backend enforcement

All paths below are `../carmen-turborepo-backend/apps/backend-gateway/src/backstage/`, HEAD `c9d788829` (2026-10-27). Routes live under `@Controller('api-system/backstage')` (renamed from `api-system/platform`).

| `PATCH license-features/:id` | same, `license_feature.manage` | `backstage_license_features.controller.ts:106-108` |
| `GET license-feature-groups` | `license_feature_group.read` | `backstage_license_feature_groups/backstage_license_feature_groups.controller.ts:85-87` |
| `GET license-feature-groups/:id` | `license_feature_group.read` | `backstage_license_feature_groups.controller.ts:119-121` |

Unlike the [Licenses](/en/backstage/licenses) module (where every `GET` on the licence ledgers carries no `@RequireBackstagePermission` at all, authorized instead by cluster scope), **every route in this module — reads included — carries an explicit `@RequireBackstagePermission` decorator.** There is no scope-based fallback here: this catalog and its bundles are platform-wide, not cluster-scoped, so there is no narrower scope for a guard to fall back to.

### 4.3 A cross-module permission dependency, not this module's own key

**Verify this before assuming the Bundles tab is self-contained on permissions.** `GroupCatalogPanel`'s Features-composition divisor and `LicenseFeatureGroupEdit`'s entire feature picker both load their catalog through `subscriptionService.getFeatureCatalog()`, which calls `GET /api-system/backstage/license-features` — **not** `/license-features/all`. That plain route is defined in a different controller entirely, `backstage_subscriptions/backstage_subscriptions.controller.ts:251-253`, and requires **`subscription.read`** — the [Licenses](/en/backstage/licenses) module's own key, not `license_feature.read` or `license_feature_group.read`.

Consequence: a session holding `license_feature_group.read` + `license_feature_group.manage` but **not** `subscription.read` can fully open `/license-modules`, list bundles, and open `/license-modules/:id/edit` to change a bundle's name, sort order, or active status — but the Features-count composition bar on the list silently disappears (`catalogTotal` stays `null`, no divisor to draw a bar against), and the feature picker on the edit page fails outright (`catalog.failed === true`, rendering a retry button in place of the picker) — blocking the one thing that screen exists for, without the route itself ever having said no. This is a real, verified cross-module dependency, not a bug in either module: the shared endpoint exists because the same "which features are currently sellable" catalog is what a subscription's feature picker needs too, and reusing one endpoint avoids two implementations of "filter out `hide`" ever disagreeing.
