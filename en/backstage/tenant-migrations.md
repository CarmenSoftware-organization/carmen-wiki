## 1. Overview

Tenant Migrations is the platform's fleet-wide console for the tenant-schema Prisma migrations every business unit's own database must eventually pick up. It lives at its own top-level route, `/tenant-migrations`, with its own sidebar entry in the Organization group (rendered as a sub-row beneath Business Units, next to Tenant Seed Data and Data Import) — its own route, permission (`tenant_migration.read`) and feature flag, even though its row list comes from the same business-unit service the Business Units list page uses (`fetchAllBusinessUnits({ sort: 'code:asc' })`, which pages through the list 100 at a time, up to 10 pages). `TenantMigrationManagement.tsx` lists every business unit returned by that call in one table and lets an operator check, apply, or batch-deploy pending migrations across the whole fleet from a single screen — the same underlying backend capability the per-BU `TenantMigrationCard` on the [Business Units edit page](/en/backstage/business-units/ui-screens) §4.5 exposes for one BU at a time (§3.5).

Reaching the page, seeing the BU table and running **Check** needs `tenant_migration.read` plus this module's `tenant_migrations` feature flag. Anything that changes a tenant database — Apply, Deploy all, Resolve, Apply dashboard views — additionally needs `tenant_migration.apply`: the frontend disables those buttons with a "Requires the tenant_migration.apply permission." tooltip, and the backend's `TenantMigrationGuard` checks the same key per route regardless of what the frontend does (§4). Before 2026-09-29 the whole screen was super-admin-only (`isSuperAdmin`); that gate is gone. Historically, this module's content lived as a sub-page of Business Units (`business-units/tenant-migrations.md`); it has been relocated here because `/tenant-migrations` has always been its own route, its own nav entry, and its own feature key (`tenant_migrations`, distinct from `business_units`) — the [Business Units](/en/backstage/business-units) page now links here for the fleet-wide picture and keeps only the embedded per-BU card's story on its own sub-page.

## 2. Business Context

A Carmen Blue deployment runs one Prisma-managed schema per business unit (property/hotel), all sharing the same migration history defined in one `@repo/prisma-shared-schema-tenant` package. Whenever that package gains a new migration, every tenant schema across every cluster needs `prisma migrate deploy` run against it before the corresponding application code can rely on the new columns/tables — and a hospitality operator can have dozens of properties on differently-paced rollout schedules. Without a fleet view, an operator would have to open each BU's own edit page and check its Technical tab one at a time; this screen exists specifically to answer "which tenants are behind, and by how much" in one glance (`FleetSync`, §3.1), and to let an operator holding `tenant_migration.apply` (or a CI/CD pipeline via a deploy token, §4.2) push all of them forward — or roll through the whole fleet in one batch — without leaving the page.

## 3. Key Concepts

### 3.1 Screen layout

- **Header** — `PageHeader` titled "Tenant migrations", subtitle "Check which tenant databases are behind on schema migrations, and roll them out."
- **Fleet Sync summary card** (`FleetSync`) — a horizontal card showing `{in-sync count} / {total BUs}` in large monospace type, a three-segment (green/amber/red) progress bar for in-sync/behind/errored, and a legend row with counts (a total-pending-migrations figure appears only once it is non-zero). Before the first "Check all" run it shows "Not checked yet" instead of the bar. The card's action slot holds **Check all**, **Deploy all**, and **Export**.
- **Deploy Console** (`DeployConsole`) — renders only while a "Deploy all" batch is in flight: a dark terminal-style panel with a progress bar (applied/total for the BU currently migrating), the current BU code, and a scrolling, colour-coded log line per completed BU (green for applied/up-to-date, red for failed).
- **Search box** — client-side filter over the BU table (code/name), focusable via the global search shortcut.
- **BU table** (`DataTable`, 3 sticky-left columns) — **Code** (links to `/business-units/:id/edit`), **Name**, **Schema** (new, PR #296 — the BU's `db_schema` in monospace with the linked `tb_database_pool` name beneath it in smaller text, `—` when no schema is set; this is the one derived column that is deliberately left searchable, since typing a schema name and finding the row that points at it is a real operator question), **Status** (a badge — "In sync" / "N behind" / "Error" / "Not checked", plus an inline "Applying X/Y … current-migration-name" line while a row's Apply is streaming, or an inline error message; once a row has been checked, a second badge shows the dashboard-views state — "N views behind" or "Views in sync" — or an inline "Views: …" error if micro-data could not report), **Last checked** (HH:MM:SS, client-local), and a row-actions column (icon-only **Check**, **Apply** only when that row has pending migrations, an **Apply dashboard views** icon on every checked row (disabled, with an "Views in sync" tooltip, when nothing is behind — §3.2c), and — since PR #297 — a **Resolve** wrench icon on every row whose status is `error`, §3.2a). Status and Last checked sort client-side by header click since PR #292 (`accessorFn` over the already-derived rank/time — the `accessorFn` exists only to enable the sort button; both columns are explicitly excluded from the search box so a status rank or a timestamp can never match a typed search term). There is no on-screen Pending count column — the Status badge already states the count ("3 behind" / "In sync"); the CSV export (below) keeps one, plus the Schema and pool columns, since a bare value is genuinely useful there for further calculation.
- **Empty state** — "No business units" with a "Go to Business Units" button, shown when the fleet has zero BUs (not zero pending migrations).
- A dev-only `DevDebugSheet` shows the raw business-unit list the page loaded.

Since `254b05ee` (2026-09-30) the list is loaded with `fetchAllBusinessUnits`, which pages through `GET /api-system/business-units` (page size 100, at most 10 pages, `utils/fetchAllPages.ts`); the old single `perpage: 1000` fetch and its "Showing N of M business units" warning are gone.

### 3.2a Resolving a stuck migration from the screen

`prisma migrate resolve --applied|--rolled-back <name>` rewrites one row of the tenant's `_prisma_migrations` table **without running that migration's SQL** — the only tool for a migration that failed partway and now blocks every later `migrate deploy`. The backend endpoint has existed since the module shipped; what PR #297 (2026-09-16) added is the frontend path:

- **Where the button appears.** On **every** row whose status is `error`, not only rows where a failed migration name could be parsed — deliberately, per the commit's own rationale: tying the button's visibility to a successful parse would make it vanish the day Prisma rewords its output, exactly when it is needed. The cost is that a row erroring for an unrelated reason (a DB that cannot be reached, say) also shows the wrench; the backend answers honestly in that case.
- **The dialog** (`TenantMigrationResolveDialog`, shared verbatim by this table and the per-BU card — one implementation, since both hit the same endpoint and must carry the same warning) asks for the migration folder name (validated client-side against `MIGRATION_NAME_RE = /^[0-9]{6,}_[A-Za-z0-9_-]+$/`, the same regex the backend uses; a non-matching name gets an inline message and a disabled button) and an action select that **defaults to `rolled-back`** — the safer side, because marking a migration `applied` when its SQL never ran leaves the schema silently behind forever, and Deploy will never touch that name again. The dialog copy says so outright.
- **The name is pre-filled** from the raw `err.response.data.message` of the failed `GET /status` — `parseFailedMigration()` (`utils/migrationError.ts`) takes the first `\d{6,}_slug` token *after* the word "fail" in Prisma's output, because the names before that line are the ones that succeeded. It reads the raw axios error on purpose rather than `getErrorDetail()`, which redacts messages in production: reading the redacted copy would make the pre-fill work on a developer's machine and silently do nothing on production.
- **After success** the row is re-checked immediately (`checkOne(bu)`); without that, the row would keep its old Error badge although the fix already landed.

### 3.2c Dashboard views (micro-data) alongside Prisma migrations

Each BU's tenant schema also carries dashboard views owned by micro-data. Since `c65b21f5` (2026-10-06) this screen shows and applies them next to the Prisma state:

- **Status.** `GET /status` for a single BU adds `views` (`{ bu_code, schema, baseline_applied, pending[], changed[], applied[] }`, or `{ error }`) fetched from micro-data when the gateway has `MICRO_DATA_MIGRATION_TOKEN` configured; `all` deliberately skips it so one status call cannot fan out to N micro-data requests (`tenant-migrations.service.ts`). The row's second badge counts `pending + changed`.
- **Apply.** The row's Apply-views icon calls `POST …/views/apply` directly (a repair path). The normal path is automatic: the gateway's deploy stream chains a views step after each BU's Prisma deploy (`chain-views-after-prisma.ts`), emitting log heartbeats (`views: applying …`, every 20 s while it runs) and a `views-complete` event per BU; the page folds that event into the row's views status and logs a "views: applied N" or "failed" line in the Deploy Console. If the Prisma step failed the BU's views step is reported as `skipped: prisma failed`.
- **Summary.** The final `done` event's summary gains `views_failed: string[]` (BU codes); the Deploy-all toast reads "Deployed: N ok, M failed, views failed on K." and downgrades to a warning when K > 0.
- **When off.** If the gateway has no micro-data token, `views` is absent and the step is skipped (`viewsClient.isEnabled()`), so the badge and icon never appear for that status.

### 3.2b Business-unit list rows and the Schema column

Both new columns read fields the row list already carried (`tb_business_unit.db_schema`, `database_pool.name`) — no new request. Below the `lg` breakpoint `DataTable` renders one card per row, and the pool name wraps rather than truncates there, since a truncated pool name inside a card has no hover tooltip to reveal the rest (measured at 390px: a 218px name in a 206px cell).

**Deploy all's own labeling is deliberately state-dependent** (`../carmen-backstage` commit `dbb1107`, 2026-09-01, which also removed the on-screen Pending column above): the button reads `variant={behindCount > 0 ? 'destructive' : 'outline'}` — destructive-red only when a nonzero number of BUs are behind, labeled with its own blast radius ("Deploy 3 behind" instead of the generic "Deploy all"), and disabled (not merely muted) once a check has run and found nothing pending. The rationale, from the button's own source comment, is that this domain has no cancel/rollback endpoint, so the most visually urgent control on the screen should not be the one an operator can least undo.

### 3.3 Migration states, and what advances or stalls one

There is no persisted "migration status" row anywhere in the platform's own schema (see [Data Model](/en/backstage/tenant-migrations/data-model) §2) — every state shown on this screen is derived live, per request, by shelling out to the Prisma CLI against the target tenant database and pattern-matching its text output:

- **`up_to_date`** — `prisma migrate status` output matches `/up to date/i`.
- **`has_pending`** — output matches `/not yet been applied/i`; the specific pending migration names are then pulled out of the same text with a generic `\d{14}_[a-z0-9_]+` pattern.
- **Anything else with a non-zero exit code** falls through to a plain error (`Result.error`) — there is no dedicated "stuck" or "failed" classification in this code. A migration that previously failed partway through `migrate deploy` is reported by Prisma's own CLI in whatever wording Prisma uses for that condition, which this service does not special-case; it will not match `has_pending` or `up_to_date` and will surface to the operator as a generic status-check error carrying Prisma's raw text — which is exactly the text the frontend's `parseFailedMigration()` mines for the Resolve dialog's pre-filled name (§3.2a).

**Advancing a migration** runs `prisma migrate deploy --schema <schema>` against the tenant's resolved connection string; a resolved connection comes from `tb_business_unit.db_schema` plus its linked `tb_database_pool` row (host/port/database/username, and a decrypted password) — **not** from a `db_connection` column, which no longer exists on `tb_business_unit` (§4.3 flags a stale comment in the frontend service file that still describes the old mechanism). On success the CLI's `Applying migration \`name\`` lines are parsed to build the "applied" list streamed back as `applying` progress events; a `done` event with `already_up_to_date: applied.length === 0` closes the stream.

**What a failed `deploy` leaves behind:** a non-zero exit from `prisma migrate deploy` is reported as a stream `error` event (or an HTTP error on the non-stream path) carrying the sanitized CLI output — the operation is not retried and nothing in the backend inspects *which* migration failed. Per-BU and batch runs are guarded by in-memory locks (`runningBuIds` per BU, `isBatchRunning` for the fleet) that return a 409 "already running" while held, but neither lock outlives the request — there is nothing that remembers a BU was left mid-migration once the process moves on. The endpoint built to clear a genuinely stuck migration is `POST :bu_id/resolve` (`prisma migrate resolve --applied|--rolled-back <name>`); **since PR #297 it is reachable from this screen and from the per-BU card** (§3.2a) — the 2026-09-06 revision of this page recorded that no frontend code called it, which was true then and is no longer.

**Batch deploy only protects the *next* BU, not the one in flight.** `deployAllStream`'s own backend comment (`apps/micro-business/src/authen/tenant_migration/tenant_migration.service.ts:538-625` in `../carmen-turborepo-backend`) states cancellation stops the batch from starting the next tenant; the BU currently mid-migration when a client disconnects runs to completion (or its own timeout) regardless — the frontend's `AbortController` on unmount only stops the browser from listening, per the doc comment on `tenantMigrationService._streamDeploy`. There is no cancel/rollback endpoint for this domain at all.

### 3.4 Kill switch and the CI deploy-token path

The entire tenant-migration controller sits behind `TENANT_MIGRATION_API_ENABLED`, an environment-variable boolean that **defaults to `false`** when unset (`boolFromString(false)`, `../carmen-turborepo-backend/apps/backend-gateway/src/libs/config.env.ts:209`) — every call, including a plain status check, 403s with "Tenant migration API is disabled" until an operator explicitly sets it to the literal string `true`. This is a plain env var, unlike its similarly-named sibling on the separate [Backstage Migrations](/en/backstage/backstage-migrations) module, whose own on/off switch was moved into `tb_backstage_config` (`backstage_migration.api_enabled`) — the comment above `BACKSTAGE_DEPLOY_TOKEN` in `config.env.ts` (lines 199-206) is about that other module, not this one; this module's switch has not moved.

Besides a session holding the route's `tenant_migration.*` key, the backend also accepts an `x-deploy-token` header (compared with `timingSafeEqual`, matched against `TENANT_DEPLOY_TOKEN`) as an alternative credential, intended for a CI/CD pipeline to trigger deploys without a human session. This SPA screen never exercises that path — it only ever authenticates as the signed-in operator — so the deploy-token route is invisible from this UI entirely; using it requires calling the API directly (e.g. via the Bruno collection, §6).

### 3.5 Relationship to the Business Units edit page

- The per-BU `TenantMigrationCard` on [Business Units — UI Screens](/en/backstage/business-units/ui-screens) §4.5 and this page call the **same** `tenantMigrationService` (`getStatus`, `deployStream`, `deployAllStream`) and the same backend controller — there is exactly one implementation of "check status" and "apply migrations," surfaced from two screens. [Business Units — Tenant Migrations](/en/backstage/business-units/tenant-migrations) is now a short pointer covering only that embedded card; this page is the full account of the fleet-wide screen.
- Both surfaces use the same permission split. On the Business Unit edit page the card renders only for `tenant_migration.read` and is passed `canApply = hasPermission('tenant_migration.apply', …)`, both with `clusterId={BACKSTAGE_SCOPED_RECORD}` (`BusinessUnitEdit.tsx:828-836`); inside the card, Check is disabled only when the BU has no pool + schema (`checkReason` = `hasDbConnection` false), while Apply and Resolve also need `canApply` (`TenantMigrationCard.tsx:49-51`). This fleet table has no `hasDbConnection` pre-check: it lets an operator attempt Check/Apply on any row and surfaces whatever error `resolveConnection` throws (§3.3) once the request is made.
- Both surfaces open the **same** `TenantMigrationResolveDialog` (§3.2a). The card had a second defect fixed in the same PR: it used to swallow a failed `GET /status` entirely, leaving a toast that vanished in four seconds and a BU that read "Not checked" forever; it now keeps the error on screen (`role="alert"`, raw message) so the Resolve button has something to attach to and a name to pre-fill.
- There is **no in-app link** between the two screens in either direction — confirmed by reading both components' source. The only way to this page is the sidebar's "Tenant Migrations" entry or typing the URL; this page's own "Code" column links straight to that BU's edit page, not to a filtered version of itself.

## 4. Roles and Permissions

### 4.2 Backend enforcement

Every migration-domain endpoint sits behind `TenantMigrationGuard` (`../carmen-turborepo-backend/apps/backend-gateway/src/auth/guards/tenant-migration.guard.ts`), applied once to the whole controller via `@UseGuards(TenantMigrationGuard)`. It enforces `TENANT_MIGRATION_API_ENABLED` first, before any credential check, so a disabled flag 403s regardless of who is asking. It then requires **one** of: a matching `x-deploy-token` header (constant-time compared, §3.4; the actor is recorded as `ci:deploy-token`), or a Keycloak session whose route-declared Backstage permission passes `BackstagePermissionGuard` **at Backstage scope** — a grant held only for one cluster is rejected (`Missing backstage permission: <key> (backstage scope required)`), because these routes touch any BU and `all`. The route keys are `tenant_migration.read` for `GET :bu_id/status` and `tenant_migration.apply` for `deploy`, `deploy/stream`, `views/apply` and `resolve` (`tenant-migrations.controller.ts`); a super-admin passes both. A route that declared no key would be refused outright. The frontend's `applyReason` ("Requires the tenant_migration.apply permission.") is a UI convenience that matches, rather than substitutes for, this server-side check — unlike the confirmed gaps documented for [SQL Workbench](/en/backstage/sql-workbench) and [Query Dataset](/en/inventory/system-config/query-dataset), the tenant-migrations backend guard is not bypassable by calling the API directly without the key.

### 4.3 Re-verified against current source: a stale comment, corrected

The frontend's `tenantMigrationService.ts` still carries this comment, unchanged since it was first written (`../carmen-backstage` commit `8fc1124`, 2026-06-29): *"The backend resolves the target tenant DB from the BU's stored db_connection."* That description was overtaken by `../carmen-turborepo-backend` commit `af2437074` (2026-08-13), which moved connection resolution from the retired `tb_business_unit.db_connection` JSON column to `db_schema` + the linked `tb_database_pool` row (confirmed by direct read of `resolveConnection()` in `apps/micro-business/src/tenant/tenant.service.ts` — no code path in the current tree reads `db_connection` for this purpose). The comment was never updated to match; it is documentation debt in the source, not a description of current behavior, and this page describes the pool/schema mechanism the code actually runs (§3.3).

### 4.4 Re-verified against current source: a dead error-status mapping on the stream path

The gateway's `deployStream` handler maps a pre-stream connection failure to an HTTP status by pattern-matching the error message (`resolvePreStreamErrorStatus()`, `tenant-migrations.controller.ts`), added in commit `4ca923229` (2026-06-30) when `resolveConnection` failures still read "no database connection configured" / "unsupported database provider." The same `af2437074` refactor (§4.3) changed the actual thrown messages to "is not linked to a database pool", "has no database schema configured", "has been deleted", and "is inactive" — none of which match `resolvePreStreamErrorStatus`'s regex. The practical effect: since 2026-08-13, a BU with no pool linked, no schema set, or an inactive/deleted pool returns HTTP 500 from `/deploy/stream` (the function's unmatched-message fallback) instead of the documented 422. The message text itself still reaches the operator correctly (the frontend's row `errorMsg` renders the raw text regardless of status code, and `handleMigrationError` only special-cases 403/409), so this is a real gap in the API's documented status-code contract, not a gap in what the operator sees on screen. `GET /status` and the non-streaming `POST /deploy` are unaffected — they return their status via `StdResponse.fromResult()`'s generic `ErrorCode` mapping, not this regex.
