# Backstage Migrations

**Backstage Database Migrations** (the sidebar row reads "Backstage Migrations") is one screen, `BackstageMigrationManagement` at `/backstage/migrations`, that runs two different kinds of operation against the **one platform database every cluster and business unit shares** — not a single tenant's database. The first kind is a Prisma schema migration (Deploy, Resolve); the second is a catalog of 8 seed scripts plus 7 drift checks — 6 of the checks read-only, the seventh a check that writes (inside always-rolled-back transactions) and is hidden from this console (§3.3) — that populate or verify platform-wide reference data: currencies, permissions, Backstage roles, license features, application API allowlists, and one per-business-unit operation covered in §3.4. Because every write here lands in a table every tenant reads from, this page states — operation by operation — what is safe to click again and what is not, rather than a single blanket "idempotent" claim.

> **At a Glance**
> **Component:** `BackstageMigrationManagement` &nbsp;·&nbsp; **Route:** `/backstage/migrations`, guarded by `<PrivateRoute requireSuperAdmin feature="backstage_migrations">` (`../carmen-backstage/src/App.tsx:481-488`) &nbsp;·&nbsp; **Nav:** `superAdminOnly: true` — **that flag, not the absence of a permission key, is what gates this menu row** — `feature: 'backstage_migrations'`, `groupKey: 'navGroup.database'`, no `permission` field at all (`backstageNav.ts:61`) &nbsp;·&nbsp; **Backend authorities:** a matching `x-deploy-token` header (checked **first**) or a super-admin session (the fallback) — both sit behind one enable switch, `backstage_migration.api_enabled` (§3.1, §4) &nbsp;·&nbsp; **Catalog:** 2 migration actions (Deploy, Resolve) + 15 seed/check operations (8 seed, 7 check), 14 of them visible in this console &nbsp;·&nbsp; **e2e suite:** one read-only smoke spec, `../carmen-backstage-e2e/tests/platform-migrations/platform-migrations-smoke.spec.ts` (§5) &nbsp;·&nbsp; **Sub-pages:** 0

## 1. Overview

`BackstageMigrationManagement.tsx` (705 lines) renders four stacked cards plus a shared run console. The **Status** card (`BackstageMigrationManagement.tsx:361-442`) shows whether the platform database has pending migrations, with a single **Apply migrations** button that runs Deploy; a collapsible **Raw Prisma output** toggle shows the sanitized CLI text behind that verdict. Below it, a collapsed-by-default **Resolve a stuck migration (advanced)** card (`:445-518`) lets an operator mark one migration folder `applied` or `rolled-back` in `_prisma_migrations` by name, without running its SQL. Below that, two catalog cards — **Seed data** (amber left border, a "Writes data" badge) and **Drift checks** — each render one row per operation via `OpRow` (`pages/backstageMigration/OpRow.tsx`), fetched from a single registry, `backstageSeedService.getCatalog()` (`:168`). A `RunConsole` at the bottom (`pages/backstageMigration/RunConsole.tsx`) shows every action's output — deploy, resolve, and every seed/check run — in one shared, capped-at-20-entries ledger (`useRunLog`, `runLog.ts:32`), because the real workflow on this page is a sequence (deploy, then seed, then check what changed), not isolated one-shot actions (`runLog.ts:6-9`).

Every request from this page travels frontend → `backend-gateway` (where the authorization guard runs, §3.1) → an internal RPC call → `micro-business`, which is the process that actually shells out to `prisma` or spawns a `bun <script>` child process against the platform database. The gateway's own `BackstageMigrationsService`/`BackstageSeedsService` are thin RPC proxies with no logic of their own (`../carmen-turborepo-backend/apps/backend-gateway/src/backstage/backstage-migrations/backstage-migrations.service.ts:1-50`, `backstage-seeds/backstage-seeds.service.ts:1-59`); `micro-business`'s own controllers (`apps/micro-business/src/authen/backstage_migration/backstage_migration.controller.ts`, `backstage_seed/backstage_seed.controller.ts`) apply **no second authorization check** — they trust the gateway's guard entirely.

An operator who needs a specific business unit for one operation (§3.4) is prompted by `BuSwitcher` (`BackstageMigrationManagement.tsx:670-693`); a dev-only debug panel (`DevDebugSheet`) shows the raw `/api-system/backstage/migrations/status` payload, but only in a local dev build — the component itself returns `null` unless `import.meta.env.DEV` (`../carmen-backstage/src/components/ui/dev-debug-sheet.tsx:18`), so this is not an RBAC control.

## 2. Business Context

Every platform-wide reference table — permissions, roles, currencies, license features — is defined in source (`prisma-shared-schema-backstage/prisma/seed.*.data.ts`) but only becomes real data through one of the scripts this console runs. Before this console existed those scripts were `bun run db:seed.*`/`db:check.*` commands, runnable only by someone with a shell on a host that can reach the platform database directly. This page is the operator-facing wrapper around exactly the same scripts (§3.3 cites each one), with one addition the CLI never had: a live, streamed run console, so an operator watching a seed that touches hundreds of permission rows (`seed.permission.data.ts` has roughly 278 entries) can see it progress instead of waiting on a blank terminal.

The stakes are the reason this page exists in the shape it does: every script here writes to the **one** platform database, not a tenant's. A `seed-backstage-role-permission` run that goes wrong does not affect one customer — it affects the permission catalog every cluster's role screen reads. That is also why the console deliberately does **not** expose one CLI script that still exists in source: `db:seed.backstage-super-admin` reads a `SUPER_ADMIN_USER_ID` environment variable and grants that user id unconditional super-admin — with no operator choice of *whom* and, confirmed by reading the script, no `created_by_id` written anywhere (`seed.backstage-super-admin.ts:1-47`) — so there would be no audit trail of who was granted or by whom. The catalog's own comment states the reason for the exclusion is that [Super Admins](/en/backstage/super-admins) already does this properly, through a screen that does record who acted (`BACKSTAGE_SEED_CATALOG`, `backstage_seed.catalog.ts:22-29`); reading the excluded script confirms the comment is accurate, not merely present.

## 3. Key Concepts

### 3.1 Two authorities behind one switch — and which actor each one records

`BackstageMigrationGuard.canActivate()` (`../carmen-turborepo-backend/apps/backend-gateway/src/auth/guards/backstage-migration.guard.ts:115-137`) is the single authorization checkpoint for **every** route in this module — both the migrations controller and the seeds controller declare `@UseGuards(BackstageMigrationGuard)` (`backstage-migrations.controller.ts:65`, `backstage-seeds.controller.ts:36`). It runs in this exact order:

1. **The switch, checked first.** `isApiEnabled()` reads the `backstage_migration` row's `api_enabled` field from `tb_backstage_config`, cached for 60 seconds; a missing row, an unreadable one, or the field being anything other than exactly `true` all read as **off** (`backstage-migration.guard.ts:69-94`). If the switch is off, every route in this module answers `403 Backstage migration API is disabled` regardless of who is calling — a deploy token and a super-admin session are equally refused (`:116-118`).
2. **The deploy token, checked first among the two authorities.** If the switch is on, the guard compares the request's `x-deploy-token` header against `envConfig.BACKSTAGE_DEPLOY_TOKEN` using a constant-time comparison (`isTokenEqual`, `:100-107`, `timingSafeEqual`). A match sets `request.deployActor = 'ci:deploy-token'` and returns `true` immediately — **no Keycloak call, no super-admin lookup at all** for this path (`:119-125`). `BACKSTAGE_DEPLOY_TOKEN` defaults to an empty string (`apps/backend-gateway/src/libs/config.env.ts:206`), and an empty configured token can never equal a presented one in the guard's own comparison (`presentedToken && configuredToken && ...`, `:122`), so this path is inert in any environment where the token has not been explicitly set.
3. **Super-admin, the fallback.** Only when no token matches does the guard run `KeycloakGuard` then `BackstageSuperAdminGuard` (`:126-131`); the latter makes an RPC call (`backstage-permissions.effective`) and allows the request only when the response's `is_super_admin` is exactly `true`, failing closed (denying) on any RPC error (`backstage-super-admin.guard.ts:40-70`). On success the guard sets `request.deployActor = 'super-admin:<user_id>'` (`backstage-migration.guard.ts:135-136`).

Both the migrations controller and the seeds controller log a structured audit entry naming this same `deployActor` on every call (`executeAuditLog`, `backstage-migrations.controller.ts:87`; the seeds controller streams instead of buffering a single result, so it has no equivalent audit line — see §6); `micro-business`'s own controller wraps every mutating call in `runWithAuditContext` using the caller's `user_id`/`tenant_id` from the RPC payload (`backstage_migration.controller.ts:59-64,76-78`). **This is the fuller account the [Backstage Config](/en/backstage/backstage-config) page's own §3.2 alludes to**: moving `PLATFORM_MIGRATION_API_ENABLED` into this config key made the *config key itself* super-admin-only to edit, but it did not remove the CI deploy-token path into the migration endpoints this key gates — that path is checked first, not last, and is only as inert as `BACKSTAGE_DEPLOY_TOKEN` being left unset.

### 3.2 Two consoles sharing one lock, with different transports and timeouts

**Deploy/Resolve** (`micro-business`'s `BackstageMigrationService`) shells out to the local Prisma CLI with `execFile`, no shell, and a fixed timeout (`BACKSTAGE_MIGRATION_TIMEOUT_MS`, default `120000` ms / 2 minutes — `apps/micro-business/src/libs/config.env.ts:132`), buffering the whole result before responding (`backstage_migration.service.ts:154-171`). **Seed/Check** (`BackstageSeedService`) instead `spawn`s `bun <script>` and streams stdout/stderr line-by-line as NDJSON over the gateway's HTTP response, with its own longer timeout (`BACKSTAGE_SEED_TIMEOUT_MS`, default `300000` ms / 5 minutes — `config.env.ts:135`), because seed scripts can run far longer than a schema migration (`backstage_seed.service.ts:224-241`). Both redact connection strings and `SYSTEM_(DATABASE|DIRECT)_URL` from every line they emit (`sanitize()`, present in both services) and both build an allowlisted child environment so the spawned process cannot read unrelated service secrets (`buildChildEnv()`, both services).

Both services serialize through the **same** lock, `BackstageDbLock` (`apps/micro-business/src/authen/backstage_db/backstage_db.lock.ts`) — a plain in-memory `running` boolean, moved out of `BackstageMigrationService` specifically so a `migrate deploy` and a `seed.permission` run could not proceed at the same time against the same database (`:16-21`). A second call while one is in flight gets `409 A backstage database operation is already running` (`BackstageDbBusyError`, surfaced as `ErrorCode.ALREADY_EXISTS`), which the frontend shows as a `toast.warning`, not an error (`errorText()`/`notifyError()`, `BackstageMigrationManagement.tsx:46-57`). **The lock's own doc-comment is explicit about its scope: one process, not one cluster of replicas** (`backstage_db.lock.ts:25-27`) — if `micro-business` runs more than one instance, this 409 cannot prevent two instances from running conflicting operations at the same moment; see §6.

Closing the browser tab or losing the connection mid-run does **not** stop the underlying process on either path: the seed stream's teardown only sets a `cancelled` flag so no more events are emitted to a dead connection, and explicitly does not call `child.kill()` — the code comment states this is intentional, matching tenant-migration behavior, because a half-killed seed can leave half-written data (`backstage_seed.service.ts:289-296`). The lock is released only when the child process actually exits.

### 3.3 The catalog: what each operation does, and what is safe to re-run

**Migration actions** (not part of the seed/check catalog — these are the Status card's own buttons):

| Action | What it does | Safe to re-run? |
| --- | --- | --- |
| **Deploy** (`POST .../migrations/deploy`) | Runs `prisma migrate deploy --schema <platform schema>`, applying every migration not yet recorded in `_prisma_migrations` (`backstage_migration.service.ts:236-270`). | **Yes, as a console action.** Prisma tracks applied migrations by name; deploying again with nothing pending returns `already_up_to_date: true` and `applied_migrations: []` (matched from `/No pending migrations to apply/i` in the CLI output, `:258`) — clicking it twice in a row does nothing the second time. This vouches only for the button, not for any individual migration's own SQL being safe to apply twice outside Prisma's once-per-name tracking; that would require reading each migration file, which is outside this page's scope. |
| **Resolve** (`POST .../migrations/resolve`) | Marks one migration folder `applied` or `rolled-back` in `_prisma_migrations` **without running its SQL** — a status-only correction for a migration that failed partway, used to unblock every later Deploy (`backstage_migration.service.ts:272-312`). | **Repeating the same call is a no-op**, but choosing the **wrong action once** is the real hazard: marking a migration `applied` when its SQL never actually ran leaves the schema silently behind forever, because Deploy will never touch that migration name again. The console's own copy states this outright: "Choosing wrong records a migration that never ran as if it had." (`en.ts:3735`). |

**Seed and check operations** — 8 seed (`writes: true`) + 7 check (6 read-only, 1 that writes and is hidden from this console), from `BACKSTAGE_SEED_CATALOG` (`backstage_seed.catalog.ts`; `seed-application-api` and `check-application-api` were added 2026-09-07, PR #282 on the SPA side supplying their labels; the file's own doc comment still says "9 seeds + 7 checks" — stale since `seed-report-template-upload` was removed, the array holds 8 + 7), each confirmed by reading its script directly:

| Op id | Group | What it does | Safe to re-run? |
| --- | --- | --- | --- |
| `seed-currency-iso` | seed | Upserts the ISO 4217 currency list (code/symbol/name) into `tb_currency_iso`. | **Yes.** `upsert` keyed on the unique `iso_code` (`seed.currency-iso.ts:174-187`) — re-running reapplies the same values. |
| `seed-permission` | seed | Upserts every app-level permission (`PERMISSION_SEED`) into `tb_permission` by `resource`+`action`; soft-deletes any entry flagged `delete: true`. | **Yes.** Find-then-update-or-create by `resource`+`action` (`seed.permission.ts:12-57`); a `delete: true` entry that is already soft-deleted is simply skipped again. |
| `seed-backstage-permission` | seed | Same pattern for `tb_backstage_permission`, and additionally soft-deletes the `tb_backstage_role_tb_permission` links of any permission it retires. | **Yes — and specifically built to recover a partial run.** It looks up every row matching a retiring resource+action, active or already soft-deleted, so a crash between soft-deleting the permission and cascading its links is fixed by simply running it again (`seed.backstage-permission.ts:16-45`; the reasoning in the comment is confirmed by the code beneath it). |
| `seed-backstage-role` | seed | Upserts the fixed platform-level roles (`tb_backstage_role`) by `name`. | **Yes.** Find-by-name, update-or-create (`seed.backstage-role.ts:12-27`). |
| `seed-backstage-role-permission` | seed | Upserts each platform role by name, then links it to every permission its pattern expands to, skipping a link that already exists. | **Yes for adding coverage — it never revokes.** A link removed from `ROLE_PERMISSIONS` in source is never deleted from the database by running this again (`seed.backstage-role-permission.ts:20-46`); `check-backstage-role-permission` (below) is how that kind of drift is actually found. |
| `seed-role-permission` | seed, requires `bu_id` | Upserts **one business unit's** tenant application roles (`tb_application_role`) and their permission links (`tb_application_role_tb_permission`), scoped to that BU. **Not the platform RBAC tables — see §3.4.** | **Yes per BU, additive-only** — the identical upsert-role/skip-existing-link pattern as `seed-backstage-role-permission` (`seed.role-permission.ts:487-556`). Re-running against the same BU past the first run changes nothing; running it against a BU whose application roles were hand-edited will not correct or remove those edits, only add whatever is still missing. |
| `seed-license-feature` | seed | Upserts `tb_license_feature` by `key`, reviving a soft-deleted row rather than creating a duplicate, and soft-deletes ("retires") any key no longer present in the seed data. | **Yes.** Deliberately does not overwrite `state`/`is_active` on a row that already exists — those columns are operator-set through the Licenses screen, and are written by this script only when the row is newly created (`seed.license-feature.ts:33-67`) — so re-running cannot silently flip a feature an admin has already turned on or off. |
| `seed-application-api` | seed | Upserts the **x-app-id allowlist** — which `api_name` values each registered application (`tb_application`) may call, from the hand-maintained `seed.application-api.data.ts` (exported once from DEV on 2026-09-07; `allow_all: true` apps carry an empty list because the guard skips the check for them entirely). Console label: "App API allowlist — Which x-app-id may call which API". | **Yes, additive-only by design.** The seeder never deletes: admins also edit this list through the Applications screen (`application-permission.*` endpoints), so a grant present in the DB but absent from the file is *reported* by `check-application-api`, not revoked (`backstage_seed.catalog.ts:49-51`). |
| `check-permission` | check | Read-only: diffs `PERMISSION_SEED` against `tb_permission`, listing what a `seed-permission` run would create, update, or soft-delete. | **Always safe** — confirmed by reading the whole file: no `create`/`update`/`delete`/`upsert` call anywhere in `check.permission-drift.ts`. |
| `check-backstage-permission` | check | The same diff for `tb_backstage_permission` against `BACKSTAGE_PERMISSION_SEED`. | **Always safe** — confirmed the same way (`check.backstage-permission-drift.ts`). |
| `check-backstage-role-permission` | check | Read-only: recomputes each platform role's expected permission set from `ROLE_PERMISSIONS` and diffs it against the live `tb_backstage_role_tb_permission` links. | **Always safe** — confirmed the same way (`check.backstage-role-permission-drift.ts`). |
| `check-endpoint-permission` | check | Read-only: parses `backend-gateway` controller source to find every tenant-scoped route (`api/:bu_code/*`, `api/config/:bu_code/*`) and checks each has a matching `PERMISSION_SEED` entry. Its own header states it "never touches the database and never writes a file" (`check.endpoint-permission-coverage.ts:20-26`). | **Always safe** — confirmed by reading the whole file; the header's claim holds. |
| `check-api-system-permission` | check | Read-only: uses `ts-morph` to parse `backend-gateway` controllers for `@RequireBackstagePermission`-guarded handlers and checks each key exists in `BACKSTAGE_PERMISSION_SEED`. Its own header documents real blind spots: an object-literal `@Controller` path, an aliased decorator import, or a controller file not named `*.controller.ts` can all be missed silently (`check.api-system-permission-coverage.ts:7-38`). | **Always safe to run** — confirmed by reading the whole file, no write call — but a clean result is proof of no *detected* gap, not proof of full coverage, per the script's own documented limitations. |
| `check-application-api` | check | Read-only, three directions (`check.application-api-drift.ts` header): (1) in the seed file but not the DB — the seed has not been run here, which users experience as 401s that persist for the `AppIdGuard` cache's 60s TTL even after the DB is fixed; (2) in the DB but not the file — someone granted it through the UI, reported for a **human** to decide whether to adopt or revoke; (3) in the file but not in `APP_API_CATALOG` — a typo, or a renamed/removed route, checkable without a DB. Console label: "Check app API allowlist". | **Always safe** — no write call anywhere in the script. Exits 1 only on directions 1 and 3; direction 2 is a report, not a failure. |
| `check-seat-pool-view` | check, marked `writes: true`, **hidden from this console** | Verifies the `v_business_unit_seat` Postgres view's seat-counting semantics against 8 hand-built cases (`check.seat-pool-view.ts:26-50`), using **one arbitrary active business unit** — picked by `findFirst`, not operator-chosen — with **each case in its own transaction** that always ends in a deliberate `throw new Error('ROLLBACK_ON_PURPOSE')`, swallowed by the caller so nothing commits (`:93-123`). | **Net effect is zero — no transaction ever commits.** For each case's short transaction, though, it deletes that BU's existing `tb_business_unit_license` rows and recreates test ones inside the same transaction (`:96`), holding a row lock on real customer licensing data while it runs. This is exactly why the catalog marks it `writes: true` unlike every other check, and why the frontend filters it out of the visible list with `HIDDEN_OPS` (`BackstageMigrationManagement.tsx:68-76,168`) instead of showing it as an ordinary read-only check — it remains callable by hitting the API directly, only not from this screen. If no active business unit exists in the target database at all, the script exits with an error instead of running (`check.seat-pool-view.ts:78-85`). |

### 3.4 `seed-role-permission`'s multi-BU picker writes tenant app-roles — not platform RBAC

`seed-role-permission` is the only catalog operation with a declared parameter (`bu_id`, required, type `uuid` — `backstage_seed.catalog.ts:42-44`), and as of commit `157a65e` (`../carmen-backstage` HEAD — "feat(platform-migrations): เลือกได้หลาย BU ตอน seed role permissions (#281)") this console lets an operator pick **several** business units at once for it, one `BuSwitcher` dialog set to `multiple` (`BackstageMigrationManagement.tsx:670-693`). The detection that decides whether an op needs this prompt at all is generic, not hardcoded to this op's id — `buParamOf()` looks for a declared `uuid` parameter whose name matches `bu`, so a future per-BU op would get the same prompt automatically (`:78-83`). Selected BUs are then run **sequentially, one request per BU, never in parallel** — `runOpBatch` awaits each `runOnce` in a `for` loop (`:296-326`) specifically because every target hits the same database script, and the code's own comment is explicit that running them concurrently would invite deadlocks and interleave the streamed logs into something unreadable (`:287-295`); a failure on one BU does not stop the rest from running, so the operator who selected five BUs still gets all five attempted (`:293-295`).

What the picker actually runs, per BU, is the same single-BU script described in §3.3: it writes rows to **`tb_application_role`** and **`tb_application_role_tb_permission`**, each scoped by `business_unit_id` (`seed.role-permission.ts:465-556`). **This is a per-tenant application-role system, a completely different pair of tables from the platform RBAC tables — `tb_backstage_role`, `tb_backstage_permission`, `tb_backstage_role_tb_permission` — that [Backstage RBAC](/en/backstage/rbac) documents.** The multi-BU picker on this page never touches anything RBAC governs; reading "seed role permissions, several BUs at once" as an RBAC operation would be the wrong mental model entirely. (`seed-backstage-role-permission`, by contrast, does write to the actual platform RBAC link table — see §3.3 — but takes no `bu_id` and cannot be run per-BU.)

## 4. Roles and Permissions

There is no `permission` string anywhere in this module — access is entirely identity-based, at three independent layers that all have to agree:

1. **Nav row:** `superAdminOnly: true` in `backstageNav.ts:61`; `buildBackstageNav()`'s filter keeps the row only `!item.superAdminOnly || opts.isSuperAdmin` (`:91-98`) — a non-super-admin never sees the menu entry at all, not even as a disabled row.
2. **Route:** `<PrivateRoute requireSuperAdmin feature="backstage_migrations">` (`App.tsx:481-488`) renders `<Forbidden />` for a signed-in non-super-admin who navigates to `/backstage/migrations` directly by URL — checked *before* the feature-flag gate, so a denied user sees 403, never a flag-driven 404 (`PrivateRoute.tsx:89-105`).
3. **Every backend endpoint:** `BackstageMigrationGuard` (§3.1) — the switch, then deploy-token-or-super-admin, re-checked on every single call regardless of what the frontend already showed.

Layer 3 is the only one of the three a direct API call cannot bypass; layers 1 and 2 are frontend convenience, not security boundaries. `BackstageSuperAdminGuard` itself resolves super-admin status by an RPC call to `backstage-permissions.effective` and checks `is_super_admin === true`, failing closed (denying access) on any RPC error rather than defaulting to allow (`backstage-super-admin.guard.ts:40-70`) — the same fail-closed direction the switch itself takes (§3.1), in contrast to the *fail-open* default used by [Backstage Config](/en/backstage/backstage-config)'s own license-enforcement switch.

## 5. e2e Coverage

**Smoke only.** `../carmen-backstage-e2e/tests/platform-migrations/platform-migrations-smoke.spec.ts` (suite "Backstage Migrations - Smoke", tag `@smoke`, cases TC-PM-010001 and the sidebar case after it) is read-only: it installs the e2e `installReadOnlyGuard` so any POST/PUT/PATCH/DELETE the page attempts is aborted, skips unless the session is a super-admin and the `platform_migrations` feature is active, then checks that the route renders its heading and that the sidebar offers the entry. **The spec is stale against the Backstage rename:** it still navigates to `/platform/migrations`, expects the heading "Platform Database Migrations" and a sidebar link reading "Backstage Migrations", and checks the feature key `platform_migrations` — the SPA now serves `/backstage/migrations`, the heading is "Backstage Database Migrations", the nav label is "Backstage Migrations", and the feature key is `backstage_migrations`. It will fail (or skip) until updated. No spec exercises Deploy, Resolve, or any seed/check run, so every behavioural claim on this page traces to `../carmen-backstage` or `../carmen-turborepo-backend` source read directly, never to test coverage.

## 6. Edge Cases

| Scenario | Behavior | Source |
| --- | --- | --- |
| `backstage_migration.api_enabled` is off | Every route in this module — migrations and seeds alike — answers `403 Backstage migration API is disabled`, for a deploy token and a super-admin alike; the switch is checked before either authority | `backstage-migration.guard.ts:116-118` |
| `x-deploy-token` header sent, but `BACKSTAGE_DEPLOY_TOKEN` was never configured | Falls through silently to the super-admin path — an empty configured token can never match a presented one | `backstage-migration.guard.ts:121-122`; `apps/backend-gateway/src/libs/config.env.ts:206` |
| Two `micro-business` instances run behind the same gateway (multi-replica) | The 409 "already running" guard is a per-process in-memory flag, not shared across replicas — two instances can both proceed with conflicting operations at the same time | `backstage_db.lock.ts:25-27` |
| `Resolve` marks a migration `applied` when its SQL was never actually run | Not detected by this console — Deploy will skip that migration name forever afterward, silently leaving the schema behind | `backstage_migration.service.ts:277-312`; console copy at `en.ts:3735` |
| Calling `check-seat-pool-view` directly via the API (bypassing the hidden-from-UI filter) | Runs normally — it is excluded only from this screen's visible list, not disabled server-side; requires at least one active, non-deleted business unit to exist, or exits with an error | `BackstageMigrationManagement.tsx:76`; `check.seat-pool-view.ts:78-85` |
| Calling `seed-role-permission` directly via the API with no `bu_id`, or a malformed one | `422`, with a message naming exactly what was missing or malformed — the frontend's own picker cannot submit without a valid selection, but a direct API caller is not stopped by it | `backstage_seed.service.ts:85-102`; `backstage-seeds.controller.ts:71-73` |
| A catalog script's file is absent from the running image | `missing: true` on that op, computed by checking the file exists in this image at catalog-fetch time; its Run button is disabled in the UI, and a direct API call gets `422 Script not found in this image` | `backstage_seed.service.ts:179-184`; `backstage-seeds.controller.ts:66` |

| `db:seed.backstage-super-admin` (a CLI script that still exists) | Deliberately absent from this console's catalog — no operator choice of whom to grant, and confirmed by reading the script that it writes no `created_by_id`, so it would leave no audit trail of who acted | `backstage_seed.catalog.ts:22-29`; `seed.backstage-super-admin.ts:1-47` |

## 7. Recommendations

Treat every row on the **Seed data** card as a deliberate write to data every cluster shares, not a routine click — the console's own confirmation copy for a single-BU write says outright that it "cannot be interrupted once started" (`en.ts:3696`), and §3.3 shows that most seed operations are additive-only: they create and update, but do not remove a row that source no longer defines. Running the matching `check-*` operation before and after a related `seed-*` run is the only way this console gives an operator to see that kind of one-directional drift, since `seed-backstage-role-permission` and `seed-role-permission` in particular never revoke a stale link on their own (§3.3). Before ever using **Resolve**, confirm independently — outside this console — whether the named migration's SQL actually ran; the action records whatever the operator asserts, with no cross-check against the database's real state (§3.3, §6). Because the concurrency lock is per-process rather than per-cluster (§3.2, §6), an environment running more than one `micro-business` instance should treat "one operator at a time" here as a manual convention, not an enforced guarantee. (`seed-report-template-upload`, which used to depend on a live external system and hardcoded credentials, was deleted from the repo on 2026-10-26 — commit `ad7499d87` — and is no longer in the catalog.)
