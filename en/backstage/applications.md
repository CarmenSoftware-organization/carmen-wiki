# Applications

The **Applications** module manages the platform's registered **API clients** — the machine callers of the backend gateway. An application record is an identity plus an access grant: its record UUID is the `x-app-id` header value the client sends on every request, and its grant is either "allow all APIs" or an explicit list of `api_name` keys picked from a backend-generated catalog. Where [Backstage Roles](/en/backstage/rbac) answers "what may this *person* do," Applications answers "what may this *program* call."

> **At a Glance**
> **Module purpose:** Register machine clients and grant them API access — `allow_all` or an explicit `api_names` list selected from a catalog grouped by module &nbsp;·&nbsp; **Audience:** Developers and QA working on the Backstage SPA and the backend gateway's `AppIdGuard` enforcement &nbsp;·&nbsp; **Key entities/tables:** `tb_application` (the client: `name`, `allow_all`, `device`, plus service-status columns `status`/`status_message`/`status_until` and app-secret columns `require_secret`/`secret_*`), `tb_application_api` (1:N grant rows, one `api_name` each), `tb_application_bypass_user` (users who keep access during maintenance/read-only) &nbsp;·&nbsp; **Identity:** record `id` (UUID) **is** the `x-app-id` value — there is no separate app-id field &nbsp;·&nbsp; **Permission key** (`../carmen-backstage/src/components/nav/backstageNav.ts`): `application.read` (list/nav) + `application.create`/`application.update`/`application.delete`, plus `application.secret.manage` / `application.secret.reveal` for the app-secret card &nbsp;·&nbsp; **Feature-flag key:** `applications` (checked on all three routes and the sidebar entry, after the permission gate) &nbsp;·&nbsp; **superAdminOnly:** No &nbsp;·&nbsp; **Sub-pages:** 3

## 1. Overview

The module follows the SPA's standard two-screen pattern:

- **`/applications` → `ApplicationManagement`** — server-side `DataTable` with debounced search (name/description), a Sheet-based **service-status** (Running / Maintenance / Read-only / Disabled, multi-select) + Device filter, CSV export (now with `status` and `status_until` columns), a **Registry** summary strip (`ApplicationRegistrySummary`, since 2026-08-24 reading a dedicated, unfiltered `GET /api-system/applications/summary` endpoint rather than sweeping the whole table client-side — total/active/inactive, a service-status segment, a full-access-vs-scoped proportion bar, an app-secret posture segment, and a per-device breakdown), and persisted UI state in `localStorage`. The App ID and Description have no columns of their own: the Name cell stacks the name link (with a **Secret required** chip painted next to it only when the application enforces `x-app-secret` — an exception-only rule, replacing the earlier Inactive badge), the record UUID in monospace with an inline copy button, then the description. **The Access column is no longer a plain badge.** Since commit `89ba8a8` (2026-09-02, `#254`) it renders `ApplicationReachCell`: a bar plus a `granted/catalogSize` fraction (e.g. `207/900`) measured against the live API catalog, switching to a warning tone with an alert-triangle icon once the application's reach equals the whole catalog (`allow_all` renders as `n/n` on the same ruler, not the word "All APIs"), with a small second line naming the module count reached. The bar and its denominator disappear — falling back to a bare count — if the catalog fetch fails, since a bar with no stated divisor is the exact defect this component exists to fix. The **Device** column is now quiet muted text (`formatDevice()`), not a badge — the Registry strip's device histogram already carries that fact once per page. **A Status column is back**, but it now shows the four-value service status (a coloured dot plus Running / Maintenance / Read-only / Disabled, with an alert-triangle once a non-running status's announced "expected back" time has passed) rather than the old Active/Inactive flag (`ApplicationManagement.tsx`, column `id: 'status'`).
- **`/applications/new` and `/applications/:id/edit` → `ApplicationEdit`** — an **`ApplicationIdentityHero`** (icon, name, device/status badges, an App ID chip with copy button, audit lines) above a two-column layout: a left **"API access"** card holding the accordion selector (the visually primary element, always present — not hidden inside a bigger form) and a right, sticky **"Settings"** card (Name, Description, Device — Device renders as quiet read-only text in view mode, not a badge; the old `is_active` Active checkbox is gone, because service status now has its own endpoint and card: commit `1c2894d`, 2026-09-02, `#255` removed the duplicate badge treatment sitting 60px below the hero's own device/status badges). The edit route still starts read-only behind an Edit toggle (unlike clusters/business-units' always-editable one-document pages); a sticky bottom bar shows Save/Cancel while editing. **Since `#255` the hero and the API access card share the list's reach ruler** (`utils/apiReach.ts`'s `reachOf()`): the hero shows the same bar + `granted/catalogSize` fraction and a "`N` of `M` modules" line the list uses, plus a count of **authority actions** held — verbs that delete a record or advance a workflow on the app's behalf (`delete`, `approve`, `submit`, `revoke`, and similar; see `AUTHORITY_VERBS` in `utils/apiCatalog.ts`). The API Names selector, read-only or editable, tints only those authority-verb chips and lists them first within each module, shows a catalog-anchored `known/total` fraction per module (with a separate `+N` warning count for grant rows pointing at api_names the catalog no longer defines), and adds a "`N` more module(s) never reached" line — the same "say what a grant does *not* reach, not only what it does" rule `#252` established for the RBAC permission grid. Turning `allow_all` on keeps any previously-selected `api_names` in the record and now says so ("Still holds `N` scoped endpoints underneath — they take effect again if full access is turned off"). That form is the **"Access definition"** zone (changed with Edit, applied with Save). Below it, for an existing record, a **"Live controls"** zone holds three cards that apply immediately with their own buttons and never go through Save: `ApplicationStatusCard` (with `ApplicationBypassUsersCard` embedded inside it) and `ApplicationSecretCard` (§1.1). A not-found state gates the whole shell when an id doesn't resolve. Its signature element remains the **API Names selector**: a collapsible accordion of `api_name` keys grouped by module, with a filter box, per-module select-all, and — replacing a bare "N selected" line — a bar+fraction+authority-count meter — rendered only when `allow_all` is off, with a warning banner shown instead whenever `allow_all` is on (in both view and edit mode).

Both screens also carry the cross-cutting **Activity Trail** feature added platform-wide: a **View History** action (list row-actions dropdown; edit-page hero actions slot) gated on `activity_log.read` with the `BACKSTAGE_SCOPED_RECORD` sentinel `clusterId`, since an application has no cluster of its own to scope against (see [Permissions](/en/backstage/applications/permissions)). Recording started 2026-08-31 (`AUDIT_RECORDING_STARTED_ON_PHASE_2`), so an application created earlier shows an empty timeline rather than implying nothing was ever changed.

The selector's options come from `GET /api-system/applications/api-catalog`. The SPA cannot add or edit catalog entries — the catalog is generated on the backend (§2) and the SPA only selects from it. See [UI Screens](/en/backstage/applications/ui-screens) for the full walkthrough.

Everything else is the SPA's standard Management-page furniture: `TableSkeleton` on first load, `EmptyState` when the list is empty (its "Add Application" CTA is `<Can>`-gated — see §4), toast feedback on mutations, a not-found state gating the whole edit shell when an id doesn't resolve, `doc_version` optimistic-lock saves, the `useUnsavedChanges` navigation guard while editing, and the dev-only Debug Sheet exposing each screen's raw API response. All three `application.*` routes and the sidebar entry additionally carry a `feature="applications"` flag on `PrivateRoute`, checked **after** the permission gate: a session without `application.*` access still sees `<Forbidden>`, but a granted session sees `NotFound` or a "Coming Soon" placeholder if the feature flag itself is set to `hide`/`inactive`.

### 1.1 Live controls: service status, bypass users, app secret

The three cards in `src/pages/applicationEdit/` operate on the saved record directly, each through its own endpoint (`applicationService.ts`), each refetching the record afterwards via `refreshRecord` without overwriting unsaved form edits. Each also reports unapplied drafts upward, so the page's `useUnsavedChanges` guard fires for them too (`ApplicationEdit.tsx`, `statusDirty`/`bypassDirty`).

| Card | What it does | Endpoint | Gate |
|---|---|---|---|
| `ApplicationStatusCard` ("Service status") | Radio group of the four statuses `running` / `maintenance` / `read_only` / `disabled`, each with help text. For a non-running draft: an optional message (max 1000 chars) and an optional **Expected back** `datetime-local` (must be in the future; informational only — nothing switches the app back automatically). **Apply status** opens a confirm dialog whose body states the effect; selecting the already-current status turns the dialog into "Update the notice". Shows a warning when a non-running status's expected-back time has already passed. | `PATCH /api-system/applications/:id/status` with `{ status, status_message?, status_until?, doc_version? }` | `<Can permission="application.update">`; read-only badge view otherwise |
| `ApplicationBypassUsersCard` (embedded in the status card) | Multi-select of users who keep full access while the app is `maintenance` or `read_only` (no effect when `disabled`). Own **Save bypass list** button, enabled only when the set differs from the saved one. | `PUT /api-system/applications/:id/bypass-users` with `{ user_ids }` (replace semantics) | `<Can permission="application.update">`; saved users shown as badges otherwise |
| `ApplicationSecretCard` ("App secret") | Shows a masked key stub `cas_` + dots + last 4 characters (same 44-char length as the real secret, so Reveal swaps text in place). **Generate secret** (first time) / **Rotate secret** (confirm dialog; the previous secret stays valid for 24 h), **Reveal** (auto-masks again after 30 s, with a draining progress bar), **Copy** (reveals first if masked), and a **Require secret** switch with its own enable/disable confirmations. Badge shows Enforced / Not enforced; lines show who rotated and when, and "Previous secret valid until …" while the grace window is open. Plaintext lives only in component state and is dropped on route change/unmount. | `POST …/secret/rotate`, `GET …/secret` (reveal), `PATCH …/secret/enforcement` with `{ require_secret, doc_version? }` (all under `/api-system/applications/:id`) | `application.secret.manage` (generate, rotate, enforcement) and `application.secret.reveal` (reveal, copy), both checked with `clusterId={BACKSTAGE_SCOPED_RECORD}`; a user with neither sees no card at all |

Self-lock protection: when the page's own `REACT_APP_API_APP_ID` equals the application being edited, the status card disables every status except Running (`isOwnApp()` in `utils/applicationStatus.ts`) and the secret card refuses to turn enforcement on if the build sends no secret. The gateway enforces the same rules — `409 APP_SELF_LOCK` on `PATCH …/status` and `409 APP_SECRET_SELF_LOCK` on `PATCH …/secret/enforcement` (`applications.controller.ts`). The secret card only renders once the record carries a boolean `has_secret` (older backends omit it). Full state-by-state behaviour is in [UI Screens](/en/backstage/applications/ui-screens) §3.5.

**What the gateway does with them** (`AppIdGuard.canActivate`, `apps/backend-gateway/src/common/guard/app-id.guard.ts`): after the 400 header check and the unknown-app 401, an app with `require_secret` and no valid `x-app-secret` header gets `401 APP_SECRET_INVALID` before anything else. Then `disabled` → `403 APP_DISABLED`; an `api_name` the app is not granted → 401; `running` → pass; `auth.*` endpoints pass in any status; a bypass user passes; `read_only` passes read-method requests; everything else gets `503 APP_MAINTENANCE` / `APP_READ_ONLY` (with `Retry-After` when `status_until` is in the future). The allowlist snapshot refreshes about once a minute, so status and enforcement changes take effect within that window (the dialogs say "within about a minute").

## 2. Business Context

Two kinds of callers hit the Carmen Blue backend: **human users**, whose sessions carry a bearer token and resolve through the RBAC permission snapshot, and **machine clients** — sibling services, integrations, and the SPAs themselves — which identify with an `x-app-id` header. Every **authenticated** request the Backstage SPA makes carries both: `Authorization: Bearer <token>` for the user and `x-app-id` for the application (`src/services/api.ts` sets `x-app-id` as a default header from the `REACT_APP_API_APP_ID` build env var; its interceptor attaches the bearer only when a token exists, so `/auth/login` goes out with `x-app-id` alone), meaning the SPA is itself a registered application record. A request can therefore fail on either axis independently — wrong user, or wrong/ungranted app id.

On the backend, guarded endpoints are wrapped in `AppIdGuard('module.action')` (backend-gateway). The guard first validates the header itself — missing or non-UUID `x-app-id` is a `400` — then checks it against an **in-memory allowlist snapshot**, not the database: `AppAllowlistRefresher` loads the snapshot from micro-cluster on boot (fail-closed — every guarded call is rejected until the first load succeeds) and refreshes it on a fixed interval (`APP_ALLOWLIST_TTL_MS`, default 60 s). The request passes when the snapshot entry for that app id has `allow_all = true` or contains the guard's `api_name`. Because enforcement reads the snapshot, grant changes (new grants, revocations, deletions, `allow_all` flips) take effect at the **next refresh**, not instantly.

The selectable catalog is **derived from those guards, not hand-maintained**: `scripts/generate-app-api-catalog/run.ts` in `carmen-turborepo-backend` scans the gateway source for `new AppIdGuard('...')` calls and emits `app-api-catalog.generated.ts` (a flat sorted list plus module groups). A new guarded endpoint appears in the SPA's selector after regeneration and a backend deploy — no database seed is involved, which is the key operational difference from the RBAC permission catalog (a Postgres table seeded by migration).

## 3. Key Concepts

- **App ID = record UUID.** The `tb_application.id` primary key is the `x-app-id` value. There is no separate `app_id` column or field anywhere — the SPA simply surfaces `id` under the label "App ID" (read-only, server-generated).
- **`allow_all` vs explicit list.** A boolean fork: `allow_all = true` grants every guarded endpoint and makes any `tb_application_api` rows irrelevant; `allow_all = false` grants exactly the live `api_name` rows. The SPA hides the API Names selector entirely while `allow_all` is checked, and the write payload omits the names in that case.
- **`api_name` grammar.** Keys are `resource.action` strings — the same shape as RBAC permission keys, but a **separate vocabulary from a separate source**: `api_name`s come from the `AppIdGuard` scan, RBAC keys from `tb_backstage_permission`. The action segments follow the backend controller methods, not the RBAC verb set — `cluster.findAll`, `cluster.findOne`, `cluster.uploadLogo` rather than `cluster.read` — so the two catalogs share grammar but not key strings. The generated catalog holds 1,140 keys across 181 module groups as of 2026-10-27 (counted in `app-api-catalog.generated.ts`; was 900/148 on 2026-09-05 — the catalog keeps growing as new guarded endpoints ship). The module of an `api_name` is the prefix before the first `.`; a dotless name is its own module (`src/utils/apiCatalog.ts` mirrors the backend generator's split rule exactly).
- **Replace, not delta.** `PUT /api-system/applications/:id` sends the **full desired set** as `details: { add: [{ api_name }] }` — replace semantics. This is the opposite of RBAC role writes, which send `{ add, remove }` deltas; a developer porting code between the two modules must not assume one convention. The `PUT` (and `POST`) payload now also carries `doc_version` (optimistic-concurrency token — see [Data Model](/en/backstage/applications/data-model) §2.1).
- **`device` classifies the client.** `tb_application.device` (default `"web"`; SPA value set `mobile` / `web` / `desktop` / `pos`) records what kind of client the app is. The backend gateway resolves it from the `x-app-id` header (`getDevice(appId)`) to drive device-specific behaviour downstream — e.g. a `mobile` app sees only `draft` GRNs in list views (see [good-receive-note/02-business-rules](/en/inventory/good-receive-note/02-business-rules)).
- **Service status and app secret.** `tb_application.status` is one of `running` (default) / `maintenance` / `read_only` / `disabled` (CHECK constraint in the migration, not in Prisma), with `status_message`, `status_until` (display-only), `status_changed_at`/`status_changed_by_id`. `require_secret` plus an AES-256-GCM ciphertext (`secret_ciphertext`, key `SECRET_ENCRYPTION_KEY`, decrypted only in micro-cluster), `secret_last4`, and a previous-secret slot valid for 24 h after a rotation. See §1.1 and [Data Model](/en/backstage/applications/data-model).
- **Standard platform hygiene.** `tb_application` still carries a `is_active` column, whose value in the API read model micro-cluster derives from `status` (`isActiveFor(status)` in `application.service.ts`) — the SPA no longer writes it; a record's state is `status`, the audit trio, and a soft-delete-aware unique name (`@@unique([name, deleted_at])`), so a deleted application's name can be reused.

## 4. Roles and Personas

Access to the module is permission-gated through [Backstage Roles](/en/backstage/rbac), with both route guards and in-page `<Can>` gates:

| Surface | Gate | Key |
|---|---|---|
| `/applications` route + "Applications" sidebar entry (Backstage group) | `PrivateRoute` / sidebar filter | `application.read` |
| `/applications/new` route | `PrivateRoute` | `application.create` |
| `/applications/:id/edit` route | `PrivateRoute` | `application.update` |
| Add Application button (list header + empty state) | `<Can>` | `application.create` |
| Row Edit (list actions dropdown) | `<Can>` | `application.update` |
| Row Delete (list actions dropdown) | `<Can>` | `application.delete` |
| Edit toggle (edit page hero) | `<Can>` | `application.update` |
| Row action **View History** (list dropdown) | `<Can>` | `activity_log.read`, `clusterId={BACKSTAGE_SCOPED_RECORD}` (cross-cutting Activity Trail feature — new) |
| Hero action **View History** (edit page) | `<Can>` | `activity_log.read`, `clusterId={BACKSTAGE_SCOPED_RECORD}` |
| Service status card — Apply, and bypass-users Save | `<Can>` | `application.update` (read-only view otherwise) |
| App secret card — generate, rotate, require-secret switch | `useAuth().hasPermission` | `application.secret.manage`, `clusterId={BACKSTAGE_SCOPED_RECORD}` |
| App secret card — reveal, copy | `useAuth().hasPermission` | `application.secret.reveal`, `clusterId={BACKSTAGE_SCOPED_RECORD}` |

Note that `application.delete` exists **only as an in-page gate** — no route requires it, and the edit page offers no delete action at all; deletion happens exclusively from the list row dropdown. **The empty-state "Add Application" CTA gap flagged in the previous sync is now closed** — it is wrapped in `<Can permission="application.create">` the same as the header button, confirmed by direct source read. All three routes and the sidebar entry additionally require the `applications` feature flag (checked after the permission gate). The full matrix is in [Permissions](/en/backstage/applications/permissions).

## 5. Related Modules

- [Backstage Roles](/en/backstage/rbac) — the human-access counterpart. Same `resource.action` key grammar, different catalog and enforcement path: RBAC keys live in `tb_backstage_permission` and gate user sessions; `api_name`s come from the `AppIdGuard` scan and gate `x-app-id` callers. The `application.*` keys that gate *this module's screens* are themselves RBAC keys — a human needs RBAC grants to manage machine grants.
- [users](/en/backstage/users) — applications have no user binding; the only `tb_user` references on the application tables are the audit actor columns. The schema-only `tb_application_role` family (which does join users) is unrelated to this module — see the [Data Model](/en/backstage/applications/data-model) divergences section.
