# Business Units

> **At a Glance**
> **Module purpose:** Authoring surface where the operational entity that Carmen Blue calls a **business unit** (BU) is created and configured — one row per hotel/property/legal-entity, with the fields that drive both the inventory app's tenant context and the platform's user-role and license assignments &nbsp;·&nbsp; **Audience:** Developers and QA working on the Backstage SPA; operator access is gated by **reused `cluster.*` permission keys** ([rbac](/en/backstage/rbac)) — there are no `business_unit.*` keys &nbsp;·&nbsp; **Nav entry:** `permission: 'cluster.read'` — **shared with the Clusters menu entry** ([clusters](/en/backstage/clusters)) rather than a key of its own, so the permission name gives no hint that it also opens this screen (the Tenant Migrations / Tenant Seeds / Data Import rows beneath it now carry their own `tenant_migration.read` / `tenant_seed.read` / `data_import.manage` keys) &nbsp;·&nbsp; **Feature flag:** `business_units`, checked on all three routes after the permission gate &nbsp;·&nbsp; **`superAdminOnly`:** No &nbsp;·&nbsp; **Key entities/tables:** `business_unit` (identity fields `code` — now server-generated — `name`, `alias_name`, `is_hq`, `is_active`; contact blocks for hotel/company; tax fields; date/time/number format fields; `calculation_method`, `default_currency_id`; `database_pool_id`/`db_schema`; `config[]` key/value rows; branding `logo_file_token`/`avatar_file_token`) plus `tb_business_unit_license` (the per-BU seat ledger that replaced `max_license_users`) and the BU-to-user join carrying a per-BU `role` of `admin` or `user` &nbsp;·&nbsp; **Sub-pages:** 3

## 1. Overview

A business unit is the operational tenant of the Carmen Blue platform: one BU is one hotel, one property, or one legal entity that buys, receives, counts, and consumes inventory. The list view at `/business-units` (`BusinessUnitManagement.tsx`) is a server-paginated, searchable catalogue with Active/Inactive and soft-deleted facets, CSV export, and an **Overview** summary strip (`BuSummary`, now backed by a dedicated `GET /api-system/business-units/summary` endpoint — total/active/inactive/archived counts and the number of distinct clusters spanned).

The edit page at `/business-units/:id/edit` and `/business-units/new` (`BusinessUnitEdit.tsx`) has been rewritten **twice** since the module was last synced. First from nine `CollapsibleSection` cards in a two-column grid into a single "one-document" edit-in-place scroll; then — the change this sync documents — from that scroll into a **tabbed document**: General, Location, Formats, Technical, Users, Licenses and — since 2026-10-26 — **Notes**, behind a pinned identity strip and a sticky `TabStrip`. There is still no read/edit toggle anywhere — one `canEdit` boolean (`cluster.create` for a new BU, `cluster.update` scoped to `cluster_id` for an existing one) gates every field on every tab; each individual field still commits on blur/Enter and reverts on `Escape` via the shared `InlineField` click-to-edit control, unchanged across both rewrites. Users and Licenses are omitted from the tab strip entirely while creating a BU, since both need a row to already exist. A sticky bottom bar shows Save Changes/Cancel whenever the document is dirty (or unconditionally in create mode); `Ctrl/⌘+S` still saves and `Escape` still cancels page-wide (not just inside a field) via the shared keyboard-shortcut hook — confirmed unchanged in `BusinessUnitEdit.tsx`: the save shortcut re-checks `canEdit` itself before calling Save, since a disabled button alone is no defence against a shortcut bypassing it, and the cancel shortcut only fires on an existing BU with unsaved changes (it does nothing in create mode, where Escape has no assigned action). Saves are protected by a `doc_version` optimistic-lock token, the same mechanism as [clusters](/en/backstage/clusters).

Each BU belongs to exactly one **cluster** (the `cluster_id` foreign key, selected from a dropdown in the General tab). The "create BU" flow can be entered either from the BU list page or from the cluster edit page, which navigates to `/business-units/new?cluster_id=<id>` to preselect the parent. Four things changed materially enough since the last sync to call out up front, each covered in depth on the sub-pages:

1. **`code` is no longer typed by the user.** The create form has no code field at all — the backend generates an 8-character code and retries on collision; the edit page shows it read-only. See [Data Model](/en/backstage/business-units/data-model) §2.1 and [UI Screens](/en/backstage/business-units/ui-screens) §3–4.1.
2. **The Technical tab has a schema-name randomizer.** A BU no longer holds its own database credentials (`db_connection` is gone) — it points at a shared `tb_database_pool` record and supplies its own `db_schema`, which a "Generate schema" button can fill with a random, collision-improbable name. See [UI Screens](/en/backstage/business-units/ui-screens) §4.4.
3. **Licenses is now its own tab**, split out of Users — seats (a per-BU purchase ledger) and the user roster answer different questions and no longer share a tab. See [UI Screens](/en/backstage/business-units/ui-screens) §4.7.
4. **The Licenses tab has a "New subscription" button**, gated on `subscription.manage` rather than this page's own `canEdit`, linking straight to the full-page subscription form pre-scoped to this BU and its cluster.
5. **Since 2026-09-09 the Licenses tab holds two cards and the Technical tab holds two advanced cards, not three** (`../carmen-backstage` PRs #286–#291). The seat card now also lists every subscription issued to this BU on a shared coverage timeline; a second card lists the BU's **interface licences** (`INF`, `tb_business_unit_interface_license`) with an "Add interface license" button gated on the same `subscription.manage`. The **Interface Entitlement** card is gone from the Technical tab — interface entitlement is no longer a per-BU checkbox list but a licence sold from the [Licenses](/en/backstage/licenses) module (§3.6 there). See [UI Screens](/en/backstage/business-units/ui-screens) §4.5 and §4.7.
6. **The list page snaps a stale stored page number back into range** (PR #298, 2026-09-21): `page_business_units` in `localStorage` can outlive the result set it was valid for, and a request past the last page returns `200` with no rows — which used to replace the whole table *including the pager*, stranding the operator on an "empty" list whose Overview strip still counted rows. `outOfRangePage()` (`src/utils/pageRange.ts`) now computes the last page from `paginate.total` and re-requests it. See [UI Screens](/en/backstage/business-units/ui-screens) §2.1.
7. **2026-10-27 round** (`../carmen-backstage` commits since `f1c69f1`): a staff-only **Notes** tab (`tb_business_unit_note`, `bu_note.view`/`bu_note.manage`; [UI Screens](/en/backstage/business-units/ui-screens) §4.8); a per-BU **Attachment policy** section on the Technical tab (two `attachment.*` rows in `config[]`; §4.4); `calculation_method` gained `average_per_location`; the **Per Page** format and its `perpage_format` column were removed; the Users tab lost its per-row "Shared" badge in favour of seat-effect hints in the edit/remove dialogs; the Tenant Migration/Seed cards are gated by `tenant_migration.*`/`tenant_seed.*` instead of `isSuperAdmin`; and the documented `tb_business_unit_tb_module` join was found to have been dropped back in August (see [Data Model](/en/backstage/business-units/data-model) §2.2).

Beyond identity and contact fields, the BU stores the locale knobs that the inventory runtime reads — `date_format`, `time_format`, `timezone`, the JSON `amount_format`/`quantity_format`/`recipe_format` formatters defaulting to `th-TH`, the `calculation_method`, and `default_currency_id` (a dropdown of the BU's own tenant currencies, lazy-loaded once the BU's `code` is known) — plus a `config[]` array of free-form key/value rows. Detail on individual fields and screen behaviour lives on the sub-pages — this landing page only orients.

## 2. Business Context

In hospitality, the smallest unit that has its own books, its own currency, and its own local supply chain is the property — a single hotel inside a brand group. Carmen Blue models that as a business unit: every inventory transaction (GRN, store requisition, physical count, spot check) is scoped to one BU; every report runs against one BU's schema; every user is granted access to one or more BUs with a role inside each. The `business_unit` row therefore carries far more than identity. It carries the locale settings the inventory UI displays in (date and number formats, timezone, default currency), the costing knob (`calculation_method`) the valuation engine consults, and a pointer (`database_pool_id`/`db_schema`) at the shared database server hosting its tenant schema — the platform no longer stores per-BU connection credentials directly.

Seats are no longer a single ceiling either. Where the schema used to carry one `max_license_users` integer, user capacity for a BU is now a dated purchase ledger (`tb_business_unit_license`) — one row per seat contract, summed across whatever is currently active. The edit page's General tab shows the resulting number read-only; the Licenses tab is where those purchase rows are actually reviewed (creating and editing one still happens on the full-page License Center form, not inline on this page).

Because a BU is also where users become operationally meaningful, the edit page's Users tab doubles as a user-assignment workbench. It lists everyone with access to this BU, each with a **BU role** (`admin` or `user`) that is orthogonal to the platform RBAC assignments on the user account itself ([rbac](/en/backstage/rbac)). New BU members are picked from the BU's parent cluster — a user must already exist on the cluster before they can be added to one of its BUs. Whether removing or deactivating a member here frees a cluster seat (they may also belong to another BU of the cluster) is shown as a hint in the edit/remove dialogs, driven by a backend-optional field, `frees_seat`, that may not be populated in every environment (the earlier per-row "Shared" badge was removed in 2026-10).

The Technical tab's advanced cards extend the BU beyond plain configuration into tenant-database operations, gated since the 2026-10 round by `tenant_migration.*` / `tenant_seed.*` (previously super-admin buttons): **Tenant Migrations** checks, applies and — since PR #297 — resolves pending or stuck database schema migrations against the BU's own tenant database; **Tenant Seed** runs seed scripts against it. The former third card, **Interface Entitlement**, was removed in PR #286 (2026-09-08): which POS / PMS / accounting brands a BU may switch on is now a licence question, answered by the `interface`-kind feature groups a BU holds through its interface licences (the Licenses tab, and [Licenses](/en/backstage/licenses) §3.6). The card's own "empty = unrestricted" note had also been wrong — the inventory app has always treated an empty entitlement as "nothing," so the move to a fail-closed licence changed less than it looked. Both cards are now render-gated on `tenant_migration.read` / `tenant_seed.read`, and their mutating actions on the matching `.apply` keys — no longer on `isSuperAdmin` (changed in the 2026-10 round).

## 3. Key Concepts

- **Business unit (BU)**: A single row in `business_unit` representing one hotel/property/legal entity. Every inventory transaction belongs to exactly one BU; every report runs against one BU.
- **Cluster membership**: Every BU has a non-nullable `cluster_id` selected from the cluster dropdown on the General tab. The cluster edit page can launch a create-BU flow with `cluster_id` preselected via the `/business-units/new?cluster_id=<id>` query parameter.
- **Code (`code`)**: A short identifier, unique **across the entire platform**, not just within a cluster (a partial-unique index added since the last sync — see [Data Model](/en/backstage/business-units/data-model) §2.1). **No longer entered by the user**: the backend generates an 8-character Crockford-base32 code on create and retries on collision; the field is read-only on the edit page and ignored by the backend if sent on update.
- **HQ flag (`is_hq`)**: Marks the BU as the headquarters within its cluster — a clickable "HQ" badge in the identity strip (toggles directly, no separate checkbox/section); semantics depend on consuming modules.
- **Active flag (`is_active`)**: Toggles whether the BU is operationally live — a clickable identity-strip badge, not a form checkbox. Inactive BUs remain editable in the admin surface but are filtered out of normal runtime selection. The list view exposes Active/Inactive as filter chips.
- **Structured hotel/company address**: Ten structured columns each — `*_address_line1`, `*_address_line2`, `*_sub_district`, `*_district`, `*_city`, `*_province`, `*_postal_code`, `*_country`, `*_latitude`, `*_longitude` — for both the Hotel and Company groups on the Location tab. A **Copy from hotel address** button one-way-copies all ten hotel fields into their company counterparts.
- **Tax information**: `tax_no` and `branch_no` capture the Thai tax registration plus branch designator used on printed documents.
- **Date/Time and Number formats**: `date_format`, `date_time_format`, `time_format`, `long_time_format`, `short_time_format`, `timezone`, plus JSON formatters `amount_format`/`quantity_format`/`recipe_format` — all on the Formats tab, each formatter defaulting to `{"locales":"th-TH","minimumIntegerDigits":2}`.
- **Calculation settings**: `calculation_method` (`average`/`fifo`/`average_per_location`, consumed by the inventory valuation engine) and `default_currency_id` — a `<select>` populated from the BU's own tenant currency master, lazy-loaded once the BU's code is known, falling back to a free-text UUID input if the fetch fails.
- **Configuration array (`config[]`)**: An ordered list of free-form `{ key, value, datatype }` rows on the Technical tab, persisted as a JSON array. Used by the inventory app for per-BU feature toggles and integration settings; the admin surface does not impose a schema.
- **Database pool + schema (`database_pool_id`/`db_schema`)**: Replaces the retired `db_connection` JSON blob entirely. A BU points at a shared, platform-managed `tb_database_pool` record and supplies its own schema name inside it; host/port/username/password live only on the pool record, never on this page. A "Generate schema" button can fill the schema field with a random `bu_`-prefixed name.
- **Branding (logo + avatar)**: Each BU carries a rectangular **logo** and a square **avatar**, stored as file tokens and returned by the API as embedded presigned objects. Uploads happen on the General tab's Branding section; the list page shows a small `BrandMark` avatar next to the BU name (reintroduced since the last sync, matching the identical change on [clusters](/en/backstage/clusters)).
- **Optimistic concurrency (`doc_version`)**: `tb_business_unit` carries a `doc_version` counter; the edit page resends it on every `PUT` and shows a conflict toast + reload on a stale `409`.
- **Audit columns**: The list shows Created and Updated columns (timestamp plus actor name). Both the list and the edit page now read every audit value through the shared `normalizeAudit()` helper (`src/utils/audit.ts`), which tries the nested `audit.{created,updated,deleted}.{at,id,name,avatar}` shape first and only falls back to the older flat shape (`created_at`/`created_by_name` or `created_by`, etc.) when the nested value is absent or empty — not the other way around. An Updated entry is shown only when the record was actually edited: that is decided by whether an editor name is present, or — absent a name — whether the updated timestamp differs from the created timestamp, not by a plain `updated_at === created_at` comparison.
- **Seats (`tb_business_unit_license`)**: A dated purchase ledger, one row per seat contract, replacing the removed `max_license_users` integer. Summed across active rows into the read-only "Max users" figure on the General tab; reviewed (not edited) on the Licenses tab, which links out to the full-page License Center form for actually creating or editing a row.
- **Interface licences (`tb_business_unit_interface_license`)**: A second dated ledger on the same tab since 2026-09-10 — one row per interface feature group (`interface.pos.micros3700`, `interface.accounting.carmen_gl`, …) for a date range, number prefix `INF`. The entitlement it grants is computed by the backend as `in_force = licence active by its own dates AND the BU's main subscription active`; the card badges only on `in_force` and never on the dates, so a licence "within its dates" whose main contract has lapsed shows **Capped by contract**. Reviewed here, created/edited on the License Center's `/licenses/interface/*` form.
- **BU role (`admin` vs. `user`)**: The role attached to each user-BU assignment, stored on the BU-user join row alongside `is_active` and `is_default`. This is **orthogonal** to the platform RBAC permission assignments on the user account; the BU role governs the user's behaviour inside the inventory app for that BU, not access to admin routes.
- **Add-user-from-cluster pattern**: New BU members are picked from the parent cluster's user list — a user must be a member of the cluster before they can be added to one of its BUs.
- **Soft delete**: BUs are soft-deleted via `deleted_at` / `deleted_by_name`; the list view has a "Show soft-deleted business units" filter toggle. Unlike [clusters](/en/backstage/clusters), the BU list's Delete action has no client-side dependency guard.

## 4. Roles and Personas

Access is permission-based ([Backstage RBAC](/en/backstage/rbac)) — but with the single most important gotcha in this module:

> **Key-reuse gotcha: the Business Units module has no permission keys of its own.** The `/business-units`, `/business-units/new`, and `/business-units/:id/edit` routes reuse the **`cluster.read` / `cluster.create` / `cluster.update`** keys, the sidebar entry filters on `cluster.read`, and the in-page Delete gate consumes `cluster.delete` — there are **no `business_unit.*` keys** in the catalog. `cluster.read` alone drives two sidebar entries — Clusters and Business Units — so a grant that opens the Clusters module also opens Business Units, and the two cannot be separated by permission alone (the `business_units` **feature flag**, §4 below, is the only per-module on/off switch). Tenant Migrations used to be a third entry on `cluster.read`; since the 2026-10 round it has its own `tenant_migration.read` key (`backstageNav.ts:17`). A `cluster.update` grant scoped to cluster X covers editing the BUs of cluster X. The cluster-side view of the same gotcha is in [clusters permissions](/en/backstage/clusters/permissions) §2.

| Surface | Gate type | Key | Scoped? |
|---|---|---|---|
| `/business-units` route | `requiredPermission` + `feature` | `cluster.read` + `business_units` | No |
| `/business-units/new` route | `requiredPermission` + `feature` | `cluster.create` + `business_units` | No |
| `/business-units/:id/edit` route | `requiredPermission` + `feature` | `cluster.update` + `business_units` | No |
| Sidebar "Business Units" entry | `permission` + `feature` filter | `cluster.read` / `business_units` | No |
| List: Add Business Unit button (header **and** empty state) | `<Can>` | `cluster.create` | No |
| List: row Edit action | `<Can>` | `cluster.update` | Yes — `clusterId={row.original.cluster_id}` |
| List: row View History action | `<Can>` | `activity_log.read` | Yes — `clusterId={row.original.cluster_id \|\| UNRESOLVED_CLUSTER_ID}` |
| List: row Delete action | `<Can>` | `cluster.delete` | Yes — `clusterId={row.original.cluster_id}` |
| Edit page: every field on every tab, except the two below | `canEdit = isNew ? hasPermission('cluster.create') : hasPermission('cluster.update', {clusterId})` | `cluster.create` (new) / `cluster.update` (existing) | Yes for existing BUs — `clusterId={formData.cluster_id \|\| UNRESOLVED_CLUSTER_ID}` |
| Technical tab: Database Pool picker | `<Can>`, nested inside `canEdit` | `database_pool.read` | No |
| Licenses tab: New subscription button | supplied by parent, gated separately from `canEdit` | `subscription.manage` | No |
| Licenses tab: Add interface license button | supplied by parent, gated separately from `canEdit` | `subscription.manage` | No |
| Edit page: Tenant Migrations / Tenant Seed cards (visibility) | `hasPermission('tenant_migration.read' / 'tenant_seed.read', { clusterId: BACKSTAGE_SCOPED_RECORD })`, independent of `canEdit` | `tenant_migration.read` / `tenant_seed.read` | Unscoped branch |
| Edit page: both cards' mutating actions (Deploy/Resolve/Run) | `canApply` prop = `hasPermission('tenant_migration.apply' / 'tenant_seed.apply', …)`; the status-check button needs no apply key | `tenant_migration.apply` / `tenant_seed.apply` | Unscoped branch |
| Edit page: Notes tab and panel | `hasPermission('bu_note.view', { clusterId: bu.cluster_id })` to see; plus `bu_note.manage` to write | `bu_note.view` / `bu_note.manage` | Yes — the BU's parent cluster |

The scoped (`clusterId`) gates resolve against the BU's **parent cluster** — a role assignment scoped to cluster A renders row Edit/Delete/View History only on BUs whose `cluster_id` is A, while the unscoped route guards pass on any cluster-scoped grant. Note the `UNRESOLVED_CLUSTER_ID` sentinel: when `formData.cluster_id` is empty (a cluster-less BU, or before the Cluster dropdown has a value in create mode), the check is deliberately kept on `checkPermission`'s scoped branch (fail closed) rather than falling through to the broad "any cluster" branch.

A second, narrower permission gates one control **inside** the page-wide `canEdit` boundary: the Database Pool picker on the Technical tab additionally requires `database_pool.read` — a session with `cluster.update` on this BU but not `database_pool.read` still edits everything else, but sees the pool name and schema read-only with a note explaining why. The resolution algorithm, bootstrap exception, and super-admin bypass live in [rbac permissions](/en/backstage/rbac/permissions).

**Backend note on the edit form's `PUT` (corrected 2026-10-27).** At the gateway, `PUT /api-system/business-units/:id` (`backstage_business-units.controller.ts:402-403`) carries only `AppIdGuard` — unlike the sibling `POST` (`cluster.create`, line 292-294) and `DELETE` (`cluster.delete`, line 677-679), which stack `BackstagePermissionGuard`. An earlier revision of this page called that an authorization gap; it is not one, because the gateway delegates and `micro-cluster` enforces it: `business-unit.service.ts:753-763` calls `ClusterAdminAuthzService.canWriteCluster(userId, clusterId, 'cluster.update')` (and again for the destination cluster when a BU is moved) — true for a super admin, an active admin member of that cluster, or a Backstage role grant of `cluster.update` for it — and answers `CLUSTER_USER_NOT_CLUSTER_ADMIN` otherwise. The decorator-based permission-coverage checker simply cannot see that service-level check.
