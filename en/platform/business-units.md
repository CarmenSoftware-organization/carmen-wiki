# Business Units

> **At a Glance**
> **Module purpose:** Authoring surface where the operational entity that Carmen calls a **business unit** (BU) is created and configured — one row per hotel/property/legal-entity, with the form fields that drive both the inventory app's tenant context and the platform's user-role assignments &nbsp;·&nbsp; **Audience:** Developers and QA working on the Platform admin SPA; operator access is gated by **reused `cluster.*` permission keys** ([rbac](/en/platform/rbac)) — there are no `business_unit.*` keys &nbsp;·&nbsp; **Key entities/tables:** `business_unit` (identity fields `code`, `name`, `alias_name`, `is_hq`, `is_active`, `max_license_users`; contact blocks for hotel/company; tax fields; date/time/number format fields; `calculation_method`, `default_currency_id`; `db_connection`; `config[]` key/value rows; branding `logo_file_token`/`avatar_file_token`) plus the BU-to-user join carrying a per-BU `role` of `admin` or `user` &nbsp;·&nbsp; **Sub-pages:** 3

## 1. Overview

A business unit is the operational tenant of the Carmen platform: one BU is one hotel, one property, or one legal entity that buys, receives, counts, and consumes inventory. The list view at `/business-units` (`BusinessUnitManagement.tsx`) is a server-paginated, searchable catalogue with Active/Inactive and soft-deleted facets, CSV export, and an **Overview** summary strip (`BuSummary` — total/active/inactive/archived counts and the number of distinct clusters spanned). The per-row logo thumbnail column that used to sit in this list is gone.

The edit page at `/business-units/:id/edit` and `/business-units/new` (`BusinessUnitEdit.tsx`) was rewritten from nine `CollapsibleSection` cards in a two-column grid into a single **"one-document" edit-in-place page** — there is no read/edit toggle any more; every field is always rendered in its editable form, gated by one `canEdit` boolean (`cluster.create` for a new BU, `cluster.update` scoped to `cluster_id` for an existing one). A hero card (logo/avatar, code, cluster name, and clickable Active/HQ status badges) sits above six inline field groups — **Details, Location, Contact, Company, Tax, Date & time** — that replace the old Basic/Hotel/Company/Tax/Date-Time-Formats sections; each field commits on blur/Enter via a shared `InlineField` control (click-to-edit, `Escape` reverts). Four more complex sections follow in the same continuous scroll: **Calculation Settings**, **Number Formats**, **Branding** (logo + avatar upload), **Configuration**, and **Database Connection** (now a structured, editable form — see §3) — then, on existing BUs only, three "advanced" cards (**Tenant Migrations**, **Tenant Seed**, **Interface Entitlement** — visible to any editor with BU access; only their mutating actions are super-admin-gated, see §3) and finally the **Users** card. A sticky bottom bar shows Save Changes/Cancel whenever the document is dirty (or unconditionally in create mode); `Ctrl/⌘+S` and `Escape` work as keyboard shortcuts. Saves are protected by a `doc_version` optimistic-lock token, same mechanism as [clusters](/en/platform/clusters).

Each BU belongs to exactly one **cluster** (the `cluster_id` foreign key, selected from a dropdown in the Details group). The "create BU" flow can be entered either from the BU list page or from the cluster edit page, which navigates to `/business-units/new?cluster_id=<id>` to preselect the parent. Beyond identity and contact fields, the BU stores the locale knobs that the inventory runtime reads — `date_format`, `time_format`, `timezone`, the JSON `amount_format`/`quantity_format`/`recipe_format` formatters defaulting to `th-TH`, the `calculation_method`, and `default_currency_id` (now a proper dropdown of the BU's own tenant currencies, lazy-loaded once the BU's `code` is known) — plus a `config[]` array of free-form key/value rows and a `db_connection` block, now held as an editable list of known + custom key/value fields (not a read-only JSON blob) that points the BU at its tenant schema. Detail on individual fields and screen behaviour lives on the sub-pages — this landing page only orients.

## 2. Business Context

In hospitality, the smallest unit that has its own books, its own currency, and its own local supply chain is the property — a single hotel inside a brand group. Carmen models that as a business unit: every inventory transaction (GRN, store requisition, physical count, spot check) is scoped to one BU; every report runs against one BU's schema; every user is granted access to one or more BUs with a role inside each. The `business_unit` row therefore carries far more than identity. It carries the locale settings the inventory UI displays in (date and number formats, timezone, default currency), the costing knob (`calculation_method`) the valuation engine consults, the per-tenant database connection the platform uses to route queries to that property's schema, and the licence ceiling (`max_license_users`) that caps how many users may sign in.

Because a BU is also where users become operationally meaningful, the edit page doubles as a user-assignment workbench. The Users card lists everyone with access to this BU, each with a **BU role** (`admin` or `user`) that is orthogonal to the platform RBAC assignments on the user account itself ([rbac](/en/platform/rbac)). New BU members are picked from the BU's parent cluster — a user must already exist on the cluster before they can be added to one of its BUs, which keeps tenant boundaries clean. Access to the BU routes is permission-gated, but with a twist: the module borrows the `cluster.read` / `cluster.create` / `cluster.update` keys instead of defining its own — see §4.

Three cards on the edit page extend the BU beyond plain configuration into tenant-database operations, and none of them is render-gated — any session with BU edit access sees all three whenever the BU already exists: **Tenant Migrations** checks and applies pending database schema migrations against the BU's own tenant database; **Tenant Seed** runs seed scripts against it; and **Interface Entitlement** controls which named interface/brand the BU is licensed to show (an empty selection means unrestricted — every interface shows, matching the gateway's default). It is only their *mutating* actions that require `isSuperAdmin` (and, for the first two, a non-empty `db_connection`) — a non-super-admin editor still sees the card, but gets a disabled button with a "Super-admin required." tooltip on Tenant Migrations/Tenant Seed (this also covers their status-check button, so a non-super-admin never loads pending-migration data), or a plain "Super-admin required." message in place of the selection UI on Interface Entitlement. Each calls its own dedicated service module, not `businessUnitService`.

## 3. Key Concepts

- **Business unit (BU)**: A single row in `business_unit` representing one hotel/property/legal entity. Every inventory transaction belongs to exactly one BU; every report runs against one BU.
- **Cluster membership**: Every BU has a non-nullable `cluster_id` selected from the cluster dropdown. The cluster edit page can launch a create-BU flow with `cluster_id` preselected via the `/business-units/new?cluster_id=<id>` query parameter.
- **HQ flag (`is_hq`)**: Marks the BU as the headquarters within its cluster — shown as a clickable "HQ" badge in the hero card (toggles directly, no separate checkbox/section); semantics depend on consuming modules.
- **Active flag (`is_active`)**: Toggles whether the BU is operationally live — also a clickable hero badge now, not a form checkbox. Inactive BUs remain editable in the admin surface but are filtered out of normal runtime selection. The list view exposes Active/Inactive as filter chips.
- **Max licensed users (`max_license_users`)**: Optional integer cap on how many users may be assigned to the BU. Blank means unlimited.
- **Structured hotel/company address**: The former single `hotel_address`/`company_address` free-text fields have been replaced by ten structured columns each — `*_address_line1`, `*_address_line2`, `*_sub_district`, `*_district`, `*_city`, `*_province`, `*_postal_code`, `*_country`, `*_latitude`, `*_longitude` — for both the "Location" (hotel) group and the "Company" group. A **Copy from hotel address** button on the Company group one-way-copies all ten hotel fields into their company counterparts in one click (still just a local form edit — nothing is saved until the sticky Save bar fires).
- **Tax information**: `tax_no` and `branch_no` capture the Thai tax registration plus branch designator used on printed documents.
- **Date/Time formats**: `date_format`, `date_time_format`, `time_format`, `long_time_format`, `short_time_format`, and `timezone` configure how the inventory UI renders timestamps for this BU — now grouped into a single "Date & time" inline group rather than a standalone form section.
- **Number formats**: Three JSON formatters — `amount_format`, `quantity_format`, `recipe_format` — plus a `perpage_format` JSON that drives pagination defaults. Each formatter defaults to `{"locales":"th-TH","minimumIntegerDigits":2}` (perpage defaults to `{"default":10}`).
- **Calculation settings**: `calculation_method` (`average`/`fifo`, consumed by the inventory valuation engine) and `default_currency_id` — now a `<select>` populated from `GET /api/config/:buCode/currencies` (the BU's own tenant currency master, lazy-loaded once the BU's code is known), falling back to a free-text UUID input if the fetch fails; the resolved code/name/symbol/decimals are still shown alongside in read mode.
- **Configuration array (`config[]`)**: An ordered list of free-form `{ key, value, datatype }` rows persisted as a JSON array on the BU. The Data Type selector now includes an `enum` option alongside `string`/`number`/`boolean`/`date`/`json`. Used by the inventory app for per-BU feature toggles and integration settings; the admin surface does not impose a schema.
- **Database connection (`db_connection`)**: No longer a read-only `<pre>` blob — it is a hybrid editable form: seven **known fields** (`host`, `port`, `database`, `schema`, `user`, `password`, `ssl`) rendered as typed inputs (password masked with a show/hide toggle; `ssl` as a checkbox), plus an open-ended list of **additional key/value rows** for anything else. The password field is write-only on read (the backend always redacts it to an empty string) — a super-admin-gated **Reveal current password** button calls a dedicated on-demand endpoint to show the real stored value; leaving the field blank on save does *not* clear the stored password.
- **Branding (logo + avatar)**: Each BU carries a rectangular **logo** and a square **avatar**, stored in Prisma as file tokens (`logo_file_token`, `avatar_file_token`) and returned by the API as embedded presigned objects (`logo: { url, expires_at }`, `avatar: { url, expires_at }`). Uploads happen on the edit page's Branding card via dedicated multipart endpoints; the list page no longer shows a logo thumbnail column (dropped along with the Overview summary strip's introduction, mirroring the identical change on [clusters](/en/platform/clusters)).
- **Optimistic concurrency (`doc_version`)**: `tb_business_unit` carries a `doc_version` counter (added 2026-07-16, all 35 platform tables); the edit page resends it on every `PUT` and shows a conflict toast + reload on a stale `409`.
- **Audit columns**: The list shows Created and Updated columns (timestamp plus actor name). The SPA flattens the nested `audit` object from API responses (`audit.created.{at,name}`, `audit.updated.{at,name}`) for the date columns, tolerating the older flat shape, which wins when present (`item.created_at ?? item.audit?.created?.at`). The Updated cell is omitted when `updated_at` equals `created_at`.
- **BU role (`admin` vs. `user`)**: The role attached to each user-BU assignment, stored on the BU-user join row alongside `is_active` and `is_default`. The `BU_ROLES` constant (now in `businessUnitEdit/types.ts`) defines exactly two values. This is **orthogonal** to the platform RBAC permission assignments on the user account; the BU role governs the user's behaviour inside the inventory app for that BU, not access to admin routes.
- **Add-user-from-cluster pattern**: New BU members are picked from the parent cluster's user list (`clusterUsers`) — a user must be a member of the cluster before they can be added to one of its BUs. This dialog flow (and the Edit/Remove dialogs) is unchanged by the one-document rewrite — only the page-level read/edit split around it was removed.
- **Soft delete**: BUs are soft-deleted via `deleted_at` / `deleted_by_name`; the list view has a "Show soft-deleted business units" filter toggle that overlays a red `Deleted` badge and an extra "Deleted By" column for audit. Unlike [clusters](/en/platform/clusters), the BU list's Delete action has no client-side dependency guard.

## 4. Roles and Personas

Access is permission-based ([Platform RBAC](/en/platform/rbac)) — but with the single most important gotcha in this module:

> **Key-reuse gotcha: the Business Units module has no permission keys of its own.** The `/business-units`, `/business-units/new`, and `/business-units/:id/edit` routes reuse the **`cluster.read` / `cluster.create` / `cluster.update`** keys, the sidebar entry filters on `cluster.read`, and the in-page Delete gate consumes `cluster.delete` — there are **no `business_unit.*` keys** in the catalog. Any grant that opens the Clusters module also opens Business Units, and the two cannot be separated. A `cluster.update` grant scoped to cluster X covers editing the BUs of cluster X. The cluster-side view of the same gotcha is in [clusters permissions](/en/platform/clusters/permissions) §2.

| Surface | Gate type | Key | Scoped? |
|---|---|---|---|
| `/business-units` route | `requiredPermission` | `cluster.read` | No |
| `/business-units/new` route | `requiredPermission` | `cluster.create` | No |
| `/business-units/:id/edit` route | `requiredPermission` | `cluster.update` | No |
| Sidebar "Business Units" entry | `permission` filter | `cluster.read` | No |
| List: Add Business Unit button | `<Can>` | `cluster.create` | No |
| List: row Edit action | `<Can>` | `cluster.update` | Yes — `clusterId={row.original.cluster_id}` |
| List: row Delete action | `<Can>` | `cluster.delete` | Yes — `clusterId={row.original.cluster_id}` |
| Edit page: every field, Reveal password | `canEdit = isNew ? hasPermission('cluster.create') : hasPermission('cluster.update', {clusterId})` | `cluster.create` (new) / `cluster.update` (existing) | Yes for existing BUs — `clusterId={formData.cluster_id \|\| UNRESOLVED_CLUSTER_ID}` |
| Edit page: Tenant Migrations / Tenant Seed / Interface Entitlement cards (visibility) | none — renders whenever `!isNew`, independent of `canEdit` | — | No |
| Edit page: same 3 cards' mutating actions (Deploy/Run/Save, plus the status-check button on the first two) | `isSuperAdmin` (button-level check inside each card; independent of `canEdit`) | — | No |

The scoped (`clusterId`) gates resolve against the BU's **parent cluster** — a role assignment scoped to cluster A renders row Edit/Delete only on BUs whose `cluster_id` is A, while the unscoped route guards pass on any cluster-scoped grant. There is no separate Edit-toggle gate any more: the edit page computes one `canEdit` boolean and passes it to every section, including the Users card's Add/Edit/Remove affordances (previously ungated at the action level — now folded into the same page-wide check, an effectively identical outcome). Note the `UNRESOLVED_CLUSTER_ID` sentinel: when `formData.cluster_id` is empty (a cluster-less BU, or before the Cluster dropdown has a value in create mode), the check is deliberately kept on `checkPermission`'s scoped branch (fail closed) rather than falling through to the broad "any cluster" branch. The resolution algorithm, bootstrap exception, and super-admin bypass live in [rbac permissions](/en/platform/rbac/permissions).
