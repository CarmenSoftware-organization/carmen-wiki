# Business Units

> **At a Glance**
> **Module purpose:** Authoring surface where the operational entity that Carmen calls a **business unit** (BU) is created and configured — one row per hotel/property/legal-entity, with the fields that drive both the inventory app's tenant context and the platform's user-role and license assignments &nbsp;·&nbsp; **Audience:** Developers and QA working on the Platform admin SPA; operator access is gated by **reused `cluster.*` permission keys** ([rbac](/en/platform/rbac)) — there are no `business_unit.*` keys &nbsp;·&nbsp; **Nav entry:** `permission: 'cluster.read'` — **shared with two other menu entries** ([clusters](/en/platform/clusters) and [Tenant Migrations](/en/platform/business-units/tenant-migrations)) rather than a key of its own, so the permission name gives no hint that it also opens this screen &nbsp;·&nbsp; **Feature flag:** `business_units`, checked on all three routes after the permission gate &nbsp;·&nbsp; **`superAdminOnly`:** No &nbsp;·&nbsp; **Key entities/tables:** `business_unit` (identity fields `code` — now server-generated — `name`, `alias_name`, `is_hq`, `is_active`; contact blocks for hotel/company; tax fields; date/time/number format fields; `calculation_method`, `default_currency_id`; `database_pool_id`/`db_schema`; `config[]` key/value rows; branding `logo_file_token`/`avatar_file_token`) plus `tb_business_unit_license` (the per-BU seat ledger that replaced `max_license_users`) and the BU-to-user join carrying a per-BU `role` of `admin` or `user` &nbsp;·&nbsp; **Sub-pages:** 3

## 1. Overview

A business unit is the operational tenant of the Carmen platform: one BU is one hotel, one property, or one legal entity that buys, receives, counts, and consumes inventory. The list view at `/business-units` (`BusinessUnitManagement.tsx`) is a server-paginated, searchable catalogue with Active/Inactive and soft-deleted facets, CSV export, and an **Overview** summary strip (`BuSummary`, now backed by a dedicated `GET /api-system/business-units/summary` endpoint — total/active/inactive/archived counts and the number of distinct clusters spanned).

The edit page at `/business-units/:id/edit` and `/business-units/new` (`BusinessUnitEdit.tsx`) has been rewritten **twice** since the module was last synced. First from nine `CollapsibleSection` cards in a two-column grid into a single "one-document" edit-in-place scroll; then — the change this sync documents — from that scroll into a **six-tab document**: General, Location, Formats, Technical, Users, Licenses, behind a pinned identity strip and a sticky `TabStrip`. There is still no read/edit toggle anywhere — one `canEdit` boolean (`cluster.create` for a new BU, `cluster.update` scoped to `cluster_id` for an existing one) gates every field on every tab; each individual field still commits on blur/Enter and reverts on `Escape` via the shared `InlineField` click-to-edit control, unchanged across both rewrites. Users and Licenses are omitted from the tab strip entirely while creating a BU, since both need a row to already exist. A sticky bottom bar shows Save Changes/Cancel whenever the document is dirty (or unconditionally in create mode); `Ctrl/⌘+S` still saves and `Escape` still cancels page-wide (not just inside a field) via the shared keyboard-shortcut hook — confirmed unchanged in `BusinessUnitEdit.tsx`: the save shortcut re-checks `canEdit` itself before calling Save, since a disabled button alone is no defence against a shortcut bypassing it, and the cancel shortcut only fires on an existing BU with unsaved changes (it does nothing in create mode, where Escape has no assigned action). Saves are protected by a `doc_version` optimistic-lock token, the same mechanism as [clusters](/en/platform/clusters).

Each BU belongs to exactly one **cluster** (the `cluster_id` foreign key, selected from a dropdown in the General tab). The "create BU" flow can be entered either from the BU list page or from the cluster edit page, which navigates to `/business-units/new?cluster_id=<id>` to preselect the parent. Four things changed materially enough since the last sync to call out up front, each covered in depth on the sub-pages:

1. **`code` is no longer typed by the user.** The create form has no code field at all — the backend generates an 8-character code and retries on collision; the edit page shows it read-only. See [Data Model](/en/platform/business-units/data-model) §2.1 and [UI Screens](/en/platform/business-units/ui-screens) §3–4.1.
2. **The Technical tab has a schema-name randomizer.** A BU no longer holds its own database credentials (`db_connection` is gone) — it points at a shared `tb_database_pool` record and supplies its own `db_schema`, which a "Generate schema" button can fill with a random, collision-improbable name. See [UI Screens](/en/platform/business-units/ui-screens) §4.4.
3. **Licenses is now its own tab**, split out of Users — seats (a per-BU purchase ledger) and the user roster answer different questions and no longer share a tab. See [UI Screens](/en/platform/business-units/ui-screens) §4.7.
4. **The Licenses tab has a "New subscription" button**, gated on `subscription.manage` rather than this page's own `canEdit`, linking straight to the full-page subscription form pre-scoped to this BU and its cluster.

Beyond identity and contact fields, the BU stores the locale knobs that the inventory runtime reads — `date_format`, `time_format`, `timezone`, the JSON `amount_format`/`quantity_format`/`recipe_format` formatters defaulting to `th-TH`, the `calculation_method`, and `default_currency_id` (a dropdown of the BU's own tenant currencies, lazy-loaded once the BU's `code` is known) — plus a `config[]` array of free-form key/value rows. Detail on individual fields and screen behaviour lives on the sub-pages — this landing page only orients.

## 2. Business Context

In hospitality, the smallest unit that has its own books, its own currency, and its own local supply chain is the property — a single hotel inside a brand group. Carmen models that as a business unit: every inventory transaction (GRN, store requisition, physical count, spot check) is scoped to one BU; every report runs against one BU's schema; every user is granted access to one or more BUs with a role inside each. The `business_unit` row therefore carries far more than identity. It carries the locale settings the inventory UI displays in (date and number formats, timezone, default currency), the costing knob (`calculation_method`) the valuation engine consults, and a pointer (`database_pool_id`/`db_schema`) at the shared database server hosting its tenant schema — the platform no longer stores per-BU connection credentials directly.

Seats are no longer a single ceiling either. Where the schema used to carry one `max_license_users` integer, user capacity for a BU is now a dated purchase ledger (`tb_business_unit_license`) — one row per seat contract, summed across whatever is currently active. The edit page's General tab shows the resulting number read-only; the Licenses tab is where those purchase rows are actually reviewed (creating and editing one still happens on the full-page License Center form, not inline on this page).

Because a BU is also where users become operationally meaningful, the edit page's Users tab doubles as a user-assignment workbench. It lists everyone with access to this BU, each with a **BU role** (`admin` or `user`) that is orthogonal to the platform RBAC assignments on the user account itself ([rbac](/en/platform/rbac)). New BU members are picked from the BU's parent cluster — a user must already exist on the cluster before they can be added to one of its BUs. A "Shared" badge on a user row flags membership shared with another BU in the same cluster (so removing them here alone would not free a cluster-level seat) — this is new since the last sync and depends on a backend-optional field, `frees_seat`, that may not be populated in every environment.

The Technical tab's advanced cards extend the BU beyond plain configuration into tenant-database operations, unchanged in gating from the last sync: **Tenant Migrations** checks and applies pending database schema migrations against the BU's own tenant database; **Tenant Seed** runs seed scripts against it; and **Interface Entitlement** controls which named interface/brand the BU is licensed to show (an empty selection means unrestricted). None of the three is render-gated — any session with BU edit access sees all three whenever the BU already exists; only their *mutating* actions (and, for the first two, the status-check button itself) require `isSuperAdmin`.

## 3. Key Concepts

- **Business unit (BU)**: A single row in `business_unit` representing one hotel/property/legal entity. Every inventory transaction belongs to exactly one BU; every report runs against one BU.
- **Cluster membership**: Every BU has a non-nullable `cluster_id` selected from the cluster dropdown on the General tab. The cluster edit page can launch a create-BU flow with `cluster_id` preselected via the `/business-units/new?cluster_id=<id>` query parameter.
- **Code (`code`)**: A short identifier, unique **across the entire platform**, not just within a cluster (a partial-unique index added since the last sync — see [Data Model](/en/platform/business-units/data-model) §2.1). **No longer entered by the user**: the backend generates an 8-character Crockford-base32 code on create and retries on collision; the field is read-only on the edit page and ignored by the backend if sent on update.
- **HQ flag (`is_hq`)**: Marks the BU as the headquarters within its cluster — a clickable "HQ" badge in the identity strip (toggles directly, no separate checkbox/section); semantics depend on consuming modules.
- **Active flag (`is_active`)**: Toggles whether the BU is operationally live — a clickable identity-strip badge, not a form checkbox. Inactive BUs remain editable in the admin surface but are filtered out of normal runtime selection. The list view exposes Active/Inactive as filter chips.
- **Structured hotel/company address**: Ten structured columns each — `*_address_line1`, `*_address_line2`, `*_sub_district`, `*_district`, `*_city`, `*_province`, `*_postal_code`, `*_country`, `*_latitude`, `*_longitude` — for both the Hotel and Company groups on the Location tab. A **Copy from hotel address** button one-way-copies all ten hotel fields into their company counterparts.
- **Tax information**: `tax_no` and `branch_no` capture the Thai tax registration plus branch designator used on printed documents.
- **Date/Time and Number formats**: `date_format`, `date_time_format`, `time_format`, `long_time_format`, `short_time_format`, `timezone`, plus JSON formatters `amount_format`/`quantity_format`/`recipe_format`/`perpage_format` — all on the Formats tab, each formatter defaulting to `{"locales":"th-TH","minimumIntegerDigits":2}`.
- **Calculation settings**: `calculation_method` (`average`/`fifo`, consumed by the inventory valuation engine) and `default_currency_id` — a `<select>` populated from the BU's own tenant currency master, lazy-loaded once the BU's code is known, falling back to a free-text UUID input if the fetch fails.
- **Configuration array (`config[]`)**: An ordered list of free-form `{ key, value, datatype }` rows on the Technical tab, persisted as a JSON array. Used by the inventory app for per-BU feature toggles and integration settings; the admin surface does not impose a schema.
- **Database pool + schema (`database_pool_id`/`db_schema`)**: Replaces the retired `db_connection` JSON blob entirely. A BU points at a shared, platform-managed `tb_database_pool` record and supplies its own schema name inside it; host/port/username/password live only on the pool record, never on this page. A "Generate schema" button can fill the schema field with a random `bu_`-prefixed name.
- **Branding (logo + avatar)**: Each BU carries a rectangular **logo** and a square **avatar**, stored as file tokens and returned by the API as embedded presigned objects. Uploads happen on the General tab's Branding section; the list page shows a small `BrandMark` avatar next to the BU name (reintroduced since the last sync, matching the identical change on [clusters](/en/platform/clusters)).
- **Optimistic concurrency (`doc_version`)**: `tb_business_unit` carries a `doc_version` counter; the edit page resends it on every `PUT` and shows a conflict toast + reload on a stale `409`.
- **Audit columns**: The list shows Created and Updated columns (timestamp plus actor name). Both the list and the edit page now read every audit value through the shared `normalizeAudit()` helper (`src/utils/audit.ts`), which tries the nested `audit.{created,updated,deleted}.{at,id,name,avatar}` shape first and only falls back to the older flat shape (`created_at`/`created_by_name` or `created_by`, etc.) when the nested value is absent or empty — not the other way around. An Updated entry is shown only when the record was actually edited: that is decided by whether an editor name is present, or — absent a name — whether the updated timestamp differs from the created timestamp, not by a plain `updated_at === created_at` comparison.
- **Seats (`tb_business_unit_license`)**: A dated purchase ledger, one row per seat contract, replacing the removed `max_license_users` integer. Summed across active rows into the read-only "Max users" figure on the General tab; reviewed (not edited) on the Licenses tab, which links out to the full-page License Center form for actually creating or editing a row.
- **BU role (`admin` vs. `user`)**: The role attached to each user-BU assignment, stored on the BU-user join row alongside `is_active` and `is_default`. This is **orthogonal** to the platform RBAC permission assignments on the user account; the BU role governs the user's behaviour inside the inventory app for that BU, not access to admin routes.
- **Add-user-from-cluster pattern**: New BU members are picked from the parent cluster's user list — a user must be a member of the cluster before they can be added to one of its BUs.
- **Soft delete**: BUs are soft-deleted via `deleted_at` / `deleted_by_name`; the list view has a "Show soft-deleted business units" filter toggle. Unlike [clusters](/en/platform/clusters), the BU list's Delete action has no client-side dependency guard.

## 4. Roles and Personas

Access is permission-based ([Platform RBAC](/en/platform/rbac)) — but with the single most important gotcha in this module:

> **Key-reuse gotcha: the Business Units module has no permission keys of its own.** The `/business-units`, `/business-units/new`, and `/business-units/:id/edit` routes reuse the **`cluster.read` / `cluster.create` / `cluster.update`** keys, the sidebar entry filters on `cluster.read`, and the in-page Delete gate consumes `cluster.delete` — there are **no `business_unit.*` keys** in the catalog. `cluster.read` alone drives three sidebar entries — Clusters, Business Units, and Tenant Migrations — so a grant that opens the Clusters module also opens Business Units and Tenant Migrations, and none of the three can be separated from the others by permission alone (the `business_units`/`tenant_migrations` **feature flags**, §4 below, are the only per-module on/off switch left). A `cluster.update` grant scoped to cluster X covers editing the BUs of cluster X. The cluster-side view of the same gotcha is in [clusters permissions](/en/platform/clusters/permissions) §2.

| Surface | Gate type | Key | Scoped? |
|---|---|---|---|
| `/business-units` route | `requiredPermission` + `feature` | `cluster.read` + `business_units` | No |
| `/business-units/new` route | `requiredPermission` + `feature` | `cluster.create` + `business_units` | No |
| `/business-units/:id/edit` route | `requiredPermission` + `feature` | `cluster.update` + `business_units` | No |
| Sidebar "Business Units" entry | `permission` + `feature` filter | `cluster.read` / `business_units` | No |
| List: Add Business Unit button (header **and** empty state) | `<Can>` | `cluster.create` | No |
| List: row Edit action | `<Can>` | `cluster.update` | Yes — `clusterId={row.original.cluster_id}` |
| List: row View History action | `<Can>` | `activity_log.read` | Yes — `clusterId={row.original.cluster_id \|\| UNRESOLVED_CLUSTER_ID}` |
| List: row Delete action | `<Can>` | `cluster.delete` | Yes — `clusterId={row.original.cluster_id}` |
| Edit page: every field on every tab, except the two below | `canEdit = isNew ? hasPermission('cluster.create') : hasPermission('cluster.update', {clusterId})` | `cluster.create` (new) / `cluster.update` (existing) | Yes for existing BUs — `clusterId={formData.cluster_id \|\| UNRESOLVED_CLUSTER_ID}` |
| Technical tab: Database Pool picker | `<Can>`, nested inside `canEdit` | `database_pool.read` | No |
| Licenses tab: New subscription button | supplied by parent, gated separately from `canEdit` | `subscription.manage` | No |
| Edit page: Tenant Migrations / Tenant Seed / Interface Entitlement cards (visibility) | none — renders whenever `!isNew`, independent of `canEdit` | — | No |
| Edit page: same 3 cards' mutating actions (Deploy/Run/Save, plus the status-check button on the first two) | `isSuperAdmin` (button-level check inside each card; independent of `canEdit`) | — | No |

The scoped (`clusterId`) gates resolve against the BU's **parent cluster** — a role assignment scoped to cluster A renders row Edit/Delete/View History only on BUs whose `cluster_id` is A, while the unscoped route guards pass on any cluster-scoped grant. Note the `UNRESOLVED_CLUSTER_ID` sentinel: when `formData.cluster_id` is empty (a cluster-less BU, or before the Cluster dropdown has a value in create mode), the check is deliberately kept on `checkPermission`'s scoped branch (fail closed) rather than falling through to the broad "any cluster" branch.

A second, narrower permission gates one control **inside** the page-wide `canEdit` boundary: the Database Pool picker on the Technical tab additionally requires `database_pool.read` — a session with `cluster.update` on this BU but not `database_pool.read` still edits everything else, but sees the pool name and schema read-only with a note explaining why. The resolution algorithm, bootstrap exception, and super-admin bypass live in [rbac permissions](/en/platform/rbac/permissions).

## 5. Related Modules

- [clusters](/en/platform/clusters) — every BU is owned by exactly one cluster via `cluster_id`; the cluster edit page launches the create-BU flow with the parent preselected through the `/business-units/new?cluster_id=<id>` query parameter, and the `cluster.*` keys that gate this module are documented from the cluster side in [clusters permissions](/en/platform/clusters/permissions)
- [users](/en/platform/users) — supplies the user accounts that get assigned to BUs through the Users tab; new BU members are drawn from the parent cluster's user list, and clicking a name jumps to the user edit page
- [rbac](/en/platform/rbac) — the permission model behind every gate in §4: catalog, roles, scoped assignments, super-admin bypass, and (§5 there) the legacy role-enum model this module was gated by until 2026-06
- [report-templates](/en/platform/report-templates) — `allow_business_unit` / `deny_business_unit` chip inputs there scope a report template by the BU `code` values defined here
- **licenses** (not yet a documented wiki module) — the full-page License Center (`/licenses/:clusterId`) that the Licenses tab's Manage/New subscription buttons link out to; seat and BU-quota purchase rows are actually created and edited there, not on this page
