# Platform Migrations

**Platform Migrations** is one screen, `PlatformMigrationManagement` at `/platform/migrations`, that runs two different kinds of operation against the **one platform database every cluster and business unit shares** — not a single tenant's database. The first kind is a Prisma schema migration (Deploy, Resolve); the second is a catalog of 8 seed scripts plus 6 drift checks — 5 of the checks read-only, the sixth a check that writes and is hidden from this console (§3.3) — that populate or verify platform-wide reference data: currencies, permissions, platform roles, license features, and one per-business-unit operation covered in §3.4. Because every write here lands in a table every tenant reads from, this page states — operation by operation — what is safe to click again and what is not, rather than a single blanket "idempotent" claim.

> **At a Glance**
> **Component:** `PlatformMigrationManagement` &nbsp;·&nbsp; **Route:** `/platform/migrations`, guarded by `<PrivateRoute requireSuperAdmin feature="platform_migrations">` (`../carmen-platform/src/App.tsx:434-441`) &nbsp;·&nbsp; **Nav:** `superAdminOnly: true` — **that flag, not the absence of a permission key, is what gates this menu row** — `feature: 'platform_migrations'`, `groupKey: 'navGroup.database'`, no `permission` field at all (`platformNav.ts:53`) &nbsp;·&nbsp; **Backend authorities:** a matching `x-deploy-token` header (checked **first**) or a super-admin session (the fallback) — both sit behind one enable switch, `platform_migration.api_enabled` (§3.1, §4) &nbsp;·&nbsp; **Catalog:** 2 migration actions (Deploy, Resolve) + 14 seed/check operations, 13 of them visible in this console &nbsp;·&nbsp; **e2e suite:** **None** — `../carmen-platform-e2e/tests/` has no `platform-migrations` directory &nbsp;·&nbsp; **Sub-pages:** 0

## 1. Overview

`PlatformMigrationManagement.tsx` (696 lines) renders four stacked cards plus a shared run console. The **Status** card (`PlatformMigrationManagement.tsx:361-442`) shows whether the platform database has pending migrations, with a single **Apply migrations** button that runs Deploy; a collapsible **Raw Prisma output** toggle shows the sanitized CLI text behind that verdict. Below it, a collapsed-by-default **Resolve a stuck migration (advanced)** card (`:444-518`) lets an operator mark one migration folder `applied` or `rolled-back` in `_prisma_migrations` by name, without running its SQL. Below that, two catalog cards — **Seed data** (amber left border, a "Writes data" badge) and **Drift checks** — each render one row per operation via `OpRow` (`pages/platformMigration/OpRow.tsx`), fetched from a single registry, `platformSeedService.getCatalog()` (`:167-169`). A `RunConsole` at the bottom (`pages/platformMigration/RunConsole.tsx`) shows every action's output — deploy, resolve, and every seed/check run — in one shared, capped-at-20-entries ledger (`useRunLog`, `runLog.ts:32`), because the real workflow on this page is a sequence (deploy, then seed, then check what changed), not isolated one-shot actions (`runLog.ts:6-9`).

Every request from this page travels frontend → `backend-gateway` (where the authorization guard runs, §3.1) → an internal RPC call → `micro-business`, which is the process that actually shells out to `prisma` or spawns a `bun <script>` child process against the platform database. The gateway's own `PlatformMigrationsService`/`PlatformSeedsService` are thin RPC proxies with no logic of their own (`../carmen-turborepo-backend-v2/apps/backend-gateway/src/platform/platform-migrations/platform-migrations.service.ts:1-47`, `platform-seeds/platform-seeds.service.ts:1-65`); `micro-business`'s own controllers (`apps/micro-business/src/authen/platform_migration/platform_migration.controller.ts`, `platform_seed/platform_seed.controller.ts`) apply **no second authorization check** — they trust the gateway's guard entirely.

An operator who needs a specific business unit for one operation (§3.4) is prompted by `BuSwitcher` (`PlatformMigrationManagement.tsx:662-685`); a dev-only debug panel (`DevDebugSheet`) shows the raw `/api-system/platform/migrations/status` payload, but only in a local dev build — the component itself returns `null` unless `import.meta.env.DEV` (`../carmen-platform/src/components/ui/dev-debug-sheet.tsx:18`), so this is not an RBAC control.

## 2. Business Context

Every platform-wide reference table — permissions, roles, currencies, license features — is defined in source (`prisma-shared-schema-platform/prisma/seed.*.data.ts`) but only becomes real data through one of the scripts this console runs. Before this console existed those scripts were `bun run db:seed.*`/`db:check.*` commands, runnable only by someone with a shell on a host that can reach the platform database directly. This page is the operator-facing wrapper around exactly the same scripts (§3.3 cites each one), with one addition the CLI never had: a live, streamed run console, so an operator watching a seed that touches hundreds of permission rows (`seed.permission.data.ts` has roughly 278 entries) can see it progress instead of waiting on a blank terminal.

The stakes are the reason this page exists in the shape it does: every script here writes to the **one** platform database, not a tenant's. A `seed-platform-role-permission` run that goes wrong does not affect one customer — it affects the permission catalog every cluster's role screen reads. That is also why the console deliberately does **not** expose one CLI script that still exists in source: `db:seed.platform-super-admin` reads a `SUPER_ADMIN_USER_ID` environment variable and grants that user id unconditional super-admin — with no operator choice of *whom* and, confirmed by reading the script, no `created_by_id` written anywhere (`seed.platform-super-admin.ts:8-39`) — so there would be no audit trail of who was granted or by whom. The catalog's own comment states the reason for the exclusion is that [Super Admins](/en/platform/super-admins) already does this properly, through a screen that does record who acted (`PLATFORM_SEED_CATALOG`, `platform_seed.catalog.ts:25-29`); reading the excluded script confirms the comment is accurate, not merely present.

## 3. Key Concepts

### 3.1 Two authorities behind one switch — and which actor each one records

`PlatformMigrationGuard.canActivate()` (`../carmen-turborepo-backend-v2/apps/backend-gateway/src/auth/guards/platform-migration.guard.ts:118-140`) is the single authorization checkpoint for **every** route in this module — both the migrations controller and the seeds controller declare `@UseGuards(PlatformMigrationGuard)` (`platform-migrations.controller.ts:59`, `platform-seeds.controller.ts:36`). It runs in this exact order:

1. **The switch, checked first.** `isApiEnabled()` reads the `platform_migration` row's `api_enabled` field from `tb_platform_config`, cached for 60 seconds; a missing row, an unreadable one, or the field being anything other than exactly `true` all read as **off** (`platform-migration.guard.ts:69-94`). If the switch is off, every route in this module answers `403 Platform migration API is disabled` regardless of who is calling — a deploy token and a super-admin session are equally refused (`:119-121`).
2. **The deploy token, checked first among the two authorities.** If the switch is on, the guard compares the request's `x-deploy-token` header against `envConfig.PLATFORM_DEPLOY_TOKEN` using a constant-time comparison (`isTokenEqual`, `:103-110`, `timingSafeEqual`). A match sets `request.deployActor = 'ci:deploy-token'` and returns `true` immediately — **no Keycloak call, no super-admin lookup at all** for this path (`:122-128`). `PLATFORM_DEPLOY_TOKEN` defaults to an empty string (`apps/backend-gateway/src/libs/config.env.ts:219`), and an empty configured token can never equal a presented one in the guard's own comparison (`presentedToken && configuredToken && ...`, `:125`), so this path is inert in any environment where the token has not been explicitly set.
3. **Super-admin, the fallback.** Only when no token matches does the guard run `KeycloakGuard` then `PlatformSuperAdminGuard` (`:129-134`); the latter makes an RPC call (`platform-permissions.effective`) and allows the request only when the response's `is_super_admin` is exactly `true`, failing closed (denying) on any RPC error (`platform-super-admin.guard.ts:40-70`). On success the guard sets `request.deployActor = 'super-admin:<user_id>'` (`platform-migration.guard.ts:135-139`).

Both the migrations controller and the seeds controller log a structured audit entry naming this same `deployActor` on every call (`executeAuditLog`, `platform-migrations.controller.ts:81-88`; the seeds controller streams instead of buffering a single result, so it has no equivalent audit line — see §6); `micro-business`'s own controller wraps every mutating call in `runWithAuditContext` using the caller's `user_id`/`tenant_id` from the RPC payload (`platform_migration.controller.ts:59-64,76-78`). **This is the fuller account the [Platform Config](/en/platform/platform-config) page's own §3.2 alludes to**: moving `PLATFORM_MIGRATION_API_ENABLED` into this config key made the *config key itself* super-admin-only to edit, but it did not remove the CI deploy-token path into the migration endpoints this key gates — that path is checked first, not last, and is only as inert as `PLATFORM_DEPLOY_TOKEN` being left unset.

### 3.2 Two consoles sharing one lock, with different transports and timeouts

**Deploy/Resolve** (`micro-business`'s `PlatformMigrationService`) shells out to the local Prisma CLI with `execFile`, no shell, and a fixed timeout (`PLATFORM_MIGRATION_TIMEOUT_MS`, default `120000` ms / 2 minutes — `apps/micro-business/src/libs/config.env.ts:146`), buffering the whole result before responding (`platform_migration.service.ts:154-171`). **Seed/Check** (`PlatformSeedService`) instead `spawn`s `bun <script>` and streams stdout/stderr line-by-line as NDJSON over the gateway's HTTP response, with its own longer timeout (`PLATFORM_SEED_TIMEOUT_MS`, default `300000` ms / 5 minutes — `config.env.ts:149`), because seed scripts can run far longer than a schema migration (`platform_seed.service.ts:224-241`). Both redact connection strings and `SYSTEM_(DATABASE|DIRECT)_URL` from every line they emit (`sanitize()`, present in both services) and both build an allowlisted child environment so the spawned process cannot read unrelated service secrets (`buildChildEnv()`, both services).

Both services serialize through the **same** lock, `PlatformDbLock` (`apps/micro-business/src/authen/platform_db/platform_db.lock.ts`) — a plain in-memory `running` boolean, moved out of `PlatformMigrationService` specifically so a `migrate deploy` and a `seed.permission` run could not proceed at the same time against the same database (`:16-21`). A second call while one is in flight gets `409 A platform database operation is already running` (`PlatformDbBusyError`, surfaced as `ErrorCode.ALREADY_EXISTS`), which the frontend shows as a `toast.warning`, not an error (`errorText()`/`notifyError()`, `PlatformMigrationManagement.tsx:46-57`). **The lock's own doc-comment is explicit about its scope: one process, not one cluster of replicas** (`platform_db.lock.ts:25-27`) — if `micro-business` runs more than one instance, this 409 cannot prevent two instances from running conflicting operations at the same moment; see §6.

Closing the browser tab or losing the connection mid-run does **not** stop the underlying process on either path: the seed stream's teardown only sets a `cancelled` flag so no more events are emitted to a dead connection, and explicitly does not call `child.kill()` — the code comment states this is intentional, matching tenant-migration behavior, because a half-killed seed can leave half-written data (`platform_seed.service.ts:289-296`). The lock is released only when the child process actually exits.

### 3.3 The catalog: what each operation does, and what is safe to re-run

**Migration actions** (not part of the seed/check catalog — these are the Status card's own buttons):

| Action | What it does | Safe to re-run? |
| --- | --- | --- |
| **Deploy** (`POST .../migrations/deploy`) | Runs `prisma migrate deploy --schema <platform schema>`, applying every migration not yet recorded in `_prisma_migrations` (`platform_migration.service.ts:231-256`). | **Yes, as a console action.** Prisma tracks applied migrations by name; deploying again with nothing pending returns `already_up_to_date: true` and `applied_migrations: []` (matched from `/No pending migrations to apply/i` in the CLI output, `:251`) — clicking it twice in a row does nothing the second time. This vouches only for the button, not for any individual migration's own SQL being safe to apply twice outside Prisma's once-per-name tracking; that would require reading each migration file, which is outside this page's scope. |
| **Resolve** (`POST .../migrations/resolve`) | Marks one migration folder `applied` or `rolled-back` in `_prisma_migrations` **without running its SQL** — a status-only correction for a migration that failed partway, used to unblock every later Deploy (`platform_migration.service.ts:258-301`). | **Repeating the same call is a no-op**, but choosing the **wrong action once** is the real hazard: marking a migration `applied` when its SQL never actually ran leaves the schema silently behind forever, because Deploy will never touch that migration name again. The console's own copy states this outright: "Choosing wrong records a migration that never ran as if it had." (`en.ts:3356`). |

**Seed and check operations** — 8 seed (`writes: true`) + 6 check (5 read-only, 1 that writes and is hidden from this console), from `PLATFORM_SEED_CATALOG` (`platform_seed.catalog.ts:35-68`), each confirmed by reading its script directly:

| Op id | Group | What it does | Safe to re-run? |
| --- | --- | --- | --- |
| `seed-currency-iso` | seed | Upserts the ISO 4217 currency list (code/symbol/name) into `tb_currency_iso`. | **Yes.** `upsert` keyed on the unique `iso_code` (`seed.currency-iso.ts:174-187`) — re-running reapplies the same values. |
| `seed-permission` | seed | Upserts every app-level permission (`PERMISSION_SEED`) into `tb_permission` by `resource`+`action`; soft-deletes any entry flagged `delete: true`. | **Yes.** Find-then-update-or-create by `resource`+`action` (`seed.permission.ts:12-57`); a `delete: true` entry that is already soft-deleted is simply skipped again. |
| `seed-platform-permission` | seed | Same pattern for `tb_platform_permission`, and additionally soft-deletes the `tb_platform_role_tb_permission` links of any permission it retires. | **Yes — and specifically built to recover a partial run.** It looks up every row matching a retiring resource+action, active or already soft-deleted, so a crash between soft-deleting the permission and cascading its links is fixed by simply running it again (`seed.platform-permission.ts:16-45`; the reasoning in the comment is confirmed by the code beneath it). |
| `seed-platform-role` | seed | Upserts the fixed platform-level roles (`tb_platform_role`) by `name`. | **Yes.** Find-by-name, update-or-create (`seed.platform-role.ts:12-27`). |
| `seed-platform-role-permission` | seed | Upserts each platform role by name, then links it to every permission its pattern expands to, skipping a link that already exists. | **Yes for adding coverage — it never revokes.** A link removed from `ROLE_PERMISSIONS` in source is never deleted from the database by running this again (`seed.platform-role-permission.ts:20-46`); `check-platform-role-permission` (below) is how that kind of drift is actually found. |
| `seed-role-permission` | seed, requires `bu_id` | Upserts **one business unit's** tenant application roles (`tb_application_role`) and their permission links (`tb_application_role_tb_permission`), scoped to that BU. **Not the platform RBAC tables — see §3.4.** | **Yes per BU, additive-only** — the identical upsert-role/skip-existing-link pattern as `seed-platform-role-permission` (`seed.role-permission.ts:474-543`). Re-running against the same BU past the first run changes nothing; running it against a BU whose application roles were hand-edited will not correct or remove those edits, only add whatever is still missing. |
| `seed-report-template-upload` | seed | For each of ~60 hardcoded report ids, downloads a `.fpx` file from a **live external legacy report designer** and uploads it to MinIO, then sets `tb_report_template.template_file_token` on the DB row matched by name. The script carries more than one hardcoded credential, of two different shapes: the external system's login is an **unconditional literal username and password** baked directly into the script, never read from an environment variable at all (`seed.report-template-upload.ts:14-15`); separately, its MinIO access key and secret key are each read from an environment variable **with a hardcoded literal fallback** (`:18-19`) — that fallback value only ever takes effect if the operator has not set the corresponding variable, a materially different risk than the unconditional pair. | **Yes.** It explicitly skips any template that already has a `template_file_token` (`:265-269`), so re-running only processes templates a previous run left un-uploaded. Unlike every other op here, its safety also depends on an external system staying reachable and those hardcoded/fallback credentials continuing to be valid — a failure here can mean the external site or MinIO credentials changed, not a bug in this console. |
| `seed-license-feature` | seed | Upserts `tb_license_feature` by `key`, reviving a soft-deleted row rather than creating a duplicate, and soft-deletes ("retires") any key no longer present in the seed data. | **Yes.** Deliberately does not overwrite `state`/`is_active` on a row that already exists — those columns are operator-set through the Licenses screen, and are written by this script only when the row is newly created (`seed.license-feature.ts:33-67`) — so re-running cannot silently flip a feature an admin has already turned on or off. |
| `check-permission` | check | Read-only: diffs `PERMISSION_SEED` against `tb_permission`, listing what a `seed-permission` run would create, update, or soft-delete. | **Always safe** — confirmed by reading the whole file: no `create`/`update`/`delete`/`upsert` call anywhere in `check.permission-drift.ts`. |
| `check-platform-permission` | check | The same diff for `tb_platform_permission` against `PLATFORM_PERMISSION_SEED`. | **Always safe** — confirmed the same way (`check.platform-permission-drift.ts`). |
| `check-platform-role-permission` | check | Read-only: recomputes each platform role's expected permission set from `ROLE_PERMISSIONS` and diffs it against the live `tb_platform_role_tb_permission` links. | **Always safe** — confirmed the same way (`check.platform-role-permission-drift.ts`). |
| `check-endpoint-permission` | check | Read-only: parses `backend-gateway` controller source to find every tenant-scoped route (`api/:bu_code/*`, `api/config/:bu_code/*`) and checks each has a matching `PERMISSION_SEED` entry. Its own header states it "never touches the database and never writes a file" (`check.endpoint-permission-coverage.ts:19-25`). | **Always safe** — confirmed by reading the whole file; the header's claim holds. |
| `check-api-system-permission` | check | Read-only: uses `ts-morph` to parse `backend-gateway` controllers for `@RequirePlatformPermission`-guarded handlers and checks each key exists in `PLATFORM_PERMISSION_SEED`. Its own header documents real blind spots: an object-literal `@Controller` path, an aliased decorator import, or a controller file not named `*.controller.ts` can all be missed silently (`check.api-system-permission-coverage.ts:7-38`). | **Always safe to run** — confirmed by reading the whole file, no write call — but a clean result is proof of no *detected* gap, not proof of full coverage, per the script's own documented limitations. |
| `check-seat-pool-view` | check, marked `writes: true`, **hidden from this console** | Verifies the `v_business_unit_seat` Postgres view's seat-counting semantics against 8 hand-built cases (`check.seat-pool-view.ts:26-50`), using **one arbitrary active business unit** — picked by `findFirst`, not operator-chosen — inside a database transaction that always rolls back via a deliberate `throw('ROLLBACK_ON_PURPOSE')` (`:56-104`). | **Net effect is zero — the transaction never commits.** For the transaction's short duration, though, it deletes that BU's existing `tb_business_unit_license` rows and recreates test ones inside the same transaction (`:76-90`), holding a row lock on real customer licensing data while it runs. This is exactly why the catalog marks it `writes: true` unlike every other check, and why the frontend filters it out of the visible list with `HIDDEN_OPS` (`PlatformMigrationManagement.tsx:68-76,168`) instead of showing it as an ordinary read-only check — it remains callable by hitting the API directly, only not from this screen. If no active business unit exists in the target database at all, the script exits with an error instead of running (`check.seat-pool-view.ts:62-65`). |

### 3.4 `seed-role-permission`'s multi-BU picker writes tenant app-roles — not platform RBAC

`seed-role-permission` is the only catalog operation with a declared parameter (`bu_id`, required, type `uuid` — `platform_seed.catalog.ts:42-44`), and as of commit `157a65e` (`../carmen-platform` HEAD — "feat(platform-migrations): เลือกได้หลาย BU ตอน seed role permissions (#281)") this console lets an operator pick **several** business units at once for it, one `BuSwitcher` dialog set to `multiple` (`PlatformMigrationManagement.tsx:662-685`). The detection that decides whether an op needs this prompt at all is generic, not hardcoded to this op's id — `buParamOf()` looks for a declared `uuid` parameter whose name matches `bu`, so a future per-BU op would get the same prompt automatically (`:78-83`). Selected BUs are then run **sequentially, one request per BU, never in parallel** — `runOpBatch` awaits each `runOnce` in a `for` loop (`:296-326`) specifically because every target hits the same database script, and the code's own comment is explicit that running them concurrently would invite deadlocks and interleave the streamed logs into something unreadable (`:287-295`); a failure on one BU does not stop the rest from running, so the operator who selected five BUs still gets all five attempted (`:293-295`).

What the picker actually runs, per BU, is the same single-BU script described in §3.3: it writes rows to **`tb_application_role`** and **`tb_application_role_tb_permission`**, each scoped by `business_unit_id` (`seed.role-permission.ts:452-543`). **This is a per-tenant application-role system, a completely different pair of tables from the platform RBAC tables — `tb_platform_role`, `tb_platform_permission`, `tb_platform_role_tb_permission` — that [Platform RBAC](/en/platform/rbac) documents.** The multi-BU picker on this page never touches anything RBAC governs; reading "seed role permissions, several BUs at once" as an RBAC operation would be the wrong mental model entirely. (`seed-platform-role-permission`, by contrast, does write to the actual platform RBAC link table — see §3.3 — but takes no `bu_id` and cannot be run per-BU.)

## 4. Roles and Permissions

There is no `permission` string anywhere in this module — access is entirely identity-based, at three independent layers that all have to agree:

1. **Nav row:** `superAdminOnly: true` in `platformNav.ts:53`; `buildPlatformNav()`'s filter keeps the row only `!item.superAdminOnly || opts.isSuperAdmin` (`:91-98`) — a non-super-admin never sees the menu entry at all, not even as a disabled row.
2. **Route:** `<PrivateRoute requireSuperAdmin feature="platform_migrations">` (`App.tsx:434-441`) renders `<Forbidden />` for a signed-in non-super-admin who navigates to `/platform/migrations` directly by URL — checked *before* the feature-flag gate, so a denied user sees 403, never a flag-driven 404 (`PrivateRoute.tsx:87-103`).
3. **Every backend endpoint:** `PlatformMigrationGuard` (§3.1) — the switch, then deploy-token-or-super-admin, re-checked on every single call regardless of what the frontend already showed.

Layer 3 is the only one of the three a direct API call cannot bypass; layers 1 and 2 are frontend convenience, not security boundaries. `PlatformSuperAdminGuard` itself resolves super-admin status by an RPC call to `platform-permissions.effective` and checks `is_super_admin === true`, failing closed (denying access) on any RPC error rather than defaulting to allow (`platform-super-admin.guard.ts:40-70`) — the same fail-closed direction the switch itself takes (§3.1), in contrast to the *fail-open* default used by [Platform Config](/en/platform/platform-config)'s own license-enforcement switch.

## 5. e2e Coverage

**None.** `../carmen-platform-e2e/tests/` contains `applications`, `auth`, `broadcast`, `business-units`, `changelog`, `clusters`, `dashboard`, `journeys`, `landing`, `news`, `permission-catalog`, `print-template-mapping`, `profile`, `report-templates`, `roles`, `super-admins`, `user-platform`, and `users` — no `platform-migrations` or equivalent directory exists. Every claim on this page traces to `../carmen-platform` or `../carmen-turborepo-backend-v2` source read directly, never to test coverage.

| --- | --- | --- |

| `x-deploy-token` header sent, but `PLATFORM_DEPLOY_TOKEN` was never configured | Falls through silently to the super-admin path — an empty configured token can never match a presented one | `platform-migration.guard.ts:124-125`; `apps/backend-gateway/src/libs/config.env.ts:219` |
| Two `micro-business` instances run behind the same gateway (multi-replica) | The 409 "already running" guard is a per-process in-memory flag, not shared across replicas — two instances can both proceed with conflicting operations at the same time | `platform_db.lock.ts:25-27` |
| `Resolve` marks a migration `applied` when its SQL was never actually run | Not detected by this console — Deploy will skip that migration name forever afterward, silently leaving the schema behind | `platform_migration.service.ts:277-301`; console copy at `en.ts:3356` |
| Calling `check-seat-pool-view` directly via the API (bypassing the hidden-from-UI filter) | Runs normally — it is excluded only from this screen's visible list, not disabled server-side; requires at least one active, non-deleted business unit to exist, or exits with an error | `PlatformMigrationManagement.tsx:76`; `check.seat-pool-view.ts:57-65` |
| Calling `seed-role-permission` directly via the API with no `bu_id`, or a malformed one | `422`, with a message naming exactly what was missing or malformed — the frontend's own picker cannot submit without a valid selection, but a direct API caller is not stopped by it | `platform_seed.service.ts:85-102`; `platform-seeds.controller.ts:71-73` |
| A catalog script's file is absent from the running image | `missing: true` on that op, computed by checking the file exists in this image at catalog-fetch time; its Run button is disabled in the UI, and a direct API call gets `422 Script not found in this image` | `platform_seed.service.ts:179-184`; `platform-seeds.controller.ts:66` |
| Closing the browser tab or losing the connection mid-run | The running process is **not** killed — it keeps running to completion server-side; only the browser stops receiving further log lines | `platform_seed.service.ts:289-296` |
| `db:seed.platform-super-admin` (a CLI script that still exists) | Deliberately absent from this console's catalog — no operator choice of whom to grant, and confirmed by reading the script that it writes no `created_by_id`, so it would leave no audit trail of who acted | `platform_seed.catalog.ts:25-29`; `seed.platform-super-admin.ts:8-39` |

## 7. Recommendations

Treat every row on the **Seed data** card as a deliberate write to data every cluster shares, not a routine click — the console's own confirmation copy for a single-BU write says outright that it "cannot be interrupted once started" (`en.ts:3319`), and §3.3 shows that most seed operations are additive-only: they create and update, but do not remove a row that source no longer defines. Running the matching `check-*` operation before and after a related `seed-*` run is the only way this console gives an operator to see that kind of one-directional drift, since `seed-platform-role-permission` and `seed-role-permission` in particular never revoke a stale link on their own (§3.3). Before ever using **Resolve**, confirm independently — outside this console — whether the named migration's SQL actually ran; the action records whatever the operator asserts, with no cross-check against the database's real state (§3.3, §6). Because the concurrency lock is per-process rather than per-cluster (§3.2, §6), an environment running more than one `micro-business` instance should treat "one operator at a time" here as a manual convention, not an enforced guarantee. And because `seed-report-template-upload` depends on a live external system and more than one hardcoded credential in that script — an unconditional pair for the external login, plus a MinIO key pair that falls back to a hardcoded literal only when its own environment variable is unset (§3.3) — a failure specific to that one operation is worth checking against the external system and MinIO configuration before assuming this console is broken.
