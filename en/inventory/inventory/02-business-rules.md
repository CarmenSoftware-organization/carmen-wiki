# Inventory — Business Rules

> **At a Glance**
> **Rule families:** `INV_VAL_*` validation &nbsp;·&nbsp; `INV_AUTH_*` permission &nbsp;·&nbsp; `INV_CALC_*` calc &nbsp;·&nbsp; `INV_POST_*` posting &nbsp;·&nbsp; `INV_XMOD_*` cross-module
> **Rule count:** approximately 60 rules
> **Audience:** Test author + developer — every rule ID is anchored from `04-test-scenarios*` pages
> **Status lifecycle:** Section 5.1 (where present) carries the Live UI vs BRD discrepancy callouts

## 1. Overview

This page captures the operational business rules that govern the **inventory module** — the ledger that every other movement-generating module (GRN receipts, store-requisition issues / transfers, physical / spot counts, credit notes, manual stock-in / stock-out) posts into. Because inventory is movement-driven rather than document-driven, the rule set here looks different from the GRN / PR / PO catalogues: there is no `doc_status` lifecycle to manage, no save / approve / commit progression, and no single "posting event" that fires per row. Each transaction is itself the posting event; validation runs **before** the transaction is written, calculation populates the cost-layer (and, on the average-method close, the period snapshot), authorization is RBAC-plus-source-document, posting effects are ledger-only (no GL fan-out exists — see § 5's caveat), and the period-end close is a separate rule set that carries lot balances forward and stamps future movements into the new open period.

Two structural points colour every rule below and are worth restating up front. **First**, there is **no `tb_stock_balance` row** — current on-hand at `(product_id, location_id)` is derived as the plain `Σ (cost_layer.in_qty − cost_layer.out_qty)` over all non-soft-deleted layers (`getLocationBalance`; the close/open carry-over rows keep the plain sum correct across period boundaries). So rules that look like "increment the balance" actually mean "write a new `tb_inventory_transaction_cost_layer` row with the right `in_qty` / `out_qty` / `cost_per_unit` so the derived sum advances correctly" (see [inventory/01-data-model](/en/inventory/inventory/01-data-model) § 5 item 1). **Second**, `location_type` (`inventory`, `direct`, `consignment` on `tb_location.location_type`) is the setting that changes posting mechanics for `direct` locations specifically: a `direct` receipt writes the normal inbound cost-layer row **plus** an automatically-generated offsetting outbound row at the same cost (net on-hand zero) — `consignment` was found to have no distinct code path and is treated the same as `inventory` for cost-layer writes (see [01-data-model](/en/inventory/inventory/01-data-model) § 5 items 7–8). No GL/journal-posting code was found for any of the three values — see [01-data-model](/en/inventory/inventory/01-data-model) § 1 and the Posting Rules (§ 5) below.

## 2. Validation Rules

Rule IDs follow `INV_VAL_NNN`. Validation runs **at post time** — i.e. when the source module (GRN, SR, count, credit note, manual stock-in / stock-out) attempts to write the `tb_inventory_transaction` row and its children. There is no save-time / commit-time split because there is no draft state on the transaction itself; the source document carries that progression.

> **Error-string caveat (this pass):** only `INV_VAL_005`'s `Insufficient stock…` message and `INV_VAL_009`'s SR from-location message were verified as literal service strings. The other quoted messages in this table are **illustrative paraphrases** of schema constraints (`NOT NULL`, enum validity, FK resolution) — the database and DTO layers enforce the conditions, but the exact wording is not from source. `INV_VAL_006`'s "new-lot uniqueness" is enforced by the `@@unique([lot_no, lot_index])` index, and lot numbers are **system-generated** (`RC{YY}{MM}{seq}`, `ISS-…`, `CLOSE-…`, `OPEN-…`), not user-entered — there is no user-facing lot-entry validation. `INV_VAL_013`'s compensating-reversal precondition is unconfirmed (no such guard found; `deleted_at` is simply never set by any current inventory code path).

## 3. Calculation Rules

All monetary values are stored as `Decimal(20, 5)` on the cost-layer and detail rows. Display rounding is half-up to 2 decimals for currency amounts and 3 decimals for quantities. Intermediate computations use the full 5dp precision; only the final stored / displayed value is rounded.

Rule IDs follow `INV_CALC_NNN`.

| Rule ID | Formula |
| ------- | ------- |
| `INV_CALC_001` (detail total_cost) | `total_cost = qty × cost_per_unit` (signed by `qty`'s sign). Stored at 5dp on `tb_inventory_transaction_detail`. |
| `INV_CALC_002` (cost-layer total_cost — inbound) | For `in_qty > 0`: `total_cost = in_qty × cost_per_unit` on `tb_inventory_transaction_cost_layer`. |
| `INV_CALC_003` (cost-layer total_cost — outbound) | For `out_qty > 0`: `total_cost = out_qty × cost_per_unit` where `cost_per_unit` is picked by the costing method (see `INV_CALC_005` / `INV_CALC_006`). |
| `INV_CALC_004` (current on-hand — derived) | `balance(product, location) = Σ in_qty − Σ out_qty` over all non-soft-deleted cost layers at the key (`getLocationBalance` / `calculateBalance`). No snapshot anchor and no date cutoff — the period close's `close_period` (out) / `open_period` (in) rows keep the plain sum correct across period boundaries. Per-lot availability for FIFO uses the same idea per lot: receipts grouped by `lot_no` minus consumption matched via `parent_lot_no` (`getAvailableFifoLots`). |
| `INV_CALC_005` (FIFO outbound cost pick) | **Corrected in this pass — the method is a single tenant/BU-wide setting, not per-product.** `InventoryTransactionService.getCalculationMethod(bu_code)` reads `tb_business_unit.calculation_method` (platform schema, `enum_calculation_method { average, fifo }`, default `average`) once per posting batch and applies it to every product in the tenant. When the BU is on `fifo`: posting an outbound layer iterates `tb_inventory_transaction_cost_layer` rows at `(location_id, product_id)` ordered by `lot_seq_no` ascending, consuming `out_qty` from each layer's remaining balance until satisfied. Each consumed layer produces its own outbound cost-layer row with `cost_per_unit = layer.cost_per_unit`; the outbound transaction may therefore have **multiple** cost-layer rows for a single detail row when consumption spans lots. |
| `INV_CALC_006` (Weighted-average outbound cost pick) | When the BU-wide `calculation_method = average`: outbound `cost_per_unit = current_average_cost(location, product) at post time`. The current average is the most recent `tb_inventory_transaction_cost_layer.average_cost_per_unit` at `(location_id, product_id)` for that product (refreshed by every inbound — see `INV_CALC_007`). No per-product override of the BU setting was found. |
| `INV_CALC_007` (Weighted-average refresh on inbound) | When an inbound posts under WEIGHTED_AVERAGE: `new_average = (prior_on_hand × prior_average + in_qty × in_cost_per_unit) / (prior_on_hand + in_qty)` rounded to 5dp. Written to `average_cost_per_unit` on the new inbound cost-layer row. Subsequent reads at `(location_id, product_id)` pick up this value. |
| `INV_CALC_008` (Period close — lot carry-over, FIFO method) | **Corrected in this pass.** When `tb_business_unit.calculation_method = fifo`, `processCloseTransactions` computes every lot's remaining balance (`Σ in_qty − Σ out_qty` consumed via `parent_lot_no`), then writes one `close` transaction (detail `qty = −remaining`, cost-layer `transaction_type = close_period`, new lot `CLOSE-{YYMM}-{seq}`, `out_qty = remaining`) zeroing each surviving lot in the closing period, and one `open` transaction (`OPEN-{YYMM}-{seq}`, `transaction_type = open_period`, `in_qty = remaining`) re-creating it in the next period at the same `cost_per_unit`. **No `tb_period_snapshot` row is written on the FIFO path.** |
| `INV_CALC_009` (Period close — average method) | When `calculation_method = average`, `processAverageClose` (period-end.close-average.helper.ts) restates the period's issue layers at the final average, writes the close/open carry-over transactions, **and writes `tb_period_snapshot` rows** — one per `(product, location)` bucket with `opening_* / receipt_* / issue_* / adjustment_* / closing_*` qty+cost columns and `diff_amount`, `snapshot_at = period.end_at`. The snapshot table is populated **only** by this average-method path. |
| `INV_CALC_010` (Next-period creation) | `ensureNextPeriod` finds-or-creates the following `tb_period` row (`fiscal_month + 1`, rolling the year, `period = YYMM`, `status = open`, first-to-last-day UTC boundaries). Closing a period therefore auto-provisions the next one; there is no separate "open period" admin step in this module. |
| `INV_CALC_011` (Credit-note amount adjustment) | For `enum_transaction_type = credit_note_amount`: write a cost-layer row with `in_qty = out_qty = 0`, `diff_amount = vendor_credit_amount` (signed; negative for vendor concession reducing cost), `transaction_type = credit_note_amount`. The cost on the originating lot is recalculated: `new_lot_cost_per_unit = (original_lot_total_cost + diff_amount) / original_lot_qty`. Downstream consumption from the same lot picks up the revalued cost; already-consumed portions are not retroactively adjusted (the price variance flows through `diff_amount`). |
| `INV_CALC_012` (Rounding) | All rounding is half-up. Stored values use the column precision; intermediate computations carry 5dp; on-the-fly aggregations re-read rounded values from each step. |
| `INV_CALC_013` (Balance-view valuation — signed) | The `v_inventory_inventory_balance` view values **signed quantity × unit cost**, not unsigned `total_cost`. Previously it summed unsigned `total_cost`, which overstated value when outbound layers were present; corrected by migration `063_v_inventory_inventory_balance_costfix` (fixed 2026-06-17). Formula: `net_qty = SUM(itd.qty)` (signed: + inbound, − outbound); `amount = SUM(itd.qty × itd.cost_per_unit)`; `unit_cost = amount / net_qty` (0 when `net_qty = 0`). |

### 3.1 Worked example (Weighted-average tenant, ฿ THB)

A product in a business unit with `calculation_method = average` (the BU-wide setting — see `INV_CALC_005`), no prior on-hand. Three movements in chronological order at the same inventory-type location:

- **GRN receipt #1** (`enum_transaction_type = good_received_note`): `in_qty = 100`, `cost_per_unit = ฿10.00`.
  - Cost layer: `in_qty = 100`, `cost_per_unit = ฿10.00`, `total_cost = ฿1,000.00`.
  - `new_average = (0 × 0 + 100 × 10.00) / (0 + 100) = ฿10.00000` per `INV_CALC_007`.
- **GRN receipt #2** (`good_received_note`): `in_qty = 50`, `cost_per_unit = ฿14.00`.
  - Cost layer: `in_qty = 50`, `cost_per_unit = ฿14.00`, `total_cost = ฿700.00`.
  - `new_average = (100 × 10.00 + 50 × 14.00) / (100 + 50) = (1,000 + 700) / 150 = ฿11.33333` per `INV_CALC_007`.
- **Store-requisition issue** (`issue`): `out_qty = 80`.
  - Outbound cost-layer row: `out_qty = 80`, `cost_per_unit = ฿11.33333` (picked from `current_average_cost` per `INV_CALC_006`), `total_cost = ฿906.67` (`80 × 11.33333` rounded to 2dp).
  - `new_average` remains `฿11.33333` (issues don't change the average under weighted-average; only inbound does).
- Current on-hand per `INV_CALC_004`: `0 (no prior snapshot) + (100 + 50 − 80) = 70 units`; valuation `70 × 11.33333 = ฿793.33`.

For a **FIFO** business unit (`calculation_method = fifo`, `INV_CALC_005`): the issue would consume from receipt #1 first (`lot_at_date` / `lot_seq_no` ascending) — `out_qty = 80` at `cost_per_unit = ฿10.00` (one cost-layer row), `total_cost = ฿800.00`. Receipt #1's remaining balance becomes `100 − 80 = 20` units at `฿10.00`; receipt #2's balance is untouched at `50` units at `฿14.00`. Closing inventory valuation: `20 × 10.00 + 50 × 14.00 = ฿900.00`.

### 3.2 Worked example (location_type = direct)

A product receipt to a `direct` location — corrected in this pass to the actual `createDirectExpenseOut` mechanism (see `INV_VAL_009`):

- **GRN receipt** (`good_received_note`, location_type = direct): `qty = 30`, `cost_per_unit = ฿8.00`, `total_cost = ฿240.00`.
  - Inventory transaction header written; **inbound** detail (`qty = +30`) + cost-layer row (`in_qty = 30`, lot `RC{YY}{MM}{seq}`) written exactly as for an inventory-type location.
  - The service then immediately writes a second, **offsetting outbound** detail (`qty = −30`, `from_lot_no` = the receipt lot) + cost-layer row (`transaction_type = issue`, `out_qty = 30`, lot `ISS-{yyyy}-{MM}-{seq}`) at the same `฿8.00` cost, under the **same** transaction header.
  - Net on-hand at `(direct_location, product)` = `30 − 30 = 0` — "consumed on arrival".
  - Under the average method the direct receipt is excluded from the product's weighted-average computation (`average_cost_per_unit = 0` on both layers).
  - No GL/journal entry is written by any code found in this pass (the `Dr Department Expense / Cr AP` entry previously documented here is unconfirmed design intent).

### 3.3 Worked example (Balance-view valuation, signed — `INV_CALC_013`)

The `v_inventory_inventory_balance` view must value the **net** position, not the gross inflow. Three movements on one `(location, product, lot)` key:

- **Receive 10 @ ฿100** → `qty = +10`, `cost_per_unit = ฿100`.
- **Receive 10 @ ฿120** → `qty = +10`, `cost_per_unit = ฿120`.
- **Issue 5** → `qty = −5`.

```
net_qty   = SUM(itd.qty)                 = +10 + 10 − 5            = 15
amount    = SUM(itd.qty × cost_per_unit) = 10×100 + 10×120 − 5×110 = ฿1,650
unit_cost = amount / net_qty             = 1,650 / 15              = ฿110
```

The corrected view returns `net_qty = 15`, `amount = ฿1,650`, `unit_cost = ฿110`. The **old** formula summed unsigned `total_cost` (`1,000 + 1,200 + 550 = ฿2,750`) — overstating the value of an issued-down position. Corrected by migration `063_v_inventory_inventory_balance_costfix` (fixed 2026-06-17).

## 4. Authorization Rules

Rule IDs follow `INV_AUTH_NNN`. Authorization is enforced by RBAC at the source-document layer plus a small set of inventory-module-specific rules. The inventory transaction itself has **no `user_action.execute` set** because there is no workflow stage — RBAC on the source module (GRN, SR, count, credit note, manual stock-in / stock-out) is what permits the post. The inventory module owns the rules below that gate **direct** inventory writes (manual stock-in / stock-out, period-end rollforward, configuration of location and product-location parameters).

**Correction (this pass):** every "above-threshold routes to Controller / Finance" rule below (formerly `INV_AUTH_001`–`INV_AUTH_003`, `INV_AUTH_005`, `INV_AUTH_006`) described a multi-tier, threshold-gated approval chain (Store Keeper → Inventory Controller → Finance → Finance Manager) for `tb_stock_in` / `tb_stock_out`. A repo-wide search of `carmen-turborepo-backend-v2` for `threshold` returns zero hits inside the inventory, stock-in, stock-out, or period-end services (the only hits anywhere are an unrelated spot-check minimum-cost filter and rate-limiting config); `enum_stage_role` (`create, approve, purchase, issue, view_only`) has no `finance` member; and `tb_stock_in` / `tb_stock_out` authoring lives under the sibling **inventory-adjustment** wiki module (`/inventory-management/inventory-adjustment`), not under this "inventory" module's routes (`transaction`, `period-end`) at all. ## 5. Posting Rules

The inventory module does not have a document `doc_status` lifecycle — every posted transaction is immutable on write. The state diagram is therefore degenerate: each transaction transitions `(none) → posted` and may, via a compensating reversal, be marked `deleted_at` (logically reversed but never physically removed). The interesting rules are the **fan-out effects** that fire on the write.

Rule IDs follow `INV_POST_NNN`.

> **GL caveat (this pass):** every "GL: Dr … / Cr …" effect previously listed in this table was stripped — no journal-posting code exists anywhere in the inventory posting path (see [01-data-model](/en/inventory/inventory/01-data-model) § 1). The rows below describe only the ledger writes the code actually performs.

| Rule ID | Transition / Event | Effects |
| ------- | ------------------ | ------- |
| `INV_POST_001` | Post inbound (`good_received_note`, `transfer_in`, `adjustment_in`) | Insert `tb_inventory_transaction` (header) and `tb_inventory_transaction_detail` (per product, `qty > 0`). Insert one or more `tb_inventory_transaction_cost_layer` rows (`splitFifoCost` may split one receipt into multiple `lot_index` rows for exact decimal reconciliation) with `in_qty > 0`, `cost_per_unit`, generated `lot_no` (`RC{YY}{MM}{seq}` for GRN receipts), `lot_seq_no`, `at_period` / `period_id` from the current open period. Under the average method, recompute `average_cost_per_unit` per `INV_CALC_007` and back-fill it onto **all** the product's existing non-direct layers (`updateMany`). |
| `INV_POST_002` | Post outbound (`issue`, `transfer_out`, `adjustment_out`) | Insert header + detail (`qty < 0`). FIFO BU: consume available lots ordered by `lot_at_date` / `lot_seq_no` / `lot_index` ascending (`getAvailableFifoLots` / `consumeFifoLots`), one outbound layer row per consumed lot, each carrying that lot's `cost_per_unit` and `parent_lot_no`. Average BU: single outbound layer at the current average. `INV_VAL_005` (`Insufficient stock…`) is checked before the write (except credit-note paths). |
| `INV_POST_003` | Post receipt to `direct`-type location | **Corrected:** normal inbound detail + layer written, then an automatic offsetting outbound detail + `issue` layer at the same cost under the same header (`createDirectExpenseOut`) — net on-hand zero. Direct receipts are excluded from the average computation. No confirmed GL effect. See `INV_VAL_009` / § 3.2. |
| `INV_POST_004` | Post receipt to `consignment`-type location | **Corrected:** no consignment-specific code path exists — the receipt posts exactly like an `inventory`-type receipt (`INV_POST_001`). The memo-register / no-AP narrative was unconfirmed design intent and has been removed. |
| `INV_POST_005` | Post issue from `consignment`-type location | **Corrected:** identical to `INV_POST_002`; no dual COGS/AP posting code exists. Consignment is an allowed SR from-location type (`sr-type.helper.ts`) and is swept by physical count / period-end like `inventory` locations. |
| `INV_POST_006` | Transfer between locations (`store_requisition` transfer with source ≠ destination) | `transfer_out` layer(s) at source (`out_qty > 0`, cost picked per the BU method) + `transfer_in` layer(s) at destination (`in_qty > 0`, `cost_per_unit = transfer_out.cost_per_unit`, `parent_lot_no` = source lot). `INV_VAL_005` runs against the source location's balance. No confirmed GL effect. |
| `INV_POST_007` | Credit-note amount adjustment (`credit_note_amount`) | Insert cost-layer row(s) with `diff_amount` carrying the signed credit. If the originating lot's receiving period is still open, the lot is re-priced (average BU: re-price via an SO-at-old-average / SI-at-new-average pair per location); if the receiving period is `closed`/`locked` (`isLotPeriodClosed`), the lot's value is left untouched and the credit books as a current-period `diff_amount` only. No confirmed GL effect. |
| `INV_POST_008` | Credit-note quantity adjustment (`credit_note_quantity`) | Insert cost-layer row(s) with `out_qty = credit_qty` consuming from the originating GRN's lots. Consumption deliberately does **not** throw on insufficient stock — the shortfall books to `diff_amount` (see `INV_VAL_005`). The source GRN's rows are not edited. No confirmed GL effect. |
| `INV_POST_009` | Period close (**Close period** button → `PeriodEndService.closeCurrent`) | Pre-close gate (`validatePeriodEnd`): counts blocking documents in the period date range — PR/PO/SR still `in_progress` with `workflow_next_stage ≠ '-'`; GRN whose `doc_status` is **not** in `{draft, committed, voided}` (draft GRNs do *not* block); CN not in `{draft, completed, cancelled, voided}`; plus every required physical-count location (`location_type ∈ {inventory, consignment}`, `physical_count_type = yes`, active) must have a `completed` `tb_physical_count` for the period. If clear: run the close inside one transaction with a `FOR UPDATE` lock — write `close`/`open` carry-over transactions per `INV_CALC_008`/`INV_CALC_009` (snapshot rows only on the average path), set `tb_period.status = closed`, and mark the period's `tb_physical_count_period` rows `completed`. |
| `INV_POST_010` | Period open (`enum_inventory_doc_type = open`) | Chained inside the same `closeCurrent` transaction — `ensureNextPeriod` finds-or-creates the next `tb_period` (`status = open`), then `writeOpenTransaction` re-creates each surviving lot in the new period (`OPEN-{YYMM}-{seq}`, `in_qty = remaining`, same `cost_per_unit`, `parent_lot_no` = the closed lot). Carry-in layers (`open_period`, `eop_in`) are value-locked: excluded from current-period re-pricing (`CARRIED_IN_TRANSACTION_TYPES`). |
| `INV_POST_011` | Period lock (`closed → locked` on `tb_period.status`) | **Not part of this module.** No lock/reopen endpoint exists on `period-end.controller.ts`; `locked` is set by the separate `period` service backing the [system-config/period](/en/inventory/system-config/period) screen. `findCurrent` treats a `locked` period as the current one (`status ∈ {open, locked}`), so a locked period can still be displayed — and closed — via this module. |
| `INV_POST_012` | Reversal (compensating transaction) | No generic reversal endpoint exists on the inventory transaction API. Corrections are made through the source modules (credit note against a GRN, stock-out/stock-in via [inventory-adjustment](/en/inventory/inventory-adjustment)); each writes its own new transaction. `deleted_at` on `tb_inventory_transaction` is never set by any current code path. |

State diagram (degenerate, single-state):

```
[*] → posted → (compensating reversal optional) → posted (with deleted_at set on original)
```

The transaction row is immutable after write; reversal is a new row, not a state change.
