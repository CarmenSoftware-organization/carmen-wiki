# Store Requisition — Test Scenarios — Requester

> **At a Glance**
> **Persona:** Requester (Outlet Manager at consuming destination) &nbsp;·&nbsp; **Module:** [store-requisition](/en/inventory/store-requisition) &nbsp;·&nbsp; **Scenarios:** ~29
> **Categories:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **E2E coverage:** `tests/701-sr.spec.ts` (TC-SR-01xxxx..05xxxx) in `../carmen-inventory-frontend-e2e/`; oracle-backed cases in `docs/test-cases/gaps/701-sr-gap.md` sections 01–05 (form, header rules, add/remove lines, stock dialog, save/discard, Submit dialog)
> **Re-synced 2026-09-22:** no `sr_type` picker, `sr_no`/`sr_date` finalised at submit, no source-availability check, no auto-save, owner-only single/batch delete, date-pattern dialog, destination product check — rows below corrected in place.

This page captures the test scenarios that the Requester persona (the **Outlet Manager** at the consuming destination) directly drives in the `store-requisition` module. The Requester's involvement begins when a stock need is identified at the outlet (a planned production event, a par-level breach, a banquet event sheet, or a recipe-driven auto-create from `[recipe](/en/inventory/recipe)`) and ends when the SR leaves the requester zone — either through submit (handoff to whoever holds the first workflow stage) or through soft-deleting the own `draft` (the only confirmed pre-submit removal path; there is no confirmed `in_progress` withdrawal). Scenarios are grouped into **happy paths** (`draft` walk: create / line entry / submit; auto-create from recipe; resubmit after send-back), **RBAC** (Requester not assigned to department; whether a requester can also approve their own SR is **unconfirmed** — no code-level check was found), **validation** (negative tests against `SR_VAL_001`–`SR_VAL_009` that the Requester can trigger at save or submit), and a small set of **edge cases** around soft vs hard source-availability mode, split cost-dimension lines, decimal precision on `requested_qty`, and concurrent submits on the same outlet. Cross-persona handoffs that pivot off the Requester (Scenarios 1, 2, 3, 4 in the parent overview) live in [04-test-scenarios.md](./04-test-scenarios.md), not here.

## 2. Permission / Authorization

| # | Scenario | Expected behaviour (allow/deny + reason) |
| - | -------- | --------------------------------------- |
| REQ-PERM-01 | Outlet Manager creates SR at `doc_status = draft` and submits | **Allow.** Requester owns the editable `draft → in_progress` transition for their own department's SRs. `New SR`, line entry, attachment upload, and `Submit` are all enabled on a non-submitted SR. The Approver and Fulfiller see the document in `in_progress` after submit but it is no longer editable by the Requester. Maps to TC-SR-010001 + TC-SR-050001. |
| REQ-PERM-02 | User with no SR workflow that allows create opens `/new` | **Deny — workflow gate, not RBAC.** `/new` is wrapped in `CreateWorkflowGate`; the user sees `AccessDeniedBlock` (`None of the approval flows let you start a store requisition.`) instead of the form. No department-membership error exists on create (the create DTO only requires `department_id` to be present). Maps to TC-SR-010002 (`test.fixme`). |
| REQ-PERM-03 | Requester edits own `draft` SR | **Allow.** Header and line edits, attachment upload, delete — all enabled while `doc_status = draft`. Per `SR_AUTH_002`. |
| REQ-PERM-08 | Another requester deletes a draft they do not own — **added 2026-09-22** | **Deny — ownership.** `DELETE .../store-requisitions/:id` → `SR_DELETE_FORBIDDEN` (403, `You are not the owner of this store requisition`); in a batch call the item is reported with `reason = not_owner` and nothing is deleted. Platform super-admins bypass the check. |
| REQ-PERM-04 | Requester attempts to edit own `in_progress` SR (after submit) | **Deny — document has left requester's hands.** Edit endpoints reject with `"SR at status in_progress is not editable by the requester; the document is under approval / fulfilment."` Exception: if the workflow has routed the SR back to the requester stage (send-back from approver), editing is re-enabled at the requester stage only. Per `SR_AUTH_002` second clause. |
| REQ-PERM-05 | Requester attempts to approve own SR | **Unconfirmed whether blocked.** A repo-wide search of `store-requisition.service.ts` and `store-requisition.logic.ts` found no `requestor_id` cross-check at the approve action. If the same user holds both the Requester and an approve-tagged stage's role assignment, current source does not appear to stop them from approving their own SR — this should be verified against a live tenant before being asserted as blocked or allowed in test assertions. |
| REQ-PERM-06 | Requester attempts to withdraw an already-submitted (`in_progress`) SR | **Deny — no such action exists.** `store-requisition.service.ts` has no `cancel` / `withdraw` endpoint for `in_progress` documents; the **Delete** action is restricted to `doc_status = draft`. Once submitted, the requester's only path to terminate the document is to ask whoever holds the current workflow stage to invoke the whole-document reject (which sets `voided`). |
| REQ-PERM-07 | Requester attempts to edit `completed` SR | **Deny — terminal state.** Header and line edits blocked across all personas (not just Requester) on `completed` SRs; the only post-commit correction path is `[inventory-adjustment](/en/inventory/inventory-adjustment)`. Maps to permission-denial across personas. |

## 3. Validation / Error

| # | Scenario | Trigger | Expected error |
| - | -------- | ------- | -------------- |
| REQ-VAL-01 | Running-code pattern missing at submit | Tenant has no `STORE-REQUISITION` running-code pattern; requester submits a draft. | **500 at submit** — `generateSRNo()` throws `Failed to get running code pattern for SR` / `Missing running code pattern config for SR`; the draft (still `draft-<hex>`) stays `draft`. Create itself never needs the numbering service (`SR_VAL_001`). |
| REQ-VAL-02 | Missing source / destination locations | `from_location_id` or `to_location_id` left empty; requester clicks **Save** or **Submit**. | **Blocked client-side** — the form marks the field invalid (`sr-form-schema.ts`) and, on Submit, shows the toast `Some details are missing — jumped to the field to fix.` instead of opening the confirm dialog; an API call without them is a 400 from the create DTO (`SR_VAL_002`). Source = destination is only prevented by the destination lookup excluding the source. Maps to TC-SR-050002 / gap `TC-SR-0101xx`. |
| REQ-VAL-03 | `direct` location chosen as the **source** (e.g. via API) | `from_location_id` points at a `direct` location. | **Reject at create** — `SR_VAL_003` (rewritten). Server returns 400 `from_location must be inventory or consignment, not direct`. There is no movement-type/destination mismatch error: `sr_type` is derived from the destination (gap `TC-SR-010109` asserts the live derivation). |
| REQ-VAL-04 | Missing `sr_date` or `expected_date < sr_date` | Requester left `sr_date` null or entered `expected_date = sr_date − 1 day`; clicks **Save** or **Submit**. | **Reject** — `SR_VAL_004`. Server returns `"Requisition date is required; expected date must be on or after requisition date."` Maps to TC-SR-010004 (missing expected delivery date). |
| REQ-VAL-05 | Missing `department_id` | (a) API create without `department_id`; (b) legacy draft without a department submitted by a user with two department memberships; (c) …with no membership. | (a) **400 at create** (DTO, since `1dbaf76b1`). (b) **422 `SR_DEPARTMENT_AMBIGUOUS`** listing the department names — the client must send one. (c) **422 `SR_DEPARTMENT_NOT_FOUND`**. With exactly one membership the department is derived silently (`SR_VAL_005`). |
| REQ-VAL-06 | Empty SR (no lines) at submit | Requester forgot to add lines; clicks **Submit**. | **Reject at submit** — `SR_VAL_006` cascaded. Server returns `"SR must contain at least one line item before it can be submitted."` Maps to TC-SR-050003 (empty line items). |
| REQ-VAL-07 | Inactive / discontinued product on a line | Requester picked a product that has since been marked inactive (active in the catalog cache but inactive in master). | **Reject at save line / submit** — `SR_VAL_006`. Server returns `"Product is required and must be active for issue from the source location."` |
| REQ-VAL-08 | Duplicate product+dimension on the same SR | Requester adds `Rice-1kg` with `dimension = [{cost_centre: 'Banquet'}]` twice (instead of editing the existing line). | **Reject at save line** — `SR_VAL_007`. Server returns `"This product is already on the SR with the same cost-dimension allocation; edit the existing line or use a different dimension to split."` Per the `SRT1_*` unique index. |
| REQ-VAL-09 | `requested_qty = 0` or negative on a line | Requester left the quantity at default 0, or typed `-25`. | Negative: the form flags the cell (`requested_qty ≥ 0`, red border, no text message) and Save/Submit are blocked with the `{n} items are still incomplete` toast. Zero: **Save succeeds** (create DTO accepts any number); **Submit rejects** with 400 `Store requisition is not ready to submit — store_requisition_detail.<n>.requested_qty: …` (`ValidateSRBeforeSubmitSchema` `positive()`, `SR_VAL_008`). Maps to TC-SR-020002. |
| REQ-VAL-10 | Product not enabled at the destination — **replaces the source-availability case (no such check exists, `SR_VAL_009`)** | A line's product has no `tb_product_location` row for `to_location_id`. | **Reject at submit** — `SR_VAL_015`. Server returns 400 `The following products are not allowed in the destination location: <product names>`; the SR stays `draft`. TC-SR-020003 / 030002 ("insufficient stock" at submit) describe behaviour that does not exist. |
| REQ-VAL-11 | Today outside every open inventory period at submit — **added 2026-09-22** | Inventory periods closed for the current month. | Submit returns 422 `SR_DATE_PATTERN_REQUIRED`; the client opens the date-pattern dialog. *Date in the open period* → `sr_date` = last day of the current open period, submit retried and accepted; *Today* → accepted but the SR cannot be issued until that period opens; **Cancel** leaves the draft untouched. With no open period at all: 422 `SR_NO_OPEN_PERIOD` (`SR_VAL_014`, `SR_VAL_016`). |

## 4. Edge Cases

| # | Scenario | Condition | Expected |
| - | -------- | --------- | -------- |
| REQ-EDGE-01 | Request exceeds source on-hand | `requested_qty = 100`; source on-hand = 60. | **Submit allowed, no warning.** No availability check or reservation exists at submit (`SR_VAL_009` unconfirmed); the requester can see on-hand only in the Inventory Information dialog. The over-request surfaces at the approver's trim or at the issue stage (`SR_VAL_013`). |
| REQ-EDGE-02 | Split cost-dimension on the same product | Same-product two-row entry per REQ-HP-03; the two rows have distinct `dimension` JSON values. | Both rows persist (the `SRT1_*` unique index includes `dimension`); they flow independently through approval (each can be trimmed / rejected separately) and fulfilment (each writes a separate inventory transaction). GL/journal-entry cost-splitting is unconfirmed — no journal-posting code was found for this module. Edge: identical product+dimension is a duplicate per REQ-VAL-08. |
| REQ-EDGE-03 | Decimal precision on `requested_qty` | Outlet manager enters `requested_qty = 12.345` (3 decimal places, well within `Decimal(20, 5)`). | **Accepted at storage.** Quantity stored at 5dp precision; display rounded half-up to 3dp ("12.345"); flows through approval and issue unchanged; the linked inventory transaction's `received_base_qty` / `cost_per_unit` use the same precision contract. Per `SR_CALC_007`. |
| REQ-EDGE-04 | Concurrent submits on the same outlet (two requesters, two SRs against the same source) | Outlet has two requesters (Outlet Manager and a deputy); both submit an SR against `WH-Central` at the same time, both requesting `Rice-1kg` quantity that together exceeds source on-hand. | **Both submits succeed individually.** Each SR passes `SR_VAL_009` on its own snapshot (the check is per-SR, not aggregated across concurrent submits). The race is resolved at approval (Approver sees both and can trim) and at fulfilment (`SR_VAL_013` live check at commit catches the over-commitment). One SR commits in full; the other commits partial or hits a stock-out. Variance recorded on the partial. |
| REQ-EDGE-05 | Long `description` and many attachments | Requester writes a 4,000-character `description` and attaches 10 PDF / image files via `tb_store_requisition_comment.attachments`. | **Accepted within Prisma limits.** `description` is `VarChar` (no length cap); `attachments` JSONB array carries the 10 file refs (`{originalName, fileToken, contentType}`). Storage backend (S3) holds the files; the SR carries only the tokens. Approver / Fulfiller see the attachments in the activity log. |
| REQ-EDGE-06 | Leaving the form with unsaved changes — **corrected 2026-09-22: there is no auto-save** | Requester is mid-line-entry and navigates away (Back, sidebar) without saving. | `useNavigationGuard` shows the *Discard changes?* dialog with **Keep editing** / **Discard**; nothing is persisted until **Save**. `grep setInterval\|autosave routes/store-operation/store-requisition/` returns nothing, so TC-SR-040003 ("Auto-Save Draft Every 60 Seconds") has no behaviour to assert (gap `TC-SR-040105`). |
| REQ-EDGE-07 | Duplicate an existing SR — **added 2026-09-22** | Any saved SR opened in view mode. | **Duplicate** in the header navigates to `/new?duplicate_id=<id>`; header and lines are pre-filled (`buildSrDuplicateValues`), the form is dirty from the start (baseline is the empty form), and **Save** creates a new `draft-<hex>` document; the source SR is unchanged. |
