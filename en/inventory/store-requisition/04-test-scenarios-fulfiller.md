# Store Requisition — Test Scenarios — Fulfiller

> **At a Glance**
> **Persona:** Fulfiller (Store Keeper / Warehouse Supervisor at source) &nbsp;·&nbsp; **Module:** [store-requisition](/en/inventory/store-requisition) &nbsp;·&nbsp; **Scenarios:** ~27
> **Categories:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **E2E coverage:** maps to `tests/701-sr.spec.ts` (TC-SR-120001..120004+ Issuance) in `../carmen-inventory-frontend-e2e/`

This page captures the test scenarios that the Fulfiller persona (whoever holds the workflow stage tagged `enum_stage_role.issue`, typically titled Store Keeper / Warehouse Supervisor) directly drives in the `store-requisition` module. The Fulfiller's involvement begins when an SR reaches the issue-tagged stage of `in_progress` (after upstream approve-tagged stages complete) and ends at the final workflow-stage advance — the same generic `POST .../approve` call the Approver uses (`useIssueStoreRequisition` and `useApproveStoreRequisition` hit the identical endpoint, differing only in the `stage_role` tag). Scenarios are grouped into **happy paths** (full issuance matching `approved_qty`, partial issuance at-issue stock-out, `sr_type = transfer` incrementing destination on-hand, `sr_type = issue` into a `direct` destination with no destination on-hand change), **RBAC** (stage-gated authorization, location-scoped fulfiller permission), **validation** (negative tests against `SR_VAL_008` — `issued_qty > approved_qty`, `SR_VAL_011`/`SR_VAL_013` — final-stage-advance gates), and **edge cases** around optimistic concurrency and multi-line mixed outcomes (some lines fully issued, others short, others zero). **Corrected this pass:** lot selection is not a Fulfiller action — `createFifoConsumption()` in `inventory-transaction.service.ts` assigns lots automatically by FIFO; there is no lot-selection UI in the SR frontend. Segregation of duties (Approver ≠ Fulfiller), a closed-period commit block (`SR_VAL_014`), and GL/journal-entry posting were checked against current source and found unconfirmed — scenarios built on those claims are corrected below. Cross-persona handoffs that pivot off the Fulfiller (Scenarios 1, 2, 6, 8 in the parent overview) live in [04-test-scenarios.md](./04-test-scenarios.md), not here.

## 2. Permission / Authorization

| # | Scenario | Expected behaviour (allow/deny + reason) |
| - | -------- | --------------------------------------- |
| FUL-PERM-01 | Fulfiller in `user_action.execute` at the issue-tagged stage acts on SR at their source | **Allow.** Enter `issued_qty` and click **Issue** are enabled while `doc_status = in_progress` and `workflow_current_stage` is tagged `enum_stage_role.issue`. Per `SR_AUTH_007`. |
| FUL-PERM-02 | Fulfiller from a different source location attempts to act | **Unconfirmed as a location-scoped restriction.** No `from_location_id IN my_locations` check was found in `store-requisition.service.ts` for this action; the confirmed gate is workflow-stage membership (`user_action.execute`), not location. Do not assert a location-scope error message in test expectations without independent verification. |
| FUL-PERM-03 | Fulfiller attempts to set `issued_qty > approved_qty` | **Deny — value cap.** Per `SR_VAL_008`. The screen blocks the entry client-side; the server rejects with `"Quantities must satisfy 0 ≤ issued_qty ≤ approved_qty ≤ requested_qty."` |
| FUL-PERM-04 | ~~Approver attempts to fulfil own-approved SR above SoD threshold~~ — corrected this pass | — | **Removed.** No segregation-of-duties check and no relaxation threshold exist in current source — the same user can approve and then issue the same SR at any value with no code-level block. |
| FUL-PERM-05 | Fulfiller attempts to act on `completed` SR | **Deny — terminal state.** Per the global rule, `completed` is locked across all personas. Post-commit corrections go through `[inventory-adjustment](/en/inventory/inventory-adjustment)`. |
| FUL-PERM-06 | ~~Fulfiller attempts to skip lot selection~~ — corrected this pass | — | **Not applicable.** There is no lot-selection UI to skip — `SR_VAL_012` (lot info present on the linked inventory transaction) is satisfied automatically by `createFifoConsumption()`; it is not a client-facing validation the Fulfiller can trigger. |

## 3. Validation / Error

| # | Scenario | Trigger | Expected error |
| - | -------- | ------- | -------------- |
| FUL-VAL-01 | `issued_qty > approved_qty` on a line | Fulfiller enters `issued_qty = 12` on a line with `approved_qty = 10`. | **Reject** — `SR_VAL_008`. Server returns `"Quantities must satisfy 0 ≤ issued_qty ≤ approved_qty ≤ requested_qty."` Common cause: typo / data-entry mistake. |
| FUL-VAL-02 | `issued_qty < 0` on a line | Fulfiller accidentally enters a negative quantity. | **Reject** — `SR_VAL_008`. Server returns the same invariant error. |
| FUL-VAL-03 | Final-stage advance with no approved lines | All lines have `approved_qty = 0` (e.g. every line was rejected in a prior `/approve` call, but the whole-document `/reject` was never invoked). | **Reject** — `SR_VAL_011`. Server returns `"SR must contain at least one approved line (approved quantity > 0) before it can be committed."` **Corrected this pass:** this is a plausible state, not a bug — rejecting every line does not automatically void the document; a separate whole-document reject call is required to terminate it. |
| FUL-VAL-04 | ~~Lot data missing on linked inventory transaction~~ — corrected this pass | — | **Not a Fulfiller-triggerable scenario.** Lot assignment is automatic FIFO; there is no lot-selection step the Fulfiller can skip or leave incomplete. |
| FUL-VAL-05 | Source on-hand below `issued_qty` at the final-stage advance (live check) | Live `SR_VAL_013` check: another SR consumed source on-hand between the Fulfiller entering `issued_qty` and clicking Issue; on-hand now < `issued_qty`. | **Reject** — `SR_VAL_013`. Server returns `"Source stock-out at issue: line <seq> requires <issued_qty> but only <on_hand> is available at <from_location_name>."` Fulfiller reduces `issued_qty` to live on-hand and re-submits (the FUL-HP-04 partial-issuance pattern). |
| FUL-VAL-06 | ~~Closed-period commit attempt~~ — corrected this pass | — | **Removed.** A repo-wide search of `store-requisition.service.ts`, `store-requisition.logic.ts`, and the SR DTOs for `period` returned zero hits; treat `SR_VAL_014` as unconfirmed. |
| FUL-VAL-07 | Optimistic-concurrency mismatch at the final-stage advance | Another user (concurrent tab, or background system) has updated `doc_version` on the SR between read and the Issue call. | **Reject** — generic optimistic-concurrency. Server rejects with a `409`; the frontend re-fetches the fresh `doc_version` before retrying (`fetchFreshSr()` in `use-sr-form-actions.ts`). |

## 4. Edge Cases

| # | Scenario | Condition | Expected |
| - | -------- | --------- | -------- |
| FUL-EDGE-01 | ~~Decimal precision on `issued_qty` and multi-lot split (manual)~~ — corrected this pass | Lot-controlled product, `approved_qty = 5.500` (3-dp). | **Precision claim stands, mechanism corrected.** `issued_qty` is stored at 5dp precision per `Decimal(20, 5)` and display-rounded half-up to 3dp (`SR_CALC_007`). The split across lots (if any) is computed automatically by `consumeFifoLots()` — there is no lot-sub-form for the Fulfiller to enter or validate per-lot quantities against. |
| FUL-EDGE-02 | ~~Lot data partially present (lot picked but no expiry)~~ — corrected this pass | — | **Not a Fulfiller-facing scenario.** Since lot assignment is automatic and not a manual pick, a "picked a lot with missing expiry" state cannot originate from Fulfiller action; any such gap would be a source-side data-quality issue in the inventory module, out of scope for this persona's tests. |
| FUL-EDGE-03 | Inventory sub-ledger stamped with the SR's document type | After the final-stage advance, `tb_inventory_transaction.inventory_doc_type = store_requisition` is queryable for reconciliation. | **Confirmed** per `SR_XMOD_003` / `enum_inventory_doc_type`. Whether any downstream GL reconciliation happens against this is unconfirmed — no journal/ledger code was found for this module. |
| FUL-EDGE-04 | Final-stage advance triggers cost-layer FIFO consumption from multiple lots | Source uses FIFO costing; line has `issued_qty = 10`, oldest layer has remaining 4 units, next layer has remaining 30. | **Two cost-layer consumption rows.** `createFifoConsumption()` consumes 4 units from the oldest layer at its `cost_per_unit`, then 6 units from the next layer; this is fully automatic — the Fulfiller has no manual role in lot or layer selection. |
| FUL-EDGE-05 | ~~Pre-commit lot selection saved as draft state~~ — corrected this pass | — | **Not applicable.** There is no pre-commit lot-selection state to save — lots are resolved only at the final-stage advance itself, not entered ahead of time. |
| FUL-EDGE-06 | Transfer-type SR with destination location currently inactive | `sr_type = transfer`; destination `tb_location` is marked `is_active = false` between approval and issuance. | **Unconfirmed.** No explicit `is_active` check on `to_location_id` was found in the final-stage-advance path this pass; treat any "reject — location inactive" claim as unconfirmed until independently verified. |
| FUL-EDGE-07 | UoM conversion at issue (issue in a different UoM than approval) | Product has two UoMs (`Bottle` and `Case = 12 Bottle`); approved in `Case = 5`. | **Not independently re-verified this pass.** The general UoM-conversion pattern used elsewhere in the inventory-transaction layer is plausible but a per-line UoM-switch-at-issue path specific to SR was not traced in `store-requisition.logic.ts` this pass. |
| FUL-EDGE-08 | ~~Batch commit (multiple SRs in one transaction window)~~ — corrected this pass | — | **Removed.** No batch-issue endpoint or scheduled job was found for this module (mirrors the same finding already made for GRN); each SR is issued individually through its own `/approve` call. |
