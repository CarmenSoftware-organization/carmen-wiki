# Store Requisition — Test Scenarios — Approver

> **At a Glance**
> **Persona:** Approver (Department Head + higher-tier approvers) &nbsp;·&nbsp; **Module:** [store-requisition](/en/inventory/store-requisition) &nbsp;·&nbsp; **Scenarios:** ~27
> **Categories:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **E2E coverage:** maps to `tests/701-sr.spec.ts` (TC-SR-060001..060005, 070001..070003, 080001..080002, 090001+, 100001+, 110001+) in `../carmen-inventory-frontend-e2e/`

This page captures the test scenarios that the Approver persona (whoever holds a workflow stage tagged `enum_stage_role.approve`, typically titled Department Head) directly drives in the `store-requisition` module. The Approver's involvement begins when an SR transitions to `in_progress` and the workflow lands at a stage where the Approver is in `user_action.execute`; it ends when all lines have been actioned (advancing the workflow to the next stage) or when the Approver invokes the separate whole-document reject (`voided`). Scenarios are grouped into **happy paths** (per-line approve in full, trim down with `approved_message`, reject bundled into the same `/approve` call, send-back with `review_message` via a separate `/review` call), **RBAC** (stage-gated authorization per `SR_AUTH_014`; segregation of duties between Requester and Approver is **unconfirmed** — no code-level check was found), **validation** (negative tests against `SR_VAL_010` — `approved_qty > requested_qty`), and **edge cases** around concurrent approvers on different lines and the whole-document reject boundary. **Corrected this pass:** multi-tier value-threshold escalation, approval delegation, SLA time-out escalation, and a budget-module integration were checked against `store-requisition.service.ts`, `store-requisition.logic.ts`, and the workflow orchestrator and found unconfirmed (zero hits for `threshold`, `delegat`, or a budget route) — scenarios built on those claims are removed or marked unconfirmed below. Cross-persona handoffs that pivot off the Approver (Scenarios 1, 3, 4, 5 in the parent overview) live in [04-test-scenarios.md](./04-test-scenarios.md), not here.

## 1. Happy Path

| # | Scenario | Pre-condition | Steps | Expected |
| - | -------- | ------------- | ----- | -------- |
| APR-HP-01 | Approve all lines in full | SR `SR-A` at `doc_status = in_progress`, `workflow_current_stage = 'approval-stage-1'`; three lines, each with `requested_qty > 0` and `approved_qty = 0`; Approver `bann@blueledgers.com` is in `user_action.execute`; Requester ≠ Approver. | 1. Open the approvals dashboard. 2. Click SR `SR-A`. 3. For each line, set `approved_qty = requested_qty`. 4. Click **Submit Approval Decision**. | All three lines get `approved_by_id = bann`, `approved_by_name = "Bann"`, `approved_date_at = now()`; per-line `history` appended with `{ status: 'approved' }`; workflow advances `workflow_current_stage` to the fulfilment stage; `user_action.execute` populated with fulfillers at `from_location_id`; SR stays `in_progress` (status does not change at approval — only the workflow stage does). Maps to TC-SR-070001. |
| APR-HP-02 | Trim one line, approve others in full | SR `SR-B`: line 1 (`requested_qty = 25`), line 2 (`requested_qty = 15`), line 3 (`requested_qty = 10`); source on-hand on line 2 is only 12. | 1. Open `SR-B`. 2. Line 1: `approved_qty = 25` (full). 3. Line 2: `approved_qty = 12`, `approved_message = "trimmed to source on-hand"`. 4. Line 3: `approved_qty = 10` (full). 5. Submit decision. | Per-line: line 1 fully approved at 25, line 2 trimmed to 12 with `approved_message`, line 3 fully approved at 10; all three lines get the approve signature; workflow advances to fulfilment; the Fulfiller sees the trim with the reason; the variance `requested_qty − approved_qty = 3` on line 2 is the approver's trim, not yet a fulfilment gap (that happens at issue). Maps to TC-SR-090001 (Adjust Approved Quantity). |
| APR-HP-03 | Reject a line, bundled with other lines' decisions in one `/approve` call | SR `SR-C`: line 1 (`requested_qty = 50` for "Champagne-VintageX", outlet asks for 50 bottles for a non-existent event). | 1. Open `SR-C`. 2. Line 1: mark **Reject**. 3. Enter `reject_message = "no banquet event scheduled this week; quantity unjustified"`. 4. Confirm. 5. Submit the `/approve` call. | Line 1: `approved_qty = 0`, `reject_by_id = bann`, `reject_by_name = "Bann"`, `reject_date_at = now()`, `reject_message` populated; per-line `history` appended with `{ status: 'rejected' }`; the SR continues to the next workflow stage if other lines were approved. **Corrected this pass:** rejecting every line in this call does not automatically void the document — a separate whole-document `/reject` call is required for that (see `04-test-scenarios.md` Scenario 5). Maps to TC-SR-080001-adjacent (the whole-document reject itself maps to TC-SR-110001). |
| APR-HP-04 | Send the whole document back for correction | SR `SR-D`: line 1 (`requested_qty = 25` for rice, unclear rationale). | 1. Open `SR-D`. 2. Mark line 1 **Review**. 3. Enter `review_message = "please justify the 25-unit rice request"`. 4. Confirm — this becomes a `/review` call, not `/approve`. 5. Submit. | Line 1: `review_by_id = bann`, `review_by_name = "Bann"`, `review_date_at = now()`, `review_message` populated; per-line `history` appended with `{ status: 'review', to_stage: 'requester' }`; `approved_qty` remains 0; workflow routes the SR back to the requester stage. **Corrected this pass:** if any other line in the same submission was marked approve or reject, `computeSrAction()` routes the whole submission as a send-back — those other lines' approve/reject selections are not applied in this call. Maps to TC-SR-100001 (Request Review). |
| APR-HP-05 | Mixed approve + reject on a single `/approve` call | SR `SR-E` with 3 lines: line 1 (`requested_qty = 10`, fine), line 2 (`requested_qty = 20`, over source on-hand of 15), line 3 (`requested_qty = 5`, unjustified). | 1. Open `SR-E`. 2. Line 1: approve at 10. 3. Line 2: trim to 15 with `approved_message`. 4. Line 3: reject with `reject_message`. 5. Submit the `/approve` call. | Confirmed in `computeSrAction()`: approve and reject can mix in one `/approve` call. Lines 1, 2 get approve signatures (full and trimmed); line 3 gets a reject signature; the workflow advances when every line at the current stage has been actioned. **Corrected this pass:** a fourth line marked `review` cannot be submitted alongside these in the same call — `review` must be its own submission (see APR-HP-04); the previous version of this scenario described a 4-line mix including a send-back, which `computeSrAction()` does not support in one call. Maps to TC-SR-080001 (Approve Item-level — mixed lines). |
| APR-HP-06 | ~~Multi-tier escalation to second-stage approver (value threshold)~~ — corrected this pass | — | — | **Removed as described.** No `threshold` hits were found anywhere in `store-requisition.service.ts`, `store-requisition.logic.ts`, or the workflow orchestrator — there is no confirmed value-based trigger for routing to a second approval stage. If a tenant's `tb_workflow` genuinely defines more than one `approve`-tagged stage, the document advances through them using the ordinary mechanism in APR-HP-01–03 — this is a generic property of the shared workflow engine, not an SR-specific "multi-tier" feature. |
| APR-HP-07 | ~~Approver delegation — deputy acts~~ — corrected this pass | — | — | **Removed.** A repo-wide search for `delegat` against this module and the workflow orchestrator returned zero hits; there is no confirmed delegation mechanism to test. |

## 2. Permission / Authorization

| # | Scenario | Expected behaviour (allow/deny + reason) |
| - | -------- | --------------------------------------- |
| APR-PERM-01 | Approver in `user_action.execute` at current stage acts on SR | **Allow.** Approve / trim / reject / send-back actions are all enabled on lines while `doc_status = in_progress` and `workflow_current_stage` matches. Per `SR_AUTH_005`. |
| APR-PERM-02 | User NOT in `user_action.execute` attempts to approve | **Deny — workflow-stage gating.** Per `SR_AUTH_014`. User sees the SR in the activity feed but the **Approve** button is hidden / disabled; direct API call rejects with `"You are not assigned to act on this requisition at the current stage."` No `approved_qty` write. Maps to TC-SR-070002 (Unauthorized User Attempts to Approve). |
| APR-PERM-03 | Requester attempts to approve own SR | **Unconfirmed whether blocked.** No `requestor_id` cross-check was found in `store-requisition.service.ts` or `store-requisition.logic.ts` at the approve action. Do not assert a SoD block in test expectations until this is independently verified against a live tenant. |
| APR-PERM-04 | Approver attempts to set `approved_qty > requested_qty` | **Deny — value cap.** Per `SR_VAL_010`. The screen blocks the entry client-side; the server rejects via `"Approved quantity cannot exceed requested quantity; to grant more, the requester must amend and resubmit."` Approver must either trim to `requested_qty` or send the line back asking the requester to amend. |
| APR-PERM-05 | Approver rejects line without `reject_message` | **Deny — mandatory reason.** Per `SR_VAL_010` second clause. The Reject dialog requires non-empty `reject_message`; server rejects empty submissions with `"Rejection reason is required."` |
| APR-PERM-06 | Approver attempts to edit `requested_qty` on a line | **Deny — Approver scope.** Approver can set `approved_qty` (and the signature columns) but not `requested_qty` (which is requester scope and locked at submit). The line's `requested_qty` field is read-only on the approval screen. To change the requested quantity, the Approver sends the line back for correction (APR-HP-04). |
| APR-PERM-07 | Approver attempts to act on `completed` SR | **Deny — terminal state.** Per the global rule, `completed` is locked across all personas. The Approver may inspect the historical signature for audit but cannot re-approve or revoke. |

## 3. Validation / Error

| # | Scenario | Trigger | Expected error |
| - | -------- | ------- | -------------- |
| APR-VAL-01 | `approved_qty > requested_qty` per line | Approver attempts `approved_qty = 30` on a line with `requested_qty = 25`. | **Reject** — `SR_VAL_010` first clause. Server returns `"Approved quantity cannot exceed requested quantity; to grant more, the requester must amend and resubmit."` |
| APR-VAL-02 | `approved_qty < 0` | Approver attempts a negative approved quantity (data-entry error or API mis-use). | **Reject** — `SR_VAL_008` (the quantity invariant rejects negatives at every stage). Server returns `"Quantities must satisfy 0 ≤ issued_qty ≤ approved_qty ≤ requested_qty."` |
| APR-VAL-03 | Reject line with empty `reject_message` | Approver clicks Reject and submits without entering a reason. | **Reject** — `SR_VAL_010` second clause. Server returns `"Rejection reason is required."` |
| APR-VAL-04 | Send-back with empty `review_message` | Approver clicks Send Back and submits without entering a reason. | **Reject** — same family as VAL-03. Server returns `"Review message is required when sending an SR back for correction."` |
| APR-VAL-05 | Approver acts on line outside their stage | Approver is in `user_action.execute` for stage 1, but tries to act on a line whose `current_stage_status` is at stage 2 (already moved past stage 1 — unusual sequencing). | **Reject** — `SR_AUTH_014`. Server returns `"You are not assigned to act on this requisition at the current stage."` |
| APR-VAL-06 | ~~Budget exceeded warning at approval~~ — corrected this pass | — | **Unconfirmed.** `TC-SR-070003` in `701-sr.spec.ts` carries a test-plan annotation describing a budget-exceeded warning, but no budget-module route, field, or wiring to the SR approve screen was found in `carmen-inventory-frontend-react` or `carmen-turborepo-backend-v2`. Treat the annotation as illustrative test-plan copy, not confirmed behavior, until a budget integration is found. |

## 4. Edge Cases

| # | Scenario | Condition | Expected |
| - | -------- | --------- | -------- |
| APR-EDGE-01 | Concurrent approvers on different lines | Two approvers (both in `user_action.execute` for the same stage) open the same SR and each click approve on different lines simultaneously. | **Per-line locking.** The system locks at the line level via optimistic concurrency (`doc_version` on the detail). Each line accepts the first approver who acts; the second approver acting on the same line gets a "line already actioned" message and is asked to refresh. No double-write, no lost signature. Workflow advances when all lines have been actioned by some approver. |
| APR-EDGE-02 | Whole-document reject after every line marked reject | Approver marks every active line reject (each with its own `reject_message`) and then separately invokes the whole-document reject action. | **`doc_status = voided`, not `cancelled`.** **Corrected this pass:** there is no automatic cancel — `StoreRequisitionService.reject()` is a distinct call the approver must invoke; `cancelled` is never assigned by any current service method. The requester is notified. |
| APR-EDGE-03 | ~~Time-out / SLA escalation~~ — corrected this pass | — | **Removed.** No SLA-timeout or auto-escalation logic was found in the workflow orchestrator or this module; treat any "stale-approval" auto-escalation claim as unconfirmed. |
| APR-EDGE-04 | Approver trims to exactly source on-hand at approval time | Source on-hand visible to Approver = 15; Approver trims `approved_qty = 15` (matches on-hand). | **Approval accepted.** By the final workflow-stage advance, source on-hand may have moved (other consumption). `SR_VAL_013` re-runs at that point against live on-hand — if on-hand has fallen below 15, the issuing stage short-issues; if it has risen, no impact (issuance is capped at `approved_qty = 15` anyway). The Approver does NOT see the at-issue stock-out risk at approval time. |
| APR-EDGE-05 | ~~Multi-tier with second-stage further trim~~ — corrected this pass | — | **Unconfirmed as a value-threshold feature.** If a tenant's `tb_workflow` defines a second `approve`-tagged stage, the same generic approve mechanism applies there too, and the per-line `history` JSON would capture both stages' actions in sequence — but no confirmed trigger routes an SR to a second stage based on value, and this was not independently verified against a live multi-stage tenant this pass. |
| APR-EDGE-06 | Approver acts then immediately edits within the same session | Approver approves line 1 at 25, then realises they meant to trim; tries to re-set `approved_qty = 20`. | **Within-session re-decision permitted before workflow advance.** As long as the workflow stage has not yet advanced (typically because other lines on the stage are not yet actioned), the Approver may update their own signature on a line; the `approved_date_at` updates, the latest `approved_qty` is the canonical value, the `history` JSON records the change. Once the workflow advances (all lines actioned, decision submitted), the line is locked at this stage. |
| APR-EDGE-07 | ~~Bulk approve from approvals list~~ — corrected this pass | Approver selects multiple SRs in the list. | **Not confirmed as a list-level action.** The list's only confirmed bulk action is **Export Selected** (`TC-SR-060003`, `sr-component.tsx`'s bulk-actions button). Bulk approve/reject/review exists only *within* a single SR's line table (`sr-item-fields.tsx`'s `handleBulkApprove` / `handleBulkReject` / `handleBulkReview`, applying a decision to multiple selected lines on one document) — not across multiple SR documents from the list. Do not test for a cross-document bulk-approve action. |
| APR-EDGE-08 | Bulk-select lines within one SR and apply one decision | SR has 5 lines; Approver selects 3 via row checkboxes and clicks the bulk-approve action shown when a selection is active. | **Confirmed real** — `sr-item-fields.tsx` shows bulk approve / reject / review controls once `selectedRows.length > 0` and `canBulkAction` is true; the action applies the chosen `stage_status` to every selected line, then the normal per-line `SR_VAL_010` rules apply at submission. This is a within-document, per-line bulk action, not a cross-document one (see APR-EDGE-07). |
