## 1. Overview

This page captures the operational business rules that govern the **costing module** — the engine that picks `cost_per_unit` for every outbound stock movement, refreshes `average_cost_per_unit` on every inbound, and — on average-method business units only — writes the period-locked `closing_cost_per_unit` at period close. Because costing is **not** a separate document module — it is a behaviour layer over [inventory](/en/inventory/inventory)'s ledger — the rule set here looks different from the GRN / PR / SR catalogues: there is no document lifecycle of its own, no save / approve / commit progression, no `doc_status`. Instead, the rules below describe **how the engine reads its configuration, picks the cost, performs the arithmetic, refreshes the average, and anchors the period boundary**. Every rule is **invoked from** an inventory transaction post or a period-end run that lives in the inventory module; the costing module owns the rule's logic, not the trigger. There is no distinct RBAC authority layered on top of the engine — see Section 4.

Two structural points colour every rule below. **First**, the **costing method is configured at the business unit, not per product** (per [costing/01-data-model](/en/inventory/costing/01-data-model) § 5 item 1). The engine resolves the method via `tb_business_unit.calculation_method` (platform schema, default `average`; `getCalculationMethod(bu_code)`, `inventory-transaction.service.ts:402-408`) once per call and applies it to every detail line in the transaction. There is no per-product override; mixed FIFO / WA across products at the same business unit is **not** a supported configuration. Under **average** the running average is kept **per product across all locations** (`getNetTotals(tx, productId)`, `:1487-1509`) and re-stamped on every live layer of the product. **Second**, every cost picked at post time is **immutable on write** — once written to `tb_inventory_transaction_cost_layer.cost_per_unit`, the value is part of the historical ledger and cannot be edited even if the configured method changes later. Two exceptions exist and both replace rows rather than edit them: (a) a credit-note-amount adjustment writes `diff_amount` and recalculates the originating lot's `cost_per_unit` per `INV_CALC_011`; (b) an average-unit GRN that was posted at save and is then voided, rejected, or edited before commit has its whole movement soft-deleted and (for an edit) re-posted (`voidGrnLedger` / `repostGrnLedgerIfChanged`, `good-received-note.ledger.ts:298-459`), refused if any received lot was already consumed. These properties — single method per business unit, immutable cost on the layer row — are what make the costing audit trail defensible across periods.

## 2. Validation Rules

Rule IDs follow `COST_VAL_NNN`. Validation runs **at cost-pick time** — i.e. when the inventory transaction post invokes the costing engine to populate `cost_per_unit` / `average_cost_per_unit` on the cost-layer row about to be written. There is no save-time or commit-time split; the engine is called once per cost-layer row and either returns a valid cost or fails the parent transaction.

| Rule ID | Condition | When enforced | Error / behaviour |
| ------- | --------- | ------------- | ----------------- |
| `COST_VAL_001` | The business unit resolves to a `tb_business_unit` row; `calculation_method ∈ {average, fifo}`. `getCalculationMethod` falls back to `fifo` when the column is empty (`:408`); an unknown value throws `Unknown calculation method` (`:882`). | Cost-pick time | Parent transaction rolled back. |
| `COST_VAL_002` | For **FIFO** cost-pick on outbound: at least one `tb_inventory_transaction_cost_layer` row exists at `(location_id, product_id)` with `in_qty − Σ subsequent out_qty > 0`. If on-hand is zero (no consumable layer), the engine cannot pick a cost. | Cost-pick time (outbound) | Reject with `"FIFO: no available cost layer at (location, product) to consume."` Parent transaction rejected per `INV_VAL_005` (no-negative-balance). |
| `COST_VAL_003` | For **WA** cost-pick on outbound: the product has a positive net quantity in the ledger so `getCurrentAverageCost` (`:1478-1481`, product-wide) returns a non-zero average, and the **location** balance covers the issue (`getLocationBalance`, `:1545`). | Cost-pick time (outbound) | Reject on insufficient location balance; a product with no live layers anywhere yields average `0`. |
| `COST_VAL_002b` | For a **GRN** inbound: `grn_date` must fall inside an inventory period with `status ∈ {open, locked}`, resolved by date range (`resolvePeriodForDate`, `:1426-1442`; `assertDateInOpenPeriod` in the GRN logic). | GRN save (average units), commit, approve | `GRN_DATE_OUTSIDE_OPEN_PERIOD` (422) before any layer is written; the engine itself throws if it reaches the write with no period. |
| `COST_VAL_004` | `cost_per_unit` returned by the engine is non-negative and finite. Same constraint as `INV_VAL_007` but enforced specifically at the cost-pick boundary so a corrupt source value (e.g. a vendor pricelist with a negative entry) is caught before the cost-layer write. | Cost-pick time | Reject with `"Cost-pick produced an invalid cost_per_unit (negative or non-finite): <value>."` Parent transaction rolled back. |
| `COST_VAL_005` | For **WA** inbound recompute: `calculateNewAverageCost` (`inventory-cost.formula.ts:90-101`) returns `0` when the combined quantity `(existing_net_qty + new_qty) ≤ 0` rather than throwing; the result is rounded to **2 dp**. There is no explicit negative-input guard in the formula — negative values are prevented upstream by the document validations. | Cost-pick time (inbound, WA only) | No rejection at this layer; a zero divisor yields average `0` (corrected 2026-09-22 — the earlier "reject with … invalid inputs" message does not exist in code). |
| `COST_VAL_006` | For **credit-note-amount** adjustments (`enum_transaction_type = credit_note_amount`): the originating lot identified by `lot_no, lot_index` exists in `tb_inventory_transaction_cost_layer`, has not been fully drained (positive remaining `(Σ in_qty − Σ out_qty) > 0` OR the lot's original receipt event is still present in the ledger for cost rebasing), and the credit-note `diff_amount` is signed (negative for vendor concession reducing cost; positive for additional charge). | Cost-pick time (credit-note path) | Reject with `"Credit-note-amount adjustment: originating lot not found or fully drained without remaining cost rebasing context."` Per `INV_VAL_011`. |
| `COST_VAL_007` | For **count-variance** posts (count completes → `tb_stock_in` / `tb_stock_out` rollup), the configured count-costing source (`enum_physical_count_costing_method`) resolves to a valid cost: `standard` requires `tb_product.standard_cost > 0`; `last` and `last_receiving` require at least one matching prior layer at `(location, product)`; `average` requires a non-zero `average_cost_per_unit`. | Cost-pick time (count-variance) | Reject with `"Count-variance valuation: configured count-costing-method <X> cannot resolve a cost (missing standard_cost / no prior layer)."` Count-derived stock-in / stock-out cannot post; routes back to Controller. |
| `COST_VAL_008` | For **end-of-period rollforward** (`enum_transaction_type ∈ {close_period, open_period, eop_in, eop_out}`): the closing period's snapshot rows are computed before the open-period rollforward begins; `closing_cost_per_unit` is the cost the rollforward carries into the next period; both must be present and consistent. | Period-end orchestration | Reject the rollforward run with `"Cannot rollforward period <YYMM> → next: closing snapshot for <N> (location, product, lot) keys is missing or has null closing_cost_per_unit."` Period stays at `open`. |
| ~~`COST_VAL_009`~~ | **Removed — not a real rule.** The planning-stage design doc (`docs/persona-doc/System Process/proc-03-cost-calculation.md` P4 Q1 in `carmen-inventory-frontend-e2e`) records "costing method locked at implementation, cannot change after go-live" as a **stakeholder-confirmed design intent**, not an implemented guard. `tb_business_unit.calculation_method` is written from the platform/cluster-admin business-unit screen (`platform_business-units.controller.ts`); a repo-wide search of `carmen-turborepo-backend-v2` found no on-hand check, no drain precondition, and no rejection path anywhere in that write path. | — | Not enforced. If the tenant changes `calculation_method` with non-zero on-hand today, nothing in the backend stops it — existing cost-layer rows keep their already-picked `cost_per_unit`/`average_cost_per_unit` (immutable per Section 4), but new movements immediately switch to the new method's cost-pick logic. Flag as a real gap if this matters for the target audience — it is not currently guarded. |
| `COST_VAL_010` | Cost-pick on **transfers** between locations (`transfer_out` → `transfer_in` paired rows): the `transfer_in` cost equals the `transfer_out` cost (no cost change on movement) — the engine writes `transfer_in.cost_per_unit = transfer_out.cost_per_unit`. This is enforced by the post pipeline; a manual override (different cost on the in than the out) is rejected. | Cost-pick time (transfer) | Reject with `"Transfer cost mismatch: transfer_in.cost_per_unit must equal transfer_out.cost_per_unit."` Per the transfer-coherence rule. |
| `COST_VAL_011` | Cost-pick on **direct-cost locations** (`tb_location.location_type = direct`): the engine **does not run** because the receipt is expensed at receipt; no cost-layer row is written. An attempt to invoke the cost-pick for a direct-cost location is silently skipped (not an error — the inventory transaction still writes a header + detail for audit per `INV_POST_003`). | Cost-pick time (direct location) | No error; the engine returns "skipped — direct location, no cost layer required". |
| ~~`COST_VAL_012`~~ | **Removed — no consignment-specific cost-pick branch exists.** A repo-wide search of `inventory-transaction.service.ts` for `consignment` returns zero hits. The only location-type branch the cost engine special-cases is `direct` (Section 5 `COST_POST_005`); `consignment` locations are costed the same way as any other inventory-type receiving location. | — | — |

## 3. Calculation Rules

All monetary values are stored as `Decimal(20, 5)` on the cost-layer and detail rows, but **the engine rounds every unit cost it writes to 2 dp** (`Math.round(x × 100) / 100` in `inventory-transaction.service.ts:941,1134`, `calculateNewAverageCost`, `getCurrentAverageCost`) and reconciles layer totals to that precision (`splitFifoCost(qty, total, 2)`). The GRN money chain that feeds it carries 5 dp. Display rounding is 2 decimals for currency amounts and 3 decimals for quantities. The rules below are the engine's arithmetic; they are invoked by the rules in Section 2 (validation) and Section 5 (posting).

Rule IDs follow `COST_CALC_NNN`. These rules **delegate to** or **align with** the inventory-module rules `INV_CALC_001`–`INV_CALC_012` because the cost-layer arithmetic is the same set of formulas viewed from the costing perspective.

| Rule ID | Formula |
| ------- | ------- |
| `COST_CALC_001` (FIFO outbound cost-pick) | When `tb_business_unit.calculation_method = fifo` (or runtime override) and the cost-pick is outbound: iterate `tb_inventory_transaction_cost_layer` rows at `(location_id, product_id)` ordered by `lot_seq_no` ascending, taking only rows with positive remaining balance. For each consumed lot, produce **one** outbound cost-layer row at `cost_per_unit = lot.cost_per_unit` and `out_qty = min(lot.remaining, total_out_qty − already_consumed)`. Stop when `total_out_qty` is fully consumed. Each consumed-lot row's `total_cost = out_qty × cost_per_unit`. **A single outbound detail line may produce multiple cost-layer rows** when the consumption spans lots — this is the FIFO multi-row pattern. Equivalent to `INV_CALC_005`. |
| `COST_CALC_002` (WA outbound cost-pick) | When `calculation_method = average` and the cost-pick is outbound: `current_average = getCurrentAverageCost(product)` = `Round2(Σ net cost / Σ net qty)` over **every live layer of the product, all locations** (`getNetTotals`, `:1487-1509`, netting each layer's `in_qty − out_qty` at its own `cost_per_unit`). Produce **one** outbound cost-layer row at `cost_per_unit = current_average` and `out_qty = total_out_qty`; `total_cost = out_qty × current_average`. The average is **not** re-stamped by outbound. Equivalent to `INV_CALC_006`. **Corrected 2026-09-22:** not per `(location, product)`. |
| `COST_CALC_003` (WA inbound recompute) | When `calculation_method = average` and the cost-pick is inbound: `new_average = Round2((existing_net_cost + new_total_cost) / (existing_net_qty + new_qty))` (`calculateNewAverageCost`, `inventory-cost.formula.ts:90-101`; `0` when the combined qty is `≤ 0`), where the existing totals come from `getNetTotals(product)` and the new receipt aggregates every non-direct line of the same product in the document. Written to `average_cost_per_unit` on the new layers **and re-stamped on every live, non-direct layer of the product** (`:1236-1247`). If `existing_net_qty = 0`, the new average equals the receipt's landed unit cost. **2 dp, not 5 dp.** Equivalent to `INV_CALC_007`. |
| `COST_CALC_004` (FIFO inbound layer creation) | When `calculation_method = fifo` and the cost-pick is inbound: `lot_seq_no = max(lot_seq_no where at_period = <period>) + 1` (**period-scoped**, `:1399-1406`), `lot_no = <location_code><YYMM><lot_seq_no padded to 4>` (`buildLotNo`), `cost_per_unit = Round2(total_cost / qty)`, layers `splitFifoCost(qty, total_cost, 2)` → one row per `lot_index` reconciling to the exact total, `lot_at_date = grn_date`, `average_cost_per_unit = 0` (`:998`). **Corrected 2026-09-22:** no shadow average is written under FIFO. |
| `COST_CALC_005` (Credit-note-amount lot revaluation) | When `enum_transaction_type = credit_note_amount`: write a cost-layer row with `in_qty = 0, out_qty = 0, diff_amount = signed_amount`. Recalculate the originating lot's `cost_per_unit`: `new_lot_cost_per_unit = (original_lot_total_cost + diff_amount) / original_lot_qty`. Downstream consumption from the same lot picks up the revalued cost via the FIFO pick reading `cost_per_unit` on the lot's most recent revaluation row; **already-consumed** portions are not retroactively adjusted (the credit-note's effect flows entirely through `diff_amount` on the layer, leaving previously costed outbound rows untouched). Equivalent to `INV_CALC_011`. |
| `COST_CALC_006` (Period snapshot — closing cost-per-unit) | At period close on **average** units only: `closing_cost_per_unit = closing_total_cost / closing_qty` where `closing_qty = opening_qty + receipt_qty − issue_qty + adjustment_qty` and `closing_total_cost = opening_total_cost + receipt_total_cost − issue_total_cost + adjustment_total_cost + Σ diff_amount`, written to `tb_inventory_period_snapshot` (`period-end.close-average.helper.ts:480`). FIFO units write no snapshot (`COST_POST_007`). Equivalent to `INV_CALC_010`. |
| `COST_CALC_011` (Landed cost — GRN inbound feed) | **New 2026-09-22.** Per receipt event: `stock_qty = received_base_qty + foc_base_qty`; `extra_share = allocateExtraCost(mode, Σ extra_cost_detail.amount, lines)` — `by_qty` = equal share per line with `stock_qty > 0`, `by_value` = weighted by `stock_qty`, `manual` = none (`good-received-note.extra-cost.ts:40-61`); `stock_cost = base_net_amount + calcBase(extra_share, exchange_rate)`; `cost_per_unit = Round2(stock_cost / stock_qty)`; each layer's `extra_cost_amount = splitByWeight(base_extra_share, layer quantities)` (`inventory-transaction.service.ts:73-92,965-1002`). Events with `received_base_qty = 0` are dropped before posting (`:849`), so a FOC-only event posts nothing unless it shares a document with a paid event — and then only through the per-item loop. Direct-location receipts are issued straight back out at the same cost (`createDirectExpenseOut`). |
| `COST_CALC_007` (Period rollforward — opening cost preservation) | At period open: `opening_qty / opening_cost_per_unit / opening_total_cost = previous_period.closing_qty / closing_cost_per_unit / closing_total_cost`. For FIFO, the `open_period` cost-layer rows preserve the **per-lot** breakdown so FIFO sequence carries across the boundary; `lot_seq_no` is preserved unchanged. For WA, the rollforward writes a single open-period layer per `(location, product)` carrying the prior closing average. Equivalent to `INV_CALC_008`. |
| `COST_CALC_008` (Count-variance valuation — by `enum_physical_count_costing_method`) | When a count produces a variance line and the count-variance posting code writes `cost_per_unit` on the `tb_stock_in` / `tb_stock_out` rollup: resolve the cost by the configured `enum_physical_count_costing_method`: `standard` → `tb_product.standard_cost`; `last` → most recent cost-layer `cost_per_unit` at `(location, product)` regardless of direction; `average` → most recent `average_cost_per_unit`; `last_receiving` → most recent inbound layer's `cost_per_unit` (filter `transaction_type ∈ {good_received_note, adjustment_in, transfer_in}`). The picked cost flows into the count-rollup document's lines and then into the cost-layer post via the normal FIFO / WA write path. |
| `COST_CALC_009` (Standard cost — recipe baseline) | `tb_product.standard_cost` is read by recipe costing and by `enum_physical_count_costing_method = standard`. It is **not** read by the FIFO / WA cost-pick on regular inbound / outbound. Updates to `standard_cost` are prospective; existing cost-layer rows are not retroactively adjusted. |
| `COST_CALC_010` (Rounding) | **Corrected 2026-09-22.** Ledger unit costs (`cost_per_unit`, `average_cost_per_unit`) are rounded to **2 dp** with JavaScript `Math.round` (half away from zero for positives); layer `total_cost` values are reconciled so they sum exactly to the 2-dp document total (`splitFifoCost`); `extra_cost_amount` shares come from `splitByWeight` at the same precision. Document-side amounts (`base_net_amount`, deviation percentages) are 5 dp. Columns remain `Decimal(20, 5)`. Display: 2 dp for currency, 3 dp for quantities. |

### 3.1 Worked example (FIFO, business unit `BU-A` with `calculation_method = fifo`)

Two products at the same business unit are both FIFO (the method is per business unit, not per product). Consider product `P-1` at location `LOC-A` (code `LA`) in period `2609` with no prior on-hand:

- **Inbound 1** (GRN commit, `good_received_note`): `in_qty = 100`, landed `cost_per_unit = ฿10.00`, `lot_seq_no = 1` → `lot_no = LA26090001`, `lot_index = 1`.
  - Cost-layer row: `in_qty = 100, cost_per_unit = ฿10.00, total_cost = ฿1,000.00, extra_cost_amount = 0, average_cost_per_unit = 0` (no shadow average under FIFO).
- **Inbound 2** (GRN commit, single line, goods `base_net_amount = ฿650.00` for 50 units plus a `฿50.00` freight extra cost allocated to that line): `stock_cost = 700.00`, `cost_per_unit = Round2(700.00 / 50) = ฿14.00`, `lot_seq_no = 2` → `lot_no = LA26090002`.
  - Cost-layer row: `in_qty = 50, cost_per_unit = ฿14.00, total_cost = ฿700.00, extra_cost_amount = ฿50.00, average_cost_per_unit = 0`.
- **Outbound** (SR issue): `out_qty = 80`. FIFO consumes `LOT-1` first (`lot_seq_no = 1`).
  - Cost-layer row: `out_qty = 80, cost_per_unit = ฿10.00, total_cost = ฿800.00, from_lot_no = LOT-1` (single row — fits within `LOT-1`'s 100-unit balance). Per `COST_CALC_001`.
  - `LOT-1` remaining: `100 − 80 = 20`; `LOT-2` untouched at `50`.
  - On-hand valuation: `20 × 10.00 + 50 × 14.00 = ฿900.00`.
- **Outbound** (SR issue): `out_qty = 30`. FIFO consumes the remaining `LOT-1` (`20 units at ฿10.00`) plus `10 units` from `LOT-2 (at ฿14.00)`.
  - Cost-layer row 1: `out_qty = 20, cost_per_unit = ฿10.00, total_cost = ฿200.00, from_lot_no = LOT-1`.
  - Cost-layer row 2: `out_qty = 10, cost_per_unit = ฿14.00, total_cost = ฿140.00, from_lot_no = LOT-2`.
  - This is the **two-row FIFO outbound** — a single SR detail line produces multiple cost-layer rows.
  - On-hand valuation: `LOT-2: 40 × 14.00 = ฿560.00`.

### 3.2 Worked example (WA, business unit `BU-B` with `calculation_method = average`)

Same product `P-1` at `LOC-A`, same physical movements, but at a different business unit with WA configured. Note that on this unit the GRN's movement is written at **save**, not commit (`postsInventoryAtSave`), and that the average is product-wide — a second location `LOC-B` holding `P-1` would share it:

- **Inbound 1**: `in_qty = 100, cost_per_unit = ฿10.00`.
  - Cost-layer row: `in_qty = 100, cost_per_unit = ฿10.00, total_cost = ฿1,000.00, average_cost_per_unit = ฿10.00`.
- **Inbound 2**: `in_qty = 50, cost_per_unit = ฿14.00`.
  - `new_average = Round2((1,000.00 + 700.00) / 150) = Round2(11.33333) = ฿11.33` per `COST_CALC_003`; written on the new layer **and re-stamped on Inbound 1's layer**.
- **Outbound** (SR issue): `out_qty = 80`. WA reads the product average `฿11.33` per `COST_CALC_002`.
  - Cost-layer row (single): `out_qty = 80, cost_per_unit = ฿11.33, total_cost = ฿906.40`.
  - Average not re-stamped by the outbound; `getNetTotals` now nets `(100×10 + 50×14 − 80×11.33) / (150 − 80) = 793.60 / 70 = ฿11.34` for the *next* receipt's recompute (netting at each layer's own cost, `inventory-cost.formula.ts` `sumNetTotals`).
  - On-hand: `70 units × ฿11.33 = ฿793.10` at the stamped average.
- **Outbound** (SR issue): `out_qty = 30`.
  - Cost-layer row (single): `out_qty = 30, cost_per_unit = ฿11.33, total_cost = ฿339.90`.
  - On-hand: `40 × 11.33 = ฿453.20`.

Same physical flow, different total COGS (FIFO produced `฿800 + ฿200 + ฿140 = ฿1,140`; WA produced `฿906.40 + ฿339.90 = ฿1,246.30`). The difference is **only** the cost-pick rule; the qty ledger is identical. In a rising-price scenario, FIFO COGS is lower and ending-inventory value higher — see [`calculation-methods.md`](./calculation-methods.md) § 5 for the full comparison. **Corrected 2026-09-22:** the earlier version of this example carried the average at 5 dp (`฿11.33333`); the engine rounds it to 2 dp.

### 3.3 Worked example (Credit-note-amount revaluation)

Continuing from § 3.1 (FIFO): vendor concedes a `฿100.00` price reduction post-receipt on the `LOT-2` purchase (originally `50 units at ฿14.00, total ฿700.00`). The credit note posts as `enum_transaction_type = credit_note_amount`:

- Cost-layer row: `in_qty = 0, out_qty = 0, diff_amount = −฿100.00, transaction_type = credit_note_amount, lot_no = LOT-2`.
- `LOT-2` revalued per `COST_CALC_005`: `new_cost_per_unit = (700.00 + (−100.00)) / 50 = ฿12.00`.
- The next outbound consuming from `LOT-2` picks up `cost_per_unit = ฿12.00` (not `฿14.00`); previously consumed portions (the 10 units consumed in § 3.1's second outbound at `฿14.00`) are **not** retroactively adjusted — the variance flows through `diff_amount` on the cost-layer ledger only. No general-ledger posting occurs anywhere in this flow (no journal-entry code exists in the backend); `diff_amount` is the entire durable record of the revaluation.

## 5. Posting Rules

The costing module's "posting" is the cost-layer row write performed by the engine at the moment an inventory transaction posts. The rules below describe **what the engine writes** on the cost-layer row for each `enum_transaction_type`, including the cost-pick logic, the average refresh, the lot-sequence assignment, and the `diff_amount` revaluation path. These rules are invoked from `INV_POST_001`–`INV_POST_010` in the inventory module.

Rule IDs follow `COST_POST_NNN`. They **extend** (do not duplicate) the inventory posting rules.

| Rule ID | Trigger | Costing-engine effect |
| ------- | ------- | --------------------- |
| `COST_POST_001` | Inbound to inventory-type location (`enum_transaction_type ∈ {good_received_note, adjustment_in, transfer_in}`) | Engine picks the inbound cost (from the source document — GRN **landed** cost per `COST_CALC_011`, confirmed live 2026-09-22; stock-in unit cost; transfer-in cost from the paired `transfer_out`). Writes one `tb_inventory_transaction_detail` and one or more cost-layer rows: `in_qty > 0`, `cost_per_unit = Round2(picked_cost)`, `lot_no = <location_code><YYMM><run>`, `lot_index` per split row, `lot_seq_no` period-scoped per `COST_CALC_004`, `extra_cost_amount` (GRN only), `period_id` / `at_period` from the document date. **Average units:** refreshes and re-stamps `average_cost_per_unit` per `COST_CALC_003`. **FIFO units:** writes `average_cost_per_unit = 0` — **corrected 2026-09-22**, no shadow WA is maintained. **GRN timing:** the write happens at `commit()` on FIFO units and already at `save()` on average units (`postsInventoryAtSave`, `good-received-note.ledger.ts:49-51`); the movement header records `info.posted_at_save` so commit does not post twice. |
| `COST_POST_002` | Outbound from inventory-type location (`enum_transaction_type ∈ {issue, adjustment_out, transfer_out}`) | Engine resolves the business unit's `calculation_method`. **FIFO branch** per `COST_CALC_001`: iterate available layers by `lot_seq_no` asc, writing one cost-layer row per consumed layer with `out_qty`, `cost_per_unit = consumed_lot.cost_per_unit`, `from_lot_no = consumed_lot.lot_no`. **WA branch** per `COST_CALC_002`: write a single cost-layer row with `out_qty = total`, `cost_per_unit = current_average`, `from_lot_no` left null or set to a sentinel "WA pool" if needed. Average **not** refreshed (outbound doesn't re-blend). |
| `COST_POST_003` | Credit-note-amount adjustment (`enum_transaction_type = credit_note_amount`) | Engine writes a cost-layer row with `in_qty = 0`, `out_qty = 0`, `diff_amount = signed_amount`, `transaction_type = credit_note_amount`, `lot_no = originating_lot`. Updates the originating lot's `cost_per_unit` per `COST_CALC_005`. Downstream FIFO outbound from the same lot picks up the revalued cost. The originating lot's `lot_seq_no` is preserved. |
| `COST_POST_004` | Credit-note-quantity adjustment (`enum_transaction_type = credit_note_quantity`) | Engine treats as outbound: writes a cost-layer row with `out_qty = credit_qty`, `cost_per_unit = originating_lot.cost_per_unit`, `from_lot_no = originating_lot`. The outbound is bound to the originating GRN's lot (not a free FIFO pick) because the credit-note semantically reverses that specific receipt. |
| `COST_POST_005` | Receipt to direct-cost location (`enum_transaction_type = good_received_note` with `tb_location.location_type = direct`) | **Corrected:** the engine does **not** skip the layer — `createFifoTransaction` / `createAverageTransaction` write the normal inbound cost-layer row, then immediately write an automatic offsetting outbound (`createDirectExpenseOut`) at the same cost under the same transaction header, so the location's net on-hand is zero. Direct receipts are excluded from the weighted-average computation (they don't contribute to `average_cost_per_unit`). No GL effect — no journal-posting code exists anywhere in the backend. |
| ~~`COST_POST_006`~~ | **Removed — no consignment-specific posting branch exists** (see the removed `COST_VAL_012` above). Consignment-location receipts are costed the same as any other inventory-type receipt. | — |
| `COST_POST_007` | Period close (`enum_inventory_doc_type = close`) | System-invoked from `PeriodEndService.closeCurrent`, gated only by `inventory_management.period_end.execute` on the caller — no separate engine-level RBAC. **Average-method business units only:** for each `(location_id, product_id)` bucket, compute `closing_qty / closing_cost_per_unit / closing_total_cost` per `COST_CALC_006` and write to `tb_inventory_period_snapshot` (`period-end.close-average.helper.ts:480`), plus `close_period` cost-layer rows. **FIFO-method business units:** no snapshot row is written at all — `findAllRemainingLots` + `writeCloseTransaction` carry the residual lot balances forward as `close_period` cost-layer rows instead (`period-end.close-transaction.helper.ts`). This split is easy to miss when reading only the average path. Closing a period does not post to the GL. |
| `COST_POST_011` | Void / reject / edit of an average-unit GRN posted at save | `voidGrnLedger()` (`good-received-note.ledger.ts:298-377`): refuses with `GRN_RECEIPT_ALREADY_CONSUMED` (409) when any received lot has an out-layer under another header; otherwise soft-deletes the movement header and its cost layers, clears the events' `inventory_transaction_id`, and re-stamps the products' average from what remains (`restampAverageCostForProducts`). `repostGrnLedgerIfChanged()` then posts a fresh movement when the edit changed qty/cost. Committed GRNs are never unwound. |
| `COST_POST_008` | Period open (`enum_inventory_doc_type = open`) | Chained with `COST_POST_007`. Writes `open_period` cost-layer rows for the next period at `cost_per_unit = previous.closing_cost_per_unit`, `lot_seq_no` preserved from the closed lot per `COST_CALC_007`. FIFO sequence carries across the period boundary. The next period's first outbound at `(location, product)` reads from the `open_period` row's cost. |
| `COST_POST_009` | Count-variance posting (`enum_inventory_doc_type ∈ {stock_in, stock_out}` derived from a completed count) | Engine resolves the count-costing source per `enum_physical_count_costing_method` and picks the cost per `COST_CALC_008`. Writes the cost-layer row through the normal `COST_POST_001` (overage → adjustment_in) or `COST_POST_002` (shortage → adjustment_out) path, with the picked cost passed through. The count's variance valuation source is preserved in the activity log for audit. |
| `COST_POST_010` | Standard-cost change on `tb_product.standard_cost` | **No cost-layer effect.** Standard cost is a reference value; updating it does not write any cost-layer row, does not change any prior `average_cost_per_unit` or any prior `cost_per_unit`. The change is prospective: subsequent count-variance posts (where `enum_physical_count_costing_method = standard`) read the new value; recipe baseline costs recompute on next access; no retroactive adjustment. |

State diagram for cost-layer write (degenerate, single-state, mirrors inventory):

```
[*] → cost-layer row written (with cost_per_unit + average_cost_per_unit set at post time)
   → (immutable: no edit; revaluation only via credit-note-amount diff_amount, or
      period-end rollforward writing open_period / close_period anchor rows)
```

### 5.1 Cost Method × Trigger Mapping — Planning Doc vs Code

Costing has no per-document status lifecycle. Instead, the cost engine is invoked by inventory-affecting transactions. The table below maps each trigger transaction to its Average (AVCO) and FIFO effects. The "Notes / Source" column cites the real planning-stage document set at `../carmen-inventory-frontend-e2e/docs/persona-doc/System Process/*.md` where it exists, plus the code path this pass re-verified each row against; the earlier draft of this page cited this same document set under a non-existent path (`Test_case/System_Process/...`) with fabricated "capture dates" — the corrected paths and code cross-checks are below. "AVCO" is the planning doc's term for the same thing the Prisma schema calls `average`.

| Trigger transaction | AVCO effect | FIFO effect | Notes / Source |
|---|---|---|---|
| GRN (stock-in) | Re-average **at save**: `new_avg = Round2((net_cost + in_cost) / (net_qty + in_qty))`, product-wide; landed cost incl. extra cost + FOC | New cost layer(s) added **at commit**; `lot_seq_no` incremented per period; `average_cost_per_unit = 0` | `COST_CALC_003` / `COST_CALC_004` / `COST_CALC_011`; confirmed in `InventoryTransactionService.createFifoTransaction` / `createAverageTransaction` and `GoodReceivedNoteLogic.save()` / `commit()` (2026-09-22); design intent in `tx-01-grn.md` |
| CRN (credit note) | Re-average; qty removed from on-hand | Oldest layer consumed at originating lot cost (`credit_note_quantity`) or lot revalued (`credit_note_amount` via `diff_amount`) | `COST_POST_003` / `COST_POST_004`; confirmed in code (`createFifoCreditNoteQty/Amount`, `createAverageCreditNoteQty/Amount`); since 2026-09-21 one credit per product per GRN |
| Stock In adjustment | Re-average (same inbound path) — **at `PATCH …/commit`**, not at create (`stock-in.service.ts:418,471-575`) | New cost layer added at the document's unit cost | `COST_CALC_003` / `COST_CALC_004`; confirmed — GRN and stock-in share `executeAdjustmentIn` / the same cost-pick rules |
| Stock Out adjustment | Cost held (outbound consumes at prevailing average; average is not updated by outbound) | Oldest cost layer consumed first; spans multiple lots if needed | `COST_CALC_001` / `COST_CALC_002`; confirmed in code |
| Issues (SR / stock-issue) | Cost held (same as stock-out) | Oldest cost layer consumed | `COST_POST_002`; confirmed in code |
| Physical Count — variance exists | Re-average per direction (overage → re-average inbound; shortage → cost held outbound) | Overage → new cost layer; shortage → oldest layer consumed | `COST_CALC_008`; count-variance cost source is `enum_physical_count_costing_method`, separate from the regular AVCO/FIFO pick — see [01-data-model](/en/inventory/costing/01-data-model) § 2.6. Whether the count-variance rollup's cost-layer write itself was independently re-verified against `physical-count`'s own resync pass, not re-checked in this pass |
| Physical Count — no variance | **NOT triggered** | **NOT triggered** | No qty change; no cost-layer write — consistent with `getLocationBalance`'s `Σin − Σout` model |
| Store Requisition (SR) | Cost pass-through (existing layer consumed, no re-average) | Cost pass-through (existing layer consumed, no new layer) | `COST_POST_002`. The planning doc (`proc-03-cost-calculation.md` P1/P2) calls this "no recalculation — internal movement at book value"; the code confirms the cost engine is invoked to pick the existing layer's cost but does not create a new FIFO layer or re-average |
| Spot Check | **PENDING** | **PENDING** | Independently confirmed on the spot-check module's own resync pass: `submit()` has no posting effect of any kind — see [spot-check/02-business-rules](/en/inventory/spot-check/02-business-rules) § 5.1 |
| End Period Close | Average-method: locks period cost, writes `tb_inventory_period_snapshot` | FIFO-method: carries lot balances forward, writes **no** snapshot | `COST_POST_007` / `COST_POST_008`; confirmed in `period-end.close-transaction.helper.ts` / `period-end.close-average.helper.ts:480` — see the correction on `COST_POST_007` above |

### 5.2 Discrepancy Callouts — Planning Doc vs Code

> ⚠️ **SR cost-pick is pass-through — no AVCO re-average, no new FIFO layer.** Store Requisition moves goods from an inventory location to a Direct or Consignment destination at the existing unit cost. The cost engine is invoked (per `COST_POST_002`) to pick the existing layer cost, but AVCO is not re-averaged and FIFO does not create a new layer — the outbound at the source location consumes the existing lot at its existing `cost_per_unit`. Confirmed against `inventory-transaction.service.ts`; the design rationale ("internal movement at book value, no value gained or lost") is stated in the planning doc's `proc-03-cost-calculation.md` § "SR Exception — Why No Recalc" (`../carmen-inventory-frontend-e2e/docs/persona-doc/System Process/`).

> ⚠️ **Costing method has no code-enforced lock, despite the design intent.** The planning doc records "costing method locked at implementation, cannot change after go-live" as a **stakeholder-confirmed requirement** — but it is not what the current code does. See the removed `COST_VAL_009` in Section 2: there is no on-hand check, no drain precondition, and no rejection path anywhere in `tb_business_unit.calculation_method`'s write path (`platform_business-units.controller.ts`). Treat this as a genuine gap between design intent and implementation, not as an enforced rule.

> ⚠️ **Physical Count cost source is configurable, not fixed.** Count-variance posts use `enum_physical_count_costing_method` (`standard`, `last`, `average`, `last_receiving`) to select the unit cost for the variance — this is separate from the AVCO/FIFO cost-pick on regular transactions. Neither `carmen/docs` nor the planning-stage `System Process` document set describes this enum by name. Source: [01-data-model](/en/inventory/costing/01-data-model) § 2.6; `COST_CALC_008`.

> ⚠️ **CRN lot cost reversal path — needs re-verification against the credit-note module's own resync.** Whether a CRN reverses the original GRN's lot cost or uses the current cost was recorded as "TBC" in the planning doc (`proc-03-cost-calculation.md` P4 Q5) at the time it was written. The Prisma engine has two distinct code paths — `credit_note_quantity` (returns at originating lot cost) and `credit_note_amount` (revalues via `diff_amount`) — confirmed to both exist in `inventory-transaction.service.ts`; which UX flow triggers which path was not re-verified in this pass.

> ✅ **Multi-currency cost storage — verified 2026-09-22: base currency only.** The GRN feed passes `base_net_amount` and converts the extra-cost share with `calcBase(share, grn.exchange_rate)` (`good-received-note.ledger.ts:75,131`); the ledger rows carry no currency or rate column. The planning doc's "TBC" (`proc-03-cost-calculation.md` P4 Q6) is answered: valuation is in the business unit's base currency at the document's exchange rate. All worked examples on this page use Thai Baht `฿` at rate 1.
>
> ⚠️ **GRN posting timing differs by method.** On average units the movement exists while the GRN is still `saved` and is unwound if the GRN is voided / rejected / edited (`COST_POST_011`); on FIFO units nothing exists until commit. Testers checking "stock after save" must know the BU's method first.
