# Good Receive Note (GRN) — Business Rules

> **At a Glance**
> **Rule families:** `GRN_VAL_*` validation &nbsp;·&nbsp; `GRN_AUTH_*` permission &nbsp;·&nbsp; `GRN_CALC_*` calc &nbsp;·&nbsp; `GRN_POST_*` posting &nbsp;·&nbsp; `GRN_XMOD_*` cross-module
> **Rule count:** approximately 62 rules
> **Audience:** Test author + developer — every rule ID is anchored from `04-test-scenarios*` pages
> **Status lifecycle:** Section 5.1 (where present) carries the Live UI vs BRD discrepancy callouts

## 1. Overview

This page captures the operational business rules that govern a Good Receive Note (GRN) document through its lifecycle: input validation at create / edit / save / commit time, monetary calculation (line and header, including an extra-cost distribution-mode tag), authorization gates by role and document status, posting effects on each transition of `enum_good_received_note_status`, and cross-module rules with [purchase-order](/en/inventory/purchase-order), [inventory](/en/inventory/inventory), [vendor-pricelist](/en/inventory/vendor-pricelist), and [costing](/en/inventory/costing).

> ⚠️ **Re-verified 2026-09-22 — the posting event is `saved → committed` again, with one exception.** The 2026-07-15 pass documented `save()` as the posting event; between 2026-08 and 2026-09 the backend moved posting to **`commit()`** (`c815d67ce`) and then made **average-costed business units post the stock movement at `save()`** while still leaving the PO to commit (`7d6556dd0`). Current code: `GoodReceivedNoteLogic.save()` (`good-received-note.logic.ts:78-147`) validates, issues the real `grn_no`, and — only when `postsInventoryAtSave(method)` (`good-received-note.ledger.ts:49-51`) — writes the ledger with `posted_at_save = true`; `commit()` (`:165-203`) and `approve()` (`:289-320`) both run `postReceipt()` (`:228-270`), which writes the ledger if not already written and advances the PO. Section 5 is rewritten accordingly; rule IDs are kept stable.
>
> ⚠️ **Three-way match / AP posting — still not implemented; GL module exists but is not wired to GRN.** No vendor-invoice entity, capture screen, or match algorithm exists (re-checked 2026-09-22). A GL module now exists (`apps/micro-business/src/gl/`), but nothing outside `src/gl/` calls it — `GlPostingService.post()` (`gl-posting.service.ts:293`) posts only journal vouchers created by the JV/template/reversal/closing paths, and `enum_gl_jv_source.inventory` / `.ap` have no writer. `GRN_POST_006`–`GRN_POST_009` and `GRN_XMOD_007` stay "not implemented".

Two structural points colour every rule below. **First**, the lot number and cost layers live on the inventory ledger, which since 2026-08-10 points **back** at the receipt event (`tb_inventory_transaction_detail.good_received_note_detail_item_id`); the expiry date now lives on the GRN event (`tb_good_received_note_detail_item.expired_at`). There is no lot-number entry on the GRN at all — the lot is generated at posting as `<location_code><YYMM><4-digit run>` (`common/helpers/lot-number.helper.ts:27-35`). **Second**, extra-cost allocation is **now live** (`f8cd9f0d9`, 2026-09-10): `allocateExtraCost()` (`good-received-note.extra-cost.ts:40-61`) splits the extra-cost total across the lines that put stock on hand — `by_qty` = equal share per line, `by_value` = weighted by each line's stock quantity, `manual` = no allocation — and the share lands in the line's landed cost and on each cost layer's `extra_cost_amount`. The Prisma enum still has only those three modes; `by_weight` / `by_volume` do not exist. The worked example in Section 3.1 now shows what the code does, including the counter-intuitive mode names.

## 2. Validation Rules

Rule IDs follow `GRN_VAL_NNN`. **Rewritten 2026-09-22 from the code**, not from the PRD: the rules below are what `create()` / `update()` (`good-received-note.service.ts`), `POST …/verify` (`verify/good-received-note.verify-create.ts`, `good-received-note.validate.ts`), `save()`, `commit()`, `approve()`, `reject()`, and `voidGrnById()` actually enforce. Every check is reachable without side effects through `POST /api/:bu_code/good-received-notes/verify` with `verify_state ∈ {create, save, commit}` (`logic.ts:340-392`); the same functions run again when the real transition is called. Rows that existed on the previous version but have **no code** behind them are struck through and explained rather than deleted so cross-references still resolve.

## 3. Calculation Rules

All monetary values are stored as `Decimal(20, 5)` at the row level; tax and discount **rates** are stored as `Decimal(15, 5)`; the exchange rate is `Decimal(15, 5)` on the GRN header. **Rewritten 2026-09-22 from the code.** The server derives every money field of a receipt event from `received_price` in `calcGrnItemPrices()` (`good-received-note.pricing.ts:40-60`, rounding to **5 dp**) and never trusts `sub_total_price` / `net_amount` / `total_price` / `base_*` sent by the client. `discount_amount` and `tax_amount` are taken **as amounts from the request** — the backend does not recompute them from `discount_rate` / `tax_rate` (the rates are stored as snapshots; the frontend keeps amounts and rates in step in `grn-item-cells/computed-sync.tsx`). Landed cost for the ledger is computed in base currency at posting time (`stockQtyOf` / `stockCostOf`, `inventory-transaction.service.ts:73-92`) and the unit cost written to the ledger is rounded to **2 dp** (`Math.round(x × 100) / 100`, `:941,1134`).

Rule IDs follow `GRN_CALC_NNN`.

| Rule ID | Formula |
| ------- | ------- |
| `GRN_CALC_001` (line subtotal) | `sub_total_price = Round5(received_price × received_qty)` in transaction currency. FOC qty never contributes to money (`foc_qty` has no price). |
| `GRN_CALC_002` (line discount) | `discount_amount` is the amount sent by the client (must be `≤ received_price × received_qty`, `GRN_VAL_008`); `discount_rate` / `is_discount_adjustment` are stored but not used by the server-side chain. |
| `GRN_CALC_003` (line net) | `net_amount = Round5(sub_total_price − discount_amount)`. |
| `GRN_CALC_004` (line tax) | `tax_amount` is the amount sent by the client (must be `≤ received_price × received_qty`); `tax_rate` / `is_tax_adjustment` are snapshots. **No tax-inclusive branch exists in the backend** — the PRD's tax-inclusive variant is not implemented. |
| `GRN_CALC_005` (line total) | `total_price = Round5(net_amount + tax_amount)`. |
| `GRN_CALC_006` (variance) | Deviation is measured as percent **overage** only: `qty: (received_base_qty − order_base_qty) / order_base_qty × 100`; `price: (received_price/received_factor − order_price/order_factor) / (order_price/order_factor) × 100`; shortfalls score `0` (`percentOverage`, `deviation.ts:62-63`, compared at 5 dp). Feeds `GRN_VAL_006` / `GRN_VAL_007`; nothing is written back to the row. |
| `GRN_CALC_007` (header roll-ups) | `tb_good_received_note.net_amount / base_net_amount / total_amount / base_total_amount` are recomputed from the live receipt events by `recalculateGrnTotals()` (`service.ts:3513`) after every create / update, and can be forced with `POST …/good-received-notes/:id/regenerate-totals` (or `…/regenerate-totals` for all). Extra-cost amounts are **not** in the header totals. |
| `GRN_CALC_008` (base conversion) | `base_price = calcBase(received_price, exchange_rate)`; `base_sub_total_price`, `base_net_amount`, `base_total_price` likewise from their transaction-currency counterparts (`pricing.ts:55-58`); `base_discount_amount` / `base_tax_amount` from the client amounts. |
| `GRN_CALC_009` (extra-cost total) | `extra_cost_total = Σ tb_extra_cost_detail.amount` over the GRN's live extra-cost headers (document currency, **excluding** the detail's own `tax_amount`), using the mode of the **oldest** header (`applyExtraCostShares`, `ledger.ts:100-133`). |
| `GRN_CALC_010` (extra-cost — `by_value`) | `share_i = splitByWeight(extra_cost_total, weights = stock_qty_i)` where `stock_qty_i = received_base_qty_i + foc_base_qty_i`; lines with `stock_qty = 0` get no share (`allocateExtraCost`, `extra-cost.ts:49-58`). **Despite the name, `by_value` weights by quantity, not by line value.** |
| `GRN_CALC_011` (extra-cost — `by_qty`) | `share_i = extra_cost_total / n` — one **equal** share per line that puts stock on hand, regardless of size. **Despite the name, `by_qty` ignores quantities.** |
| `GRN_CALC_012` (extra-cost — `manual`) | No allocation (`allocation = ∅`); the extra cost is stored but does not reach the ledger. A per-line manual entry field does not exist yet. |
| `GRN_CALC_013` (landed cost — costing feed) | Per receipt event: `stock_qty = received_base_qty + foc_base_qty`; `stock_cost = base_net_amount + calcBase(share, exchange_rate)`; `cost_per_unit = Round2(stock_cost / stock_qty)`; `tb_inventory_transaction_detail.{qty, cost_per_unit, total_cost} = {stock_qty, cost_per_unit, stock_cost}`. The cost layers are then produced by `splitFifoCost(stock_qty, stock_cost, 2)` (exact-decimal reconciliation across one or more layer rows) and the extra-cost share is split across the same layers by quantity into `extra_cost_amount` (`inventory-transaction.service.ts:965-1002`). Events with `received_base_qty = 0` are dropped before posting (`:849`). |
| `GRN_CALC_014` (rounding mode) | Money chain: 5 dp (`ROUNDING_SCALE = 100000`). Deviation percentages: 5 dp. Ledger `cost_per_unit`: 2 dp. Display: currency 2 dp, quantity 3 dp, exchange rate always 5 dp (FE `35391bf5`). |

### 3.1 Worked example (฿ THB transaction currency)

Two lines, vendor in THB, `exchange_rate = 1.00000` (no FX), both products in a base unit with conversion factor 1, one extra-cost line allocated `by_value`.

- **Line 1** (one receipt event): `received_qty = 10.000`, `received_price = ฿125.50`, client sends `discount_amount = ฿62.75` (5%), `tax_amount = ฿83.46` (7% on net).
  - `sub_total_price = 125.50 × 10.000 = ฿1,255.00`
  - `net_amount = 1,255.00 − 62.75 = ฿1,192.25`
  - `total_price = 1,192.25 + 83.46 = ฿1,275.71`
- **Line 2** (one receipt event): `received_qty = 4.000`, `received_price = ฿89.00`, `discount_amount = ฿0.00`, `tax_amount = ฿24.92`.
  - `sub_total_price = ฿356.00`; `net_amount = ฿356.00`; `total_price = ฿380.92`
- **Extra cost** (`Σ tb_extra_cost_detail.amount = ฿200.00`, `allocate_extra_cost_type = by_value` → weighted by stock quantity 10 : 4):
  - Line 1 share: `200.00 × 10 / 14 = ฿142.85714`
  - Line 2 share: `200.00 × 4 / 14 = ฿57.14286` (`splitByWeight` reconciles so the shares sum exactly to ฿200.00)
  - Had the mode been `by_qty`, each line would get `฿100.00` regardless of quantity; had it been `manual`, neither line gets anything.
- **Header roll-up**: `net_amount = ฿1,548.25`; `total_amount = ฿1,656.63` (extra cost excluded).
- **Ledger feed** (Line 1, `foc_qty = 0`): `stock_cost = 1,192.25 + 142.85714 = ฿1,335.10714`; `cost_per_unit = Round2(1,335.10714 / 10) = ฿133.51`; cost layer(s): `in_qty = 10`, `total_cost ≈ ฿1,335.11`, `extra_cost_amount ≈ ฿142.86`.

If Line 1 also carries `foc_qty = 1.000` on the same event, `stock_qty = 11` and `cost_per_unit = Round2(1,335.10714 / 11) = ฿121.37` — the FOC unit enters stock at the diluted landed cost, and (because the weights are stock quantities) Line 1's extra-cost share rises to `200 × 11/15 = ฿146.67`.

## 5. Posting Rules

Status values are the literal members of `enum_good_received_note_status` documented in [good-receive-note/01-data-model](/en/inventory/good-receive-note/01-data-model) § 4: **`draft`**, **`saved`**, **`committed`**, **`voided`**. The full lifecycle is `draft → saved → committed`, with `voided` as an administrative escape from `draft` or `saved`. **Re-verified 2026-09-22:** the posting event is **`saved → committed`** (`commit()` / `approve()` → `postReceipt()`, `logic.ts:228-270`), which writes the ledger **and** advances the PO. On business units with `calculation_method = average`, `save()` already writes the ledger half (`logic.ts:105-143`) so the average moves immediately; the PO half still waits for commit. There is no `pending_approval`, `approved`, `rejected`, `closed`, or `cancelled` value at the Prisma level (legacy carmen/docs `GRNStatus` enum is divergent — see [good-receive-note/01-data-model](/en/inventory/good-receive-note/01-data-model) § 5 item 1).

Rule IDs follow `GRN_POST_NNN`.

| Rule ID | Transition / Event | Effects |
| ------- | ------------------ | ------- |
| `GRN_POST_001` | Create (→ `draft`) | Insert `tb_good_received_note` with `doc_status = draft`, `doc_version = 0`, `grn_no = draft-{seq}` (per-tenant counter in `tb_application_config`), `received_by_*` stamped from the caller, totals recomputed from the lines (`recalculateGrnTotals`). Sends a "GRN created" notification (`sendGRNCreatedNotification`). No inventory, no GL, no PO impact. |
| `GRN_POST_002` | Save (`draft → saved`) | `GoodReceivedNoteLogic.save()`: runs `GRN_VAL_006`–`GRN_VAL_009`; **spends the real running number** (`assignRunningGrnNo` → `generateGRNNo(grn_date)`), then `doc_status = saved`; stamps `received_by_*` if still empty. **Average-costed units only:** checks `GRN_VAL_002`, then `postGrnLedger(…, atSave = true)` writes the movement per `GRN_POST_004` and marks `tb_inventory_transaction.info = { posted_at_save: true, po_receiving_applied: false }`. **FIFO units:** no stock effect. **Never** touches the PO. |
| `GRN_POST_003` | Commit / Approve (`saved → committed`) — **the posting event** | `commit()` (`PATCH …/commit`) and `approve()` (`POST …/approve`): require `saved`, re-check `GRN_VAL_002` (a draft created in an open period may be committed after that period closed), then in one transaction `postReceipt()`: (a) if no receipt event carries `inventory_transaction_id`, write the movement per `GRN_POST_004`; (b) if `doc_type = purchase_order` and the PO half is still pending (either nothing was posted before, or the header carries `posted_at_save = true && po_receiving_applied != true`), advance the PO per `GRN_POST_005`; (c) stamp `po_receiving_applied = true` on the header. Then `doc_status = committed` (with optional `doc_version` check on commit). Idempotent: a retried commit neither double-posts stock nor double-counts the PO. Legacy `saved` GRNs posted under the pre-2026-08 save-time rule carry no mark and are treated as "PO already applied" (`isPurchaseOrderReceivingPending`, `ledger.ts:191-203`). |
| `GRN_POST_004` | Ledger write (cross-ref [inventory](/en/inventory/inventory), [costing](/en/inventory/costing)) | `postGrnLedger()` → `InventoryTransactionService.createFromGoodReceivedNote()` (`inventory-transaction.service.ts:841-884`): drop events with `received_base_qty = 0`; resolve the period **by `grn_date`** (`resolvePeriodForDate`, throws if none open); insert one `tb_inventory_transaction` header (`inventory_doc_type = good_received_note`, `inventory_doc_no = grn.id`); per event insert one `tb_inventory_transaction_detail` (`qty = received_base + foc_base`, `cost_per_unit` per `GRN_CALC_013`, `current_lot_no = <location_code><YYMM><run>`, `good_received_note_detail_item_id`) and its cost layer(s) with `transaction_type = good_received_note`, `lot_seq_no` (period-scoped), `lot_at_date = grn_date`, `period_id`, `at_period`, `extra_cost_amount`; then set the event's `inventory_transaction_id`. **FIFO:** `average_cost_per_unit = 0` on the new layers. **Average:** the product's new average (`calculateNewAverageCost` over all of the product's live layers, **per product across locations**, 2 dp) is written on the new layers and re-stamped on every existing non-direct layer of the product. **Direct locations** (`tb_location.location_type = direct`): the receipt is immediately issued back out under the same header (`createDirectExpenseOut`) and excluded from the average. No branch on the header's `post_type`. |
| `GRN_POST_005` | Commit — PO side (cross-ref [purchase-order](/en/inventory/purchase-order)) | `updatePurchaseOrderReceiving()` (`logic.ts:500-541`): for each event with a `purchase_order_detail_purchase_request_detail_id` and `received_qty > 0 || foc_qty > 0`, increment the junction row's `received_qty` **and** its FOC-received quantity (`incrementJunctionReceivedQty(…, receivedQty, …, focReceivedQty)`, junction rows row-locked first), and increment `tb_purchase_order_detail.received_qty` by `received_qty`. Then per affected PO (`updatePoStatuses`, `:543-570`): `po_status = completed` if every active line satisfies `received_qty ≥ order_qty − cancelled_qty`, else `partial`. |
| `GRN_POST_006` | ~~Commit — GL accrual for AP-pending~~ | **Not implemented.** No journal-entry, ledger, or GL-account code exists anywhere in `good-received-note.service.ts` / `good-received-note.logic.ts` — a repo-wide search for `journal`, `ledger`, and `accounts_payable` returned zero hits. Treat "Dr Inventory / Cr GRN Clearing" as design intent, not implemented behavior. |
| `GRN_POST_007` | ~~Commit — three-way-match anchor~~ | **Not implemented.** No vendor-invoice entity, capture screen, or match algorithm was found in `carmen-turborepo-backend-v2` or `carmen-inventory-frontend-react` (search terms `three-way`, `vendor_invoice`, `VendorInvoice`, `tb_invoice` — zero hits). Mirrors the identical finding already confirmed for the `purchase-order` module. |
| `GRN_POST_008` | ~~Three-way match success~~ | **Not implemented.** Same finding as `GRN_POST_007` — no AP module exists in current source to run this match. |
| `GRN_POST_009` | ~~Three-way match failure~~ | **Not implemented.** Same finding as `GRN_POST_007`/`GRN_POST_008`. |
| `GRN_POST_010` | Void / Reject (`DELETE …/void`, `POST …/reject`) | **Corrected 2026-09-22.** `voidGrnById()` (`service.ts:2231-2270`) refuses `voided` and `committed` GRNs; `reject()` (`logic.ts:406-450`) refuses anything but `draft` / `saved`. Both then call `voidGrnLedger()` (`ledger.ts:298-377`): if the GRN's live movement carries `posted_at_save = true`, refuse when any received lot has an out-layer elsewhere (`GRN_RECEIPT_ALREADY_CONSUMED`), otherwise soft-delete the movement header and its cost layers, null the events' `inventory_transaction_id`, and re-stamp the products' average (`restampAverageCostForProducts`). Legacy movements without the mark are left untouched. Then `voidGrn()` sets `doc_status = voided` and appends the reason to `note`. `reject` additionally notifies the creator. Because the PO is only advanced at commit, neither path needs to (or does) touch the PO. |
| `GRN_POST_011` | Soft delete | `deleted_at = now()`, `deleted_by_id = user`. Permitted only at `draft` (`GoodReceivedNoteService.delete()` rejects any other status). Row remains in the database; the `@@unique([grn_no, deleted_at])` index lets a new GRN reuse the same `grn_no`. |
| `GRN_POST_012` | ~~End-of-period auto-commit~~ | **Not implemented.** No batch-commit or scheduled-job code exists for this module (re-checked 2026-09-22; `micro-cronjobs` has no GRN job). |
| `GRN_POST_013` | PATCH on an average-costed `saved` GRN | `repostGrnLedgerIfChanged()` (`ledger.ts:434-459`), called at the end of `update()` (`service.ts:1919`): if the live movement carries `posted_at_save = true` and `po_receiving_applied != true`, rebuild the ledger items from the document and compare per event (`qty`, `total_cost`, 5-dp epsilon); when they differ, `voidGrnLedger()` then `postGrnLedger(…, atSave = true)`. Committed GRNs are never re-posted. |

State diagram (Prisma-canonical):

```
[*] → draft ──save──► saved ──commit / approve──► committed
        │  (AVG: ledger)        (ledger if not yet + PO advance)
        ├──void/reject──► voided
        └──delete (soft)
                saved ──void/reject──► voided   (AVG: ledger unwound, unless a lot was consumed → 409)
```

`committed` and `voided` are terminal; `committed` cannot be voided (`GRN_COMMITTED_NOT_VOIDABLE`). `draft` accepts soft-delete.

### 5.1 Status Lifecycle — Live UI vs BRD Mapping

The Prisma enum `enum_good_received_note_status` documented above is what the live UI uses. No formal BRD `FR-XXX` identifier has been assigned to the GRN status specification in the available source documents — the closest references are the `grn-master-prd.md` 3-state model and `GRN-Technical-Specification.md` 5-state enum, both divergent from Prisma (see [good-receive-note/01-data-model](/en/inventory/good-receive-note/01-data-model) § 5 item 1). The table below maps every observable live-UI status to its PRD / Technical Spec equivalent so testers and developers can reconcile the two without ambiguity. Source: `Test_case/System_Process/tx-01-grn.md` (capture date 2026-04-27).

| Live UI status | PRD / Technical Spec equivalent | Diff | Notes |
|---|---|---|---|
| `draft` | _(absent in tx-01-grn.md)_ | 🔴 new in live UI | PRD describes `Received → Committed`; no Draft state appears. Prisma default is `draft`. Editable (may be stored incomplete); placeholder number `draft-{seq}`; no stock or PO impact. |
| `saved` | `Received` (grn-master-prd.md 3-state model) | 🟡 renamed | PRD labels this state `Received`. Live UI calls it `saved` (validated, numbered, read-only in the UI). **On average-costed units the stock movement is already posted at this state**; on FIFO units it is not. The PO is not yet advanced on either. |
| `committed` | `Committed` | ✅ match | Terminal lock state and **the posting event** (`GRN_POST_003`–`GRN_POST_005`): ledger written (if not already at save) and PO advanced. No GL accrual — the GL module exists but is not called. Not voidable. |
| `voided` | _(absent in tx-01-grn.md)_ | 🔴 new in live UI | Pre-commit administrative cancellation. Not present in `Test_case/System_Process/tx-01-grn.md` status flow string. |

> ⚠️ **Discrepancy — no Draft state in Test_case:** `Test_case/System_Process/tx-01-grn.md` records the status flow as `Received → Committed` with no `Draft` state. The live Prisma schema opens with `draft` as the default creation state before `saved` (≈ `Received`). Testers should expect to see `draft` GRNs in the UI that tx-01-grn.md does not explicitly document. Source: `Test_case/System_Process/tx-01-grn.md` (capture date 2026-04-27).

> ⚠️ **Discrepancy — two creation paths:** `Test_case/System_Process/tx-01-grn.md` BR-01 documents both PO-linked and standalone (manual) GRN creation, consistent with `enum_good_received_note_type { purchase_order, manual }`. The PRD and Technical Spec only describe the PO-sourced path. Testers must cover both paths; the standalone path sets `doc_type = manual` and writes no `purchase_order_detail_id` on any line. Source: `Test_case/System_Process/tx-01-grn.md` (capture date 2026-04-27).

> ℹ️ **Note — no BRD FR-XXX identifier:** Unlike the PO module (`FR-PO-005`), no formal BRD requirement ID has been assigned to the GRN status specification in available source documents. The column heading above references `grn-master-prd.md` prose rather than a versioned BRD identifier.

> ⚙️ **Server-side rule — mobile list is `draft`-only:** The GRN list endpoint applies a device-gated view filter, `applyMobileGrnDocStatusFilter(paginate, appId)`, where the calling device is resolved from the `x-app-id` request header against the app allowlist. When the device is `mobile`, the list is forced to `doc_status = draft` only — any other `doc_status` filter on the request is stripped and replaced with `doc_status|enum = draft`. On non-mobile (desktop) devices the list is unchanged: all statuses (`draft`, `saved`, `committed`, `voided` as applicable) are returned. This is a **VIEW restriction, not a document-status rule** — a non-`draft` GRN still exists in the database and is reachable directly; it is simply not surfaced in mobile list views. Enforced server-side at the backend gateway (`carmen-turborepo-backend-v2`, helper `apps/backend-gateway/src/common/helpers/mobile-grn-doc-status-filter.ts`); **not present in the original PRD or Technical Spec.**
