# Good Receive Note (GRN) — Test Scenarios — Receiver

> **At a Glance**
> **Persona:** Receiver (Store Keeper / Receiving Clerk + Inventory Manager) &nbsp;·&nbsp; **Module:** [good-receive-note](/en/inventory/good-receive-note) &nbsp;·&nbsp; **Scenarios:** ~24
> **Categories:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **E2E coverage:** maps to `501-grn.spec.ts` in `../carmen-inventory-frontend-e2e/`
> **Re-verified 2026-09-22:** mutation timing corrected again — **commit** (`saved → committed`) posts inventory and advances the PO; on **average-costed business units** save already posts inventory (PO still at commit); void/reject unwind that early movement. Rule IDs below follow the rewritten [02-business-rules.md](./02-business-rules.md) §2 (`GRN_VAL_002`, `006`–`014`).

> **Executable coverage:** spec `../carmen-inventory-frontend-e2e/tests/501-grn.spec.ts` (76 cases; 57 without assertions per `docs/test-cases/SPEC-HEALTH.md`); gap reports `docs/test-cases/gaps/501-grn-core-gap.md` (62 cases with failing oracles) and `docs/test-cases/gaps/501-grn-from-po-gap.md` (24 wizard cases). No `501-grn-core.md` catalog page exists. The scenarios below are not mirrored there.

This page captures the test scenarios that the Receiver persona (the **Store Keeper / Receiving Clerk** at the dock plus the **Store Manager / Inventory Manager** who commits) directly drives in the `good-receive-note` module. The Receiver's involvement begins when a PO arrives at `po_status ∈ {approved, sent_or_print, partial}` (or, for `doc_type = manual`, when an ad-hoc receipt occurs) and ends when the GRN leaves the receiver zone — through `committed` (posted and locked), `voided` from `draft` / `saved`, or a flagged variance handed off to the Purchaser. Scenarios are grouped into **happy paths** (the state walk `draft → saved → committed` on FIFO and average units, manual GRN, partial GRN, expiry capture, short receipt, void with unwind), **RBAC** (permission keys), **validation** (negative tests against the real save / commit / void checklists), and **edge cases** (deviation boundaries, decimal precision, concurrent commits, multi-PO consolidation).

## 2. Permission / Authorization

| # | Scenario | Expected behaviour (allow/deny + reason) |
| - | -------- | --------------------------------------- |
| RCV-PERM-01 | User with `procurement.goods_received_note.create` + `.update` creates a GRN and saves a draft | **Allow.** `POST …/good-received-notes` (guard `goodReceivedNote.create`) and `PATCH …/:id` (`goodReceivedNote.update`); Save-draft stores an incomplete document. Maps to TC-GRN-030001 / TC-GRN-070001. |
| RCV-PERM-02 | User with `procurement.goods_received_note.commit` saves (`draft → saved`) and commits (`saved → committed`) | **Allow.** Both `PATCH …/save` and `PATCH …/commit` sit behind the **same** gateway guard `goodReceivedNote.commit` (`good-received-notes.controller.ts:1369,1626`). |
| RCV-PERM-03 | User **without** the commit permission tries to save or commit | **Deny — 403 from `AppIdGuard('goodReceivedNote.commit')`**; the **Save** and **Commit** buttons are hidden by the frontend permission check. There is no "Inventory Manager role" message — the denial is a permission-key denial. **Corrected 2026-09-22:** because save and commit share one key, a user who can save can also commit; a "Store Keeper may save but not commit" split cannot be configured today. Maps to TC-GRN-110002. |
| RCV-PERM-04 | Any user attempts to edit a `committed` GRN | **Deny.** Detail endpoints return `GRN_NON_DRAFT_NO_*_DETAIL`; the UI hides all edit affordances (`canEdit` false); comments and attachments remain allowed. Maps to TC-GRN-080005 and TC-GRN-090003. |
| RCV-PERM-05 | Segregation of duties — Receiver (GRN poster) vs Purchaser (PO buyer) | **Not implemented** (re-checked 2026-09-22): no `buyer_id` cross-check in `good-received-note.service.ts` / `.logic.ts`. |
| RCV-PERM-06 | Void a `draft` or `saved` GRN; attempt to void a `committed` one | **Allow** for `draft` / `saved` with `procurement.goods_received_note.delete` (`DELETE …/void`, guard `goodReceivedNote.delete`). **Deny** for `committed`: server returns `GRN_COMMITTED_NOT_VOIDABLE` (400) and the UI hides Void / Commit once committed (`grn-footer-action.tsx:27`). **Corrected 2026-09-22:** the guard is now server-side (the 2026-07-15 pass found only a UI guard). |
| RCV-PERM-07 | Mobile client lists GRNs | Requests whose `x-app-id` resolves to a `mobile` app get a forced `doc_status = draft` filter (`applyMobileGrnDocStatusFilter`); other statuses are not returned even if requested. Desktop clients see all statuses. |

## 3. Validation / Error

| # | Scenario | Trigger | Expected error |
| - | -------- | ------- | -------------- |
| RCV-VAL-01 | Unresolvable reference on create (`GRN_VAL_001` / `GRN_VAL_003`) | `POST …/good-received-notes` with a `vendor_id`, `purchase_order_detail_id`, or unit id that does not exist. | **Reject 404** with the unresolved-reference text ("Purchase order detail not found: …"); `POST …/verify` `{verify_state: "create", body}` lists `GRN_REFERENCE_NOT_FOUND` per id (and `GRN_UNIT_NOT_ALLOWED_FOR_PRODUCT` when the unit is not an order unit of the product). Maps to TC-GRN-030003 / 030004 / 050003. |
| RCV-VAL-02 | Received quantity without a price (`GRN_VAL_004`) | A line with `received_qty = 10` and no `received_price`. | **Reject** — `GRN_RECEIVED_PRICE_REQUIRED` ("received_price is required when received_qty is greater than 0"); the frontend blocks Save / Commit with "Unit price is required" (`grn-form-schema.ts:66-75`) but lets **Save draft** through. |
| RCV-VAL-03 | Save a GRN that is not `draft` (`GRN_VAL_009`) | `PATCH …/save` on a `saved`, `committed`, or `voided` GRN. | **Reject** — `GRN_ONLY_DRAFT_SAVABLE` (400). The UI never shows Save on a non-draft. |
| RCV-VAL-04 | Commit a GRN that is not `saved` (`GRN_VAL_010`) | `PATCH …/commit` directly on a `draft`. | **Reject** — `GRN_ONLY_SAVED_COMMITTABLE` (400); `verify` `{verify_state: "commit"}` reports the same. (The UI avoids this by chaining `/save` first.) Maps to TC-GRN-110003. |
| RCV-VAL-05 | Receipt date outside the open period (`GRN_VAL_002`) | `grn_date` in a `closed` period, or no period covering it; on an average unit click **Save**, on any unit click **Commit**. | **Reject 422** — `GRN_DATE_OUTSIDE_OPEN_PERIOD` ("The receipt date does not fall inside any open period"). `verify` `{verify_state: "create"}` flags it too. The commit dialog offers **move to open period** → `grn_date` rewritten to the period's `start_at`, after which the chain succeeds. |
| RCV-VAL-06 | Received unit not an order unit of the product (`GRN_VAL_003`) | Line with `received_unit_id` that has no conversion configured for the product. | **Reject** — conversion-factor enrichment fails ("no resolvable factor" message; `GRN_UNIT_NOT_ALLOWED_FOR_PRODUCT` on verify). Client-sent conversion factors are ignored. |
| RCV-VAL-07 | Over-receipt beyond the product's quantity ceiling (`GRN_VAL_006`) | Product `qty_deviation_limit = 5`; PO line `order_qty = 10`; Receiver enters `received_qty = 12` (20 % over). | **Reject at save** — `GRN_DEVIATION_LIMIT_EXCEEDED` (400) with `items: "<product> qty 20% > 5% (ordered 10, received 12)"`; the whole document is refused, nothing posts. With `qty_deviation_limit = 0` or `NULL` the same receipt is accepted — there is no tenant-wide tolerance. |
| RCV-VAL-07b | Over-price beyond the product's price ceiling (`GRN_VAL_007`) | Product `price_deviation_limit = 10`; `order_price = ฿100` per base unit; `received_price = ฿115`. | **Reject at save** — `GRN_DEVIATION_LIMIT_EXCEEDED`, `kind = price`, `field = received_price`. `received_price = ฿90` (cheaper) is accepted; a manual GRN (no `order_price`) is never checked. |
| RCV-VAL-07c | Discount or tax larger than the line (`GRN_VAL_008`) | Line `received_price × received_qty = ฿1,000`, `discount_amount = ฿1,200`. | **Reject at save** — `GRN_DISCOUNT_EXCEEDS_LINE_AMOUNT` (or `GRN_TAX_EXCEEDS_LINE_AMOUNT`) listing `<product> (line n)`. |
| RCV-VAL-08 | Void / reject after stock from the receipt was issued (`GRN_VAL_013`) | Average unit; `saved` GRN whose movement was posted at save; a store requisition has consumed 3 of the 10 received units. | **Reject 409** — `GRN_RECEIPT_ALREADY_CONSUMED` ("This receipt cannot be revised — stock received on it has already been issued"); document stays `saved`; a header PATCH that would change quantities is refused the same way (`repostGrnLedgerIfChanged`). |
| RCV-VAL-09 | Duplicate `(invoice_no, vendor_id)` | Two GRNs for the same vendor with the same `invoice_no`. | **Accepted.** No uniqueness rule exists in schema or code (re-checked 2026-09-22; the only unique index is `(grn_no, deleted_at)`). Worth a test precisely because the PRD claims otherwise. |

## 4. Edge Cases

| # | Scenario | Condition | Expected |
| - | -------- | --------- | -------- |
| RCV-EDGE-01 | Exact boundary on the quantity deviation ceiling | Product `qty_deviation_limit = 5`; PO line `order_base_qty = 10`; Receiver enters `received_qty = 10.5` (exactly 5 % over). | **Accepted** — `deviation (5.00000) ≤ limit (5)`; `received_qty = 10.501` is rejected per RCV-VAL-07. Comparison happens at 5 dp (`DEVIATION_SCALE = 100000`), so float noise cannot trip it. On commit `tb_purchase_order_detail.received_qty = 10.5 ≥ 10 − 0` → `po_status = completed`. |
| RCV-EDGE-02 | Decimal precision and rounding along the chain | `received_qty = 5.123`, `received_price = ฿33.333`, conversion factor `1.234567`, extra cost ฿7 `by_qty` on a single line. | `sub_total_price = 170.65946` (5 dp, `calcGrnItemPrices`); `received_base_qty = 5.123 × 1.234567`; ledger `cost_per_unit = Round2((base_net + 7) / stock_qty)`; cost layers reconcile to the exact `total_cost` (`splitFifoCost(…, 2)`); `extra_cost_amount` on the layer(s) sums to ฿7. |
| RCV-EDGE-03 | Concurrent commits on the same PO line from two sessions | GRN-A (`received_qty = 6`) and GRN-B (`received_qty = 4`) both `saved` against `PO-X` line `L1` (`order_qty = 10`); both users click **Commit** within the same second. | Both commits succeed: `updatePurchaseOrderReceiving` row-locks the junction rows (`lockJunctionRows`) and increments atomically, so `received_qty` ends at exactly 10 and `po_status = completed`; no double-count. A repeated commit of the same GRN is idempotent (`postReceipt` sees `inventory_transaction_id` and `po_receiving_applied`). Committing with a stale `doc_version` in the body returns `409`. |
| RCV-EDGE-04 | Multi-PO consolidation into a single GRN with one vendor / currency | Same vendor, same currency across `PO-A` (one line, pending 4) and `PO-B` (two lines, pending 6 each); vendor delivers a single truck covering both POs. | **One GRN with three lines spanning two POs.** Wizard step 2 multi-selects both POs (a mixed-currency selection is refused with the `mixedCurrencyError` toast, `from-po-content.tsx:93-95`); header inherits the shared vendor, currency, and exchange rate; three detail rows each carry their `purchase_order_detail_id`. **Commit** advances `received_qty` on three `tb_purchase_order_detail` rows in one transaction; `PO-A` → `completed`, `PO-B` → `completed` or `partial`. Maps to TC-GRN-040002 / 040004 (stubs) and gap cases `TC-GRN-040005`–`040028`. |
| RCV-EDGE-05 | FOC-only line vs FOC-only document | (a) GRN with one paid line and one line `received_qty = 0, foc_qty = 5`; (b) GRN whose only line is `received_qty = 0, foc_qty = 5`. | (a) Both lines post — the FOC line's ledger row has `qty = 5`, `cost_per_unit = 0` (plus any extra-cost share), and the PO junction's FOC-received counter is advanced by 5. (b) `createFromGoodReceivedNote` drops every item with `received_base_qty = 0` before posting (`inventory-transaction.service.ts:849`) → **no movement is written** and no `inventory_transaction_id` is set, yet the document still reaches `committed` and the PO FOC counter is still advanced. Document this inconsistency in the bug tracker rather than in a test expectation. |
| RCV-EDGE-06 | Edit an average-unit `saved` GRN through the API | Average unit; `saved` GRN with movement posted at save; `PATCH …/:id` changes a line's `received_qty` from 10 to 12 (server accepts — no status guard on the umbrella PATCH). | `repostGrnLedgerIfChanged`: old movement soft-deleted, new one posted (`posted_at_save = true`, PO still untouched), product average re-stamped. If the old lot was already consumed → 409 and the PATCH rolls back. |
