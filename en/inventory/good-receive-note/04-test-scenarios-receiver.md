# Good Receive Note (GRN) — Test Scenarios — Receiver

> **At a Glance**
> **Persona:** Receiver (Store Keeper / Receiving Clerk + Inventory Manager) &nbsp;·&nbsp; **Module:** [good-receive-note](/en/inventory/good-receive-note) &nbsp;·&nbsp; **Scenarios:** ~24
> **Categories:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **E2E coverage:** maps to `501-grn.spec.ts` in `../carmen-inventory-frontend-e2e/`
> **Corrected this pass (2026-07-15):** removed `accepted_qty` (no such field exists — see [01-data-model.md](./01-data-model.md)), batch-commit and end-of-period auto-commit scenarios (no matching code found), and the "post-commit reversal with elevated co-authorisation" scenario (the `/void` endpoint has no such gate). Fixed the mutation timing: **save** (`draft → saved`), not commit, is what posts inventory and advances the PO.

This page captures the test scenarios that the Receiver persona (the **Store Keeper / Receiving Clerk** at the dock plus the **Store Manager / Inventory Manager** who commits) directly drives in the `good-receive-note` module. The Receiver's involvement begins when a PO arrives at `po_status ∈ {sent, partial}` (or, for `doc_type = manual`, when an ad-hoc receipt occurs) and ends when the GRN leaves the receiver zone — either through `committed` (locked, no further module handoff confirmed), `voided` from `draft` / `saved`, or a flagged variance handed off to the Purchaser. Scenarios are grouped into **happy paths** (the state walk `draft → saved → committed`, manual GRN, partial GRN, lot/expiry capture, short-receipt variance), **RBAC** (Store Keeper vs Inventory Manager scope), **validation** (negative tests against `GRN_VAL_001`–`GRN_VAL_014`), and a small set of **edge cases** (tolerance boundaries, decimal precision, concurrent posts, multi-PO consolidation).

## 1. Happy Path

| # | Scenario | Pre-condition | Steps | Expected |
| - | -------- | ------------- | ----- | -------- |
| RCV-HP-01 | Create GRN against a single-line `sent` PO — `draft` row written | Source PO `PO-X` at `po_status = sent`, line `L1`: `order_qty = 10`, `received_qty = 0`, `cancelled_qty = 0`; vendor / currency / exchange rate snapshot present on the PO; Store Keeper `purchase@blueledgers.com` logged in with create-GRN permission. | 1. Navigate to `/procurement/goods-receive-note` → click **New GRN**. 2. Pick the vendor → pick `PO-X`. 3. Verify GRN header inherits `vendor_id`, `currency_id`, `exchange_rate` from the PO snapshot. 4. Verify line `L1` is pre-populated with `pending_qty = 10` as the default editable `received_qty`. 5. Stop without entering any data and back out. | `tb_good_received_note` row is persisted at `doc_status = draft`; `doc_type = purchase_order`; header fields populated from the PO snapshot; one `tb_good_received_note_detail` row is pre-staged referencing `purchase_order_detail_id = L1`; no `tb_inventory_transaction` row written yet (that happens at save, not at create); GRN appears in the list filtered by `draft` and is editable by the Store Keeper. Maps to TC-GRN-030001. |
| RCV-HP-02 | Save GRN for review — `draft → saved`, **the posting event** | RCV-HP-01 state plus: Receiver has entered `received_qty = 10` on `L1`, valid `received_unit_id` and `received_unit_conversion_factor > 0`, non-negative tax / discount / unit price. | 1. Document becomes visible to the Inventory Manager for review while remaining editable by the Receiver. Maps to the Save step of TC-GRN-030001 / TC-GRN-070001. |
| RCV-HP-03 | Inventory Manager commits GRN — `saved → committed`, **lock only** | RCV-HP-02 state; Inventory Manager logged in. | 1. Open the `saved` GRN. 2. Click **Commit**. | `doc_status = saved → committed`, `doc_version` incremented. **Corrected this pass:** no additional inventory write, cost-layer write, or PO-side effect was found in `commit()` — those all happened at RCV-HP-02. Commit's confirmed effect is that the document is now locked against further header/line edits. Maps to TC-GRN-110001. |
| RCV-HP-04 | Partial GRN — first half today, remainder later (PO drives `sent → partial`) | Source PO `PO-Y` at `po_status = sent`, line `L1`: `order_qty = 10`, `received_qty = 0`, `cancelled_qty = 0`; vendor delivers only 6 of 10 today; tenant permits partial receipt. | 1. Create GRN against `PO-Y`. 2. Enter `received_qty = 6`. 3. Save (posts inventory, advances PO) → Inventory Manager commits (locks). 4. When vendor delivers the remaining 4, repeat against the same PO: pending qty pre-populates as 4, enter `received_qty = 4`, save and commit. | Both GRNs persist as separate rows against the same PO line; after the first save, `tb_purchase_order_detail.received_qty = 0 → 6`, pending = 4, `po_status = sent → partial`; after the second save, `received_qty = 6 → 10`, pending = 0, `po_status = partial → completed`; inventory on-hand rises by `received_qty` on each save (6 + 4 = 10); two FIFO layers (or two weighted-average updates) recorded. Maps to TC-GRN-110004 (partial received GRN). |
| RCV-HP-05 | Manual GRN — no upstream PO, `doc_type = manual` | Tenant permits manual GRN; vendor `V-Z` active; no PO exists for this receipt. | 1. Navigate to GRN list → **New GRN** → choose **Manual**. 2. Enter vendor, currency, exchange rate, receipt date manually. 3. Add a line: product (from catalog), location, `received_qty`, receiving UoM, conversion factor, unit price. 4. Save (`draft → saved` — posts inventory). 5. Inventory Manager commits (locks). | GRN persists at `doc_type = manual`; no line carries `purchase_order_detail_id` (`GRN_VAL_004` second clause satisfied); on save, inventory transaction written, on-hand incremented, cost layer created; no PO line counter advance (no PO to advance). Maps to TC-GRN-050001. |
| RCV-HP-06 | Record lot number and expiry via the inventory-transaction linkage | RCV-HP-02 state, but the product is lot-tracked and flagged perishable; receiver has the physical lot label / expiry date from the vendor delivery note. | 1. Open the `draft` GRN line. 2. Open the lot / expiry sub-form on the line (which writes to `tb_inventory_transaction_detail` at save time, NOT to a column on the GRN line). 3. Accept the auto-generated `lot_no` (format `RC{YY}{MM}{4-digit sequence}`) or override manually. 4. Enter `expiry_date`. 5. Save the GRN. | Lot data is persisted on `tb_inventory_transaction_detail` (linked via `tb_good_received_note_detail_item.inventory_transaction_id`) at save; the recall trace from lot number back to this GRN works after save (no need to wait for commit). Maps to TC-GRN-140001 (stock movement view). |
| RCV-HP-07 | Short receipt at receiving — `received_qty < order_qty` saved with variance comment | Source PO `PO-Q` at `po_status = sent`, line `L1`: `order_qty = 10`, `received_qty = 0`; vendor delivers only 8 (2 short — damaged cartons refused at the dock). | 1. Save → Inventory Manager commits. | GRN posts `received_qty = 8`; inventory on-hand rises by `8` only at save; `tb_purchase_order_detail.received_qty = 0 → 8`, pending = 2, `po_status` stays `partial` for the unfulfilled 2 units. **Corrected this pass:** there is no separate `accepted_qty` field or per-line quality-inspection status — the shortfall is recorded purely by entering `received_qty = 8` instead of `10`; resolution (return / credit note) is coordinated with the vendor off-document. Maps to TC-GRN-080001 (Edit Line Item) variant. |
| RCV-HP-08 | Pre-commit void — Receiver / Inventory Manager voids a `saved` GRN with a reason | A `saved` GRN exists from an earlier shift; on review, the entire delivery is rejected (wrong vendor packaging, contamination). | 1. Open the `saved` GRN. 2. Click **Void**. 3. Enter the reason text. 4. Confirm in the void dialog. | `doc_status = saved → voided`; reason text persisted on the GRN. **Corrected this pass:** the inventory transaction, cost layer, and PO `received_qty` advance already written at the earlier save are **not** reversed by this action — `voidGrnById()` only updates `doc_status` and `note`. PO `received_qty` therefore stays at whatever it was advanced to at save; treat "no inventory or PO impact" claims for voiding a `saved` GRN as incorrect. Maps to TC-GRN-120001 (Void GRN — Happy Path). |

## 2. Permission / Authorization

| # | Scenario | Expected behaviour (allow/deny + reason) |
| - | -------- | --------------------------------------- |
| RCV-PERM-01 | Store Keeper creates GRN at `doc_status = draft` and saves to `saved` | **Allow.** Store Keeper owns the editable `draft → saved` transition, which is also the posting step. `New GRN`, line entry, lot data entry, attachment upload, and `Save` are all enabled on a non-committed GRN. Maps to the create / save half of TC-GRN-030001 / TC-GRN-070001. |
| RCV-PERM-02 | Inventory Manager commits a `saved` GRN (`saved → committed`) | **Allow.** Inventory Manager locks the document; server-side `commit()` requires `doc_status = saved`. |
| RCV-PERM-03 | Store Keeper attempts to commit a `saved` GRN | **Deny — Inventory Manager required.** The **Commit** button is hidden / disabled for the Store Keeper role; a direct API call returns `"Commit from status saved requires the Inventory Manager role."`; the document stays at `saved`. Maps to TC-GRN-110002 (No Permission to Commit). |
| RCV-PERM-04 | Any user attempts to edit a `committed` GRN | **Deny — terminal state.** `committed` is locked against header / line / lot / attachment edits (comments remain allowed). Edit endpoints reject with `"GRN at status committed is locked."` Maps to TC-GRN-080005 and TC-GRN-090003. |
| RCV-PERM-05 | Segregation of duties — Receiver (GRN poster) vs Purchaser (PO buyer) | **Unconfirmed.** A prior version of this row asserted a hard deny when the same user is both PO buyer and GRN poster (`PO_AUTH_010`-style rule). No `buyer_id` cross-check was found in `good-received-note.service.ts` or `good-received-note.logic.ts` during this pass — treat this control as design intent, not enforced. |
| RCV-PERM-06 | Void a `draft` or `saved` GRN | **Allow, with no server-side status guard.** The frontend only renders Void while `doc_status ∉ {committed, voided}`, but the `/void` endpoint itself (`voidGrnById`) only blocks re-voiding an already-`voided` GRN — it does not check `doc_status` otherwise. **Corrected this pass:** a prior version of this row described a "post-commit reversal requiring Inventory Manager + Finance co-authorisation" — no such gate, and no compensating reversal of any kind, was found in `voidGrnById()`. |

## 3. Validation / Error

| # | Scenario | Trigger | Expected error |
| - | -------- | ------- | -------------- |
| RCV-VAL-01 | Missing vendor at commit (`GRN_VAL_001`) | GRN at `doc_status = saved` with `vendor_id IS NULL` (left blank during multi-PO consolidation that never resolved a vendor); Inventory Manager clicks **Commit**. | **Reject** — `GRN_VAL_001`. Server returns `"Vendor is required and must be from the approved vendor list."` Maps to TC-GRN-030003 and TC-GRN-050003. |
| RCV-VAL-02 | Missing PO reference when `doc_type = purchase_order` (`GRN_VAL_004`) | GRN created via the PO-anchored path so `doc_type = purchase_order`; user manually clears the line's `purchase_order_detail_id` while editing; tries to save the line. | **Reject at save** — `GRN_VAL_004` first clause. Server returns `"PO reference is required for PO-sourced GRNs and must be absent for manual GRNs."` Maps to TC-GRN-030004 (Invalid PO). |
| RCV-VAL-03 | `received_qty = 0` AND `foc_qty = 0` on a line (`GRN_VAL_007`) | Receiver adds a line, leaves both `received_qty` and `foc_qty` at zero, clicks **Save**. | **Reject at save** — `GRN_VAL_007`. Server returns `"Each line must record either a received quantity or a free-of-charge quantity greater than zero."` Maps to TC-GRN-070002. |
| RCV-VAL-04 | Missing lot info for lot-tracked / perishable product at save (`GRN_VAL_012`) | `draft` GRN with a perishable, lot-tracked product on line `L1`; Store Keeper attempts to save without entering lot data. | **Reject.** Server returns `"Lot information is required for inventory items; line <seq> is missing lot data."` The Receiver must return to the line, open the lot sub-form (RCV-HP-06), and populate `lot_no` (auto or manual) and `expiry_date` before re-attempting save. **Note:** this page corrects "at commit" to "at save" per the actual posting timing; the exact call site enforcing this rule was not independently re-verified in this pass. |
| RCV-VAL-05 | Receive against a `voided` PO (`GRN_VAL_013`) | PO `PO-V` at `po_status = voided`; Receiver attempts to save a GRN whose line references that PO. | **Reject.** Server returns `"Cannot receive against PO <po_no>: PO status voided does not permit receiving."` Symmetrically blocked for `closed`, `completed`, `draft`, and `in_progress` POs. |
| RCV-VAL-06 | Receipt unit invalid / conversion factor ≤ 0 (`GRN_VAL_008`) | Receiver enters `received_qty = 10` but `received_unit_conversion_factor = 0`; tries to save. | **Reject at save** — `GRN_VAL_008`. Server returns `"Each receipt event must specify a valid receiving UoM with a positive conversion factor."` |
| RCV-VAL-07 | Over-receipt without tolerance enabled (`GRN_VAL_009`) | PO line `L1`: pending qty = 10; tenant over-receipt tolerance disabled (`0%`); Receiver enters `received_qty = 12` on a PO-anchored line. | **Reject at save** — `GRN_VAL_009`. Server returns `"Receipt quantity exceeds the pending quantity on PO line <po_no>:<seq>; over-receipt tolerance not enabled."` |
| RCV-VAL-08 | Duplicate `(invoice_no, vendor_id)` across non-soft-deleted GRNs (`GRN_VAL_005`) | Receiver enters `invoice_no = INV-001` on a GRN whose `vendor_id` already has a non-voided GRN with the same `invoice_no`. | **Reject at commit** — `GRN_VAL_005`. Server returns `"An invoice with this number has already been received from this vendor."` |

## 4. Edge Cases

| # | Scenario | Condition | Expected |
| - | -------- | --------- | -------- |
| RCV-EDGE-01 | Exact tolerance boundary on over-receipt | PO line `L1`: `order_qty = 10`; tenant over-receipt tolerance = `5%`; Receiver enters `received_qty = 10.5` (exactly at the upper bound). | **Accepted** — within tolerance (`10 × 1.05 = 10.5`); save succeeds; `tb_purchase_order_detail.received_qty = 0 → 10.5`; `po_status = sent → completed`. Setting `received_qty = 10.51` breaches the bound and is rejected per RCV-VAL-07. |
| RCV-EDGE-02 | Decimal precision on lot quantities | Line allows 3-dp precision; Receiver enters `received_qty = 5.123`; multi-lot capture sums to `received_qty` on the linked `tb_inventory_transaction_detail` rows (e.g. `lot A = 3.000`, `lot B = 2.123`); conversion factor `1.234567`. | **Accepted at storage.** `received_qty` and per-lot quantities stored at the line's UoM precision (3 dp); `received_base_qty = Round(received_qty × conversion_factor, 3)`; per-lot quantities must sum exactly to the line's `received_qty`. |
| RCV-EDGE-03 | Concurrent GRN saves on the same PO from two Receiver sessions | Receiver A and Receiver B both open `PO-X` (`received_qty = 0`, `order_qty = 10`); A saves `received_qty = 6` at `T`; B saves `received_qty = 4` at `T + 500ms` against the same line, both with `doc_version = N` snapshots. | **First save wins atomically.** A's GRN saves, `tb_purchase_order_detail.received_qty = 0 → 6`, `po_status = sent → partial`, `doc_version → N+1`. B's save is reconciled against the new state — either B's `received_qty = 4` saves cleanly against the fresh `pending_qty = 4`, or the optimistic-concurrency guard rejects B with a conflict message and B retries. No double-write, no `received_qty > order_qty` overflow outside tolerance. |
| RCV-EDGE-04 | Multi-PO consolidation into a single GRN with one vendor / currency | Same vendor, same currency across `PO-A` (one line, pending 4) and `PO-B` (two lines, pending 6 each); vendor delivers a single truck covering both POs. | **One GRN with three lines spanning two POs.** GRN created via the multi-PO wizard, which groups by vendor and currency (rejects a mixed-currency selection — confirmed in `grn-po-wizard-dialog.tsx`); header inherits the shared `vendor_id`, `currency_id`, `exchange_rate`; three GRN detail rows each carry their respective `purchase_order_detail_id`. Save advances `received_qty` on three different `tb_purchase_order_detail` rows in one transaction; `PO-A` flips `sent → completed`, `PO-B` flips `sent → completed` (or `partial` if not all lines fully received). Maps to TC-GRN-040002, TC-GRN-040004. |
