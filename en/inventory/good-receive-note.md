# Good Receive Note (GRN)

> **At a Glance**

> **Module purpose:** Records physical receipt of goods against a PO, posts stock-IN movements, and updates FIFO / average costing (`draft` → `saved` → `committed`, or `voided`)  ·  **Audience:** Store Keeper / Receiver, Inventory Manager, Purchaser  ·  **Key entities/tables:** `tb_good_received_note`, `tb_good_received_note_detail`, `tb_good_received_note_detail_item`, `tb_inventory_transaction`, FIFO / average-cost layers  ·  **Sub-pages:** 13
>
> **Re-verified 2026-10-27 against `carmen-turborepo-backend` `c9d788829` and `carmen-frontend` `391062b5`.** The posting model from 2026-09-22 still holds: stock posts at **`commit()`** (`saved → committed`, `good-received-note.logic.ts:170-215` → `postReceipt()` `:240-294`), and on **average-costed business units `save()` posts the stock movement early** (`postsInventoryAtSave()` → `isAverageMethod()`, `good-received-note.ledger.ts:55-57`, called from `logic.ts:104-149`); the PO is only advanced at commit. Two findings from the last round were re-checked: **"average units post at save" — still true** (and the rule now also covers the new `average_per_location` costing method), and **"a FOC-only GRN commits without a movement" — no longer true** (fixed on 2026-10-24 by `fc03b5718`; a line with only free goods now posts, see §3 FOC). New since 2026-09-22: **(a)** a `saved` GRN is **editable like a draft** except its vendor, its `grn_date`, and any line another document already depends on (the *stock lock*); on average units an edit re-posts only the lines that changed (`repostGrnLedgerIfChanged`, `ledger.ts:807-873`); a `committed` GRN keeps only the vendor-invoice header fields editable and is frozen once an active AP invoice has pulled it (`good-received-note.ap-link.ts`); **(b)** `tb_good_received_note.commit_date` is stamped on every move to `committed` (`updateGrnStatus`, `service.ts:3429-3445`; migration `20261016130000_grn_commit_date`); **(c)** under FIFO a receipt may not be dated before the latest receipt of the same product and location in the period (`GRN_DATE_BEFORE_LATEST_RECEIPT`); **(d)** an **Accounts Payable** module now exists (`apps/micro-business/src/ap/ap-invoice`; the React AP screens still run on a browser mock, `routes/accounting/accounts-payable/shared/ap-mock-repository.ts`) that matches `committed`, `post_type = ap` GRN lines and posts to the GL — the "no AP / no three-way match" statements on earlier versions of this page are retired (§1, §2, see [AP Invoice from GRN](/en/inventory/general-ledger/ap-invoice-from-grn)); the GRN itself still writes no journal. `approve()` (`POST …/approve`, `logic.ts:313-349`) is a second entry point for the same `saved → committed` posting. Voiding or rejecting an average-costed `saved` GRN unwinds the early movement (`voidGrnLedger()`, `ledger.ts:516-580`) and is refused if any received lot was already consumed or the void would leave a location negative.

## 1. Overview
A **Good Receive Note (GRN)** is the document that formally records the physical receipt of goods from a vendor and writes them into inventory. Each GRN has a header — GRN number, a **mandatory receipt date `grn_date`** (the separate `received_at` column was dropped by migration `20260907153500_drop_grn_received_at`; `grn_date` now carries that role and is `NOT NULL`), vendor, invoice number and date, currency and exchange rate, credit-term snapshot, a `post_type` (`ap` / `consignment` / `cash`), and an extra-cost header — and one or more item lines. Each line identifies the product and store location; the actual quantities, prices, and tax live on child receipt-event rows (`tb_good_received_note_detail_item`) so a single line can span multiple receipt events (split deliveries, paid-plus-FOC bundles). Each receipt event carries ordered quantity and **`order_price`** (the PO unit price, `NULL` on manual GRNs), received quantity and **`received_price`** (the unit price actually received — the single source of the line's money chain: `sub_total_price = received_price × received_qty`, `good-received-note.pricing.ts:40-60`), free-of-charge (FOC) quantity, discount, tax, and a computed line total; the header rolls these into net and grand-total figures in both transaction and base currencies. The receipt event also carries an optional **`expired_at`** (migration `20260731120000_add_inflow_price_expiry`). Lot number is **not** stored on the GRN row — the lot lives on `tb_inventory_transaction_detail`, which since migration `20260810180000_move_grn_lot_link_to_ledger` points **back** at the receipt event through `tb_inventory_transaction_detail.good_received_note_detail_item_id` (a real Prisma `@relation`, `schema.prisma:1254,1269`); the older `detail_item.inventory_transaction_id` column now only holds the movement **header** id and serves as the "already posted" flag (schema comment at `schema.prisma:1142-1143`). See [01-data-model.md](/en/inventory/good-receive-note/01-data-model) §2.3 and §5.

GRNs follow a four-state lifecycle on `enum_good_received_note_status`: `draft` (editable; drafts hold a `draft-{seq}` placeholder number, `good-received-note.service.ts:105,2381`) → `saved` (validated, real `grn_no` issued; **still editable** with the restrictions in §3 "Editing a saved GRN") → `committed` (posted; only the vendor-invoice header fields stay editable, until an AP invoice takes the GRN) → and `voided`, reachable from `draft` or `saved` only: a `committed` GRN is refused by the server (`GRN_COMMITTED_NOT_VOIDABLE`, `service.ts:2354`), and void/reject of any GRN that a live credit note references is refused (`assertGrnFreeOfCreditNotes`, `good-received-note.stock-lock.ts`). **The posting event is `saved → committed`** (`GoodReceivedNoteLogic.commit()` and `approve()` both call `postReceipt()`, `logic.ts:240-294`): that is where the `tb_inventory_transaction` rows and FIFO / average cost layers are written (`postGrnLedger()` → `InventoryTransactionService.createFromGoodReceivedNote()`) and where the source PO's junction rows, `tb_purchase_order_detail.received_qty`, and `po_status` (`partial` / `completed`) are advanced (`updatePurchaseOrderReceiving()`, `logic.ts:521-562`). The one exception is **average-costed business units** (`average` and `average_per_location`): there `save()` already writes the stock movement (`logic.ts:104-149`, marked `posted_at_save` on `tb_inventory_transaction.info`) so that the product's average moves the moment the receipt is known; commit then finds the movement already there and only applies the PO half. `save()`, `commit()`, and `approve()` each refuse a `grn_date` outside an `open`/`locked` inventory period (`assertDateInOpenPeriod`, `GRN_DATE_OUTSIDE_OPEN_PERIOD`, HTTP 422; `save()` only on average units), and on FIFO units also refuse a date earlier than the latest receipt of the same product at the same location in that period (`assertGrnInReceiptOrder`, `GRN_DATE_BEFORE_LATEST_RECEIPT`, HTTP 422, `receipt-date-order.helper.ts:164`). Once `committed`, corrections require a `tb_credit_note` against the GRN or a compensating [inventory-adjustment](/en/inventory/inventory-adjustment).

The GRN can be created from one or more purchase orders at `po_status ∈ {approved, sent_or_print, partial}` (`purchase-order.service.ts:836-846`) — multi-PO consolidation is supported when the selected POs share the same **vendor and currency** (`from-po-content.tsx:94-97` rejects a mixed-currency selection; no check on credit terms) — or manually for receipts with no upstream PO (`doc_type = manual`). The PO picker only offers what the caller may receive: the backend marks every PO, line, and delivery location with `can_use` according to the user's location grants (a line with no recorded location counts as unusable, `purchase-order.service.ts:1636-1652`), and the frontend disables rows where `can_use === false` (`grn-po-usable.ts`). Partial receipts are first-class — the GRN tracks received vs. ordered per line and, at commit, feeds `received_qty` (and the FOC quantity received) back to the source PO. **Corrected 2026-10-27:** earlier versions of this page said no vendor-invoice capture, AP posting, or three-way match exists. An **AP Invoice** document now does in the backend (`apps/micro-business/src/ap/ap-invoice`, tables `tb_ap_invoice*`; the frontend AP screens are a mock with no API calls — see [AP Invoice from GRN](/en/inventory/general-ledger/ap-invoice-from-grn)): each AP line can carry `tb_ap_invoice_detail_source` rows pointing at GRN detail items with `matched_qty`, `grn_unit_price`, `matched_amount`, and `variance_amount`; a source GRN must be live, `committed`, and `post_type = ap`, and the matched quantities across all non-void AP documents may not exceed the item's `received_qty` (`AP_GRN_NOT_COMMITTED`, `AP_GRN_OVER_MATCHED`; `ap-invoice.posting.ts:152-230,1100-1130`). Documenting the AP module itself is outside this page. The whole `routes/accounting` area (AP, `documents`) remains **mock data** that calls no API.

## 2. Business Context
The GRN is the control point where physical reality meets the books: until commit (or, on average-costed units, save) fires, a PO is only a commitment; once posted, stock on-hand and the cost layer are updated and — at commit — the source PO's `received_qty` advances. Hospitality operations run on tight food-cost margins and rely on this checkpoint to catch under-deliveries, over-deliveries, and price variances before they become inventory errors. Since 2026-08 the backend enforces two receiving controls of its own at save time: a **deviation ceiling** per product (`tb_product.price_deviation_limit` / `qty_deviation_limit`, both in percent; only the *overage* side is policed — a short delivery is a partial receipt, `good-received-note.deviation.ts:57-134`) and an **amount cap** (per-line discount and tax may not exceed `received_price × received_qty`, `good-received-note.validate.ts:42-69`). A PO/manual `doc_type` split and a locked post-commit state exist to make every receipt explainable. **Corrected 2026-09-22:** the `(invoice_no, vendor_id)` uniqueness rule cited on earlier versions of this page has **no** schema constraint and no code check — the only unique index on the header is `(grn_no, deleted_at)`.

**GL posting — precise status as of 2026-10-27.** The general-ledger module (`apps/micro-business/src/gl/`, tables `tb_gl_jv*`, `tb_gl_balance`) still has no hook in the GRN: `good-received-note.*.ts`, `inventory-transaction.service.ts`, and `period-end.*` import nothing from `@/gl`, and no code writes `enum_gl_jv_source.inventory` (`schema.prisma:4885`). What changed is that the **AP Invoice** and **AP Payment** modules now post journals into the GL with `source = ap` (`ap-invoice.posting.ts:291`, `ap-payment.posting.ts:228`) — that is how a received GRN reaches the ledger: GRN `committed` → AP invoice matched to it → AP posting. A separate read-only **external accounting-export API** (`inventory/accounting-export`, `GET /api/ext/v1/ap-invoices`) publishes `committed` GRNs (plus voided ones that had already posted) and credit notes as vendor-invoice documents for an outside accounting system, skipping `post_type = consignment` GRNs and consignment-location lines (`export-core.service.ts:194-228`, `builders/grn.ap-builder.ts`). The header's `post_type` enum (`ap` | `consignment` | `cash`, default `ap`) therefore now has two consumers — AP-invoice eligibility (`post_type = ap` only) and the export filter — but still changes nothing inside the GRN module itself; `enum_transaction_type` resolves every GRN receipt to the single value `good_received_note`.

Food-safety and quality control: every posted receipt gets a lot number and an optional expiry date. **Corrected 2026-09-22:** the lot number is built by `buildLotNo()` (`apps/micro-business/src/common/helpers/lot-number.helper.ts:27-35`) as **`<location_code><YYMM><4-digit run>`** — e.g. `MK-0126070246` — where the run number is the cost layer's `lot_seq_no`, which restarts at 1 in every inventory period (`getNextLotSeqNo`, `common/helpers/lot-seq-no.helper.ts` — the next run number is the highest `lot_seq_no` of the period **including soft-deleted layers**, so voiding a GRN cannot re-issue a lot number). The earlier `RC{YY}{MM}{seq}` format no longer exists, and there is no manual lot-number override on the GRN screen. The expiry date is captured on the receipt event (`tb_good_received_note_detail_item.expired_at`, nullable, deliberately not validated against `grn_date` so near- or past-expiry goods can still be received — schema comment at `schema.prisma:1196`). No per-line "quality hold" gate, `accepted_qty` field, or accept/reject mechanism exists — a receiving discrepancy is handled by entering less than the ordered quantity as `received_qty`. Price variance is checked against the **PO price** (`order_price` vs `received_price`, normalised to the base unit), not against the vendor pricelist; no pricelist lookup exists inside the GRN module.

## 3. Key Concepts
- **Receiving Lot**: A lot number assigned at posting on the inventory ledger (not on the GRN row), built as `<location_code><YYMM><4-digit run>` by `buildLotNo()` (`common/helpers/lot-number.helper.ts`); the run number is the period-scoped `lot_seq_no`. The ledger row (`tb_inventory_transaction_detail`) carries `good_received_note_detail_item_id` back to the receipt event, so FIFO consumption and recall traces resolve to the originating GRN line. **Corrected 2026-09-22:** the format is not `RC{YY}{MM}{seq}`, is not configurable, and has no manual override.
- **Partial Receipt**: A GRN that fulfils only part of an outstanding PO. Received quantities can be less than ordered, and at commit the source PO moves to `partial` (or `completed` once every active line satisfies `received_qty ≥ order_qty − cancelled_qty`, `updatePoStatuses`, `logic.ts:564-590`). Multiple GRNs can be raised against the same PO until it completes.
- **Over/Under Receipt**: Under-receipt never fails validation (`percentOverage` scores it 0, `deviation.ts:62-63`). Over-receipt is policed by the product's `qty_deviation_limit` (percent over `order_base_qty`; `0`/`NULL` = no ceiling) and over-price by `price_deviation_limit` (percent over `order_price` per base unit) — both evaluated at **save** and by `POST …/verify` with `verify_state = save`, and both reject the **whole document** (`GRN_DEVIATION_LIMIT_EXCEEDED`, HTTP 400). There is no tenant-wide "over-receipt tolerance" setting; the ceiling is per product master.
- **Save (`draft → saved`)**: Runs the save checklist (`findGoodReceivedNoteSaveIssues`, `validate.ts:91-103`: must be `draft`; then the content rules shared with later edits — deviation ceilings; discount/tax ≤ line value, `validate.ts:116-130`), spends the real running number (`assignRunningGrnNo`, `service.ts:2400-2418`), stamps `received_by_*` if empty, and — **only on average-costed business units** (`average`, `average_per_location`) — posts the stock movement early with `posted_at_save = true` on the movement header (unless the receipt is dated in a later period than the current one, in which case it waits for that period's brought-forward — `isHeldUntilBroughtForward`). FIFO units: no stock effect. The PO is never touched at save.
- **Editing a saved GRN** (changed 2026-10-24, `fc03b5718`, `a2218e077` before it): `PATCH` on a `saved` GRN is allowed (`checkGrnUpdateAllowed`, `good-received-note.ap-link.ts:122`). It refuses (i) any `doc_status` change (`GRN_STATUS_CHANGE_NOT_ALLOWED` — status moves only through save / commit / void / approve / reject), (ii) a changed `vendor_id` or `grn_date` (`GRN_SAVED_IDENTITY_LOCKED`, HTTP 400), and (iii) changes to a line another document depends on — its `lot` was drawn by an issue, or a live credit note references the product at that location, or the receipt's movement is a legacy one that an edit cannot re-post (`legacy_posting`) (`GRN_LINE_STOCK_LOCKED`, HTTP 409; and `GRN_COST_STOCK_LOCKED`, HTTP 409, for extra cost / currency / exchange-rate changes while any line is locked) — via `findGrnStockLocks()` (`good-received-note.stock-lock.ts:186`) / `assertStockLocksHeld()` (`:281`). The content rules save enforced are re-run on the edited document, and on average units `repostGrnLedgerIfChanged()` retires the ledger rows of changed lines (kept under a header created already-voided, `info.revised_from`) and posts only those lines afresh; unchanged lines keep their lot numbers. The detail response carries `has_stock_lock` and per-line `stock_lock_reasons` (`stock_consumed`, `credit_note`, `legacy_posting`), which the frontend turns into locked rows (`grn-form.tsx:52-61`). The frontend: vendor and date inputs are disabled on `saved`, currency / exchange rate / extra cost lock whole-document when any line is locked, there is no *Save draft* button and no Delete (backend deletes `draft` only), and Save sends `PATCH` only (`grn-header.tsx:56-67,150-179`).
- **Editing a committed GRN**: only `post_type`, credit-term fields, `invoice_no`, `invoice_date`, `invoice_f`, `payment_due_date`, `description`, and `note` may change (`HEADER_EDITABLE_KEYS`, `ap-link.ts:19-33`; anything else → `GRN_COMMITTED_HEADER_ONLY`). Once any non-void AP invoice has a line sourced from the GRN, even that is refused (`GRN_AP_LINKED_NOT_EDITABLE`, which names the AP document numbers); the detail response lists them in `ap_invoices`, and the frontend shows *Edit* disabled with the reason (`grn-header.tsx:60-65,167-175`). A `voided` GRN is never editable (`GRN_VOIDED_NOT_EDITABLE`).
- **Commit (`saved → committed`) — the posting event**: `commit()` / `approve()` re-check the open-period rule on `grn_date` (and, on FIFO, the receipt-order rule), then `postReceipt()`: (1) writes the `tb_inventory_transaction` header + one `tb_inventory_transaction_detail` and cost layer(s) per receipt event that moves stock — unless already written at save; (2) increments the PO↔PR junction row's `received_qty` and FOC-received qty and `tb_purchase_order_detail.received_qty`, then recomputes `po_status`; (3) stamps `po_receiving_applied` on the movement header so a retried commit cannot double-count; the status update also stamps `commit_date` (`service.ts:3441`). The frontend lets a **draft** be committed in one click — it chains `PATCH → /save → /commit` (`use-grn-form-actions.ts:550-565`) and, if `grn_date` is outside the current open period, asks whether to keep the date or move it to the period start (`PeriodDateChoice`, `components/share/period-date-choice.tsx`). No batch commit and no scheduled auto-commit exist.
- **Extra Cost Allocation — now confirmed live (2026-09-10, commit `f8cd9f0d9`)**: the extra-cost header's `allocate_extra_cost_type` drives a real split in `allocateExtraCost()` (`good-received-note.extra-cost.ts:40-61`) at posting time: **`by_qty` = the total is split into equal shares, one per line that puts stock on hand**; **`by_value` = shares weighted by each line's stock quantity (`received_base_qty + foc_base_qty`)**; **`manual` = nothing is allocated** (there is no per-line entry field yet). The share is converted to base currency and added to the line's landed cost (`stockCostOf() = base_net_amount + base_extra_cost_amount`, `inventory-transaction.service.ts:109-111`) and recorded on every cost layer as `extra_cost_amount` (migration `20260910130000_add_cost_layer_extra_cost`). Note the naming is counter-intuitive — `by_value` weights by quantity, `by_qty` splits evenly — document it as the code does it. The frontend offers only `by_qty` and `by_value` (`grn-extra-cost-fields.tsx:201-202`). No `by_weight` / `by_volume` mode exists.
- **FOC (Free of Charge)**: `foc_qty` on the same receipt event as the paid quantity. **FOC goes to stock**: the posted quantity is `received_base_qty + foc_base_qty` (`stockQtyOf()`, `inventory-transaction.service.ts:92-94`), so the unit cost written to the ledger is diluted (`(base_net_amount + extra cost) / (received + FOC)`, rounded to 2 dp). **A line that is FOC-only (paid quantity 0) posts to stock at zero goods cost** (plus any extra-cost share) and advances the PO's FOC-received counter (`logic.ts:530-535`). **Corrected 2026-10-27 (last round's finding is fixed):** the 2026-09-22 version of this bullet said `createFromGoodReceivedNote` first dropped items with `received_base_qty = 0`, so a FOC-only *document* committed without writing a movement while still advancing the PO FOC counter. `fc03b5718` (2026-10-24) changed the filter to `stockQtyOf(item) > 0` (`inventory-transaction.service.ts:927`; `isPostableReceipt()`, `ledger.ts:209-211`), so a FOC-only document now posts. A document with no stock quantity at all still writes no movement (`createFromGoodReceivedNote` logs a warning and returns `null`, `:929-939`).
- **`post_type` (ap / consignment / cash)**: A header-level enum (`enum_good_received_note_post_type`, default `ap`) that replaced an earlier `is_consignment` / `is_cash` boolean pair — those two boolean fields no longer exist in the schema. It is **editable on a committed GRN** (one of the vendor-invoice header fields). Inside the GRN module it still changes nothing (same movement type, no differentiated posting), but two consumers outside it read it: an AP invoice may only match GRNs with `post_type = ap` (`ap-invoice.posting.ts:1118-1122`), and the external accounting export skips `consignment` GRNs (`export-core.service.ts:228`). `enum_transaction_type` (the inventory-ledger type enum) has no "Stock In" / "Consignment In" / "Non-Inventory" members — a GRN receipt always posts as the single value `good_received_note`.

## 4. Roles and Personas
| Role | Responsibility |
| --- | --- |
| Store Keeper / Receiving Clerk | Receives the physical delivery at the dock, counts goods against the PO and the vendor delivery note, creates the GRN in `draft` status (a draft can be stored incomplete — the Save-draft button skips form validation, `use-grn-form-actions.ts:425-440`), attaches packing slips, records the receipt quantity per line, and saves (`draft → saved`: validates, issues the GRN number, posts stock early on average-costed units only). |
| Store Manager / Inventory Manager | Reviews the `saved` GRN and commits (`saved → committed`) — the step that posts stock (FIFO units) and advances the PO. Whether the same person may do both is a permission question: the gateway gates save and commit with the **same** guard key (`AppIdGuard('goodReceivedNote.commit')` on both `PATCH …/save` and `PATCH …/commit`, `good-received-notes.controller.ts:1375,1632`), and the frontend permission key is `procurement.goods_received_note.commit` (`constant/permissions.ts:89`). No role-name check exists. |
| Purchaser / Procurement Officer | Owns the upstream PO the GRN is created against, reviews receiving information for the POs they raised, and coordinates with the vendor on variances (short-ship, wrong item). |
| Department Manager | Reviews GRNs hitting the department's cost-centre and validates that received goods match what was ordered for the department. |
| System Administrator | Maintains RBAC and running-code (GRN-number) sequencing, tax codes, and currency rates; oversees the integration wiring with PO and Inventory. **Unconfirmed:** no dedicated "GRN configuration console" (lot-number-format editor, integration-endpoint panel) was found in current source — configuration surfaces for tax, currency, and running-code are generic, cross-module screens documented under [system-config](/en/inventory/system-config) and [master-data](/en/inventory/master-data), not a GRN-specific workspace. |

**Finance / AP persona — re-checked 2026-10-27.** A "Finance Team / AP Clerk" role running a three-way match from the GRN module is still not a GRN screen or role (`enum_stage_role` has no `finance` member; the GRN screens have no match or journal action). What exists now is a separate **Accounts Payable** area (`routes/accounting/accounts-payable`, backend `apps/micro-business/src/ap/`) in which an AP clerk creates an AP invoice sourced from `committed`, `post_type = ap` GRN lines (`ap-invoice.posting.ts:152-230`) — documented outside this module. From the GRN side its only effect is the freeze of the committed document described in §3 "Editing a committed GRN".

## 5. Related Modules
**Cross-module flow:**

- [purchase-order](/en/inventory/purchase-order) — GRN is created against a PO at `approved` / `sent_or_print` / `partial`; commit advances the PO's `received_qty` and `po_status`
- [inventory](/en/inventory/inventory) — commit (or save, on average-costed units) posts a stock IN movement; `GET …/good-received-notes/:id/stock-movements` (2026-08, `service.ts:2177`) returns the posted lots per line, and the frontend Stock Movement tab renders it only once the GRN is `committed` (`grnStockVisible()`, `grn-stock-table.tsx:35-45` — **committed, or `saved` on a BU whose method is `average` / `average_per_location`**, where the movement already exists; a held later-period receipt comes back with `is_posted: false`)
- [costing](/en/inventory/costing) — landed cost per line (net + allocated extra cost, over received + FOC qty) feeds FIFO lot records or the product / per-location average (`average` vs `average_per_location`); `GET …/cost/products/:product_id/last-receiving/unit/:unit_id` and `…/last-cost` (Bruno `_uncategorized/cost/`) read the last GRN price back
- [vendor-pricelist](/en/inventory/vendor-pricelist) — **no GRN-side integration**; price deviation is checked against the PO's `order_price`, not the pricelist
- [purchase-order/credit-note](/en/inventory/purchase-order/credit-note) — `GET …/good-received-notes/vendor/:vendor_id/cn` lists `saved`/`committed` GRNs that still have at least one un-credited product; since 2026-09-21 a product on a given GRN can be credited only once (`findFullyCreditedGrnIds`, `service.ts:561-617`)
