# Good Receive Note (GRN)

> **At a Glance**

> **Module purpose:** Records physical receipt of goods against a PO, posts stock-IN movements, and updates FIFO / average costing (`draft` → `saved` → `committed`, or `voided`)  ·  **Audience:** Store Keeper / Receiver, Inventory Manager, Purchaser  ·  **Key entities/tables:** `tb_good_received_note`, `tb_good_received_note_detail`, `tb_good_received_note_detail_item`, `tb_inventory_transaction`, FIFO / average-cost layers  ·  **Sub-pages:** 13
>
> **Re-verified 2026-09-22 against `carmen-turborepo-backend-v2` HEAD — the posting model moved again.** The 2026-07-15 pass found that `save()` posted stock and `commit()` only locked. That was true then; it is **no longer** what the code does. Commit `c815d67ce` ("ย้ายการลงสต๊อกจาก save() ไป commit()") moved stock posting **and** the PO `received_qty` advance to **`commit()`** (`saved → committed`, `good-received-note.logic.ts:165-203` → `postReceipt()` `:228-270`). Commit `7d6556dd0` then re-opened one exception: on business units whose `calculation_method = average`, **`save()` posts the stock movement early** (`postsInventoryAtSave()` in `good-received-note.ledger.ts:49-51`, called from `logic.ts:105-143`) so that issues made while the GRN waits in `saved` are valued at the new average; the PO is still only advanced at commit. Under **FIFO** nothing touches stock until commit. `approve()` (`POST …/approve`, `logic.ts:289-320`) is a second entry point for the same `saved → committed` posting. Voiding / rejecting an average-costed `saved` GRN now **does** unwind the early movement (`voidGrnLedger()`, `ledger.ts:298-377`) and is refused if any received lot was already consumed. The 2026-07-15 findings on three-way match and AP posting still hold for this module: no vendor-invoice capture or AP-journal code exists. What is new is a **general-ledger module** (`apps/micro-business/src/gl/`, gateway `application/gl-posting`, `gl-jv`) — it posts manual / template / reversal / closing journal vouchers only; **nothing in the GRN, inventory-transaction, or period-end code calls it** (see §2).

## 1. Overview
A **Good Receive Note (GRN)** is the document that formally records the physical receipt of goods from a vendor and writes them into inventory. Each GRN has a header — GRN number, a **mandatory receipt date `grn_date`** (the separate `received_at` column was dropped by migration `20260907153500_drop_grn_received_at`; `grn_date` now carries that role and is `NOT NULL`), vendor, invoice number and date, currency and exchange rate, credit-term snapshot, a `post_type` (`ap` / `consignment` / `cash`), and an extra-cost header — and one or more item lines. Each line identifies the product and store location; the actual quantities, prices, and tax live on child receipt-event rows (`tb_good_received_note_detail_item`) so a single line can span multiple receipt events (split deliveries, paid-plus-FOC bundles). Each receipt event carries ordered quantity and **`order_price`** (the PO unit price, `NULL` on manual GRNs), received quantity and **`received_price`** (the unit price actually received — the single source of the line's money chain: `sub_total_price = received_price × received_qty`, `good-received-note.pricing.ts:40-60`), free-of-charge (FOC) quantity, discount, tax, and a computed line total; the header rolls these into net and grand-total figures in both transaction and base currencies. The receipt event also carries an optional **`expired_at`** (migration `20260731120000_add_inflow_price_expiry`). Lot number is **not** stored on the GRN row — the lot lives on `tb_inventory_transaction_detail`, which since migration `20260810180000_move_grn_lot_link_to_ledger` points **back** at the receipt event through `tb_inventory_transaction_detail.good_received_note_detail_item_id` (a real Prisma `@relation`, `schema.prisma:1135,1150`); the older `detail_item.inventory_transaction_id` column now only holds the movement **header** id and serves as the "already posted" flag (schema comment at `:1022-1024`). See [01-data-model.md](/en/inventory/good-receive-note/01-data-model) §2.3 and §5.

GRNs follow a four-state lifecycle on `enum_good_received_note_status`: `draft` (editable; drafts hold a `draft-{seq}` placeholder number, `good-received-note.service.ts:90,2333-2339`) → `saved` (validated, real `grn_no` issued, locked for editing in the UI) → `committed` (posted and locked). `voided` is reachable from `draft` or `saved`; a `committed` GRN is now refused by the server itself (`GRN_COMMITTED_NOT_VOIDABLE`, `service.ts:2254-2256`). **The posting event is `saved → committed`** (`GoodReceivedNoteLogic.commit()` and `approve()` both call `postReceipt()`, `logic.ts:228-270`): that is where the `tb_inventory_transaction` rows and FIFO / average cost layers are written (`postGrnLedger()` → `InventoryTransactionService.createFromGoodReceivedNote()`) and where the source PO's junction rows, `tb_purchase_order_detail.received_qty`, and `po_status` (`partial` / `completed`) are advanced (`updatePurchaseOrderReceiving()`, `logic.ts:500-570`). The one exception is **average-costed business units**: there `save()` already writes the stock movement (`logic.ts:105-143`, marked `posted_at_save` on `tb_inventory_transaction.info`) so that the product's average moves the moment the receipt is known; commit then finds the movement already there and only applies the PO half. Both `save()` (average units), `commit()`, and `approve()` refuse a `grn_date` that falls outside an `open`/`locked` inventory period (`assertDateInOpenPeriod`, `GRN_DATE_OUTSIDE_OPEN_PERIOD`, HTTP 422). Once `committed`, corrections require a `tb_credit_note` against the GRN or a compensating [inventory-adjustment](/en/inventory/inventory-adjustment).

The GRN can be created from one or more purchase orders at `po_status ∈ {approved, sent_or_print, partial}` (`purchase-order.service.ts:811-816`; the PO enum was split on 2026-09-14 — `sent` became `sent_or_print` and a new `approved` value precedes it) — multi-PO consolidation is supported when the selected POs share the same **vendor and currency** (`from-po-content.tsx:93-95` rejects a mixed-currency selection; no check on credit terms) — or manually for receipts with no upstream PO (`doc_type = manual`). Partial receipts are first-class — the GRN tracks received vs. ordered per line and, at commit, feeds `received_qty` (and the FOC quantity received) back to the source PO. **Still not found (re-checked 2026-09-22):** no vendor-invoice capture, AP-journal posting, or three-way match (PO ↔ GRN ↔ invoice) exists in the frontend or backend; the `routes/accounting` area added to the frontend on 2026-07-31 renders **mock rows** generated in `routes/accounting/accounting-documents.ts` (`documentsFor()` fabricates 8 rows per document kind) and calls no API.

## 2. Business Context
The GRN is the control point where physical reality meets the books: until commit (or, on average-costed units, save) fires, a PO is only a commitment; once posted, stock on-hand and the cost layer are updated and — at commit — the source PO's `received_qty` advances. Hospitality operations run on tight food-cost margins and rely on this checkpoint to catch under-deliveries, over-deliveries, and price variances before they become inventory errors. Since 2026-08 the backend enforces two receiving controls of its own at save time: a **deviation ceiling** per product (`tb_product.price_deviation_limit` / `qty_deviation_limit`, both in percent; only the *overage* side is policed — a short delivery is a partial receipt, `good-received-note.deviation.ts:57-134`) and an **amount cap** (per-line discount and tax may not exceed `received_price × received_qty`, `good-received-note.validate.ts:22-61`). A PO/manual `doc_type` split and a locked post-commit state exist to make every receipt explainable. **Corrected 2026-09-22:** the `(invoice_no, vendor_id)` uniqueness rule cited on earlier versions of this page has **no** schema constraint and no code check — the only unique index on the header is `(grn_no, deleted_at)`.

**GL posting — precise status as of 2026-09-22.** A general-ledger module now exists in the backend (`apps/micro-business/src/gl/{gl-jv,gl-posting,gl-period,gl-budget,…}`; gateway `application/gl-jv`, `gl-posting`, `gl-reports`; tables `tb_gl_jv*`, `tb_gl_balance`, migrations `20260909170000_gl_core_master`, `20260914030000_gl_core_jv_ledger`). `GlPostingService.post()` (`gl-posting.service.ts:293`) posts a **journal voucher** (`tb_gl_jv`) into `tb_gl_balance`. The only code that creates JVs is the JV module itself (`gl-jv.service.ts:214`, source `manual`), template runs (`gl-jv-template.service.ts:786`), and the posting service's own reversal / closing vouchers (`gl-posting.service.ts:571,909,1116`). `enum_gl_jv_source` reserves `inventory` and `ap` members (`schema.prisma:4724-4736`) but **no code writes them**; a grep of `apps/micro-business/src` outside `src/gl/` for `GlPosting`, `gl-jv`, or `from '@/gl` hits only `app.module.ts` and the tenant seed set. `good-received-note.logic.ts`, `inventory-transaction.service.ts`, and `period-end.service.ts` import nothing from the GL module. **Conclusion: no GRN, inventory transaction, or period-end close posts to the GL ledger today.** A separate wiki page documents the GL module; here, keep treating "Dr Inventory / Cr AP" as not implemented. The header's `post_type` enum (`ap` | `consignment` | `cash`, default `ap`) is still stored and serialized but drives no branch anywhere in the backend; `enum_transaction_type` still resolves every GRN receipt to the single value `good_received_note`.

Food-safety and quality control: every posted receipt gets a lot number and an optional expiry date. **Corrected 2026-09-22:** the lot number is built by `buildLotNo()` (`apps/micro-business/src/common/helpers/lot-number.helper.ts:27-35`) as **`<location_code><YYMM><4-digit run>`** — e.g. `MK-0126070246` — where the run number is the cost layer's `lot_seq_no`, which restarts at 1 in every inventory period (`getNextLotSeqNo`, `inventory-transaction.service.ts:1399-1406`). The earlier `RC{YY}{MM}{seq}` format no longer exists, and there is no manual lot-number override on the GRN screen. The expiry date is captured on the receipt event (`tb_good_received_note_detail_item.expired_at`, nullable, deliberately not validated against `grn_date` so near- or past-expiry goods can still be received — schema comment at `:1076`). No per-line "quality hold" gate, `accepted_qty` field, or accept/reject mechanism exists — a receiving discrepancy is handled by entering less than the ordered quantity as `received_qty`. Price variance is checked against the **PO price** (`order_price` vs `received_price`, normalised to the base unit), not against the vendor pricelist; no pricelist lookup exists inside the GRN module.

## 3. Key Concepts
- **Receiving Lot**: A lot number assigned at posting on the inventory ledger (not on the GRN row), built as `<location_code><YYMM><4-digit run>` by `buildLotNo()` (`common/helpers/lot-number.helper.ts`); the run number is the period-scoped `lot_seq_no`. The ledger row (`tb_inventory_transaction_detail`) carries `good_received_note_detail_item_id` back to the receipt event, so FIFO consumption and recall traces resolve to the originating GRN line. **Corrected 2026-09-22:** the format is not `RC{YY}{MM}{seq}`, is not configurable, and has no manual override.
- **Partial Receipt**: A GRN that fulfils only part of an outstanding PO. Received quantities can be less than ordered, and at commit the source PO moves to `partial` (or `completed` once every active line satisfies `received_qty ≥ order_qty − cancelled_qty`, `logic.ts:543-570`). Multiple GRNs can be raised against the same PO until it completes.
- **Over/Under Receipt**: Under-receipt never fails validation (`percentOverage` scores it 0, `deviation.ts:62-63`). Over-receipt is policed by the product's `qty_deviation_limit` (percent over `order_base_qty`; `0`/`NULL` = no ceiling) and over-price by `price_deviation_limit` (percent over `order_price` per base unit) — both evaluated at **save** and by `POST …/verify` with `verify_state = save`, and both reject the **whole document** (`GRN_DEVIATION_LIMIT_EXCEEDED`, HTTP 400). There is no tenant-wide "over-receipt tolerance" setting; the ceiling is per product master.
- **Save (`draft → saved`)**: Runs the save checklist (`findGoodReceivedNoteSaveIssues`, `validate.ts:90-106`: must be `draft`; deviation ceilings; discount/tax ≤ line value), spends the real running number (`assignRunningGrnNo`, `service.ts:2392-2410`), stamps `received_by_*` if empty, and — **only on average-costed business units** — posts the stock movement early with `posted_at_save = true` on the movement header. FIFO units: no stock effect. The PO is never touched at save. The UI treats `saved` as read-only (`grn-header.tsx:81-82`: `canEdit = !isCommitted && !isVoid && !isSaved`); the backend `PATCH` has no status guard of its own, but detail add/update/delete endpoints are `draft`-only (`GRN_NON_DRAFT_NO_*_DETAIL`), and a PATCH on an average-costed `saved` GRN voids and re-posts its movement if quantities or costs changed (`repostGrnLedgerIfChanged`, `ledger.ts:434-459`).
- **Commit (`saved → committed`) — the posting event**: `commit()` / `approve()` re-check the open-period rule on `grn_date`, then `postReceipt()`: (1) writes the `tb_inventory_transaction` header + one `tb_inventory_transaction_detail` and cost layer(s) per receipt event that moves stock — unless already written at save; (2) increments the PO↔PR junction row's `received_qty` and FOC-received qty and `tb_purchase_order_detail.received_qty`, then recomputes `po_status`; (3) stamps `po_receiving_applied` on the movement header so a retried commit cannot double-count. The frontend lets a **draft** be committed in one click — it chains `PATCH → /save → /commit` (`use-grn-form-actions.ts:486-513`) and, if `grn_date` is outside the current open period, asks whether to keep the date or move it to the period start (`PeriodDateChoice`, `components/share/period-date-choice.tsx`). No batch commit and no scheduled auto-commit exist.
- **Extra Cost Allocation — now confirmed live (2026-09-10, commit `f8cd9f0d9`)**: the extra-cost header's `allocate_extra_cost_type` drives a real split in `allocateExtraCost()` (`good-received-note.extra-cost.ts:40-61`) at posting time: **`by_qty` = the total is split into equal shares, one per line that puts stock on hand**; **`by_value` = shares weighted by each line's stock quantity (`received_base_qty + foc_base_qty`)**; **`manual` = nothing is allocated** (there is no per-line entry field yet). The share is converted to base currency and added to the line's landed cost (`stockCostOf() = base_net_amount + base_extra_cost_amount`, `inventory-transaction.service.ts:90-92`) and recorded on every cost layer as `extra_cost_amount` (migration `20260910130000_add_cost_layer_extra_cost`). Note the naming is counter-intuitive — `by_value` weights by quantity, `by_qty` splits evenly — document it as the code does it. The frontend offers only `by_qty` and `by_value` (`grn-extra-cost-fields.tsx:201-202`). No `by_weight` / `by_volume` mode exists.
- **FOC (Free of Charge)**: `foc_qty` on the same receipt event as the paid quantity. **Since 2026-09-10 FOC goes to stock**: the posted quantity is `received_base_qty + foc_base_qty` (`stockQtyOf()`, `inventory-transaction.service.ts:73-75`), so the unit cost written to the ledger is diluted (`(base_net_amount + extra cost) / (received + FOC)`, rounded to 2 dp). A line that is FOC-only still posts to stock at zero cost and still advances the PO's FOC-received counter (`logic.ts:508-523`). Note `createFromGoodReceivedNote` first drops items with `received_base_qty = 0` (`inventory-transaction.service.ts:849`) — a FOC-only *document* therefore posts nothing; a FOC-only line inside a document that has at least one paid line is still posted by the per-item loop.
- **`post_type` (ap / consignment / cash)**: A header-level enum (`enum_good_received_note_post_type`, default `ap`) that replaced an earlier `is_consignment` / `is_cash` boolean pair — those two boolean fields no longer exist in the schema. **Unconfirmed:** no branching logic on `post_type` was found in the backend (no differentiated GL treatment, no distinct inventory-transaction type); the field is currently stored and exposed through the API but does not appear to change system behavior. `enum_transaction_type` (the inventory-ledger type enum) has no "Stock In" / "Consignment In" / "Non-Inventory" members — a GRN receipt always posts as the single value `good_received_note`.

## 4. Roles and Personas
| Role | Responsibility |
| --- | --- |
| Store Keeper / Receiving Clerk | Receives the physical delivery at the dock, counts goods against the PO and the vendor delivery note, creates the GRN in `draft` status (a draft can be stored incomplete — the Save-draft button skips form validation, `use-grn-form-actions.ts:400-411`), attaches packing slips, records the receipt quantity per line, and saves (`draft → saved`: validates, issues the GRN number, posts stock early on average-costed units only). |
| Store Manager / Inventory Manager | Reviews the `saved` GRN and commits (`saved → committed`) — the step that posts stock (FIFO units) and advances the PO. Whether the same person may do both is a permission question: the gateway gates save and commit with the **same** guard key (`AppIdGuard('goodReceivedNote.commit')` on both `PATCH …/save` and `PATCH …/commit`, `good-received-notes.controller.ts:1369,1626`), and the frontend permission key is `procurement.goods_received_note.commit` (`constant/permissions.ts:73`). No role-name check exists. |
| Purchaser / Procurement Officer | Owns the upstream PO the GRN is created against, reviews receiving information for the POs they raised, and coordinates with the vendor on variances (short-ship, wrong item). |
| Department Manager | Reviews GRNs hitting the department's cost-centre and validates that received goods match what was ordered for the department. |
| System Administrator | Maintains RBAC and running-code (GRN-number) sequencing, tax codes, and currency rates; oversees the integration wiring with PO and Inventory. **Unconfirmed:** no dedicated "GRN configuration console" (lot-number-format editor, integration-endpoint panel) was found in current source — configuration surfaces for tax, currency, and running-code are generic, cross-module screens documented under [system-config](/en/inventory/system-config) and [master-data](/en/inventory/master-data), not a GRN-specific workspace. |

**Removed this pass (no matching route, component, or endpoint found):** a "Finance Team / AP Clerk" role described as running a three-way match, validating extra-cost allocation pre-AP-posting, and signing off on receipt activity at period close. A repo-wide search of `carmen-turborepo-backend-v2` and `carmen-inventory-frontend-react` for `three-way`, `vendor_invoice`, `VendorInvoice`, and `tb_invoice` returned zero hits, and `enum_stage_role` (the workflow-stage-role enum shared with PR/PO) has no `finance` member — mirrors the same finding already confirmed for the `purchase-order` module.
