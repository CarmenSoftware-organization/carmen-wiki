# Period

> **At a Glance**
> **Owner:** Sysadmin / Finance Manager &nbsp;·&nbsp; **Table:** `tb_period` (+ `tb_period_snapshot`) &nbsp;·&nbsp; **Used by:** GRN, IA, count, spot-check, costing engine &nbsp;·&nbsp; The accounting calendar — gates back-dating and drives costing close &nbsp;·&nbsp; **Admin screen is a plain list + create/edit dialog — no dedicated Close/Lock/Reopen actions or Snapshot tab exist.**

![Period screen](/screenshots/system-config/period.png)

## Implementation status (verified 2026-07-16)

The `/system-admin/period` screen (`period-component.tsx` + `period-dialog.tsx`) is a **generic CRUD list**: search, status filter, Add/Export/Print, and a row-edit dialog with plain fields — `fiscal_year`, `fiscal_month`, `start_at`, `end_at`, and a **status `<Select>`** offering `open`/`closed`/`locked` directly, submitted the same way as any other field via `PATCH`. There is no distinct "Close" button, "Lock" button, "Reopen" button, confirmation/audit-reason prompt, or "Snapshot" tab anywhere in the component tree (no period-detail component exists at all in the directory — only the card, the list, and the dialog). Changing status is exactly as easy, and exactly the same UI action, as changing `fiscal_month`. The Common Tasks table below is corrected to reflect this; the enum values and posting-guard semantics themselves (§5, §6) are unaffected and remain accurate.

## 1. What & Who

Periods define the accounting calendar Carmen operates on — one row per fiscal month, identified by `YYMM` plus `fiscal_year` / `fiscal_month` integers and a `[start_at, end_at)` range. Every period has a status (`open`, `closed`, `locked`) gating which dated documents can post. Periods are the unit at which inventory cost is closed and snapshotted: when finance closes January, no further January GRNs / issues / adjustments may post, and the closing balance becomes February's opening balance.

`tb_period_snapshot` stores the per-location / per-product / per-lot inventory snapshot at a point in time — generated by the costing engine and used for trial balances, GL postings, and roll-forward. No screen in this module renders it (see Implementation status) — it is written and read by the costing engine only.

**Maintained by** Sysadmin (typically Finance Manager) via the plain edit dialog. **Read by** every posting guard and the costing engine.

## 2. Common Tasks

| Task | Where | Notes |
|---|---|---|
| Open next period | Period list → **Generate Next** (`CalendarPlus` button) | `POST .../periods/next`; auto-generates a batch (e.g. 12 months) via roll-forward |
| Change a period's status | Period row → **Edit** → **Status** dropdown → Save | Same generic edit dialog as fiscal year/month/dates — picking `closed` or `locked` here is a plain field edit, not a distinct workflow action |
| View snapshot | ~~Period detail → Snapshot tab~~ | **No such screen exists** — no period-detail component was found; snapshots are costing-engine-internal |
| Generate close snapshot | Costing engine job | Writes `tb_period_snapshot` for every (location, product, lot); not triggered from this screen |
| Export the period list | Period list → **Export** | XLSX with period/fiscal year/fiscal month/dates/status columns |

## 3. Validation & Errors

| Symptom | Cause | Action |
|---|---|---|
| "Period is closed" | Posting date inside a closed/locked period | Use current open period; or raise JV |
| "Period date overlap" | Two periods share dates | Fix range — periods must be contiguous, non-overlapping |
| `period` mismatch with fiscal date | `period != fiscal_year-2000 * 100 + fiscal_month` | Recompute and fix one value |
| Roll-forward discrepancy | Closing N ≠ Opening N+1 | Surfaces in `diff_amount`; review snapshot (not visible in any UI — query directly) |
| Cannot delete period | Snapshots, cost layers, or postings reference | Archive only; soft-delete breaks GL chain |
| Status changed to `closed`/`locked` with no confirmation step | Expected — the edit dialog has no distinct guard for this field | There is no undo screen; re-edit the row back to `open` if this was a mistake |

## 4. Edge Cases

- **Status is a plain editable field, not a workflow.** Any user who can open the Edit dialog can set any status value directly — there is no separate audit-reason prompt for reopening a closed period, contrary to a prior version of this page.
- **Snapshot regeneration.** Re-running close for the same period either overwrites or appends per Finance policy; **append at new `snapshot_at`** is the recommended audit-preserving pattern (costing-engine behavior, unconfirmed against a UI since none exists here).
- **Roll-forward integrity.** Opening N+1 must equal Closing N for every (location, product, lot); discrepancies tracked in `diff_amount`.
- **Date-range membership** resolves period at posting time.

## 6. Business Rules

- **Uniqueness.** Both `period` and `(fiscal_year, fiscal_month)` unique among non-deleted; should agree (`period == fiscal_year-2000 * 100 + fiscal_month` for 2000-2099).
- **Date integrity.** `start_at < end_at`; periods contiguous, non-overlapping.
- **Status is a free-form field in the UI, not an enforced state machine.** The edit dialog's status `<Select>` offers all three values (`open`/`closed`/`locked`) unconditionally regardless of the row's current status — no confirmed backend transition guard (e.g. blocking `locked → open`) was found either. Treat the `open → closed → locked` progression described here as *intended* usage discipline, not a system-enforced rule.
- **Posting guard.** Every dated document must resolve to an `open` period.
- **Snapshot generation.** `(period_id, snapshot_at)` per `(location, product, optional lot)`; append-at-new-`snapshot_at` preserves audit.
- **Roll-forward integrity.** Opening N+1 = Closing N per tuple.
- **Deletion guards.** Periods with snapshots / cost layers / postings cannot be deleted.
