# Inventory Adjustment — Business Rules

> **At a Glance**
> **Rule families:** `ADJ_VAL_*` validation &nbsp;·&nbsp; `ADJ_CALC_*` calculation &nbsp;·&nbsp; `ADJ_POST_*` posting
> **Rule count:** 13 rules, all directly traced to `ia-form-schema.ts`, `stock-in.service.ts` / `stock-out.service.ts`, and `inventory-transaction.service.ts`
> **Audience:** Test author + developer
> **Headline finding:** there is no approval stage — `create()` always writes `doc_status = completed` and posts to the ledger in the same transaction, regardless of cost, reason, or which button the user clicked

## 1. Overview

This page catalogues the rules actually enforced by the **inventory-adjustment module** — the two-table document layer (`tb_stock_in` / `tb_stock_out`) for manual stock corrections. An earlier version of this page (and its sibling persona/test pages) described a threshold-gated approval chain (Store Keeper auto-approve → Inventory Controller → Finance), GL journal postings, a segregation-of-duties rule, and a lot-selection sub-form. None of that exists in the current source: a repo-wide search of `carmen-turborepo-backend-v2` and `carmen-inventory-frontend-react` found zero `threshold` hits scoped to this module, zero `journal`/`ledger` hits, and no lot-entry UI anywhere in `ia-item-fields.tsx` / `ia-item-table.tsx`. This page has been rewritten from the actual Zod schema (`ia-form-schema.ts`) and backend service code.

**The single most important fact about this module:** `StockInService.create()` and `StockOutService.create()` build the object literal as `{ ...clientData, doc_status: enum_doc_status.completed }` — the explicit `doc_status: completed` is the last key in the literal, so it always wins over whatever the client sent, and the ledger write (`executeAdjustmentIn`/`executeAdjustmentOut`) happens in the same `$transaction` block. The frontend's Save button (sets `doc_status: "draft"`) and Submit button (sets `doc_status: "completed"`) both end up calling the identical `create()` mutation, so **both buttons produce the same result: an immediately posted, immutable document.** There is no reachable draft state, no approval queue, and no distinction between "saving a draft" and "submitting."

## 2. Validation Rules

Rule IDs follow `ADJ_VAL_NNN`. All of these are enforced either client-side (Zod, in `ia-form-schema.ts`) or in the backend's `create()`/`update()` methods — there is no separate "submit" validation pass distinct from creation, since creation and posting are the same event.

| Rule ID | Condition | Enforced by | Behaviour |
| ------- | --------- | ----------- | --------- |
| `ADJ_VAL_001` | `location_id` is required (non-empty). | Client (Zod `.min(1)`) and server (`STOCK_IN_LOCATION_REQUIRED` / `STOCK_OUT_LOCATION_REQUIRED` if missing on `create()`). | Reject with `"Location is required for stock in"` / `"...stock out"`. |
| `ADJ_VAL_002` | `adjustment_type_id` is required (non-null). | Client only (Zod `.refine((v) => !!v, ...)`). The backend's header validation (`validateAndEnrichHeader`) only checks the referenced `tb_adjustment_type` row exists — it does not require the field to be present, nor does it check `type` matches the document's direction. | Client rejects with a "required" message before submit is possible; a direct API call with a mismatched-direction or omitted reason is not re-checked server-side beyond existence. |
| `ADJ_VAL_003` | `date` is required and must fall within the current period's `start_at`–`end_at` window. | **Client only** (Zod `.refine`, using `useProfile().currentPeriod`). No equivalent check was found in `StockInService.create()`/`update()` or `StockOutService.create()`/`update()`. | Client rejects with a date-outside-period message; a direct API call with an out-of-period date was not found to be rejected server-side. |
| `ADJ_VAL_004` | At least one line item (`items.min(1)`). | Client (Zod) and server (`STOCK_IN_DETAIL_ITEMS_REQUIRED` / `STOCK_OUT_DETAIL_ITEMS_REQUIRED` if `stock_in_detail.add` / `stock_out_detail.add` is empty on create). | Reject with `"Stock in detail items are required"` / `"...out..."`. |
| `ADJ_VAL_005` | Each line's `product_id` is required and must resolve to an existing `tb_product`. | Client (Zod `.min(1)`) and server (`validateAndEnrichDetailItems` — collects every unmatched id and rejects with `"Product not found: <ids>"`). | Whole-document rejection listing every unmatched product id. |
| `ADJ_VAL_006` | Each line's `qty` must be `>= 1` (not merely `> 0`). | Client only (Zod `.min(1, ...)`). | A fractional quantity below 1 (e.g. `0.5`) is rejected by the form even though the column is `Decimal(20,5)` and could store it. |
| `ADJ_VAL_007` | Each line's `cost_per_unit` must be `>= 0`. | Client only (Zod `.min(0, ...)`). Only meaningful for Stock-In — the Stock-Out grid hides this column and the backend never persists it for stock-out lines (see [01 — Data Model](/en/inventory/inventory-adjustment/01-data-model) § 2.5). | Reject with a non-negative-cost message on Stock-In. |
| `ADJ_VAL_008` | `description` (header and line) is capped at 256 characters; it is **not required** — there is no `.min()` on either field. | Client only (Zod `.max(256, ...)`). | An adjustment with a blank description saves and posts successfully — this contradicts any earlier claim that a reason narrative is mandatory. |
| `ADJ_VAL_009` | Location type is restricted to Inventory / Consignment (`locationTypes={[INVENTORY_TYPE.INVENTORY, INVENTORY_TYPE.CONSIGNMENT]}` on the `LookupUserLocation` picker). | **Client only.** `validateAndEnrichHeader` in both `stock-in.logic.ts` and `stock-out.logic.ts` only checks the location exists — it does not check `location_type`. | The picker won't offer a Direct-cost location, but a direct API call with one was not found to be rejected server-side. |
| `ADJ_VAL_010` | Insufficient stock on Stock-Out (Average-costed products): `balance < requested qty`. | Server, inside `InventoryTransactionService.createAverageConsumption()` — throws `Error("Insufficient stock. Requested: <qty>, Available: <balance>")`, which surfaces as an HTTP 500 that the frontend's `handleMutationError` special-cases to show the raw message instead of a generic error. | Whole create/void transaction rolls back; document is not created / void does not proceed. **Not confirmed for FIFO-costed products** in this pass — `createFifoConsumption()`'s balance handling was not fully traced; treat as unverified for FIFO. |
| `ADJ_VAL_011` | Optimistic concurrency on update: the `doc_version` sent by the client must match the current stored value. | Server — the Prisma `update()` `where` clause includes `doc_version` alongside `id`; a stale value matches zero rows. | Since `update()` (and `createDetail`/`updateDetail`/`deleteDetail`) also require `doc_status === draft` first, and no document is ever created in `draft` (§ 1), this path is not reachable through the normal UI for any real document — see `ADJ_POST_003` below. |
| `ADJ_VAL_012` | Void precondition: the document must not already be `voided`. | Server (`STOCK_IN_ALREADY_VOIDED` / `STOCK_OUT_ALREADY_VOIDED`). Void also re-checks on-hand is sufficient to reverse each line's `qty` at the document's location (`voidStockIn`'s explicit cost-layer sum-and-compare loop; `voidStockOut`'s reversal doesn't carry an equivalent explicit check in the code read this pass). | `"Cannot void: product <code> has insufficient on-hand qty (<X>) at this location to reverse <Y>"` for stock-in void; stock-out void's guard was not independently confirmed. |
| `ADJ_VAL_013` | Reason-direction match (`tb_adjustment_type.type` vs document tree). | **Client only** — the reason picker filters `adjTypeData` by `at.type === (adjustmentType === "stock-in" ? ADJUSTMENT_TYPE.STOCK_IN : ADJUSTMENT_TYPE.STOCK_OUT)`. No server-side check confirmed (see `ADJ_VAL_002`). | Not enforceable outside the picker UI. |

## 3. Calculation Rules

| Rule ID | Formula |
| ------- | ------- |
| `ADJ_CALC_001` (line total) | `total_cost = qty × cost_per_unit`, computed client-side on every keystroke in `ia-item-table.tsx`'s `recalcTotal()`. For Stock-In this value is submitted and persisted on `tb_stock_in_detail`. For Stock-Out, the equivalent computed value is display-only — it is never persisted (see [01 — Data Model](/en/inventory/inventory-adjustment/01-data-model) § 2.5). |
| `ADJ_CALC_002` (Stock-In cost suggestion) | The line's `cost_per_unit` is pre-filled via `useProductCostByLocationQty(buCode, productId, locationId, qty)`, which returns the product's current average cost at that location — a starting suggestion only; the field remains editable and whatever value the user submits is what the ledger actually uses. |
| `ADJ_CALC_003` (Stock-Out cost preview) | The line's (non-persisted, display-only) total is pre-filled via `useProductLastReceiving(buCode, productId)` — the product's last receiving cost — purely for the user's reference; it plays no role in the actual posted cost. |
| `ADJ_CALC_004` (new average cost, Average-costed products) | On Stock-In posting: `new_average = (existingInQty × existingInCost + newQty × newTotalCost) / (existingInQty + newQty)`, computed by the shared `calculateNewAverageCost()` helper in `inventory-cost.formula.ts` and written onto the new cost-layer row's `average_cost_per_unit`. This is generic ledger logic shared with GRN/SR, not specific to this module. |
| `ADJ_CALC_005` (FIFO consumption, Stock-Out) | `createFifoConsumption()` consumes from `getAvailableFifoLots()` in ascending `lot_seq_no` order until the requested qty is satisfied, writing one outbound cost-layer row per consumed lot. |
| `ADJ_CALC_006` (Average consumption, Stock-Out) | `createAverageConsumption()` charges the entire outbound qty at the current BU-wide average cost, after the balance check in `ADJ_VAL_010`. |
| `ADJ_CALC_007` (rounding) | Monetary values round to 2 decimal places (`Math.round(x * 100) / 100`) at each cost-layer write; quantity columns store 5 decimal places (`Decimal(20,5)`). |

## 4. Authorization

No role- or threshold-based authorization was found anywhere in this module. The nav entry, the list, and the create/edit screens all gate on the single generic permission `inventory_management.view` (`constant/module-list.ts`). The catalog also defines CRUD-shaped permission keys `inventory_management.stock_in.*` / `inventory_management.stock_out.*` (`constant/permissions.ts`), but they are wired to gate two **different** Store Operations nav entries — Stock Replenishment (`.stock_in.view`) and Wastage Reporting (`.stock_out.view`) — not this module's own screens; no `hasPermission` call referencing them was found anywhere under `routes/inventory-management/inventory-adjustment/`. There is no `enum_stage_role` assignment, no workflow orchestrator call, and no per-user location scoping check beyond what the generic `LookupUserLocation` component already applies to every module. A previous version of this page described a Store-Keeper/Inventory-Controller/Finance/Auditor/System-Administrator authorization ladder with dollar thresholds and a segregation-of-duties rule — none of it has a matching route, permission key, or backend guard; see [03 — User Flow — Finance](/en/inventory/inventory-adjustment/03-user-flow-finance) and [03 — User Flow — Audit / Config](/en/inventory/inventory-adjustment/03-user-flow-audit-config) for the correction notice.

## 5. Posting Rules

Rule IDs follow `ADJ_POST_NNN`.

| Rule ID | Event | Effects |
| ------- | ----- | ------- |
| `ADJ_POST_001` | `create()` (both Save and Submit buttons call this) | Single atomic transaction: (1) header row created at `doc_status = completed`, `doc_version = 0`, auto-generated `si_no`/`so_no` via the running-code service; (2) each detail line created; (3) `executeAdjustmentIn` (Stock-In) / `executeAdjustmentOut` (Stock-Out) called per line, writing `tb_inventory_transaction` + `tb_inventory_transaction_detail` + one or more `tb_inventory_transaction_cost_layer` rows; (4) the detail's `inventory_transaction_id` stamped. No separate posting event exists — creation is posting. |
| `ADJ_POST_002` | `update()` | Only succeeds when the stored `doc_status === draft` — a state no document created through this module's `create()` ever has. Header fields and detail add/update/remove are otherwise a normal optimistic-concurrency update (`doc_version` checked per row). In practice unreachable for any document created through the normal Add Stock-In/Add Stock-Out flow. |
| `ADJ_POST_003` | `delete()` | Only succeeds when `doc_status === draft` — same unreachability as `update()`. The list view's row-menu **Delete** button, however, renders unconditionally for every row (`actionColumn` is called with no `deleteDenied`/`deletePermission`), so clicking it on any real document opens the confirm dialog and then fails server-side with `"Cannot delete a completed Stock In — inventory has already been adjusted"` (400). |
| `ADJ_POST_004` | `voidStockIn()` / `voidStockOut()` | Real backend endpoint: checks not-already-voided (`ADJ_VAL_012`), re-verifies sufficient on-hand to reverse each line (stock-in path only, confirmed), then in one transaction (a) writes a reversing `executeAdjustmentOut`/`executeAdjustmentIn` call per line at the *current* cost (stock-out void reads the cost from the original transaction's detail row via `txDetailMap`; stock-in void does not re-look-up the original cost, it reverses at whatever `executeAdjustmentOut` resolves at void time) and (b) sets `doc_status = voided` **and** `deleted_at`/`deleted_by_id` on the original header in the same update. Because the list/detail queries filter `deleted_at: null`, a voided document disappears from both — it is not merely badge-flagged. **Not reachable from the current UI**: the Void button only renders when `isEdit && !isReadOnly`, `isEdit` is only reachable by clicking Edit, and Edit only renders when `!isReadOnly` — but `isReadOnly = doc_status === 'voided' \|\| doc_status === 'completed'`, which is true for every persisted document (§ 1). Void currently requires a direct API call. |
| `ADJ_POST_005` | Count-variance rollup ([physical-count](/en/inventory/physical-count)) | `PhysicalCountService.submit()` creates `tb_stock_in` (overage lines) / `tb_stock_out` (shortage lines) directly at `doc_status = completed`, with **no `adjustment_type_id` set** (count-driven rows carry no reason code) and a note string describing the variance and the costing method used for the line cost. This pass confirmed the row creation but did not trace whether `submit()` also calls `executeAdjustmentIn`/`executeAdjustmentOut` the way the manual screens do — re-verify during `physical-count`'s own resync pass before treating the ledger-linkage as confirmed. |
