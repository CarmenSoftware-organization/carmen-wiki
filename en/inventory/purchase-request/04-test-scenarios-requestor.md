This page captures the test scenarios that the Requestor persona directly drives in the `purchase-request` module. It covers the happy paths described in [03-user-flow-requestor.md](./03-user-flow-requestor.md) Section 2, the RBAC boundaries implied by `PR_AUTH_001` and the draft-only edit rule in [02-business-rules.md](./02-business-rules.md), the submit-time validation rules `PR_VAL_001`..`PR_VAL_012` that a Requestor can trigger first-hand, and a small set of boundary / concurrency cases that fall out of `Decimal(15, 5)` / `Decimal(20, 5)` precision and the send-back loop. Cross-persona handoffs (`X-PR-02`, `X-PR-10`) that start at the Requestor and bounce off an Approver live in the parent overview, not here.

## 1. Happy Path

| # | Scenario | Pre-condition | Steps | Expected |
| - | -------- | ------------- | ----- | -------- |
| REQ-HP-01 | Create and submit a minimal PR (single line, in-base currency) | Requestor `requestor@blueledgers.com` logged in; a creatable `tb_workflow` for `purchase_request`; at least one active `tb_product`; base currency THB | 1. PR list → **New** → **Blank**. 2. Fill header: pick `workflow_id`, confirm `department_id`, enter description (`pr_date` defaults to today). 3. | REQ-HP-02 | Create and submit a multi-line PR with a comment attachment | As REQ-HP-01; vendor quotation PDF available; two active products | 1. **New**, fill header. 2. Add line 1 (Product A, qty, UoM). 3. Add line 2 (Product B, different store location, FOC qty > 0 with FOC unit). 4. Open the comment sheet → add a comment with the PDF attached. 5. Set the quantity, edit description (`PR_AUTH_001` allows because still `draft` and Requestor owns it). 6. Submit. | Draft visible on next login with last-saved state; save with qty `0` succeeded; on submit `doc_version` increments per `PR_VAL_016`; status transitions `draft → in_progress`. |
| REQ-HP-04 | Respond to send-back and resubmit | PR was submitted by this Requestor and the first-stage approver clicked **Send Back** targeting the `create` stage; PR is `pr_status = in_progress` with `workflow_current_stage` at the create stage and the Requestor back in `user_action.execute[]` | 1. Open the PR from the list / My Approval queue. 2. Read the approver comment in Workflow History. 3. Edit the offending field. 4. Click **Submit** again. | Edit succeeds because Requestor is back inside the `create` stage; `last_action = submitted` re-stamped, `workflow_current_stage` advances to the first approval stage again; `pr_status` never left `in_progress`; revision history preserves the prior submit + send-back comments (`PR_POST_008`). |
| REQ-HP-05 | Delete own draft from the detail page or list | PR exists in `pr_status = draft`; Requestor is `created_by_id` / `requestor_id`; never submitted | 1. Confirm in the modal. | `DELETE /:bu_code/purchase-requests/:id` (or `…/batch`) soft-deletes header and lines (`deleted_at`); `pr_status` unchanged (**not** `voided`); PR disappears from the list and from `sys_v_my_pending`; a non-owner gets `PR_DELETE_FORBIDDEN` before the confirm (`pr-ownership.ts`). |

In the quantity step enter quantities (rows left at `0` are dropped) → **Continue**. 4. The new-PR form opens pre-filled (workflow from the template, lines with `exchange_rate = 1`, `delivery_date` = tomorrow, no vendor / price). 5. Tweak a line, **Save**, **Submit**. | New PR is independent of the template; `tb_purchase_request_template_detail` rows are not mutated; no link back to the template is stored; PR transitions `draft → in_progress`; workflow follows the template's `workflow_id`. |
| REQ-HP-07 | Submit a PR with line-level discount and tax adjustments | As REQ-HP-01; tax profile and discount inputs enabled | 1. Submit. | Line persists with the rule-engine values from `PR_CALC_001`..`PR_CALC_005`; header roll-up `base_total_amount` = 2,256.63000 ฿ (THB base, exchange_rate = 1.00000); display layer may truncate to 2 dp but persisted value retains 5 dp. |

Submit. | `exchange_rate` is snapshotted on the line at submit and frozen for the life of the document (re-approving does not re-fetch); `base_*` columns computed per `PR_CALC_006`. |

## 2. Permission / Authorization

| # | Scenario | Expected behaviour (allow/deny + reason) |
| - | -------- | --------------------------------------- |
| REQ-PERM-01 | Requestor opens a PR they own (`requestor_id == auth.user.id`) in `pr_status = draft` | **Allow** read and edit. `PR_AUTH_001` grants the owner exclusive edit rights while the PR is `draft`. |
| REQ-PERM-02 | Requestor opens a PR owned by another user in `pr_status = draft` | **Deny edit, read-only** (no Edit / Delete / Submit toolbar). `PR_AUTH_001` reserves edit to the owner. *(An earlier revision also carved out "an explicit delegate" — unconfirmed, no delegation mechanism found; see `PR_AUTH_006`.)* List visibility itself depends on the **All Documents** / department-wide grant; if the PR is outside the Requestor's department it does not appear on the list at all. |
| REQ-PERM-03 | Requestor edits their own draft (header description and one line qty) | **Allow.** `PR_AUTH_001` is satisfied; `doc_version` increments on save per `PR_VAL_016`. |
| REQ-PERM-04 | Requestor tries to edit their own PR after submit (`pr_status = in_progress`) | **Deny.** State-machine lock — edit controls are read-only. The only way back to edit is for an approver to **Send Back** the PR to `draft`. |
| REQ-PERM-05 | Requestor cancels / deletes their own `draft` PR | **Allow.** Owner-only soft delete of a not-yet-submitted document (`PR_VAL_018`); no workflow stage was advanced. |
| REQ-PERM-06 | Requestor tries to cancel / delete their own PR after submit (`in_progress` or `approved`) | **Deny.** `DELETE` answers "Only draft purchase requests can be deleted"; the detail page shows no Delete control. A submitted PR can only be sent back to the create stage by an approver or rejected by an approver (`PR_AUTH_004` → `voided`). *(A Finance / sys-admin void — unconfirmed, `PR_AUTH_007`.)* |
| REQ-PERM-07 | Requestor tries to approve their own PR | **Deny.** Segregation of duties — the `create` stage role and the downstream `approve` stage roles are disjoint by workflow definition (see [02-business-rules.md](./02-business-rules.md) Section 4 default chain). Even if the Requestor were named on the approver stage by misconfig, `user_action.execute[]` is recomputed per stage and the create-stage owner is filtered out. |
| REQ-PERM-08 | Requestor with `noAuth` fixture / expired session opens any PR URL | **Deny — redirect to login.** Outside the auth context there is no `auth.user.id` to match against `requestor_id`; `PR_AUTH_001` cannot apply. Covered by the `noAuthTest` fixture in `301-pr.spec.ts`. |

## 3. Validation / Error

| # | Scenario | Trigger | Expected error |
| - | -------- | ------- | -------------- |
| REQ-VAL-01 | Submit without a `pr_no` (or duplicate `pr_no`) | Header insert raced two clients; or seed test creates a row with a `pr_no` that collides with an existing non-deleted row | `PR_VAL_001` — reject with `"PR reference number is required and must be unique"`. Unique index `PR0_pr_no_u` on `(pr_no, deleted_at)` enforces. |
| REQ-VAL-02 | Submit without a valid `requestor_id` / `requestor_name` snapshot | Requestor account was deactivated mid-edit, or snapshot lost | `PR_VAL_002` — reject with `"Requestor is required"`. |
| REQ-VAL-03 | Submit with `department_id` empty | Header `department_id` cleared (client) or absent in the stored row (server) | Client Zod: "required" on department; server `PR_VAL_003` — `"Department is required"` (`PR_ERROR.DEPARTMENT_REQUIRED`). *A membership check against the requestor's departments — unconfirmed, no code path.* |
| REQ-VAL-04 | Submit without a `workflow_id` (or pointing at a workflow whose scope ≠ `purchase-request`) | Header `workflow_id` cleared | `PR_VAL_004` — reject with `"A valid PR workflow must be selected"`. |
| REQ-VAL-05 | Submit with `pr_date` missing | Clear `pr_date` | `PR_VAL_005` — `"PR date is required"`. *A future-date rejection — unconfirmed, no code path; a future `pr_date` is accepted today.* |
| REQ-VAL-06 | Submit a PR with zero non-deleted lines | Save header only, then click Submit | `PR_VAL_006` — reject with `"A PR must contain at least one line item"`. Submit button is also disabled in the UI per `TC-PR-050604`. |
| REQ-VAL-07 | Save a line without a `product_id` (or with an inactive product) | Free-text description only, no product picked; or product was soft-deleted in the catalogue | `PR_VAL_007` — reject with `"Product is required on every line"`. NOT NULL also enforced at the DB layer. |
| REQ-VAL-08 | Submit a line that orders nothing (`requested_qty = 0` and `foc_qty = 0`), or a negative qty | Leave both quantities at `0` on a line and click Submit; or type `-1` | `PR_VAL_008` — the client toast "incompleteItems" names the row and the confirm dialog does not open (`findRowsMissingQty`); the server answers `"Detail line N: needs a requested_qty or a foc_qty"` / `"requested_qty must be positive"`. **Save** of the same draft succeeds — the rule is submit-time only. A FOC-only line (`requested_qty = 0`, `foc_qty > 0`, FOC unit set) passes. |
| REQ-VAL-09 | Save a line without a `delivery_date` | Clear the delivery-date cell | Client Zod (`pr-form-schema.ts:83`) — "required". *Rejecting a `delivery_date` earlier than `pr_date` — unconfirmed, no code path (`TC-PR-050211` asserts the UI only).* |
| REQ-VAL-10 | Add a second line for the same `(product_id, location_id, dimension)` already on the PR | Duplicate line entry within the same PR | `PR_VAL_010` — reject with `"Same product cannot be requested twice for the same location and dimension"`. Unique index `PR1_purchase_request_product_location_dimension_u` enforces. |
| REQ-VAL-11 | Save a line with `currency_id` missing | Clear the currency cell | Client Zod (`pr-form-schema.ts:73`) — "required". *`exchange_rate ≤ 0` and `exchange_rate_date` later than `pr_date` — unconfirmed, no code path.* |
| REQ-VAL-12 | Enter a discount or tax larger than the line value | Not reachable by the Requestor — discount / tax are edited at the `purchase` stage | See `PR_VAL_012` (line-amount caps, checked by `POST …/verify` with `stage_role = purchase`). *A `0–100` percent range check — unconfirmed, no code path.* |
| REQ-VAL-13 | Two browser tabs edit the same draft and the second one tries to save | Tab A saves description; Tab B (still on the older `doc_version`) clicks Save | `PR_VAL_016` — reject with `"Document was modified by another user; reload and retry"`. Successful saves bump `doc_version` by 1. |

## 4. Edge Cases

| # | Scenario | Condition | Expected |
| - | -------- | --------- | -------- |
| REQ-EDGE-01 | Zero quantity boundary | Line saved with `requested_qty = 0.00000` and `foc_qty = 0` | **Save** accepted (draft may be incomplete); **Submit** rejected per `PR_VAL_008` — the rule is strict `> 0` on at least one of the two quantities. `requested_qty = 0` with `foc_qty = 0.5` passes (decimal FOC allowed). Negative values are rejected on save by the client (`min(0)`) and on submit by the server. |
| REQ-EDGE-02 | Maximum decimal precision | Line entered with `requested_qty = 1.99999`, `pricelist_price = 0.00001`, `discount_rate = 99.99999`, `tax_rate = 99.99999`, `exchange_rate = 35.12345` | Persisted exactly at 5 decimals on `Decimal(15, 5)` / `Decimal(20, 5)` columns; the 6th decimal is rounded half-up before subsequent steps per the rounding policy in [02-business-rules.md](./02-business-rules.md) Section 3. Display may truncate to 2 dp but the persisted value retains 5 dp. |
| REQ-EDGE-03 | Back-dated `requested_date` (line `delivery_date` = `pr_date`) | `delivery_date == pr_date` (same calendar day) | Accepted — `PR_VAL_009` is "on or after `pr_date`", so equality is valid. |
| REQ-EDGE-04 | Far-future `requested_date` | Line `delivery_date` = `2099-12-31` | Accepted by `PR_VAL_009`; downstream stages (Approver, Purchaser) may flag during their own validation but the Requestor's submit is not blocked. |
| REQ-EDGE-05 | Line currency differs from the base currency | Line `currency_id = USD`, base THB | Allowed at the Requestor stage — base-currency conversion happens via `PR_CALC_006` using the line's `exchange_rate` (default `1` until the `purchase` stage's Auto Allocate / Price Comparison sets it). |
| REQ-EDGE-06 | Concurrent edits to the same draft | Same draft opened in two tabs; both edit different fields and click Save in quick succession | First save wins and bumps `doc_version`; second save is rejected by `PR_VAL_016` and the UI prompts a reload. Last-write-wins is **not** the policy. |
| REQ-EDGE-07 | Send-back received while the Requestor was still viewing the PR | An approver clicked **Send Back** to the create stage while the Requestor had the detail page open | On refresh / next save, the client sees `workflow_current_stage` back at the create stage and the Requestor's id in `user_action.execute[]`; edit becomes available again; `pr_status` reads `in_progress` throughout (`PR_VAL_016` still guards each save with `doc_version`). |
