# Physical Count

> **At a Glance**
> **Module purpose:** Full count of every item at a location for the current counting period, entered and submitted by a single generic role, with variance posted at final submit as end-of-period (EOP) stock-in/stock-out documents that move the ledger &nbsp;·&nbsp; **Audience:** any user holding the `inventory_management.physical_count` permission — no distinct approver, auditor, or configuration role exists in code &nbsp;·&nbsp; **Key entities/tables:** `tb_physical_count_period`, `tb_physical_count`, `tb_physical_count_detail`, three comment tables, four `enum_physical_count_*` enums &nbsp;·&nbsp; **Sub-pages:** 10

## 1. Overview

A **Physical Count** is a full count of every item at a location for the current counting period, used to reconcile the system's book balance against what is actually on the shelf. The real implementation (`../carmen-frontend/routes/inventory-management/physical-count/`) is a single continuous flow with no distinct persona hand-off: a user opens the location list for the current period (`physical-count`), starts or resumes a count for one location (`physical-count/:id/entry`), enters `actual_qty` per product line, submits the sheet for review (`physical-count/:id/review`), and confirms the final submit — which is also the step that reconciles every non-zero-variance line into a pair of stock-in/stock-out documents. Every action in this flow is gated by one CRUD permission key, `inventory_management.physical_count` (`constant/permissions.ts`); no separate approver, auditor, or configuration role, route, or permission was found anywhere in the frontend, backend, or Bruno collection for this module.

Two routes are still wired into the router but are **not reachable from any real navigation path**: `physical-count/new` and `physical-count/:id` both render `PcForm` (`pc-form.tsx`), a pre-refactor create/edit form whose only field is `department_id` — the type it edits is explicitly commented `// Legacy type (used by old form)` in `types/physical-count.ts`. No button anywhere in the list screen links to `/new`, and the real create action (`pc-component.tsx`'s `handleAction`) creates a count directly via `POST /physical-counts` and navigates straight to `/:id/entry`, never to `/:id`. Treat these two routes and the `use-pc-table.tsx` hook that backs them as orphaned pre-refactor code.

## 2. Business Context

Physical count is a regulatory and audit baseline, not a discretionary task. External auditors require a documented count at period-end to certify the inventory line on the balance sheet, and most hospitality groups have internal policy mandating cycle counts on high-risk categories at higher frequency. A complete, signed-off count is the evidence that the inventory value carried on the books is real — without it, the closing valuation is unsupported and the audit opinion is at risk.

The financial accuracy stakes are immediate. Hospitality operations run on thin food and beverage margins, and uncounted shrinkage compounds quickly: theft, spoilage, miss-pours, transfer errors, and miscategorised consumption all erode book accuracy between counts. Period-end physical count is where that drift is detected and quantified — making the count one of the largest correcting mechanisms against inventory value in many operations. A late or incomplete count means a misstated stock position and downstream errors in menu engineering and procurement forecasting.

## 3. Key Concepts

- **Count Sheet**: The working document for one location's physical count — one `tb_physical_count` row plus its `tb_physical_count_detail` lines. The product list is the union of (a) products formally assigned to the location via `tb_product_location` and (b) any product with a non-zero net quantity at that location in the counted period, so items with "phantom" stock are always caught even if not formally assigned. The quantity is read from the cost layers stamped with the counted period (`getLocationOnHand`, `location-on-hand.helper.ts`: `Σ in_qty − Σ out_qty` where `at_period` = the period's code, soft-deleted layers excluded) — the same balance the stock screens and the period close use; the earlier read of `tb_inventory_transaction_detail` also counted movements already posted into a later period and rows of voided documents. A count sheet is created **already `in_progress`** — `start_counting_at`/`start_counting_by_id` are stamped immediately on creation (`physical-count.service.ts` `create()`), not on the counter's first line entry. A **Refresh** action on the entry screen (`PATCH .../physical-counts/:id/refresh`) re-runs the same union query and appends any newly-qualifying products to an in-progress sheet.
- **Location Count Requirement** (not "frozen vs live"): `tb_location.physical_count_type` (`enum_physical_count_type`, `yes`/`no`, default `no`) is a per-location admin flag edited on the location's own config form (`master-data/location`, filter chips "Count"/"Not Count"). It marks whether a location is **required** for the period-end physical-count gate (`period-end.validate.ts`'s `validatePhysicalCount` requires `location_type ∈ {inventory, consignment}`, `physical_count_type = yes`, `is_active = true`). It is **not** a per-document frozen-vs-live counting mode: the *document*-level field of the same name (`tb_physical_count.physical_count_type`) is never set by `create()`, so every created count document simply keeps the Prisma default (`yes`). No code anywhere — frontend or backend, including the good-received-note and store-requisition services — checks for an in-progress count before allowing a posting at that location; there is no location lock.
- **Variance**: `diff_qty = actual_qty − on_hand_qty` per line, computed by the backend (not the client). Critically, `on_hand_qty` is **not** a snapshot captured when the sheet is created — it stays `0` on every line until the counter clicks **Submit for Review**, at which point `reviewItems()` recomputes `on_hand_qty` for every line as the **counted period's balance** from the cost layers (`getLocationOnHand` with `at_period` = the code of the count's period, resolved by `getCountedPeriod`) — so it is the period's brought-forward stock plus the period's own movements, not an all-time ledger sum. A quantity typed and saved mid-count therefore shows a variance against a stale `0` book quantity until that review step runs; only the review-time recomputation is meaningful. No tolerance threshold, percentage-based flagging, or recount mechanism of any kind exists in the frontend or backend for this module.
- **Save vs Submit for Review vs Submit**: three distinct backend calls drive one document to completion. **Save** (`PATCH .../save`, any time, repeatable) stamps `counted_at`/`counted_by_id` on the lines submitted and recomputes each line's `diff_qty` against whatever `on_hand_qty` is currently stored (usually still `0` before the first review). **Submit for Review** (`PATCH .../review`, once all lines have a value) recomputes the live `on_hand_qty`/`diff_qty` for every line and moves the user to the `/review` screen, but does **not** change `tb_physical_count.status` — it stays `in_progress`. **Submit** (`PATCH .../submit`, from the review screen) is the terminal action described below. `submit()` rejects with `"<N> products have not been counted yet"` if any line's `counted_at` is still null — Save and Submit-for-Review stamp `counted_at`, and that edge case is closed: `reviewItems()` also stamps `counted_at` / `counted_by_id` on any line it receives for the first time, so a line typed and sent straight to review is counted. `product_counted` on the header uses the same definition (`counted_at` set).
- **Rollup at Submit (posts to the ledger since the 2026-10 code)**: on `submit()` (`physical-count.service.ts`), inside one `$transaction`, the backend groups every non-zero-variance line by sign and creates **at most one** `tb_stock_in` (all positive-variance lines) and **at most one** `tb_stock_out` (all negative-variance lines), numbered through `reserveStockDocumentNumbers` (types `STOCK-IN` / `STOCK-OUT`, document date = the counted period's end). Both are inserted **already `doc_status = completed`** — but unlike the earlier code they are then **posted**: each line goes through `InventoryTransactionService.executeAdjustmentIn` (overage) / `executeAdjustmentOut` (shortage) via the private `postAdjustmentIn` / `postAdjustmentOut`, the `inventory_transaction_id` is written onto the detail row, and the correction moves on-hand. A posting failure (for example `Insufficient stock` when the location no longer holds the counted shortfall) rolls the whole submit back, so a count can no longer complete with a correction that moved no stock. *(The 2026-09-22 revision of this page recorded the opposite — "submit never posts to the ledger". That was true of the code at that date and is no longer true; re-verified 2026-10-27.)* Further facts, all from `submit()`:
  - **EOP adjustment types.** The headers carry `adjustment_type_id` / `adjustment_type_code` of the BU's active `eop_in` (overage) or `eop_out` (shortage) adjustment type, matched by `type` (oldest first), not by code (`findEopAdjustmentType`). If the BU has none, submit fails with ``No active adjustment type of type eop_in, eop_out for this business unit`` (naming the missing ones) and nothing is written. Tenant seeding creates `EOP-IN` / `EOP-OUT` rows (`adjustment_type_seed`, `adjustment-type.seed-set.ts` — skipped when a live row already shares the code or the type). The documents therefore read as `eop_in` / `eop_out` in the merged [inventory-adjustment](/en/inventory/inventory-adjustment) list.
  - **Dated to the counted period.** `si_date` / `so_date` = the counted period's `end_at` (falls back to now only when the count has no period), and the ledger rows are stamped into that period (`doc_date` on the adjustment-in). A count closed late still files its correction under the month it corrects. `description` = ``Physical Count Adjustment - Period yyyy-MM``; each line's `note` = ``Physical Count Adjustment - Variance: +<qty> @ <cost> (<method>)`` (overage) or ``… Variance: <qty> @ <posted cost> (<ledger method>)`` (shortage).
  - **Pricing.** Overage lines are priced before the transaction with `CostingService.getCostsPerUnit` using the BU's *Default price for added items* (`si.cost-from`, `SI_COST_FROM_CONFIG_KEY`; default `last_cost` via `SI_COST_FROM_DEFAULT`; `average` is only usable on an average-costed BU, otherwise it falls back to the default with a warning), cut off at the end of the counted period's last business day (`as_of`) and scoped to the counted period. Shortage lines carry no price in advance: `executeAdjustmentOut` draws the lots (FIFO) or applies the average at that moment, and `getPostedCost` writes the posted `cost_per_unit` / `total_cost` back onto the stock-out line. This replaces the old `enum_business_unit_config_key.physical_count_costing_method` key (default `last_receiving`).
  - **Still no structured link** back to the `tb_physical_count` — the only trace is the shared `description` / `note` text.
- **Counting round is opened from Period End (since 2026-08-27).** `physical-count.service.ts` `create()` refuses to open a count unless the period's `tb_physical_count_period.status = counting` ("Physical Count Period is not in counting status"), and the only code path that sets `counting` is **Start Period Close** on `/inventory-management/period-end` (`POST /period-ends/start-counting`, `PeriodEndService.startCounting` — gated by open GRN / stock-in / stock-out / SR documents). The round belongs to the **active** period — the oldest `open` **or `locked`** one (`findCurrentOpenPeriod`); `PhysicalCountPeriodService.create` rejects any other period with ``Period is not the active period (<code>)``, and `findCurrent` uses the same lookup. The physical-count list mirrors this: `pc-component.tsx` shows a **"Counting has not started"** dialog with a **Go to Period End** button when `period.status !== "counting"` instead of calling `POST /physical-counts`. The 2026-07-15 revision's "no code path sets `counting`" gap is closed.
