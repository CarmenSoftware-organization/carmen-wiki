# Purchase Order — Test Scenarios — Purchaser

> **At a Glance**
> **Persona:** Purchaser (Procurement Officer) &nbsp;·&nbsp; **Module:** [purchase-order](/en/inventory/purchase-order) &nbsp;·&nbsp; **Scenarios:** ~34
> **Categories:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **E2E coverage:** maps to `tests/402-po-purchaser-journey.spec.ts` and `tests/401-po.spec.ts` in `../carmen-inventory-frontend-e2e/`

> **Executable coverage (2026-09-22):** catalog `../carmen-inventory-frontend-e2e/docs/user-stories/402-po-purchaser-journey.md` (32 cases) + `docs/user-stories/401-po.md` (60 cases); gap reports `docs/test-cases/gaps/402-po-purchaser-journey-gap.md` (39 uncovered cases) + `gaps/401-po-create-flows-gap.md` (29); specs `tests/402-po-purchaser-journey.spec.ts`, `tests/401-po.spec.ts`. The specs still look for a **Send to Vendor** button and a `SENT` badge; at HEAD the button is **Send Email**, final approval lands on `approved`, and a successful send lands on `sent_or_print`. Scenarios below were corrected to HEAD, not to the specs.

This page captures the test scenarios that the Purchaser persona (also titled **Procurement Officer**) directly drives in the `purchase-order` module. The Purchaser owns the PO from creation through transmission to the vendor — the span from `po_status = draft` to `sent_or_print` ([03-user-flow-purchaser.md](./03-user-flow-purchaser.md) Section 2). Three creation paths exist: a **manual PO** (`po_type = manual`) raised directly by procurement, a **PR-sourced PO** (`po_type = purchase_request`) materialised via the 3-step From PR page inside the Purchase Order module (`/procurement/purchase-order/from-pr`) through the bridge table `tb_purchase_order_detail_tb_purchase_request_detail` ([01-data-model.md](./01-data-model.md) Section 2.3), and a **price-list-sourced PO** (`po_type = pricelist`) via the 4-step from-price-list wizard. Scenarios are grouped into the happy paths described in the user flow, the RBAC boundary enforced by `PO_AUTH_001`–`PO_AUTH_003` and `PO_AUTH_006` (Purchaser's edit / submit / transmit scope) versus `PO_AUTH_005` (Manager-only soft-delete) and `PO_AUTH_011` (stage-gated approval — authorization not amount-gated, though which stage a PO reaches can be, via the assigned workflow's `routing_rules`, `PO_AUTH_004` — see `02-business-rules.md` § 4), the validation rules in [02-business-rules.md](./02-business-rules.md) Section 2 (`PO_VAL_001`–`PO_VAL_016`) that the Purchaser can trigger from create / edit / submit time, and a small set of edge cases around decimal precision, currency, concurrency, and vendor-master state changes. Cross-persona handoffs that pivot off the Purchaser (`X-PO-01`, `X-PO-02`, `X-PO-05`, `X-PO-10`) live in the parent overview, not here.

## 2. Permission / Authorization

| # | Scenario | Expected behaviour (allow/deny + reason) |
| - | -------- | --------------------------------------- |
| PUR-PERM-01 | Purchaser opens own PO (current user matches `tb_purchase_order.buyer_id`, or is in `user_action.execute[]` at the current `workflow_current_stage`) | **Allow** read across all statuses and the create / edit / submit / transmit actions per `PO_AUTH_001`–`PO_AUTH_003` and `PO_AUTH_006`. Detail page loads with header + items + Item Details panel (TC-PO-060301, TC-PO-060302). |
| PUR-PERM-02 | Purchaser views another Purchaser's PO (RBAC-scoped read) | **Allow** read when the tenant's RBAC grants `purchase-order:read` to all `enum_stage_role = purchase` users (default); **deny** write actions (Edit / Submit / Send-to-Vendor / Close) because `PO_AUTH_002` requires the user to be the assigned buyer or hold the current `workflow_current_stage`. Direct API call to edit returns `"You are not authorised to edit this PO at the current stage"`. |
| PUR-PERM-03 | Purchaser edits a `draft` PO they own | **Allow** per `PO_AUTH_002` (`po_status ∈ {draft, in_progress}` and user is the assigned buyer). All header and line fields editable; **Edit / Delete / Submit** buttons present on `draft` (TC-PO-060303); modifying qty / adding lines / cancelling edit / submitting all succeed (TC-PO-060401..TC-PO-060405). |
| PUR-PERM-04 | Purchaser edits an `approved` / `sent_or_print` PO they own | **Deny** per `PO_VAL_016` — the detail page is read-only from `approved` onward (`po-footer-action.tsx` `isTerminal`); the only enabled actions are **Send Email**, **Close**, **Cancel**, comments. A direct `PUT` / `PATCH .../save` carrying prices is rejected by the `po_status === draft` guards. **Corrected 2026-09-22:** no "Amendment panel" or per-line `cancelled_qty` editor exists. |
| PUR-PERM-05 | Purchaser attempts to approve a PO at the current workflow stage | **Allow only if the workflow definition assigns the Purchaser to that stage** (`PO_AUTH_011` — authorization gated purely by `user_action.execute[]`, not by amount). A single-stage workflow may assign the Purchaser's own stage as final, letting the same user submit and approve. **Deny** when the workflow assigns a different stage owner. Direct call to advance the stage from a non-listed user is rejected by `PO_AUTH_011` with `"You are not in the authorised approver set for this stage"`. **Corrected this pass:** the previous version of this scenario gated *self-approval eligibility* on a "tenant high-value threshold" and a segregation-of-duties rule (`PO_AUTH_010`); neither self-approval gating nor SoD was found in current source. Separately (and confirmed, not part of the original wrong claim): the assigned workflow's `routing_rules` can still route *which* stage is next by `total_amount` (`PO_AUTH_004`) — a document-routing mechanism, not a self-approval eligibility check. |
| PUR-PERM-06 | Purchaser removes own `draft` PO (soft-delete) | **Allow when the Purchaser created it** (`PO_AUTH_005`: `remove()` checks `po_status = draft` then `isDocumentOwner(purchaseOrder, userId)` or super-admin). **Deny** for a draft created by someone else — the API rejects it even though the UI may show the button (TC-PO-060303). **Corrected 2026-09-22:** the previous version reserved this to the Procurement Manager and quoted an error string ("Soft-delete from draft is restricted to the Procurement Manager") that does not exist; the real message is "Only draft purchase orders can be deleted" for non-draft, and an ownership error otherwise. |
| PUR-PERM-07 | Purchaser attempts to reject a PO at a stage they do not hold | **Deny.** Per `PO_AUTH_011`, only whoever is in `user_action.execute[]` for the current `workflow_current_stage` can reject (`in_progress → voided`, direct and terminal). `voided` is only reachable from `in_progress` via reject. The Purchaser can, however, **Cancel** a `draft`, `in_progress`, `approved`, or `sent_or_print` PO (landing on `closed`). |
| PUR-PERM-08 | Purchaser closes a `partial` PO (early termination) | **Allow.** `closePO()` has no role gate beyond authentication (`PO_AUTH_008`, `purchase-order.service.ts` L6083-6094); the React header shows **Close** on `approved` / `sent_or_print` when `canClose`. **Corrected 2026-09-22** from "Deny — Inventory Manager scope". |

## 3. Validation / Error

| # | Scenario | Trigger | Expected error |
| - | -------- | ------- | -------------- |
| PUR-VAL-01 | Submit a PO without a `po_no` (DB-level fallback) | Force a save with `po_no` blank via direct API call (UI generates one by default) | Reject — `PO_VAL_001`. Server returns `"PO reference number is required and must be unique."`; the DB unique index `@@unique([po_no, deleted_at])` is the last-resort guard. |
| PUR-VAL-02 | Submit a PO whose `vendor_id` references a soft-deleted or inactive `tb_vendor` row | Pick vendor `V_old` whose `deleted_at IS NOT NULL` or `is_active = false`; save and submit | Reject — `PO_VAL_002`. Server returns `"Vendor is required and must be from the approved vendor list."`; UI vendor picker filters out inactive and deleted vendors but a stale selection caught at submit triggers the validation. |
| PUR-VAL-03 | Submit a PO with `exchange_rate = 0` or negative | Set `exchange_rate = 0` on the header and try to save / submit | Reject — `PO_VAL_003`. Server returns `"Transaction currency and a positive exchange rate are required."`; UI input enforces `> 0` but a direct API call is caught by the validation. |
| PUR-VAL-04 | Submit a PO with `delivery_date < order_date` | Set `order_date = 2026-05-15`, `delivery_date = 2026-05-14`; click Save / Submit | Reject — `PO_VAL_006`. Server returns `"Delivery date must be on or after the order date."`; UI date picker warns inline; submit attempt blocked. |
| PUR-VAL-05 | Submit a PO with a line `order_qty = 0` | Set `order_qty = 0` on one line; click Submit | Reject — `PO_VAL_008`. Server returns `"Order quantity must be greater than zero and a unit of measure is required."`; the line is flagged in red in the items table. |
| PUR-VAL-06 | Submit a PO line with `price < 0`, or `price = 0` without the FOC flag | Set `price = -10` on a line, or `price = 0` with `is_foc = false`; click Submit | Reject — `PO_VAL_010`. Server returns `"Unit price must be non-negative; price of 0 requires the FOC flag."`; UI shows the inline error on the line. |
| PUR-VAL-07 | Save a draft PO without any line items, then attempt to submit | From the **Blank** create wizard, save header only with no lines, then click Submit | Reject — `PO_VAL_012`. Server returns `"PO must contain at least one line item."`; UI **Save** button stays disabled or the page stays on `/new` when no lines are present (TC-PO-060204). |
| PUR-VAL-08 | Attempt to submit a PO whose lines mix vendors or currencies | Add line `L1` with `vendor_id = V1, currency_id = THB`, and line `L2` with `vendor_id = V2, currency_id = THB` (forced via direct API call — UI prevents the mixed-vendor selection by binding lines to the header `vendor_id`) | Reject — `PO_VAL_013`. Server returns `"All lines on a PO must share the header vendor and currency. Split into separate POs by vendor+currency."`; the single-vendor / single-currency invariant is enforced at submit. |
| PUR-VAL-09 | Convert an approved PR to a PO but the bridge row is missing | Force a direct insert of a `tb_purchase_order_detail` row with `po_type = purchase_request` on the parent PO and no entry in `tb_purchase_order_detail_tb_purchase_request_detail`; click Submit | Reject — `PO_VAL_014`. Server returns `"PR-sourced PO lines must be linked to an originating PR line via the bridge table."`; the From-PR wizard always writes the bridge row, so this validation primarily guards direct-API / data-fix paths. |
| PUR-VAL-10 | Attempt to amend `vendor_id` or `currency_id` on an `approved` / `sent_or_print` PO | Open the PO and try to change the header vendor or currency via direct `PUT .../purchase-orders/:id` (UI disables the fields) | Reject — `PO_VAL_016`; the update path requires `po_status = draft`. Nothing is mutable after `approved` except via Cancel / Close. |
| PUR-VAL-11 | Discount or tax larger than the line value | Line `order_qty = 2`, `price = ฿100.00`, `discount_amount = ฿250.00` (or `tax_amount = ฿250.00`); call `POST /verify` `{ verify_state: 'save' }` then **Save** | Reject — `PO_VAL_017` (`findAmountCapIssues`, `verify-save.ts` L148): `discount_exceeds_line` / `tax_exceeds_line` issue on the line; verify returns `200 { is_valid: false }` listing it alongside any other failing rule. |
| PUR-VAL-12 | Line without a delivery location | Create payload whose `purchase_order_detail.add[0]` omits `location_id` | Reject — `PO_VAL_019` (`create-purchase-order.dto.ts` L65 `location_id: z.string().uuid()`): Zod validation error before the service runs. |
| PUR-VAL-13 | Send Email from a non-emailable status | PO at `draft` or `in_progress`; call `POST .../purchase-orders/:id/send-email` | Reject — "Purchase order in status draft cannot be emailed to a vendor" (`EMAILABLE_PO_STATUSES`); the React header hides **Send Email** outside `approved | sent_or_print | partial | closed | completed`. |

## 4. Edge Cases

| # | Scenario | Condition | Expected |
| - | -------- | --------- | -------- |
| PUR-EDGE-01 | Zero-quantity submit-time guard combined with line save-time guard | Purchaser tries to save a line with `order_qty = 0` (caught at save by `PO_VAL_008`); then tries to bypass UI by submitting the PO with the line edited to `0` post-save via direct API call | Both the save-line and submit-time runs of `PO_VAL_008` reject the line with `"Order quantity must be greater than zero and a unit of measure is required."`; submit aborts; line stays at the prior valid value; no `tb_purchase_order_detail` row is mutated. |
| PUR-EDGE-02 | Maximum decimal precision on line `price` | Line `price = 99999999999.99999` (15 integer + 5 fraction digits, the upper bound of `Decimal(20, 5)`) with `order_qty = 1.99999`; tax_rate `7%`, no discount | Accepted at storage; `sub_total_price = Round(99999999999.99999 × 1.99999, 2)` computed per `PO_CALC_001`; rounding uses half-up via `PO_CALC_012`; `base_qty = Round(1.99999 × conv_factor, 3)` per `PO_CALC_006`; header `total_qty` aggregates in base UoM at 3 dp per `PO_CALC_011`; all stored Decimals fit within `Decimal(20, 5)` for money and `Decimal(15, 5)` for rates. |
| PUR-EDGE-03 | Back-dated `delivery_date` equal to `order_date` (lower bound of `PO_VAL_006`) | Set `order_date = 2026-05-15`, `delivery_date = 2026-05-15`; click Save / Submit | Accepted — `PO_VAL_006` enforces `delivery_date >= order_date` (inclusive). The same-day case passes; PO saves and submits normally. Setting `delivery_date = order_date − 1d` would fail (covered by PUR-VAL-04). |
| PUR-EDGE-04 | Multi-currency (or multi-delivery-date) consolidation in the Convert-to-PO dialog | Select two approved PRs in step 1: `PR-A` with `currency_id = THB` and `PR-B` with `currency_id = USD`, both for `vendor_id = V1` and the same `delivery_date` | The dialog's step 2 auto-groups by `(vendor_id, delivery_date, currency_id)` → **two** draft-PO groups (one per currency), not one — confirmed via `buildPoGroupKey` in `purchase-order.service.ts`. Each resulting PO satisfies `PO_VAL_013`. The same split applies if the two PRs share a currency but differ on `delivery_date`. A direct API call to force both lines into a single PO is rejected with `"All lines on a PO must share the header vendor and currency. Split into separate POs by vendor+currency."` (`PO_VAL_013`). |
| PUR-EDGE-05 | Concurrent edits on the same draft PO from two Purchaser sessions | Purchaser A and Purchaser B both load draft PO `PO-X` at `doc_version = 3`; A saves a qty change at `T` (`doc_version → 4`); B saves a price change at `T + 1s` using the stale `doc_version = 3` | First save wins: A's qty change is persisted, `doc_version = 4`. B's save is rejected by the optimistic-concurrency guard with `"This PO was modified by another user. Please refresh and re-apply your changes."`; B's client prompts a refresh. No double-write or lost-update is created. |
| PUR-EDGE-06 | Send Email with a bad recipient / disabled profile | PO at `po_status = approved`; (a) `to[]` contains an address the SMTP relay rejects; (b) the chosen `profile_id` is disabled | (a) `send-email` returns HTTP 200 `{ sent: false, rejected: ['bad@…'] }`; PO stays `approved`; `tb_activity` `email_sent` records the failed attempt; the dialog lists the rejected address for correction. (b) `400` "Email profile is disabled" (or "Email profile not found") — pre-flight validation, nothing logged, PO stays `approved`. **Corrected 2026-09-22:** the previous version quoted vendor-master checks ("Vendor email is not configured…", "Vendor is no longer active…") that do not exist in `sendEmailToVendor`; recipients come from the dialog, not from `tb_vendor.email`. |
| PUR-EDGE-08 | Two PRs with different requested dates, same vendor + currency, converted with a `delivery_date` override | API: `POST .../purchase-orders/group-pr` `{ pr_ids: [A, B], delivery_date: '2026-10-01' }` | One group, not two — the override collapses the date dimension of `buildPoGroupKey`; `confirm-pr` with the same override creates one PO with `delivery_date = 2026-10-01`. Without the override the same PRs split into two POs (PUR-EDGE-04). The React page cannot exercise this yet (sends no overrides). |
| PUR-EDGE-07 | Submit a PO immediately after a soft-delete on the same `po_no` (uniqueness re-use) | A prior PO with `po_no = PO-2026-000123` was soft-deleted (`deleted_at IS NOT NULL`) per `PO_POST_012`; the Purchaser drafts a new PO and the numbering service issues the same `po_no` | Accepted — the unique index `@@unique([po_no, deleted_at])` allows reuse because `deleted_at` differs. New PO saves and submits normally; the prior soft-deleted row remains in the database for audit. Hard-delete-in-draft is reserved to the Procurement Manager (`PO_AUTH_005`) so this scenario originates from a Manager-driven cleanup. |
