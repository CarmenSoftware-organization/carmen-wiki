> ⚠️ **Major correction this pass.** The previous version of this page described a Procurement-Manager-specific "high-value approval gate" (amount threshold / pricelist-deviation routing) and an entire "configurational surface" — vendor-ranking edits, Convert-to-PO grouping-rule edits, unit-conversion edits, pricelist-tolerance edits, threshold edits, and bulk void/close — with ~15 scenarios (PM-HP-07 through PM-HP-09 and most of the PERM/VAL/EDGE sections) that had **no matching e2e test IDs and no matching route or component** in current source. A repo-wide search for vendor-ranking and bulk-action code returned nothing relevant, and no PM-specific config editor was found. Those scenarios are removed here rather than rewritten with invented mechanics; this page now covers only the confirmed, e2e-grounded approval flow (`403-po-approver-journey.spec.ts`) plus the confirmed Close/Cancel overrides.
>
> **The amount-threshold half of that claim, however, was itself wrongly dismissed** — a follow-up search confirms `total_amount`-based stage routing is real, just generic (the workflow's `routing_rules`, configured from the **Routing** tab of `/system-admin/workflow`, shared by PR/PO/SR — not a PM-specific gate or config screen). See `PO_AUTH_004` in [02-business-rules.md](./02-business-rules.md).

This page captures the test scenarios that the Procurement Manager persona (the `fc@blueledgers.com` fixture user in current e2e specs) drives in the `purchase-order` module. Unlike the Purchaser — who owns the document end-to-end — the Procurement Manager acts as a **workflow-stage approver**: whichever stage the tenant's workflow definition assigns them to, with *authorization to act* gated purely by `user_action.execute[]` (`PO_AUTH_011`) — not amount or deviation. *Which* stage is next, however, can itself be amount-driven: the assigned workflow's `routing_rules` may skip or jump stages by `total_amount` (`PO_AUTH_004`); no deviation-percentage condition field was found in current source. At the current stage the Manager runs **Approve** (`PO_POST_004` if final — landing on `approved`, **not** transmitting — else `PO_POST_003`), **Send Back** (`PO_POST_005` — resets the stage cursor, does **not** change `po_status`), or **Reject** (direct, terminal `in_progress → voided`), and from mobile **swipe-approve** (`PO_AUTH_012`). Like any user with the PO open, the Manager can **Close** (`{in_progress, approved, sent_or_print, partial} → closed`, `PO_POST_011`) or **Cancel**. **Corrected 2026-09-22:** soft-delete-in-draft is an owner / super-admin right (`PO_AUTH_005`), not a Manager one.

## 2. Permission / Authorization

| # | Scenario | Expected behaviour (allow/deny + reason) |
| - | -------- | --------------------------------------- |
| PM-PERM-01 | PM approves a PO whose current `workflow_current_stage` assigns them via `user_action.execute[]` | **Allow** per `PO_AUTH_011`. The Approve PO action drives `in_progress → sent` via `PO_POST_004` if this is the final stage (TC-PO-070305..TC-PO-070307), or advances the stage cursor otherwise; Send Back resets the stage without changing `po_status` (`PO_POST_005`, TC-PO-070308..TC-PO-070309); Reject drives `in_progress → voided` directly (TC-PO-070310..TC-PO-070311). |
| PM-PERM-02 | PM attempts to approve a PO whose current stage does not assign them | **Deny.** The PO does not appear in the Manager's My Approvals queue because `user_action.execute` for its current stage does not contain the Manager's user-id. A direct API call to advance the stage is rejected by `PO_AUTH_011` with `"You are not in the authorised approver set for this stage"`. **Corrected this pass:** the previous version of this scenario framed the denial around an amount threshold; the actual gate is purely `user_action.execute[]` membership. |
| PM-PERM-03 | PM Cancels or Closes a PO at `approved` / `sent_or_print` / `partial` | **Allow.** `Cancel` accepts `{draft, in_progress, approved, sent_or_print}`; `Close` accepts `{in_progress, approved, sent_or_print, partial}`; both land on `closed`. Neither has a role gate beyond authentication (`cancel()` L3400, `closePO()` L6083; gateway has no `@Permission` on either route). |
| PM-PERM-04 | PM removes a `draft` PO created by a Purchaser | **Deny.** `remove()` requires `isDocumentOwner` or platform super-admin (`PO_AUTH_005`); the Manager's alternative is **Cancel** (→ `closed`). **Corrected 2026-09-22** from "Manager-only soft-delete". |

## 3. Validation / Error

| # | Scenario | Trigger | Expected error |
| - | -------- | ------- | -------------- |
| PM-VAL-01 | PM attempts any action (Approve / Send Back / Reject / Cancel / Close) on a PO already at a terminal state (`voided`, `completed`, `closed`) | Open a `voided` PO; the toolbar buttons are hidden / disabled; force a direct API call to advance the status | Reject — per `PO_VAL_015`. Approve / reject / review require `po_status = in_progress` (`approve()` L2845 `where: { id, po_status: in_progress }`); `cancel()` returns "Cannot cancel purchase order with status 'voided'. Only draft, in_progress, approved, or sent_or_print orders can be cancelled."; `closePO()` the analogous close message. |
| PM-VAL-02 | PM attempts to Close a `partial` PO where all lines are already fully received (`received_qty = order_qty − cancelled_qty` on every line) | Open a `partial` PO whose every line satisfies the full-receipt condition; click **Close** | Reject — the close handler detects that the PO should be at `completed` via `PO_POST_007` (the GRN-driven transition has not yet run, or has run but a race left the status at `partial`). Server returns `"PO is fully received — please refresh; the document will move to completed."` `PO_POST_011` does not fire because there is no remainder to write back to `cancelled_qty`. |

## 4. Edge Cases

| # | Scenario | Condition | Expected |
| - | -------- | --------- | -------- |
| PM-EDGE-01 | Reject fires while another approver's send-back is in flight (optimistic-concurrency race) | PM A opens the PO and clicks Send Back at `doc_version = 3`; PM B (a co-approver on the same stage) opens the same PO and clicks Reject at `T + 500ms`, still holding `doc_version = 3` | First write wins: whichever call reaches the server first commits and increments `doc_version`. The second call's `doc_version` check fails and the API returns `"This PO was modified by another user. Please refresh and re-apply your changes."` No double-write; the client refreshes to see the actual outcome (either `in_progress` with a reset stage cursor, or `voided`). |
