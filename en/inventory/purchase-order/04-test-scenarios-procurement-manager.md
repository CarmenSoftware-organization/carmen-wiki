# Purchase Order — Test Scenarios — Procurement Manager

> **At a Glance**
> **Persona:** Procurement Manager (workflow-stage approver) &nbsp;·&nbsp; **Module:** [purchase-order](/en/inventory/purchase-order) &nbsp;·&nbsp; **Scenarios:** ~12
> **Categories:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **E2E coverage:** maps to `401-po.spec.ts`, `403-po-approver-journey.spec.ts` in `../carmen-inventory-frontend-e2e/`

> ⚠️ **Major correction this pass.** The previous version of this page described a "high-value approval gate" (amount threshold / pricelist-deviation routing) and an entire "configurational surface" — vendor-ranking edits, Convert-to-PO grouping-rule edits, unit-conversion edits, pricelist-tolerance edits, threshold edits, and bulk void/close — with ~15 scenarios (PM-HP-07 through PM-HP-09 and most of the PERM/VAL/EDGE sections) that had **no matching e2e test IDs and no matching route or component** in current source. A repo-wide search for `threshold`, vendor-ranking, and bulk-action code returned nothing relevant. Those scenarios are removed here rather than rewritten with invented mechanics; this page now covers only the confirmed, e2e-grounded approval flow (`403-po-approver-journey.spec.ts`) plus the confirmed Close/Cancel overrides.

This page captures the test scenarios that the Procurement Manager persona (the `fc@blueledgers.com` fixture user in current e2e specs) drives in the `purchase-order` module. Unlike the Purchaser — who owns the document end-to-end — the Procurement Manager acts as a **workflow-stage approver**: whichever stage the tenant's workflow definition assigns them to, gated purely by `user_action.execute[]` (`PO_AUTH_011`) — no amount threshold or deviation percentage was found in current source. At the current stage the Manager runs **Approve** (`PO_POST_004` if final, else `PO_POST_003`), **Send Back** (`PO_POST_005` — resets the stage cursor, does **not** change `po_status`), or **Reject** (direct, terminal `in_progress → voided`). The Manager additionally holds **soft-delete-in-draft** (`PO_AUTH_005`) and, shared with the Inventory Manager, **Close** (`{sent, partial, in_progress} → closed`, `PO_AUTH_008`, `PO_POST_011`).

## 2. Permission / Authorization

| # | Scenario | Expected behaviour (allow/deny + reason) |
| - | -------- | --------------------------------------- |
| PM-PERM-01 | PM approves a PO whose current `workflow_current_stage` assigns them via `user_action.execute[]` | **Allow** per `PO_AUTH_011`. The Approve PO action drives `in_progress → sent` via `PO_POST_004` if this is the final stage (TC-PO-070305..TC-PO-070307), or advances the stage cursor otherwise; Send Back resets the stage without changing `po_status` (`PO_POST_005`, TC-PO-070308..TC-PO-070309); Reject drives `in_progress → voided` directly (TC-PO-070310..TC-PO-070311). |
| PM-PERM-02 | PM attempts to approve a PO whose current stage does not assign them | **Deny.** The PO does not appear in the Manager's My Approvals queue because `user_action.execute` for its current stage does not contain the Manager's user-id. A direct API call to advance the stage is rejected by `PO_AUTH_011` with `"You are not in the authorised approver set for this stage"`. **Corrected this pass:** the previous version of this scenario framed the denial around an amount threshold; the actual gate is purely `user_action.execute[]` membership. |
| PM-PERM-03 | PM Cancels or Closes a PO at `sent` / `partial` | **Allow.** `Cancel` accepts `{draft, in_progress, sent}`; `Close` accepts `{sent, partial, in_progress}`; both land on `closed`. Neither is exclusive to this role in current source — the specific role gate on these two endpoints beyond generic authentication was not confirmed this pass. |

## 3. Validation / Error

| # | Scenario | Trigger | Expected error |
| - | -------- | ------- | -------------- |
| PM-VAL-01 | PM attempts any action (Approve / Send Back / Reject / Cancel / Close) on a PO already at a terminal state (`voided`, `completed`, `closed`) | Open a `voided` PO; the toolbar buttons are hidden / disabled; force a direct API call to advance the status | Reject — per `PO_VAL_015` ("Status transitions follow the state machine in Section 5; out-of-order transitions are blocked"). Server returns `"Invalid status transition from voided to sent"` (or the analogous from-state). |
| PM-VAL-02 | PM attempts to Close a `partial` PO where all lines are already fully received (`received_qty = order_qty − cancelled_qty` on every line) | Open a `partial` PO whose every line satisfies the full-receipt condition; click **Close** | Reject — the close handler detects that the PO should be at `completed` via `PO_POST_007` (the GRN-driven transition has not yet run, or has run but a race left the status at `partial`). Server returns `"PO is fully received — please refresh; the document will move to completed."` `PO_POST_011` does not fire because there is no remainder to write back to `cancelled_qty`. |

## 4. Edge Cases

| # | Scenario | Condition | Expected |
| - | -------- | --------- | -------- |
| PM-EDGE-01 | Reject fires while another approver's send-back is in flight (optimistic-concurrency race) | PM A opens the PO and clicks Send Back at `doc_version = 3`; PM B (a co-approver on the same stage) opens the same PO and clicks Reject at `T + 500ms`, still holding `doc_version = 3` | First write wins: whichever call reaches the server first commits and increments `doc_version`. The second call's `doc_version` check fails and the API returns `"This PO was modified by another user. Please refresh and re-apply your changes."` No double-write; the client refreshes to see the actual outcome (either `in_progress` with a reset stage cursor, or `voided`). |
