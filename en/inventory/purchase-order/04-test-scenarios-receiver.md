# Purchase Order — Test Scenarios — Receiver

> **At a Glance**
> **Persona:** Receiver (Store Keeper + Inventory Manager) &nbsp;·&nbsp; **Module:** [purchase-order](/en/inventory/purchase-order) &nbsp;·&nbsp; **Scenarios:** ~22
> **Categories:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **E2E coverage:** no dedicated Receiver spec yet; shared coverage in `tests/401-po.spec.ts` (TC-PO-340001..340003 GRN sync, TC-PO-060501..060504 Close) in `../carmen-inventory-frontend-e2e/`

> **Executable coverage (2026-09-22):** no Receiver-persona PO catalog exists; PO-side effects of receipt are covered from the GRN suite (`tests/501-*`, see [good-receive-note](/en/inventory/good-receive-note) `04-test-scenarios`) and `docs/user-stories/401-po.md` (60 cases; gap `docs/test-cases/gaps/401-po-create-flows-gap.md`, 29). Scenarios below were corrected to source HEAD: GRN is allowed from `approved` (before the vendor email), FOC quantities are received and stocked, and every `sent` below became `sent_or_print`.

This page captures the test scenarios that the Receiver persona (the **Store Keeper** at the dock plus the **Inventory Manager** who oversees closure for the location) directly drives in the `purchase-order` module. The Receiver's involvement begins when the PO reaches `po_status = approved` (receipt is unlocked at approval — `findOnePoForGrn` accepts `approved`, `sent_or_print`, `partial`) and ends when the PO leaves the receipt zone — either through `completed` (full receipt), `partial` (open balance carried forward), or `closed` (anyone closes an `{in_progress, approved, sent_or_print, partial}` PO). The GRN posting itself lives in the downstream `[good-receive-note](/en/inventory/good-receive-note)` module; this page captures only the **PO-side effects** — how a GRN flips `tb_purchase_order.po_status` via `PO_POST_006` (`sent → partial`) and `PO_POST_007` (`* → completed`), how the Inventory Manager closes a PO with the remainder written to `cancelled_qty` via `PO_POST_011`, and how the PO line counters (`received_qty`, `cancelled_qty`) advance against `order_qty` ([03-user-flow-receiver.md](./03-user-flow-receiver.md) Section 2). Scenarios are grouped into the happy paths described in the user flow, the RBAC boundary enforced by `PO_AUTH_008` (Receiver / Inventory Manager scope) versus `PO_AUTH_001`–`PO_AUTH_003` (Purchaser scope), the validation rules around `received_qty`, over-receipt tolerance, and voided / closed-PO state guards, and a small set of edge cases around tolerance boundaries, decimal precision, concurrency, and multi-currency context. **Corrected this pass:** a prior version of this overview also cited `PO_AUTH_010` (segregation of duties, GRN poster ≠ PO buyer/transmitter) as an enforced rule — a repo-wide search of both the GRN and PO backend services found no matching code; treat it as unconfirmed design intent, not a live guard. **Also corrected this pass:** a prior version referenced an `accepted_qty` field distinct from `received_qty` throughout the scenarios below — a repo-wide search of the Prisma schema and both the frontend and backend source found zero hits for `accepted_qty` / `acceptedQty`. No such field exists; this mirrors the finding already confirmed and corrected in the [good-receive-note](/en/inventory/good-receive-note) module's own resync pass. Every scenario below has been rewritten to post only `received_qty`, with quality issues or shortfalls recorded as a lower `received_qty` plus a free-text GRN comment rather than a second structured quantity. Cross-persona handoffs that pivot off the Receiver (`X-PO-03`, `X-PO-04`, `X-PO-06`, `X-PO-08`) live in the parent overview, not here.

## 1. Happy Path

| RCV-HP-01 | GRN full receipt against a single-line `sent_or_print` PO drives `→ completed` | PO `PO-X` at `po_status = sent_or_print` with one line: `order_qty = 10`, `received_qty = 0`, `cancelled_qty = 0`; vendor delivery matches PO line exactly; Receiver logged in with `can_use = true` on the line's location (`tb_location_user`) | 1. In `[good-receive-note](/en/inventory/good-receive-note)` start a new GRN → pick the vendor (`GET .../purchase-orders/grn/vendor`) → pick `PO-X` (`GET .../purchase-orders/grn/vendor/:vendor_id`, line shows `can_use = true`). 2. `GET .../purchase-orders/grn/:id` builds the draft: header inherits `vendor_id`, `currency_id`; the line carries `remain_qty = 10`. 3. Post. | GRN detail row written; `tb_purchase_order_detail.received_qty` rises `0 → 10` (`incrementPoDetailReceivedQty`); bridge `received_qty` incremented; inventory on-hand incremented by 10. `updatePoStatuses` finds every line `received_qty ≥ order_qty − cancelled_qty` → `po_status = completed` per `PO_POST_007`; the PO detail line now shows the GRN number under the Order / GRN column (`pr_details[].grn[]`, PR-sourced lines only); PO becomes read-only for receipt. A later **Send Email** still sends and logs, but `markPoAsSent` matches `approved` only, so the status stays `completed` / `partial`. |

| RCV-HP-02 | GRN partial receipt against a single-line `sent_or_print` PO drives `→ partial` | PO `PO-Y` at `po_status = sent_or_print` with one line: `order_qty = 10`, `received_qty = 0`, `cancelled_qty = 0`; vendor delivers only 6 of 10 today | 1. New GRN → vendor → `PO-Y`. 2. Enter `received_qty = 6`. 3. Review variance: short by 4. 4. Post. | `tb_purchase_order_detail.received_qty` rises `0 → 6`; pending balance `order_qty − received_qty − cancelled_qty = 10 − 6 − 0 = 4` carried forward (`remain_qty` on the next GRN draft). Since at least one line still has `received_qty < order_qty − cancelled_qty`, `po_status = sent_or_print → partial` per `PO_POST_006`; PO stays open for further GRN posts. |
| RCV-HP-03 | Partial then remainder — multi-step GRN cycle reaches `completed` via `partial` | PO `PO-Z` at `po_status = partial` from RCV-HP-02 (`order_qty = 10`, `received_qty = 6`, `cancelled_qty = 0`, pending balance 4); vendor delivers the remaining 4 in a follow-up shipment | 1. New GRN → vendor → `PO-Z` (still listed: `partial` is receivable). 2. GRN draft shows `remain_qty = 4`. 3. Enter `received_qty = 4`. 4. Post. | `tb_purchase_order_detail.received_qty` rises `6 → 10`; pending balance `= 0`. Every line now satisfies `received_qty + cancelled_qty ≥ order_qty` → `po_status = partial → completed` per `PO_POST_007`; full receipt history is `sent_or_print → partial → completed`; two GRN rows persist against the same PO line and both GRN numbers show on the PO line (TC-PO-340003); no further GRNs accepted. |
| RCV-HP-04 | Quality issue logged via a lower `received_qty` (no separate acceptance quantity) | PO `PO-Q` at `po_status = sent_or_print`, line `L1`: `order_qty = 10`, `received_qty = 0`; vendor delivers 10 but 2 fail inspection (damaged cartons) | 1. New GRN → vendor → `PO-Q`. 2. Enter `received_qty = 8` (only the 8 that pass inspection). 3. Write a GRN comment noting "2 damaged on arrival — refused, staged for vendor return." 4. Post. | GRN posts `received_qty = 8`; `tb_purchase_order_detail.received_qty` rises `0 → 8`; inventory on-hand rises by `8` only, at save. There is no separate `accepted_qty` field or per-line quality-inspection status (zero hits repo-wide); the 2 damaged units are never recorded as physically received, and the discrepancy exists only as the free-text GRN comment. Since `received_qty (8) + cancelled_qty (0) < order_qty (10)`, the line has a pending balance of 2 and `po_status = sent_or_print → partial` per `PO_POST_006`. If the 2 units were received and later found defective, the vendor-side correction is a [Credit Note](/en/inventory/purchase-order/credit-note) of type `quantity_return` against this GRN — each product on a GRN can be credited once. |
| RCV-HP-05 | Close a `partial` PO with remainder written to `cancelled_qty` | PO `PO-C` at `po_status = partial`, line `L1`: `order_qty = 10`, `received_qty = 6`, `cancelled_qty = 0`; vendor confirms they cannot supply the remaining 4 (out of stock / discontinued); any authenticated user with the PO open | 1. Open `PO-C` → click **Close** on the PO header (TC-PO-060503, TC-PO-060504). 2. Confirm in the close dialog (`POST .../purchase-orders/:id/close` `{}` — no reason field on the endpoint). 3. Optionally add a comment (e.g. "vendor cannot supply remainder — discontinued SKU"). | For each line still pending, the application writes the remainder to `cancelled_qty` so that `received_qty + cancelled_qty = order_qty`: `L1.cancelled_qty = 4`, `received_qty = 6`, `order_qty = 10`. `po_status = partial → closed` per `PO_POST_011`; buyer notified; `closed` is terminal — no further GRNs accepted, no return to `partial`. **Corrected 2026-09-22:** no Inventory-Manager role gate and no mandatory reason exist in `closePO()`. |
| RCV-HP-06 | GRN against a multi-line PO with mixed full / partial line outcomes | PO `PO-M` at `po_status = sent_or_print` with three lines: `L1` (`order_qty = 10`, pending 10), `L2` (`order_qty = 5`, pending 5), `L3` (`order_qty = 8`, pending 8); vendor delivers `L1 = 10` (full), `L2 = 3` (short by 2), `L3 = 8` (full) | 1. Open `PO-M` → **Receive**. 2. Per-line entry: `L1` `received_qty = 10`; `L2` `received_qty = 3`; `L3` `received_qty = 8`. 3. Variance summary: `L2` short by 2. 4. **Post**. | `L1.received_qty = 0 → 10`, `L2.received_qty = 0 → 3`, `L3.received_qty = 0 → 8`. Line-wise evaluation: `L1` and `L3` are full but `L2` still has `received_qty (3) < order_qty − cancelled_qty (5)`. Header rule: since at least one line is open, `po_status = sent → partial` per `PO_POST_006` — NOT `completed`. PO stays open for a follow-up GRN against `L2` only (Receiver may also escalate to Inventory Manager to close on the `L2` remainder if vendor cannot supply). |

## 2. Permission / Authorization

| # | Scenario | Expected behaviour (allow/deny + reason) |
| - | -------- | --------------------------------------- |
| RCV-PERM-01 | Receiver posts a GRN against a PO at `po_status ∈ {approved, sent_or_print}` | **Allow** per `PO_AUTH_008` (`receivableStatuses = {approved, sent_or_print, partial}`) when the line's location has `can_use = true` for the caller. The `[good-receive-note](/en/inventory/good-receive-note)` Create flow accepts the PO selection; PO-side counters update; `po_status` transitions per `PO_POST_006` / `PO_POST_007` based on line-wise evaluation. |
| RCV-PERM-01b | Receiver without `tb_location_user` membership for the line's location | **Deny (UI) / unconfirmed (API).** `GET .../purchase-orders/grn*` returns `can_use = false` on that location and the picker disables it; whether the GRN create endpoint re-checks location membership server-side belongs to the GRN module's own pass. |
| RCV-PERM-02 | Receiver attempts a GRN against a PO at `po_status = draft` or `in_progress` | **Deny** per `PO_AUTH_008`. The PO does not appear in the GRN module's vendor / PO picker (`findAllForGrn` filters `po_status in {approved, sent_or_print, partial}`); a direct `GET .../purchase-orders/grn/:id` returns "Purchase order must be in approved, sent_or_print or partial status to create a goods received note"; counters are unchanged. |
| RCV-PERM-03 | Receiver attempts to modify PO header (vendor, currency, delivery date) | **Deny — Purchaser-only.** Per `PO_AUTH_002` (Purchaser scope), header / line edits are reserved to the assigned buyer; the Receiver may neither edit the header nor the line price / qty / discount. The PO detail page in the Receiver's view is read-only for header / lines — only the **Receive** and (for Inventory Manager) **Close** buttons are interactive. A direct API edit call returns `"You are not authorised to edit this PO at the current stage"`. |
| RCV-PERM-04 | GRN poster = PO buyer / transmitter | **Unconfirmed.** A prior version of this scenario asserted a segregation-of-duties rule (`PO_AUTH_010`) rejecting this case — a repo-wide search of both the GRN and PO backend services found no matching buyer-vs-poster check. Treat this as unverified rather than a confirmed deny. |
| RCV-PERM-05 | Receiver (Store Keeper) closes a `partial` PO (early termination) | **Allow.** `closePO()` (`{in_progress, approved, sent_or_print, partial} → closed`, `PO_POST_011`) has no role gate beyond authentication and the gateway route has no `@Permission`. **Corrected 2026-09-22:** the previous version required an Inventory Manager role and quoted an error string ("Close from status partial requires the Inventory Manager role.") that does not exist. |
| RCV-PERM-06 | Receiver attempts a GRN against a PO at `po_status = completed` or `closed` | **Deny — terminal status.** Per `PO_POST_007` / `PO_POST_011`, `completed` and `closed` are terminal for receipt purposes; no further GRNs are accepted. The PO does not appear in the GRN module's open-PO list; a direct API call returns `"PO is at terminal receipt status <status> — no further receipts can be posted."` |
| RCV-PERM-07 | Inventory Manager closes a `partial` PO they did NOT raise | **Allow** per `PO_AUTH_008`. The Inventory Manager's authority is tied to the delivery location, not to PO authorship. The close succeeds with reason text appended to `tb_purchase_order_comment`. |

## 3. Validation / Error

| # | Scenario | Trigger | Expected error |
| - | -------- | ------- | -------------- |
| RCV-VAL-01 | Over-receipt without tolerance — `received_qty > pending balance` | PO line `L1`: `order_qty = 10`, `received_qty = 0`, `cancelled_qty = 0`; tenant over-receipt tolerance disabled or set to `0%`; Receiver enters `received_qty = 12` | Reject — `PO_XMOD_004`. Server returns `"Received quantity exceeds the pending balance and tenant over-receipt tolerance is not configured."`; the GRN line is capped at the pending qty (10) or the post is blocked entirely; PO counters unchanged. |
| RCV-VAL-02 | Zero `received_qty` on a GRN line | Receiver enters `received_qty = 0` on a line and clicks **Post** | Reject — `PO_XMOD_003` / GRN-side validation. Server returns `"Received quantity must be greater than zero on every GRN line; remove the line if nothing was received against it."`; the GRN cannot post with a zero-qty line; PO counters unchanged. |
| RCV-VAL-03 | GRN against a `voided` PO | PO `PO-V` at `po_status = voided` (reached only via a direct, terminal reject from `in_progress` — never from `approved` / `sent_or_print` / `partial`); Receiver attempts to open the GRN flow from the GRN module directly | Reject — `voided` is terminal. The PO does not appear in the open-PO list; `GET .../purchase-orders/grn/:id` returns "Purchase order must be in approved, sent_or_print or partial status to create a goods received note". Since `voided` is only reachable from `in_progress`, such a PO never reached a receivable status at all. |
| RCV-VAL-04 | Partial GRN when remaining qty is unreceivable (negative pending) | PO line `L1`: `order_qty = 10`, `received_qty = 8`, `cancelled_qty = 2` (so pending balance = 0); Receiver attempts to post a GRN with `received_qty = 1` on `L1` | Reject — `PO_XMOD_003`. Server returns `"PO line has no remaining open balance — received_qty (8) + cancelled_qty (2) = order_qty (10)."`; the GRN line cannot post on `L1`; if other lines on the PO are still open, those may post independently. |
| RCV-VAL-05 | GRN against a PO whose vendor was flipped to `is_active = false` after transmission | PO `PO-W` at `po_status = sent_or_print`; `tb_vendor.is_active = false` on the PO's vendor | **Unconfirmed — no code path found.** `findOnePoForGrn` / `findAllForGrn` filter on `po_status` and `deleted_at` only; a grep of `purchase-order.service.ts` for an `is_active` check on `tb_vendor` in the GRN-facing queries found none, and the quoted message "Vendor is no longer active and cannot deliver further goods." does not exist. Expected at HEAD: the GRN posts normally; blacklisting is a vendor-master concern documented in [master-data/vendor](/en/inventory/master-data/vendor). |

## 4. Edge Cases

| # | Scenario | Condition | Expected |
| - | -------- | --------- | -------- |
| RCV-EDGE-01 | Exact tolerance boundary on over-receipt | PO line `L1`: `order_qty = 10`, `received_qty = 0`, `cancelled_qty = 0`; tenant over-receipt tolerance = `5%`; Receiver enters `received_qty = 10.5` (exactly at the upper bound) | Accepted — `PO_XMOD_004`. `received_qty = 10.5` is within tolerance (`10 × 1.05 = 10.5`); GRN posts; `tb_purchase_order_detail.received_qty = 10.5`; line evaluation: `received_qty (10.5) ≥ order_qty − cancelled_qty (10)` → fully received; `po_status = sent_or_print → completed` per `PO_POST_007`. Setting `received_qty = 10.51` would breach the bound and be rejected per RCV-VAL-01. (Tolerance enforcement itself lives in the GRN module; the PO side only sees the resulting `received_qty`.) |
| RCV-EDGE-02 | Decimal precision on `received_qty` | Receiver enters `received_qty = 5.123` on a line whose order UoM allows 3-dp precision; conversion factor `1.234567`, `received_base_qty` computed in storage UoM | Accepted at storage; `received_qty` stored at the line's UoM precision (3 dp); `received_base_qty` computed as `received_qty × conv_factor` for inventory roll-up (per [good-receive-note/01-data-model.md](/en/inventory/good-receive-note/01-data-model) — no separate `accepted_qty` field exists to track a second precision); PO `received_qty` aggregates without precision loss; all stored Decimals fit within `Decimal(20, 5)`. |
| RCV-EDGE-03 | Concurrent GRN posts on the same PO from two Receiver sessions | Receiver A and Receiver B both open `PO-X` (`po_status = sent_or_print`, `received_qty = 0`, `order_qty = 10`); A posts `received_qty = 6` at `T`; B posts `received_qty = 4` at `T + 500ms` against the same line, both with `doc_version = 3` snapshots | First post wins atomically: A's GRN posts, `tb_purchase_order_detail.received_qty = 0 → 6`, `po_status = sent_or_print → partial`, `doc_version → 4`. B's post is reconciled against the new state — either the GRN module re-reads `pending_qty = 4` and posts B's `received_qty = 4` cleanly (advancing `received_qty → 10`, `po_status → completed`), or the optimistic-concurrency guard rejects B with `"This PO was modified by another user. Please refresh and re-apply your changes."` and B retries. No double-write, no lost-update, no `received_qty > order_qty` overflow outside the over-receipt tolerance. |
| RCV-EDGE-04 | Multi-currency context — PO base currency matters for valuation | PO `PO-F` with `currency_id = USD`, `exchange_rate = 36.50` (against base `THB`); line `L1`: `order_qty = 10`, `price = $50.00`; Receiver posts GRN `received_qty = 10` | GRN posts at the PO's transaction currency (`USD`); inventory valuation is dual-posted — transaction value `$500.00` and base value `Round($500.00 × 36.50, 2) = ฿18,250.00` per `PO_CALC_008`–`PO_CALC_011`; the PO's `exchange_rate` snapshot at the time of PO submission is the rate used for the GRN-driven inventory valuation, not the current spot rate; `po_status = sent_or_print → completed` per `PO_POST_007`. |
