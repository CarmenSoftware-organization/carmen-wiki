# ใบสั่งซื้อ (Purchase Order) — Test Scenarios — Procurement Manager

> **At a Glance**
> **Persona:** Procurement Manager (workflow-stage approver) &nbsp;·&nbsp; **Module:** [purchase-order](/th/inventory/purchase-order) &nbsp;·&nbsp; **Scenarios:** ~12
> **Categories:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **E2E coverage:** map ไปยัง `401-po.spec.ts`, `403-po-approver-journey.spec.ts`, `201-my-approvals.spec.ts` ใน `../carmen-inventory-frontend-e2e/`

> **Executable coverage (2026-09-22):** catalog `../carmen-inventory-frontend-e2e/docs/user-stories/403-po-approver-journey.md` (19 case) + `docs/user-stories/201-my-approvals.md` (20 case, คิว PR/PO/SR ที่ใช้ร่วมกัน); gap report `docs/test-cases/gaps/403-po-approver-journey-gap.md` (49) + `gaps/201-my-approvals-gap.md` (34); spec `tests/403-po-approver-journey.spec.ts`, `tests/201-my-approvals.spec.ts` ข้อความ approve dialog และ regex badge `/approved|sent/i` ของ spec 403 ยังผ่านที่ HEAD เพราะการอนุมัติขั้นสุดท้ายตอนนี้ลงที่ status `approved` จริง; ข้อความ dialog ของ FE "Once approved, the PO will be sent to the vendor" (`messages/en.json` L3899) ล้าสมัยแล้ว — การอนุมัติไม่ส่งอีกต่อไป

> ⚠️ **แก้ไขครั้งใหญ่ในรอบนี้** เวอร์ชันก่อนหน้าของหน้านี้อธิบาย "high-value approval gate" เฉพาะของ Procurement Manager (amount threshold / pricelist-deviation routing) และ "configurational surface" ทั้งชุด — การแก้ไข vendor-ranking, การแก้ไข grouping-rule ของ Convert-to-PO, การแก้ไข unit-conversion, การแก้ไข pricelist-tolerance, การแก้ไข threshold, และ bulk void/close — พร้อม ~15 scenarios (PM-HP-07 ถึง PM-HP-09 และส่วนใหญ่ของ PERM/VAL/EDGE sections) ที่ **ไม่มี e2e test ID ที่ตรงกันและไม่มี route หรือ component ที่ตรงกัน** ในซอร์สโค้ดปัจจุบัน การค้นทั่ว repo สำหรับ vendor-ranking และ bulk-action code ไม่พบสิ่งใดที่เกี่ยวข้อง และไม่พบ config editor เฉพาะของ PM scenarios เหล่านั้นถูกตัดออกที่นี่แทนที่จะเขียนใหม่ด้วย mechanics ที่แต่งขึ้น หน้านี้ตอนนี้ครอบคลุมเฉพาะ approval flow ที่ยืนยันได้และอิง e2e (`403-po-approver-journey.spec.ts`) บวก Close/Cancel overrides ที่ยืนยันได้
>
> **ส่วนที่เป็น amount-threshold ของ claim เดิม กลับถูกตัดทิ้งผิดพลาดเอง** — การค้นหาติดตามผลยืนยันว่าการ route stage ตาม `total_amount` มีจริง เพียงแต่เป็นกลไกทั่วไป (`routing_rules` ของ workflow ตั้งค่าได้จากแท็บ **Routing** ใน `/system-admin/workflow` ใช้ร่วมกันระหว่าง PR/PO/SR — ไม่ใช่ gate หรือหน้าจอ config เฉพาะของ PM) ดู `PO_AUTH_004` ใน [02-business-rules.md](./02-business-rules.md)

หน้านี้ capture test scenarios ที่ persona Procurement Manager (user fixture `fc@blueledgers.com` ใน e2e specs ปัจจุบัน) ขับเคลื่อนในโมดูล `purchase-order` ต่างจาก Purchaser — ผู้เป็นเจ้าของเอกสารตั้งแต่ต้นจนจบ — Procurement Manager ทำหน้าที่เป็น **workflow-stage approver**: stage ใดก็ตามที่ workflow definition ของ tenant assign ให้พวกเขา โดย *authorization ในการดำเนินการ* gate ด้วย `user_action.execute[]` เท่านั้น (`PO_AUTH_011`) — ไม่ใช่ amount หรือ deviation แต่ *stage ไหน* ที่เป็น stage ถัดไปเองอาจขับเคลื่อนด้วย amount ได้: `routing_rules` ของ workflow ที่ assign ให้อาจ skip หรือกระโดดข้าม stage ตาม `total_amount` (`PO_AUTH_004`); ไม่พบ condition field แบบ deviation-percentage ใด ๆ ในซอร์สโค้ดปัจจุบัน ที่ stage ปัจจุบัน Manager รัน **Approve** (`PO_POST_004` ถ้าเป็น final — ลงที่ `approved` **ไม่** ส่ง — มิฉะนั้น `PO_POST_003`), **Send Back** (`PO_POST_005` — reset stage cursor, **ไม่** เปลี่ยน `po_status`), หรือ **Reject** (direct, terminal `in_progress → voided`) และจาก mobile **swipe-approve** (`PO_AUTH_012`) เช่นเดียวกับ user ใดก็ตามที่เปิด PO อยู่ Manager สามารถ **Close** (`{in_progress, approved, sent_or_print, partial} → closed`, `PO_POST_011`) หรือ **Cancel** ได้ **แก้ไข 2026-09-22:** soft-delete-in-draft เป็นสิทธิ์ของเจ้าของ / super-admin (`PO_AUTH_005`) ไม่ใช่ของ Manager

## 2. Permission / Authorization

| # | Scenario | Expected behaviour (allow/deny + เหตุผล) |
| - | -------- | --------------------------------------- |
| PM-PERM-01 | PM approve PO ที่ `workflow_current_stage` ปัจจุบัน assign พวกเขาผ่าน `user_action.execute[]` | **Allow** ตาม `PO_AUTH_011` Approve PO action ขับเคลื่อน `in_progress → sent` ผ่าน `PO_POST_004` ถ้าเป็น final stage (TC-PO-070305..TC-PO-070307) หรือ advance stage cursor ในกรณีอื่น; Send Back reset stage โดยไม่เปลี่ยน `po_status` (`PO_POST_005`, TC-PO-070308..TC-PO-070309); Reject ขับเคลื่อน `in_progress → voided` โดยตรง (TC-PO-070310..TC-PO-070311) |
| PM-PERM-02 | PM พยายาม approve PO ที่ current stage ไม่ได้ assign พวกเขา | **Deny** PO ไม่ปรากฏใน My Approvals queue ของ Manager เพราะ `user_action.execute` สำหรับ stage ปัจจุบันไม่มี user-id ของ Manager Direct API call เพื่อ advance stage ถูก reject โดย `PO_AUTH_011` ด้วย `"You are not in the authorised approver set for this stage"` **แก้ไขในรอบนี้:** เวอร์ชันก่อนหน้าของ scenario นี้ frame การ deny รอบ amount threshold; gate จริงคือ membership ใน `user_action.execute[]` เท่านั้น |
| PM-PERM-03 | PM Cancel หรือ Close PO ที่ `approved` / `sent_or_print` / `partial` | **Allow** `Cancel` ยอมรับ `{draft, in_progress, approved, sent_or_print}`; `Close` ยอมรับ `{in_progress, approved, sent_or_print, partial}`; ทั้งคู่จบที่ `closed` ทั้งคู่ไม่มี role gate นอกเหนือจาก authentication (`cancel()` L3400, `closePO()` L6083; gateway ไม่มี `@Permission` บน route ทั้งสอง) |
| PM-PERM-04 | PM ลบ `draft` PO ที่ Purchaser สร้าง | **Deny** `remove()` ต้องการ `isDocumentOwner` หรือ platform super-admin (`PO_AUTH_005`); ทางเลือกของ Manager คือ **Cancel** (→ `closed`) **แก้ไข 2026-09-22** จาก "soft-delete เฉพาะ Manager" |

## 3. Validation / Error

| # | Scenario | Trigger | Expected error |
| - | -------- | ------- | -------------- |
| PM-VAL-01 | PM พยายาม action ใดก็ตาม (Approve / Send Back / Reject / Cancel / Close) บน PO ที่อยู่ terminal state แล้ว (`voided`, `completed`, `closed`) | เปิด `voided` PO; ปุ่มใน toolbar ถูกซ่อน / disable; force direct API call เพื่อ advance status | Reject — ตาม `PO_VAL_015` Approve / reject / review ต้องการ `po_status = in_progress` (`approve()` L2845 `where: { id, po_status: in_progress }`); `cancel()` คืน "Cannot cancel purchase order with status 'voided'. Only draft, in_progress, approved, or sent_or_print orders can be cancelled."; `closePO()` ข้อความ close ที่คล้ายกัน |
| PM-VAL-02 | PM พยายาม Close `partial` PO ที่ทุกบรรทัดรับครบแล้ว (`received_qty = order_qty − cancelled_qty` บนทุกบรรทัด) | เปิด `partial` PO ที่ทุกบรรทัดพอใจเงื่อนไขรับครบ; คลิก **Close** | Reject — close handler ตรวจพบว่า PO ควรอยู่ที่ `completed` ผ่าน `PO_POST_007` (transition ที่ขับเคลื่อนโดย GRN ยังไม่รันหรือรันแล้วแต่ race ทำให้ status ค้างที่ `partial`) Server return `"PO is fully received — please refresh; the document will move to completed."` `PO_POST_011` ไม่ fire เพราะไม่มีส่วนที่เหลือให้เขียนกลับไปยัง `cancelled_qty` |
