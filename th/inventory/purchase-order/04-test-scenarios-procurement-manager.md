# ใบสั่งซื้อ (Purchase Order) — Test Scenarios — Procurement Manager

> **At a Glance**
> **Persona:** Procurement Manager (workflow-stage approver) &nbsp;·&nbsp; **Module:** [purchase-order](/th/inventory/purchase-order) &nbsp;·&nbsp; **Scenarios:** ~12
> **Categories:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **E2E coverage:** map ไปยัง `401-po.spec.ts`, `403-po-approver-journey.spec.ts` ใน `../carmen-inventory-frontend-e2e/`

> ⚠️ **แก้ไขครั้งใหญ่ในรอบนี้** เวอร์ชันก่อนหน้าของหน้านี้อธิบาย "high-value approval gate" (amount threshold / pricelist-deviation routing) และ "configurational surface" ทั้งชุด — การแก้ไข vendor-ranking, การแก้ไข grouping-rule ของ Convert-to-PO, การแก้ไข unit-conversion, การแก้ไข pricelist-tolerance, การแก้ไข threshold, และ bulk void/close — พร้อม ~15 scenarios (PM-HP-07 ถึง PM-HP-09 และส่วนใหญ่ของ PERM/VAL/EDGE sections) ที่ **ไม่มี e2e test ID ที่ตรงกันและไม่มี route หรือ component ที่ตรงกัน** ในซอร์สโค้ดปัจจุบัน การค้นทั่ว repo สำหรับ `threshold`, vendor-ranking, และ bulk-action code ไม่พบสิ่งใดที่เกี่ยวข้อง scenarios เหล่านั้นถูกตัดออกที่นี่แทนที่จะเขียนใหม่ด้วย mechanics ที่แต่งขึ้น หน้านี้ตอนนี้ครอบคลุมเฉพาะ approval flow ที่ยืนยันได้และอิง e2e (`403-po-approver-journey.spec.ts`) บวก Close/Cancel overrides ที่ยืนยันได้

หน้านี้ capture test scenarios ที่ persona Procurement Manager (user fixture `fc@blueledgers.com` ใน e2e specs ปัจจุบัน) ขับเคลื่อนในโมดูล `purchase-order` ต่างจาก Purchaser — ผู้เป็นเจ้าของเอกสารตั้งแต่ต้นจนจบ — Procurement Manager ทำหน้าที่เป็น **workflow-stage approver**: stage ใดก็ตามที่ workflow definition ของ tenant assign ให้พวกเขา gate ด้วย `user_action.execute[]` เท่านั้น (`PO_AUTH_011`) — ไม่พบ amount threshold หรือ deviation percentage ใด ๆ ในซอร์สโค้ดปัจจุบัน ที่ stage ปัจจุบัน Manager รัน **Approve** (`PO_POST_004` ถ้าเป็น final, มิฉะนั้น `PO_POST_003`), **Send Back** (`PO_POST_005` — reset stage cursor, **ไม่** เปลี่ยน `po_status`), หรือ **Reject** (direct, terminal `in_progress → voided`) Manager ยังถือ **soft-delete-in-draft** (`PO_AUTH_005`) เพิ่มเติม และร่วมกับ Inventory Manager ถือ **Close** (`{sent, partial, in_progress} → closed`, `PO_AUTH_008`, `PO_POST_011`)

## 2. Permission / Authorization

| # | Scenario | Expected behaviour (allow/deny + เหตุผล) |
| - | -------- | --------------------------------------- |
| PM-PERM-01 | PM approve PO ที่ `workflow_current_stage` ปัจจุบัน assign พวกเขาผ่าน `user_action.execute[]` | **Allow** ตาม `PO_AUTH_011` Approve PO action ขับเคลื่อน `in_progress → sent` ผ่าน `PO_POST_004` ถ้าเป็น final stage (TC-PO-070305..TC-PO-070307) หรือ advance stage cursor ในกรณีอื่น; Send Back reset stage โดยไม่เปลี่ยน `po_status` (`PO_POST_005`, TC-PO-070308..TC-PO-070309); Reject ขับเคลื่อน `in_progress → voided` โดยตรง (TC-PO-070310..TC-PO-070311) |
| PM-PERM-02 | PM พยายาม approve PO ที่ current stage ไม่ได้ assign พวกเขา | **Deny** PO ไม่ปรากฏใน My Approvals queue ของ Manager เพราะ `user_action.execute` สำหรับ stage ปัจจุบันไม่มี user-id ของ Manager Direct API call เพื่อ advance stage ถูก reject โดย `PO_AUTH_011` ด้วย `"You are not in the authorised approver set for this stage"` **แก้ไขในรอบนี้:** เวอร์ชันก่อนหน้าของ scenario นี้ frame การ deny รอบ amount threshold; gate จริงคือ membership ใน `user_action.execute[]` เท่านั้น |
| PM-PERM-03 | PM Cancel หรือ Close PO ที่ `sent` / `partial` | **Allow** `Cancel` ยอมรับ `{draft, in_progress, sent}`; `Close` ยอมรับ `{sent, partial, in_progress}`; ทั้งคู่จบที่ `closed` ไม่มี action ใดสงวนเฉพาะ role นี้ในซอร์สโค้ดปัจจุบัน — role gate เฉพาะบน endpoint ทั้งสองนอกเหนือจาก generic authentication ยังไม่ยืนยันในรอบนี้ |

## 3. Validation / Error

| # | Scenario | Trigger | Expected error |
| - | -------- | ------- | -------------- |
| PM-VAL-01 | PM พยายาม action ใดก็ตาม (Approve / Send Back / Reject / Cancel / Close) บน PO ที่อยู่ terminal state แล้ว (`voided`, `completed`, `closed`) | เปิด `voided` PO; ปุ่มใน toolbar ถูกซ่อน / disable; force direct API call เพื่อ advance status | Reject — ตาม `PO_VAL_015` ("Status transitions follow the state machine in Section 5; out-of-order transitions are blocked") Server return `"Invalid status transition from voided to sent"` (หรือ from-state ที่คล้ายกัน) |
| PM-VAL-02 | PM พยายาม Close `partial` PO ที่ทุกบรรทัดรับครบแล้ว (`received_qty = order_qty − cancelled_qty` บนทุกบรรทัด) | เปิด `partial` PO ที่ทุกบรรทัดพอใจเงื่อนไขรับครบ; คลิก **Close** | Reject — close handler ตรวจพบว่า PO ควรอยู่ที่ `completed` ผ่าน `PO_POST_007` (transition ที่ขับเคลื่อนโดย GRN ยังไม่รันหรือรันแล้วแต่ race ทำให้ status ค้างที่ `partial`) Server return `"PO is fully received — please refresh; the document will move to completed."` `PO_POST_011` ไม่ fire เพราะไม่มีส่วนที่เหลือให้เขียนกลับไปยัง `cancelled_qty` |

## 4. Edge Cases

| # | Scenario | เงื่อนไข | Expected |
| - | -------- | --------- | -------- |
| PM-EDGE-01 | Reject fire ขณะที่ send-back ของ approver อื่นกำลัง in flight (optimistic-concurrency race) | PM A เปิด PO และคลิก Send Back ที่ `doc_version = 3`; PM B (co-approver บน stage เดียวกัน) เปิด PO เดียวกันและคลิก Reject ที่ `T + 500ms` ยังถือ `doc_version = 3` | Write แรกชนะ: call ใดถึง server ก่อนจะ commit และเพิ่ม `doc_version` การเช็ค `doc_version` ของ call ที่สองล้มเหลวและ API return `"This PO was modified by another user. Please refresh and re-apply your changes."` ไม่มี double-write; client refresh เพื่อดู outcome จริง (ทั้ง `in_progress` ที่ stage cursor reset หรือ `voided`) |
