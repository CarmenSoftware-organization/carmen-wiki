หน้านี้ capture test scenarios ที่ Purchaser persona (เรียกอีกชื่อว่า **Procurement Officer**) ขับเคลื่อนโดยตรงในโมดูล `purchase-order` Purchaser เป็นเจ้าของ PO ตั้งแต่การสร้างไปจนถึงการส่งให้ vendor — ช่วงจาก `po_status = draft` ถึง `sent_or_print` ([03-user-flow-purchaser.md](./03-user-flow-purchaser.md) Section 2) มีสามเส้นทางการสร้าง: **manual PO** (`po_type = manual`) ที่ยกขึ้นโดย procurement โดยตรง, **PR-sourced PO** (`po_type = purchase_request`) ที่ materialise ผ่านหน้า From PR 3 ขั้นตอนภายในโมดูล Purchase Order (`/procurement/purchase-order/from-pr`) ผ่านตาราง bridge `tb_purchase_order_detail_tb_purchase_request_detail` ([01-data-model.md](./01-data-model.md) Section 2.3) และ **price-list-sourced PO** (`po_type = pricelist`) ผ่าน wizard 4 ขั้นตอนจาก price list Scenarios จัดกลุ่มเป็น happy paths ที่อธิบายใน user flow, RBAC boundary ที่บังคับโดย `PO_AUTH_001`–`PO_AUTH_003` และ `PO_AUTH_006` (ขอบเขต edit / submit / transmit ของ Purchaser) เทียบกับ `PO_AUTH_005` (soft-delete เฉพาะ Manager) และ `PO_AUTH_011` (stage-gated approval — authorization ไม่ถูก gate ด้วย amount แม้ว่า stage ที่ PO มาถึงอาจถูก gate ด้วยได้ผ่าน `routing_rules` ของ workflow ที่ assign ให้, `PO_AUTH_004` — ดู `02-business-rules.md` § 4), กฎ validation ใน [02-business-rules.md](./02-business-rules.md) Section 2 (`PO_VAL_001`–`PO_VAL_016`) ที่ Purchaser สามารถ trigger จาก create / edit / submit time และชุดเล็กของ edge cases รอบ ๆ decimal precision, currency, concurrency, และการเปลี่ยนแปลง state ของ vendor-master Cross-persona handoffs ที่ pivot บน Purchaser (`X-PO-01`, `X-PO-02`, `X-PO-05`, `X-PO-10`) อยู่ใน parent overview ไม่ใช่ที่นี่

## 2. Permission / Authorization

| # | Scenario | Expected behaviour (allow/deny + เหตุผล) |
| - | -------- | --------------------------------------- |
| PUR-PERM-01 | Purchaser เปิด PO ของตัวเอง (current user ตรงกับ `tb_purchase_order.buyer_id`, หรืออยู่ใน `user_action.execute[]` ที่ `workflow_current_stage` ปัจจุบัน) | **Allow** read ข้ามทุก statuses และ actions create / edit / submit / transmit ตาม `PO_AUTH_001`–`PO_AUTH_003` และ `PO_AUTH_006` Detail page load พร้อม header + items + Item Details panel (TC-PO-060301, TC-PO-060302) |
| PUR-PERM-02 | Purchaser ดู PO ของ Purchaser อื่น (RBAC-scoped read) | **Allow** read เมื่อ tenant's RBAC grant `purchase-order:read` ให้ทุก users `enum_stage_role = purchase` (default); **deny** write actions (Edit / Submit / Send-to-Vendor / Close) เพราะ `PO_AUTH_002` ต้องการ user เป็น buyer ที่ assigned หรือถือ `workflow_current_stage` ปัจจุบัน Direct API call เพื่อ edit return `"You are not authorised to edit this PO at the current stage"` |
| PUR-PERM-03 | Purchaser edit `draft` PO ที่พวกเขาเป็นเจ้าของ | **Allow** ตาม `PO_AUTH_002` (`po_status ∈ {draft, in_progress}` และ user เป็น buyer ที่ assigned) ฟิลด์ header และบรรทัดทั้งหมด editable; ปุ่ม **Edit / Delete / Submit** ปรากฏบน `draft` (TC-PO-060303); การ modify qty / เพิ่มบรรทัด / cancel edit / submit ทั้งหมดสำเร็จ (TC-PO-060401..TC-PO-060405) |
| PUR-PERM-04 | Purchaser edit PO ที่ `approved` / `sent_or_print` ที่พวกเขาเป็นเจ้าของ | **Deny** ตาม `PO_VAL_016` — หน้า detail เป็น read-only ตั้งแต่ `approved` เป็นต้นไป (`po-footer-action.tsx` `isTerminal`); action ที่ enable มีเพียง **Send Email**, **Close**, **Cancel**, comment `PUT` / `PATCH .../save` โดยตรงที่มีราคาถูก reject โดย guard `po_status === draft` **แก้ไข 2026-09-22:** ไม่มี "Amendment panel" หรือตัวแก้ `cancelled_qty` ต่อบรรทัด |
| PUR-PERM-05 | Purchaser พยายาม approve PO ที่ current workflow stage | **Allow เฉพาะหาก workflow definition assign Purchaser ไปยัง stage นั้น** (`PO_AUTH_011` — authorization gate ด้วย `user_action.execute[]` เท่านั้น ไม่ใช่ด้วย amount) workflow แบบ single-stage อาจ assign stage ของ Purchaser เองเป็น final stage ทำให้ user คนเดียวกัน submit และ approve ได้ **Deny** เมื่อ workflow assign stage owner เป็นคนอื่น Direct call เพื่อ advance stage จาก user ที่ไม่อยู่ใน list ถูก reject โดย `PO_AUTH_011` ด้วย `"You are not in the authorised approver set for this stage"` **แก้ไขในรอบนี้:** เวอร์ชันก่อนหน้าของ scenario นี้ gate *สิทธิ์ self-approval* ด้วย "tenant high-value threshold" และกฎ segregation-of-duties (`PO_AUTH_010`); ทั้ง self-approval gate และ SoD ไม่พบในซอร์สโค้ดปัจจุบัน แยกต่างหาก (ยืนยันแล้ว ไม่ใช่ส่วนหนึ่งของ claim ที่ผิด): `routing_rules` ของ workflow ที่ assign ให้ยังคง route ได้ว่า *stage ไหน* เป็น stage ถัดไปตาม `total_amount` (`PO_AUTH_004`) — เป็นกลไก route เอกสาร ไม่ใช่การตรวจสิทธิ์ self-approval |
| PUR-PERM-06 | Purchaser ลบ `draft` PO ของตัวเอง (soft-delete) | **Allow เมื่อ Purchaser เป็นผู้สร้าง** (`PO_AUTH_005`: `remove()` เช็ค `po_status = draft` แล้ว `isDocumentOwner(purchaseOrder, userId)` หรือ super-admin) **Deny** สำหรับ draft ที่คนอื่นสร้าง — API reject แม้ UI อาจแสดงปุ่ม (TC-PO-060303) **แก้ไข 2026-09-22:** เวอร์ชันก่อนหน้าสงวนสิทธิ์นี้ให้ Procurement Manager และอ้าง error string ("Soft-delete from draft is restricted to the Procurement Manager") ที่ไม่มีอยู่จริง; ข้อความจริงคือ "Only draft purchase orders can be deleted" สำหรับ non-draft และ ownership error ในกรณีอื่น |
| PUR-PERM-07 | Purchaser พยายาม reject PO ที่ stage ที่พวกเขาไม่ได้ถือ | **Deny** ตาม `PO_AUTH_011` เฉพาะผู้ที่อยู่ใน `user_action.execute[]` สำหรับ `workflow_current_stage` ปัจจุบันเท่านั้นที่ reject ได้ (`in_progress → voided`, direct และ terminal) `voided` reach ได้จาก `in_progress` ผ่าน reject เท่านั้น อย่างไรก็ตาม Purchaser สามารถ **Cancel** PO ที่ `draft`, `in_progress`, `approved`, หรือ `sent_or_print` ได้ (จบที่ `closed`) |
| PUR-PERM-08 | Purchaser ปิด `partial` PO (early termination) | **Allow** `closePO()` ไม่มี role gate นอกเหนือจาก authentication (`PO_AUTH_008`, `purchase-order.service.ts` L6083-6094); header ของ React แสดง **Close** บน `approved` / `sent_or_print` เมื่อ `canClose` **แก้ไข 2026-09-22** จาก "Deny — scope ของ Inventory Manager" |

## 4. Edge Cases

| # | Scenario | เงื่อนไข | Expected |
| - | -------- | --------- | -------- |
| PUR-EDGE-01 | Zero-quantity submit-time guard รวมกับ line save-time guard | Purchaser พยายาม save บรรทัดด้วย `order_qty = 0` (caught ที่ save โดย `PO_VAL_008`); แล้วพยายาม bypass UI โดย submit PO ด้วยบรรทัด edited เป็น `0` post-save ผ่าน direct API call | ทั้ง save-line และ submit-time runs ของ `PO_VAL_008` reject บรรทัดด้วย `"Order quantity must be greater than zero and a unit of measure is required."`; submit abort; บรรทัดยังที่ค่า valid ก่อน; ไม่มี `tb_purchase_order_detail` row mutate |
| PUR-EDGE-02 | ความแม่นยำ decimal สูงสุดบน line `price` | Line `price = 99999999999.99999` (15 integer + 5 fraction digits, upper bound ของ `Decimal(20, 5)`) ด้วย `order_qty = 1.99999`; tax_rate `7%`, ไม่มี discount | ยอมรับที่ storage; `sub_total_price = Round(99999999999.99999 × 1.99999, 2)` คำนวณตาม `PO_CALC_001`; การปัดเศษใช้ half-up ผ่าน `PO_CALC_012`; `base_qty = Round(1.99999 × conv_factor, 3)` ตาม `PO_CALC_006`; header `total_qty` aggregate ใน base UoM ที่ 3 dp ตาม `PO_CALC_011`; Decimals ทั้งหมดเก็บพอดีใน `Decimal(20, 5)` สำหรับเงินและ `Decimal(15, 5)` สำหรับอัตรา |
| PUR-EDGE-03 | Back-dated `delivery_date` เท่ากับ `order_date` (lower bound ของ `PO_VAL_006`) | ตั้ง `order_date = 2026-05-15`, `delivery_date = 2026-05-15`; คลิก Save / Submit | ยอมรับ — `PO_VAL_006` บังคับ `delivery_date >= order_date` (inclusive) Same-day case ผ่าน; PO save และ submit ปกติ การตั้ง `delivery_date = order_date − 1d` จะ fail (covered โดย PUR-VAL-04) |
| PUR-EDGE-04 | Multi-currency (หรือ multi-delivery-date) consolidation ใน Convert-to-PO dialog | เลือก PRs ที่อนุมัติแล้วสองใบใน step 1: `PR-A` ด้วย `currency_id = THB` และ `PR-B` ด้วย `currency_id = USD`, ทั้งคู่สำหรับ `vendor_id = V1` และ `delivery_date` เดียวกัน | Step 2 ของ dialog auto-group ด้วย `(vendor_id, delivery_date, currency_id)` → **สอง** กลุ่ม draft-PO (หนึ่งต่อ currency) ไม่ใช่หนึ่งกลุ่ม — ยืนยันผ่าน `buildPoGroupKey` ใน `purchase-order.service.ts` แต่ละ PO ที่ได้พอใจ `PO_VAL_013` การแยกแบบเดียวกันนี้เกิดขึ้นถ้า PR ทั้งสองใบมี currency เดียวกันแต่ `delivery_date` ต่างกัน direct API call เพื่อ force ทั้งสองบรรทัดเข้า PO เดียวถูก reject ด้วย `"All lines on a PO must share the header vendor and currency. Split into separate POs by vendor+currency."` (`PO_VAL_013`) |
| PUR-EDGE-05 | Concurrent edits บน draft PO เดียวกันจากสอง Purchaser sessions | Purchaser A และ Purchaser B ทั้งคู่ load draft PO `PO-X` ที่ `doc_version = 3`; A save qty change ที่ `T` (`doc_version → 4`); B save price change ที่ `T + 1s` ใช้ stale `doc_version = 3` | Save แรกชนะ: qty change ของ A persist, `doc_version = 4` save ของ B ถูก reject โดย optimistic-concurrency guard ด้วย `"This PO was modified by another user. Please refresh and re-apply your changes."`; client ของ B prompt refresh ไม่มี double-write หรือ lost-update เกิด |
| PUR-EDGE-06 | Send Email ด้วยผู้รับที่ไม่ถูกต้อง / profile ที่ปิดใช้ | PO ที่ `po_status = approved`; (a) `to[]` มีที่อยู่ที่ SMTP relay ปฏิเสธ; (b) `profile_id` ที่เลือกถูก disable | (a) `send-email` คืน HTTP 200 `{ sent: false, rejected: ['bad@…'] }`; PO ยังคง `approved`; `tb_activity` `email_sent` บันทึกความพยายามที่ล้มเหลว; dialog แสดงที่อยู่ที่ถูกปฏิเสธเพื่อแก้ไข (b) `400` "Email profile is disabled" (หรือ "Email profile not found") — pre-flight validation ไม่มี log PO ยังคง `approved` **แก้ไข 2026-09-22:** เวอร์ชันก่อนหน้าอ้างการเช็ค vendor-master ("Vendor email is not configured…", "Vendor is no longer active…") ที่ไม่มีใน `sendEmailToVendor`; ผู้รับมาจาก dialog ไม่ใช่จาก `tb_vendor.email` |
| PUR-EDGE-08 | PR สองใบที่วันที่ขอต่างกัน vendor + currency เดียวกัน แปลงพร้อม override `delivery_date` | API: `POST .../purchase-orders/group-pr` `{ pr_ids: [A, B], delivery_date: '2026-10-01' }` | หนึ่งกลุ่ม ไม่ใช่สอง — override ยุบมิติวันที่ของ `buildPoGroupKey`; `confirm-pr` ด้วย override เดียวกันสร้าง PO หนึ่งใบที่ `delivery_date = 2026-10-01` ถ้าไม่มี override PR เดียวกันจะแยกเป็นสอง PO (PUR-EDGE-04) หน้า React ยังทดสอบกรณีนี้ไม่ได้ (ไม่ส่ง override) |
| PUR-EDGE-07 | Submit PO ทันทีหลัง soft-delete บน `po_no` เดียวกัน (uniqueness re-use) | PO ก่อนที่ `po_no = PO-2026-000123` ถูก soft-deleted (`deleted_at IS NOT NULL`) ตาม `PO_POST_012`; Purchaser draft PO ใหม่และ numbering service issue `po_no` เดียวกัน | ยอมรับ — unique index `@@unique([po_no, deleted_at])` อนุญาต reuse เพราะ `deleted_at` ต่างกัน PO ใหม่ save และ submit ปกติ; row ที่ soft-deleted ก่อนยังอยู่ในฐานข้อมูลสำหรับ audit Hard-delete-in-draft สงวนสำหรับ Procurement Manager (`PO_AUTH_005`) ดังนั้น scenario นี้มีต้นทางจาก Manager-driven cleanup |
