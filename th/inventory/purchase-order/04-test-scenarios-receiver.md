# ใบสั่งซื้อ (Purchase Order) — Test Scenarios — Receiver

> **At a Glance**
> **Persona:** Receiver (Store Keeper + Inventory Manager) &nbsp;·&nbsp; **Module:** [purchase-order](/th/inventory/purchase-order) &nbsp;·&nbsp; **Scenarios:** ~22
> **Categories:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **E2E coverage:** ยังไม่มี Receiver spec เฉพาะ; shared coverage ใน `tests/401-po.spec.ts` (TC-PO-340001..340003 GRN sync, TC-PO-060501..060504 Close) ใน `../carmen-inventory-frontend-e2e/`

> **Executable coverage (2026-09-22):** ไม่มี catalog PO ของ persona Receiver; ผลฝั่ง PO ของการรับของถูก cover จาก GRN suite (`tests/501-*` ดู [good-receive-note](/th/inventory/good-receive-note) `04-test-scenarios`) และ `docs/user-stories/401-po.md` (60 case; gap `docs/test-cases/gaps/401-po-create-flows-gap.md`, 29) scenario ด้านล่างแก้ไขให้ตรง source HEAD: GRN ทำได้จาก `approved` (ก่อนอีเมลถึง vendor), ปริมาณ FOC ถูกรับและเข้าคลัง และทุก `sent` ด้านล่างกลายเป็น `sent_or_print`

หน้านี้ capture test scenarios ที่ Receiver persona (**Store Keeper** ที่ dock บวก **Inventory Manager** ที่กำกับการปิดสำหรับ location) ขับเคลื่อนโดยตรงในโมดูล `purchase-order` การ involve ของ Receiver เริ่มเมื่อ PO ถึง `po_status = approved` (การรับของปลดล็อกตอนอนุมัติ — `findOnePoForGrn` รับ `approved`, `sent_or_print`, `partial`) และจบเมื่อ PO ออกจาก receipt zone — ทั้งผ่าน `completed` (รับครบ), `partial` (open balance carry ไปข้างหน้า) หรือ `closed` (ใครก็ได้ปิด PO ที่ `{in_progress, approved, sent_or_print, partial}`) GRN posting เองอยู่ในโมดูล `[good-receive-note](/th/inventory/good-receive-note)` ปลายน้ำ; หน้านี้ capture เฉพาะ **PO-side effects** — วิธีที่ GRN flip `tb_purchase_order.po_status` ผ่าน `PO_POST_006` (`sent → partial`) และ `PO_POST_007` (`* → completed`), วิธีที่ Inventory Manager ปิด `partial` PO ด้วย remainder เขียนเป็น `cancelled_qty` ผ่าน `PO_POST_011`, และวิธีที่ PO line counters (`received_qty`, `cancelled_qty`) advance เทียบกับ `order_qty` ([03-user-flow-receiver.md](./03-user-flow-receiver.md) Section 2) Scenarios จัดกลุ่มเป็น happy paths ที่อธิบายใน user flow, RBAC boundary ที่บังคับโดย `PO_AUTH_008` (Receiver / Inventory Manager scope) เทียบกับ `PO_AUTH_001`–`PO_AUTH_003` (Purchaser scope), กฎ validation รอบ `received_qty`, over-receipt tolerance และ voided / closed-PO state guards และชุดเล็กของ edge cases รอบ tolerance boundaries, decimal precision, concurrency และ multi-currency context **แก้ไขในรอบนี้:** ภาพรวมเวอร์ชันก่อนหน้ายังอ้างถึง `PO_AUTH_010` (segregation of duties — ผู้ post GRN ≠ PO buyer/transmitter) ว่าเป็นกฎที่บังคับใช้จริง — การค้นทั่ว repo ทั้งฝั่ง GRN และ PO backend services ไม่พบโค้ดที่ตรงกัน ให้ถือว่าเป็นเพียง design intent ที่ยังไม่ยืนยัน ไม่ใช่ guard ที่ใช้งานจริง **แก้ไขในรอบนี้เช่นกัน:** เวอร์ชันก่อนหน้าอ้างอิงฟิลด์ `accepted_qty` ที่แยกจาก `received_qty` ตลอด scenarios ด้านล่าง — การค้นหาทั่ว Prisma schema และซอร์สทั้ง frontend และ backend ให้ผลศูนย์รายการสำหรับ `accepted_qty` / `acceptedQty` ไม่มีฟิลด์นี้อยู่ สอดคล้องกับข้อค้นพบที่ยืนยันและแก้ไขแล้วในรอบ resync ของโมดูล [good-receive-note](/th/inventory/good-receive-note) เอง scenario ทุกตัวด้านล่างถูกเขียนใหม่ให้ post เฉพาะ `received_qty` โดยปัญหาคุณภาพหรือการรับของขาดถูกบันทึกเป็น `received_qty` ที่น้อยกว่าพร้อม comment แบบ free-text บน GRN แทนที่จะเป็นปริมาณ structured ตัวที่สอง Cross-persona handoffs ที่ pivot บน Receiver (`X-PO-03`, `X-PO-04`, `X-PO-06`, `X-PO-08`) อยู่ใน parent overview ไม่ใช่ที่นี่

## 2. Permission / Authorization

| RCV-PERM-05 | Receiver (Store Keeper) ปิด `partial` PO (early termination) | **Allow** `closePO()` (`{in_progress, approved, sent_or_print, partial} → closed`, `PO_POST_011`) ไม่มี role gate นอกเหนือจาก authentication และ route ของ gateway ไม่มี `@Permission` **แก้ไข 2026-09-22:** เวอร์ชันก่อนหน้าต้องการ role Inventory Manager และอ้าง error string ("Close from status partial requires the Inventory Manager role.") ที่ไม่มีอยู่จริง |
| RCV-PERM-06 | Receiver พยายาม GRN เทียบกับ PO ที่ `po_status = completed` หรือ `closed` | **Deny — terminal status** ตาม `PO_POST_007` / `PO_POST_011`, `completed` และ `closed` เป็น terminal สำหรับวัตถุประสงค์ receipt; ไม่รับ GRNs เพิ่ม PO ไม่ปรากฏใน open-PO list ของโมดูล GRN; direct API call return `"PO is at terminal receipt status <status> — no further receipts can be posted."` |

## 3. Validation / Error

| # | Scenario | Trigger | Expected error |
| - | -------- | ------- | -------------- |
| RCV-VAL-01 | Over-receipt โดยไม่มี tolerance — `received_qty > pending balance` | PO line `L1`: `order_qty = 10`, `received_qty = 0`, `cancelled_qty = 0`; tenant over-receipt tolerance disable หรือตั้งเป็น `0%`; Receiver ใส่ `received_qty = 12` | Reject — `PO_XMOD_004` Server return `"Received quantity exceeds the pending balance and tenant over-receipt tolerance is not configured."`; GRN line cap ที่ pending qty (10) หรือ post block ทั้งหมด; PO counters ไม่เปลี่ยน |
| RCV-VAL-02 | Zero `received_qty` บน GRN line | Receiver ใส่ `received_qty = 0` บนบรรทัดและคลิก **Post** | Reject — `PO_XMOD_003` / GRN-side validation Server return `"Received quantity must be greater than zero on every GRN line; remove the line if nothing was received against it."`; GRN ไม่สามารถ post ด้วย zero-qty line; PO counters ไม่เปลี่ยน |
| RCV-VAL-03 | GRN เทียบกับ `voided` PO | PO `PO-V` ที่ `po_status = voided` (reach ได้เฉพาะผ่าน direct, terminal reject จาก `in_progress` — ไม่เคยจาก `approved` / `sent_or_print` / `partial`); Receiver พยายามเปิด GRN flow จากโมดูล GRN โดยตรง | Reject — `voided` เป็น terminal PO ไม่ปรากฏใน open-PO list; `GET .../purchase-orders/grn/:id` คืน "Purchase order must be in approved, sent_or_print or partial status to create a goods received note" เนื่องจาก `voided` reach ได้จาก `in_progress` เท่านั้น PO แบบนี้จึงไม่เคยไปถึง status ที่รับของได้เลย |
| RCV-VAL-04 | Partial GRN เมื่อ remaining qty เป็น unreceivable (negative pending) | PO line `L1`: `order_qty = 10`, `received_qty = 8`, `cancelled_qty = 2` (ดังนั้น pending balance = 0); Receiver พยายาม post GRN ด้วย `received_qty = 1` บน `L1` | Reject — `PO_XMOD_003` Server return `"PO line has no remaining open balance — received_qty (8) + cancelled_qty (2) = order_qty (10)."`; GRN line ไม่สามารถ post บน `L1`; ถ้าบรรทัดอื่นบน PO ยังเปิด, ตัวเหล่านั้นอาจ post อิสระ |
| RCV-VAL-05 | GRN เทียบกับ PO ที่ vendor flip เป็น `is_active = false` หลังส่ง | PO `PO-W` ที่ `po_status = sent_or_print`; `tb_vendor.is_active = false` บน vendor ของ PO | **ยังไม่ยืนยัน — ไม่พบ code path** `findOnePoForGrn` / `findAllForGrn` filter เฉพาะ `po_status` และ `deleted_at`; grep `purchase-order.service.ts` หาการเช็ค `is_active` บน `tb_vendor` ใน query ฝั่ง GRN ไม่พบ และข้อความที่อ้าง "Vendor is no longer active and cannot deliver further goods." ไม่มีอยู่จริง คาดหวังที่ HEAD: GRN post ได้ตามปกติ; การ blacklist เป็นเรื่องของ vendor master ที่บันทึกใน [master-data/vendor](/th/inventory/master-data/vendor) |

## 4. Edge Cases

| # | Scenario | เงื่อนไข | Expected |
| - | -------- | --------- | -------- |
| RCV-EDGE-01 | Exact tolerance boundary บน over-receipt | PO line `L1`: `order_qty = 10`, `received_qty = 0`, `cancelled_qty = 0`; tenant over-receipt tolerance = `5%`; Receiver ใส่ `received_qty = 10.5` (พอดี upper bound) | ยอมรับ — `PO_XMOD_004` `received_qty = 10.5` อยู่ภายใน tolerance (`10 × 1.05 = 10.5`); GRN post; `tb_purchase_order_detail.received_qty = 10.5`; line evaluation: `received_qty (10.5) ≥ order_qty − cancelled_qty (10)` → รับครบ; `po_status = sent_or_print → completed` ตาม `PO_POST_007` การตั้ง `received_qty = 10.51` จะ breach bound และ reject ตาม RCV-VAL-01 (การบังคับ tolerance เองอยู่ในโมดูล GRN; ฝั่ง PO เห็นเฉพาะ `received_qty` ที่ได้) |
| RCV-EDGE-02 | Decimal precision บน `received_qty` | Receiver ใส่ `received_qty = 5.123` บนบรรทัดที่ order UoM อนุญาต 3-dp precision; conversion factor `1.234567`, `received_base_qty` คำนวณใน storage UoM | ยอมรับที่ storage; `received_qty` เก็บที่ precision UoM ของบรรทัด (3 dp); `received_base_qty` คำนวณเป็น `received_qty × conv_factor` สำหรับ inventory roll-up (ตาม [good-receive-note/01-data-model.md](/th/inventory/good-receive-note/01-data-model) — ไม่มีฟิลด์ `accepted_qty` แยกต่างหากสำหรับ track precision ตัวที่สอง); PO `received_qty` aggregate โดยไม่มี precision loss; Decimals ทั้งหมดเก็บพอดีใน `Decimal(20, 5)` |
| RCV-EDGE-03 | Concurrent GRN posts บน PO เดียวกันจากสอง Receiver sessions | Receiver A และ B ทั้งคู่เปิด `PO-X` (`po_status = sent_or_print`, `received_qty = 0`, `order_qty = 10`); A post `received_qty = 6` ที่ `T`; B post `received_qty = 4` ที่ `T + 500ms` เทียบกับบรรทัดเดียวกัน ทั้งคู่ด้วย `doc_version = 3` snapshots | Post แรกชนะ atomically: GRN ของ A post, `tb_purchase_order_detail.received_qty = 0 → 6`, `po_status = sent_or_print → partial`, `doc_version → 4` Post ของ B reconcile เทียบกับ state ใหม่ — ทั้ง GRN module re-read `pending_qty = 4` และ post `received_qty = 4` ของ B สะอาด (advance `received_qty → 10`, `po_status → completed`) หรือ optimistic-concurrency guard reject B ด้วย `"This PO was modified by another user. Please refresh and re-apply your changes."` และ B retry ไม่มี double-write, ไม่มี lost-update, ไม่มี `received_qty > order_qty` overflow นอก over-receipt tolerance |
| RCV-EDGE-04 | Multi-currency context — PO base currency สำคัญสำหรับ valuation | PO `PO-F` ด้วย `currency_id = USD`, `exchange_rate = 36.50` (เทียบกับ base `THB`); line `L1`: `order_qty = 10`, `price = $50.00`; Receiver post GRN `received_qty = 10` | GRN post ที่สกุลเงิน transaction ของ PO (`USD`); inventory valuation dual-posted — transaction value `$500.00` และ base value `Round($500.00 × 36.50, 2) = ฿18,250.00` ตาม `PO_CALC_008`–`PO_CALC_011`; `exchange_rate` snapshot ของ PO ณ time ของ PO submission คืออัตราที่ใช้สำหรับ inventory accrual ที่ driven โดย GRN ไม่ใช่อัตรา spot ปัจจุบัน; `po_status = sent_or_print → completed` ตาม `PO_POST_007` |
