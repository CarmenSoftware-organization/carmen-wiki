# คลังสินค้า (Inventory) — Business Rules

> **At a Glance**
> **ตระกูลกฎ:** `INV_VAL_*` การตรวจสอบ &nbsp;·&nbsp; `INV_AUTH_*` สิทธิ์ &nbsp;·&nbsp; `INV_CALC_*` การคำนวณ &nbsp;·&nbsp; `INV_POST_*` การ posting &nbsp;·&nbsp; `INV_XMOD_*` ข้ามโมดูล
> **จำนวนกฎ:** ประมาณ 60 กฎ
> **ผู้ใช้งาน:** ผู้เขียนเทสและนักพัฒนา — ทุก rule ID ถูก anchor จากหน้า `04-test-scenarios*`
> **วงจรชีวิตสถานะ:** Section 5.1 (ที่มี) ถือ callout ความไม่ตรงระหว่าง Live UI vs BRD

## 1. ภาพรวม

หน้านี้รวบรวมกฎทางธุรกิจปฏิบัติการที่ปกครอง **โมดูล inventory** — ledger ที่โมดูลผลิตการเคลื่อนไหวอื่นทุกตัว (GRN receipts, store-requisition issues / transfers, physical / spot counts, credit notes, manual stock-in / stock-out) post เข้า เนื่องจาก inventory ขับเคลื่อนด้วย movement แทนที่จะด้วยเอกสาร ชุดกฎตรงนี้จึงดูแตกต่างจาก catalog ของ GRN / PR / PO: ไม่มีวงจรชีวิต `doc_status` ที่ต้องจัดการ ไม่มีความก้าวหน้า save / approve / commit และไม่มี "posting event" เดียวที่ fire ต่อ row แต่ละ transaction คือ posting event ของตัวเอง; การตรวจสอบรัน **ก่อน** transaction ถูกเขียน การคำนวณ populate cost-layer (และบนการปิดแบบ average คือ period snapshot) การกำหนดสิทธิ์เป็น RBAC-plus-source-document ผลกระทบของ posting เป็น ledger เท่านั้น (ไม่มี GL fan-out อยู่จริง — ดู caveat ของ § 5) และการปิดงวด (period-end close) คือชุดกฎแยกที่ยกยอด lot ไปข้างหน้าและประทับ movement ในอนาคตเข้างวดใหม่ที่เปิด

จุดเชิงโครงสร้างสองจุดให้สีกับทุกกฎด้านล่างและคุ้มค่าที่จะกล่าวซ้ำตั้งแต่ต้น **ประการแรก** **ไม่มี row `tb_stock_balance`** — on-hand ปัจจุบันที่ `(product_id, location_id)` derive เป็น `Σ (cost_layer.in_qty − cost_layer.out_qty)` แบบตรง ๆ ครอบ layer ที่ไม่ถูก soft-delete ทั้งหมด (`getLocationBalance`; rows carry-over close/open รักษาให้ผลรวมแบบตรงถูกต้องข้ามขอบงวด) ดังนั้นกฎที่ดูเหมือน "เพิ่ม balance" จริง ๆ หมายถึง "เขียน row `tb_inventory_transaction_cost_layer` ใหม่ที่มี `in_qty` / `out_qty` / `cost_per_unit` ที่ถูกต้องเพื่อให้ผลรวม derive ก้าวหน้าอย่างถูกต้อง" (ดู [inventory/01-data-model](/th/inventory/inventory/01-data-model) § 5 item 1) **ประการที่สอง** `location_type` (`inventory`, `direct`, `consignment` บน `tb_location.location_type`) คือการตั้งค่าที่เปลี่ยนกลไก posting เฉพาะสำหรับ location แบบ `direct`: การรับแบบ `direct` เขียน cost-layer row inbound ตามปกติ **บวก** row outbound หักล้างที่สร้างอัตโนมัติที่ต้นทุนเดียวกัน (on-hand สุทธิเป็นศูนย์) — `consignment` พบว่าไม่มี code path แยกเฉพาะและถูกปฏิบัติเหมือน `inventory` สำหรับการเขียน cost-layer (ดู [01-data-model](/th/inventory/inventory/01-data-model) § 5 items 7–8) ไม่พบโค้ด GL/journal-posting สำหรับค่าใดในสามค่านี้ — ดู [01-data-model](/th/inventory/inventory/01-data-model) § 1 และกฎ Posting (§ 5) ด้านล่าง

## 2. กฎการตรวจสอบ (Validation Rules)

Rule ID ตาม `INV_VAL_NNN` การตรวจสอบรัน **ณ เวลา post** — กล่าวคือ เมื่อโมดูล source (GRN, SR, count, credit note, manual stock-in / stock-out) พยายามเขียน row `tb_inventory_transaction` และลูก ไม่มีการแยก save-time / commit-time เพราะไม่มีสถานะ draft บนตัว transaction; เอกสาร source ถือความก้าวหน้านั้น

> **Caveat เรื่อง error string (รอบนี้):** มีเพียงข้อความ `Insufficient stock…` ของ `INV_VAL_005` และข้อความ SR from-location ของ `INV_VAL_009` เท่านั้นที่ตรวจสอบแล้วว่าเป็น string จริงใน service ข้อความ quoted อื่น ๆ ในตารางนี้เป็น **การถอดความเชิงอธิบาย** ของ constraints ใน schema (`NOT NULL`, ความ valid ของ enum, การ resolve FK) — layer ฐานข้อมูลและ DTO บังคับใช้เงื่อนไข แต่ถ้อยคำที่แน่นอนไม่ได้มาจาก source "new-lot uniqueness" ของ `INV_VAL_006` บังคับใช้โดย index `@@unique([lot_no, lot_index])` และหมายเลข lot ถูก **สร้างโดยระบบ** (`RC{YY}{MM}{seq}`, `ISS-…`, `CLOSE-…`, `OPEN-…`) ไม่ได้ป้อนโดย user — ไม่มี validation การป้อน lot ฝั่ง user เงื่อนไขเบื้องต้น compensating-reversal ของ `INV_VAL_013` ยังไม่ยืนยัน (ไม่พบ guard แบบนั้น; `deleted_at` เพียงแค่ไม่เคยถูก set โดย code path ใดของ inventory ปัจจุบัน)

## 3. กฎการคำนวณ (Calculation Rules)

ค่าจำนวนเงินทั้งหมดเก็บเป็น `Decimal(20, 5)` บน cost-layer และ detail rows การปัดเศษสำหรับการแสดงเป็น half-up ทศนิยม 2 ตำแหน่งสำหรับจำนวนเงินและ 3 ตำแหน่งสำหรับปริมาณ การคำนวณกลางใช้ precision 5dp เต็ม; เฉพาะค่าสุดท้ายที่เก็บ / แสดงถูกปัดเศษ

Rule ID ตาม `INV_CALC_NNN`

| Rule ID | สูตร |
| ------- | ------- |
| `INV_CALC_001` (detail total_cost) | `total_cost = qty × cost_per_unit` (signed ตาม sign ของ `qty`) เก็บที่ 5dp บน `tb_inventory_transaction_detail` |
| `INV_CALC_002` (cost-layer total_cost — inbound) | สำหรับ `in_qty > 0`: `total_cost = in_qty × cost_per_unit` บน `tb_inventory_transaction_cost_layer` |
| `INV_CALC_003` (cost-layer total_cost — outbound) | สำหรับ `out_qty > 0`: `total_cost = out_qty × cost_per_unit` ที่ `cost_per_unit` ถูกเลือกโดย costing method (ดู `INV_CALC_005` / `INV_CALC_006`) |
| `INV_CALC_004` (on-hand ปัจจุบัน — derive) | `balance(product, location) = Σ in_qty − Σ out_qty` ครอบ cost layers ที่ไม่ถูก soft-delete ทั้งหมดที่ key (`getLocationBalance` / `calculateBalance`) ไม่มี snapshot anchor และไม่มี date cutoff — rows `close_period` (ออก) / `open_period` (เข้า) ของการปิดงวดรักษาให้ผลรวมแบบตรงถูกต้องข้ามขอบงวด ความพร้อมใช้ต่อ lot สำหรับ FIFO ใช้แนวคิดเดียวกันต่อ lot: receipts จัดกลุ่มโดย `lot_no` ลบ consumption ที่จับคู่ผ่าน `parent_lot_no` (`getAvailableFifoLots`) |
| `INV_CALC_005` (FIFO outbound cost pick) | **แก้ไขในรอบนี้ — method เป็นการตั้งค่าระดับ tenant/BU เดียว ไม่ใช่ต่อสินค้า** `InventoryTransactionService.getCalculationMethod(bu_code)` อ่าน `tb_business_unit.calculation_method` (platform schema, `enum_calculation_method { average, fifo }`, default `average`) หนึ่งครั้งต่อ posting batch และใช้กับสินค้าทุกตัวใน tenant เมื่อ BU เป็น `fifo`: การ post outbound layer iterate rows `tb_inventory_transaction_cost_layer` ที่ `(location_id, product_id)` เรียงโดย `lot_seq_no` ascending บริโภค `out_qty` จากยอดคงเหลือของแต่ละ layer จนกว่าจะพอ แต่ละ layer ที่บริโภคผลิต outbound cost-layer row ของตัวเองที่มี `cost_per_unit = layer.cost_per_unit`; transaction outbound จึงอาจมี cost-layer rows **หลาย** rows สำหรับ detail row เดียวเมื่อ consumption ครอบคลุมหลาย lot |
| `INV_CALC_006` (Weighted-average outbound cost pick) | เมื่อ `calculation_method = average` ระดับ BU: outbound `cost_per_unit = current_average_cost(location, product) ณ เวลา post` average ปัจจุบันคือ `tb_inventory_transaction_cost_layer.average_cost_per_unit` ล่าสุดที่ `(location_id, product_id)` สำหรับสินค้านั้น (refresh โดย inbound ทุกครั้ง — ดู `INV_CALC_007`) ไม่พบ per-product override ของการตั้งค่า BU |
| `INV_CALC_007` (Weighted-average refresh on inbound) | เมื่อ inbound post ภายใต้ WEIGHTED_AVERAGE: `new_average = (prior_on_hand × prior_average + in_qty × in_cost_per_unit) / (prior_on_hand + in_qty)` ปัดเป็น 5dp เขียนไปยัง `average_cost_per_unit` บน inbound cost-layer row ใหม่ การอ่านต่อมาที่ `(location_id, product_id)` รับค่านี้ |
| `INV_CALC_008` (Period close — lot carry-over, วิธี FIFO) | **แก้ไขในรอบนี้** เมื่อ `tb_business_unit.calculation_method = fifo` `processCloseTransactions` คำนวณยอดคงเหลือของทุก lot (`Σ in_qty − Σ out_qty` โดย consumption จับคู่ผ่าน `parent_lot_no`) จากนั้นเขียนหนึ่ง `close` transaction (detail `qty = −remaining`, cost-layer `transaction_type = close_period`, lot ใหม่ `CLOSE-{YYMM}-{seq}`, `out_qty = remaining`) ทำให้แต่ละ lot ที่ยังเหลือเป็นศูนย์ในงวดที่ปิด และหนึ่ง `open` transaction (`OPEN-{YYMM}-{seq}`, `transaction_type = open_period`, `in_qty = remaining`) สร้างมันขึ้นใหม่ในงวดถัดไปที่ `cost_per_unit` เดิม **ไม่มี row `tb_period_snapshot` ถูกเขียนบนเส้นทาง FIFO** |
| `INV_CALC_009` (Period close — วิธี average) | เมื่อ `calculation_method = average` `processAverageClose` (period-end.close-average.helper.ts) restate layers การ issue ของงวดที่ average สุดท้าย เขียน transactions carry-over close/open **และเขียน rows `tb_period_snapshot`** — หนึ่ง row ต่อ bucket `(product, location)` ด้วย column qty+cost `opening_* / receipt_* / issue_* / adjustment_* / closing_*` และ `diff_amount`, `snapshot_at = period.end_at` ตาราง snapshot ถูก populate **เฉพาะ**โดยเส้นทางวิธี average นี้ |
| `INV_CALC_010` (การสร้างงวดถัดไป) | `ensureNextPeriod` find-or-create row `tb_period` ถัดไป (`fiscal_month + 1` โดย roll ปี, `period = YYMM`, `status = open`, ขอบเขต UTC วันแรกถึงวันสุดท้าย) การปิดงวดจึง provision งวดถัดไปโดยอัตโนมัติ; ไม่มีขั้นตอน admin "เปิดงวด" แยกในโมดูลนี้ |
| `INV_CALC_011` (Credit-note amount adjustment) | สำหรับ `enum_transaction_type = credit_note_amount`: เขียน cost-layer row ด้วย `in_qty = out_qty = 0`, `diff_amount = vendor_credit_amount` (signed; ลบสำหรับ vendor concession ลดต้นทุน), `transaction_type = credit_note_amount` Cost บน lot ดั้งเดิมถูกคำนวณใหม่: `new_lot_cost_per_unit = (original_lot_total_cost + diff_amount) / original_lot_qty` Consumption ต่อมาจาก lot เดียวกันรับ cost ที่ revalued; ส่วนที่บริโภคไปแล้วไม่ปรับย้อนหลัง (price variance ไหลผ่าน `diff_amount`) |
| `INV_CALC_012` (การปัดเศษ) | การปัดเศษทั้งหมดเป็น half-up ค่าที่เก็บใช้ precision ของ column; การคำนวณกลางถือ 5dp; การ aggregation on-the-fly อ่านค่าที่ปัดเศษซ้ำจากแต่ละขั้น |
| `INV_CALC_013` (การตีมูลค่าของ balance-view — signed) | View `v_inventory_inventory_balance` ตีมูลค่าด้วย **signed quantity × unit cost** ไม่ใช่ unsigned `total_cost` ก่อนหน้านี้ sum unsigned `total_cost` ซึ่งทำให้มูลค่า overstate เมื่อมี outbound layers แก้ไขโดย migration `063_v_inventory_inventory_balance_costfix` (แก้ไข 2026-06-17) สูตร: `net_qty = SUM(itd.qty)` (signed: + inbound, − outbound); `amount = SUM(itd.qty × itd.cost_per_unit)`; `unit_cost = amount / net_qty` (เป็น 0 เมื่อ `net_qty = 0`) |

### 3.1 ตัวอย่างใช้งาน (tenant แบบ Weighted-average, ฿ THB)

สินค้าใน business unit ที่มี `calculation_method = average` (การตั้งค่าระดับ BU — ดู `INV_CALC_005`) ไม่มี on-hand ก่อนหน้า สาม movements ตามลำดับเวลาที่ location ประเภท inventory เดียวกัน:

- **GRN receipt #1** (`enum_transaction_type = good_received_note`): `in_qty = 100`, `cost_per_unit = ฿10.00`
  - Cost layer: `in_qty = 100`, `cost_per_unit = ฿10.00`, `total_cost = ฿1,000.00`
  - `new_average = (0 × 0 + 100 × 10.00) / (0 + 100) = ฿10.00000` ตาม `INV_CALC_007`
- **GRN receipt #2** (`good_received_note`): `in_qty = 50`, `cost_per_unit = ฿14.00`
  - Cost layer: `in_qty = 50`, `cost_per_unit = ฿14.00`, `total_cost = ฿700.00`
  - `new_average = (100 × 10.00 + 50 × 14.00) / (100 + 50) = (1,000 + 700) / 150 = ฿11.33333` ตาม `INV_CALC_007`
- **Store-requisition issue** (`issue`): `out_qty = 80`
  - Outbound cost-layer row: `out_qty = 80`, `cost_per_unit = ฿11.33333` (เลือกจาก `current_average_cost` ตาม `INV_CALC_006`), `total_cost = ฿906.67` (`80 × 11.33333` ปัด 2dp)
  - `new_average` คงที่ `฿11.33333` (issues ไม่เปลี่ยน average ภายใต้ weighted-average; เฉพาะ inbound ที่เปลี่ยน)
- On-hand ปัจจุบันตาม `INV_CALC_004`: `0 (ไม่มี snapshot ก่อน) + (100 + 50 − 80) = 70 units`; การตีมูลค่า `70 × 11.33333 = ฿793.33`

สำหรับ business unit แบบ **FIFO** (`calculation_method = fifo`, `INV_CALC_005`): issue จะบริโภคจาก receipt #1 ก่อน (`lot_at_date` / `lot_seq_no` ascending) — `out_qty = 80` ที่ `cost_per_unit = ฿10.00` (หนึ่ง cost-layer row), `total_cost = ฿800.00` ยอดคงเหลือของ receipt #1 กลายเป็น `100 − 80 = 20` units ที่ `฿10.00`; ยอดของ receipt #2 ไม่ถูกแตะที่ `50` units ที่ `฿14.00` การตีมูลค่า inventory closing: `20 × 10.00 + 50 × 14.00 = ฿900.00`

### 3.2 ตัวอย่างใช้งาน (location_type = direct)

Receipt ของสินค้าไปยัง location `direct` — แก้ไขในรอบนี้ให้เป็นกลไก `createDirectExpenseOut` จริง (ดู `INV_VAL_009`):

- **GRN receipt** (`good_received_note`, location_type = direct): `qty = 30`, `cost_per_unit = ฿8.00`, `total_cost = ฿240.00`
  - Inventory transaction header เขียน; detail **inbound** (`qty = +30`) + cost-layer row (`in_qty = 30`, lot `RC{YY}{MM}{seq}`) เขียนเหมือนกับ location ประเภท inventory ทุกประการ
  - จากนั้น service เขียน detail **outbound หักล้าง** ตัวที่สองทันที (`qty = −30`, `from_lot_no` = lot ของ receipt) + cost-layer row (`transaction_type = issue`, `out_qty = 30`, lot `ISS-{yyyy}-{MM}-{seq}`) ที่ต้นทุน `฿8.00` เดียวกัน ภายใต้ transaction header **เดียวกัน**
  - On-hand สุทธิที่ `(direct_location, product)` = `30 − 30 = 0` — "เบิกใช้ทันทีที่มาถึง"
  - ภายใต้วิธี average การรับ direct ถูกตัดออกจากการคำนวณ weighted-average ของสินค้า (`average_cost_per_unit = 0` บนทั้งสอง layers)
  - ไม่มี GL/journal entry ถูกเขียนโดยโค้ดใดที่พบในรอบนี้ (รายการ `Dr Department Expense / Cr AP` ที่เคยบันทึกไว้ที่นี่เป็น design intent ที่ยังไม่ยืนยัน)

### 3.3 ตัวอย่างใช้งาน (การตีมูลค่าของ balance-view, signed — `INV_CALC_013`)

View `v_inventory_inventory_balance` ต้องตีมูลค่าตำแหน่ง **net** ไม่ใช่ inflow รวม สามการเคลื่อนไหวบน key `(location, product, lot)` เดียว:

- **Receive 10 @ ฿100** → `qty = +10`, `cost_per_unit = ฿100`
- **Receive 10 @ ฿120** → `qty = +10`, `cost_per_unit = ฿120`
- **Issue 5** → `qty = −5`

```
net_qty   = SUM(itd.qty)                 = +10 + 10 − 5            = 15
amount    = SUM(itd.qty × cost_per_unit) = 10×100 + 10×120 − 5×110 = ฿1,650
unit_cost = amount / net_qty             = 1,650 / 15              = ฿110
```

View ที่แก้ไขแล้วส่งคืน `net_qty = 15`, `amount = ฿1,650`, `unit_cost = ฿110` สูตร **เก่า** sum unsigned `total_cost` (`1,000 + 1,200 + 550 = ฿2,750`) — ทำให้มูลค่าของตำแหน่งที่ถูก issue ลง overstate แก้ไขโดย migration `063_v_inventory_inventory_balance_costfix` (แก้ไข 2026-06-17)

## 4. กฎการกำหนดสิทธิ์ (Authorization Rules)

Rule ID ตาม `INV_AUTH_NNN` การกำหนดสิทธิ์บังคับใช้โดย RBAC ที่ source-document layer พร้อมกฎเฉพาะโมดูล inventory ชุดเล็ก ตัว inventory transaction **ไม่มี `user_action.execute` set** เพราะไม่มี workflow stage — RBAC บนโมดูล source (GRN, SR, count, credit note, manual stock-in / stock-out) คือสิ่งที่อนุญาตการ post โมดูล inventory เป็นเจ้าของกฎด้านล่างที่ gate การเขียน inventory **โดยตรง** (manual stock-in / stock-out, period-end rollforward, การกำหนดค่าพารามิเตอร์ location และ product-location)

**การแก้ไข (รอบนี้):** ทุกกฎแบบ "เกินเกณฑ์ route ไป Controller / Finance" ด้านล่าง (เดิม `INV_AUTH_001`–`INV_AUTH_003`, `INV_AUTH_005`, `INV_AUTH_006`) อธิบายห่วงโซ่การอนุมัติหลายชั้นแบบ gate ด้วย threshold (Store Keeper → Inventory Controller → Finance → Finance Manager) สำหรับ `tb_stock_in` / `tb_stock_out` การค้นทั้ง repo ของ `carmen-turborepo-backend-v2` หา `threshold` ให้ผลศูนย์ hit ภายใน service ของ inventory, stock-in, stock-out หรือ period-end (hit เดียวที่มีที่ไหนก็ตามคือ filter ต้นทุนขั้นต่ำของ spot-check ที่ไม่เกี่ยวข้องและ config rate-limiting); `enum_stage_role` (`create, approve, purchase, issue, view_only`) ไม่มีสมาชิก `finance`; และการสร้าง `tb_stock_in` / `tb_stock_out` อยู่ใต้โมดูล wiki พี่น้อง **inventory-adjustment** (`/inventory-management/inventory-adjustment`) ไม่ได้อยู่ใต้ routes ของโมดูล "inventory" นี้ (`transaction`, `period-end`) เลย ตรงกับ fabrication เรื่อง threshold ที่ยืนยันไปแล้วในทุกโมดูลอื่นของ resync นี้ Rows ด้านล่างถูกแก้ไขให้เป็นสิ่งที่โค้ดใน scope ของโมดูล*นี้*รองรับจริง; กฎการสร้าง `tb_stock_in` / `tb_stock_out` จริง (ถ้ามี threshold ใดอยู่) เป็นของหน้าของโมดูล `inventory-adjustment` เอง จะ re-verify ใน iteration ของโมดูลนั้น

## 5. กฎ Posting

โมดูล inventory ไม่มีวงจรชีวิต `doc_status` ของเอกสาร — ทุก transaction ที่ post คือ immutable ตอนเขียน state diagram จึง degenerate: แต่ละ transaction transition `(none) → posted` และอาจผ่าน reversal compensating ถูก mark `deleted_at` (reverse เชิงตรรกะแต่ไม่เคยลบ physical) กฎที่น่าสนใจคือ **fan-out effects** ที่ fire เมื่อเขียน

Rule ID ตาม `INV_POST_NNN`

> **Caveat เรื่อง GL (รอบนี้):** ทุก effect แบบ "GL: Dr … / Cr …" ที่เคยระบุในตารางนี้ถูกตัดออก — ไม่มีโค้ด journal-posting อยู่ที่ใดเลยในเส้นทาง posting ของ inventory (ดู [01-data-model](/th/inventory/inventory/01-data-model) § 1) Rows ด้านล่างอธิบายเฉพาะการเขียน ledger ที่โค้ดทำจริง

| Rule ID | Transition / Event | Effects |
| ------- | ------------------ | ------- |
| `INV_POST_001` | Post inbound (`good_received_note`, `transfer_in`, `adjustment_in`) | Insert `tb_inventory_transaction` (header) และ `tb_inventory_transaction_detail` (ต่อสินค้า `qty > 0`) Insert rows `tb_inventory_transaction_cost_layer` หนึ่งหรือมากกว่า (`splitFifoCost` อาจ split หนึ่ง receipt เป็นหลาย rows `lot_index` เพื่อกระทบยอดทศนิยมแบบเป๊ะ) ด้วย `in_qty > 0`, `cost_per_unit`, `lot_no` ที่สร้างโดยระบบ (`RC{YY}{MM}{seq}` สำหรับ GRN receipts), `lot_seq_no`, `at_period` / `period_id` จากงวดที่เปิดอยู่ปัจจุบัน ภายใต้วิธี average คำนวณ `average_cost_per_unit` ใหม่ตาม `INV_CALC_007` และ back-fill ลงบน layers ที่ไม่ใช่ direct ที่มีอยู่**ทั้งหมด**ของสินค้า (`updateMany`) |
| `INV_POST_002` | Post outbound (`issue`, `transfer_out`, `adjustment_out`) | Insert header + detail (`qty < 0`) BU แบบ FIFO: บริโภค lots ที่มีเรียงโดย `lot_at_date` / `lot_seq_no` / `lot_index` ascending (`getAvailableFifoLots` / `consumeFifoLots`) หนึ่ง outbound layer row ต่อ lot ที่บริโภค แต่ละอันถือ `cost_per_unit` ของ lot นั้นและ `parent_lot_no` BU แบบ average: layer outbound เดียวที่ average ปัจจุบัน `INV_VAL_005` (`Insufficient stock…`) ถูกตรวจก่อนเขียน (ยกเว้นเส้นทาง credit-note) |
| `INV_POST_003` | Post receipt ไปยัง location ประเภท `direct` | **แก้ไขแล้ว:** เขียน detail + layer inbound ตามปกติ จากนั้น detail outbound หักล้างอัตโนมัติ + layer `issue` ที่ต้นทุนเดียวกันภายใต้ header เดียวกัน (`createDirectExpenseOut`) — on-hand สุทธิเป็นศูนย์ การรับ direct ถูกตัดออกจากการคำนวณ average ไม่มีผลทาง GL ที่ยืนยันได้ ดู `INV_VAL_009` / § 3.2 |
| `INV_POST_004` | Post receipt ไปยัง location ประเภท `consignment` | **แก้ไขแล้ว:** ไม่มี code path เฉพาะ consignment อยู่จริง — receipt post เหมือน receipt ประเภท `inventory` ทุกประการ (`INV_POST_001`) เรื่องเล่า memo-register / no-AP เป็น design intent ที่ยังไม่ยืนยันและถูกลบออกแล้ว |
| `INV_POST_005` | Post issue จาก location ประเภท `consignment` | **แก้ไขแล้ว:** เหมือน `INV_POST_002` ทุกประการ; ไม่มีโค้ด dual posting COGS/AP อยู่จริง Consignment เป็นประเภท SR from-location ที่อนุญาต (`sr-type.helper.ts`) และถูกกวาดโดย physical count / period-end เหมือน location แบบ `inventory` |
| `INV_POST_006` | Transfer ระหว่าง locations (`store_requisition` transfer ที่ source ≠ destination) | Layer(s) `transfer_out` ที่ source (`out_qty > 0` cost เลือกตาม method ของ BU) + layer(s) `transfer_in` ที่ destination (`in_qty > 0`, `cost_per_unit = transfer_out.cost_per_unit`, `parent_lot_no` = lot ของ source) `INV_VAL_005` รันเทียบกับ balance ของ source location ไม่มีผลทาง GL ที่ยืนยันได้ |
| `INV_POST_007` | Credit-note amount adjustment (`credit_note_amount`) | Insert cost-layer row(s) ด้วย `diff_amount` ถือ credit แบบ signed ถ้างวดรับของ lot ดั้งเดิมยังเปิดอยู่ lot ถูก re-price (BU แบบ average: re-price ผ่านคู่ SO-ที่-average-เก่า / SI-ที่-average-ใหม่ ต่อ location); ถ้างวดรับเป็น `closed`/`locked` (`isLotPeriodClosed`) มูลค่าของ lot ไม่ถูกแตะและ credit บันทึกเป็น `diff_amount` งวดปัจจุบันเท่านั้น ไม่มีผลทาง GL ที่ยืนยันได้ |
| `INV_POST_008` | Credit-note quantity adjustment (`credit_note_quantity`) | Insert cost-layer row(s) ด้วย `out_qty = credit_qty` บริโภคจาก lots ของ GRN ดั้งเดิม Consumption **ไม่** throw เมื่อสต๊อกไม่พอโดยเจตนา — ส่วนขาดบันทึกเข้า `diff_amount` (ดู `INV_VAL_005`) rows ของ GRN source ไม่ถูกแก้ไข ไม่มีผลทาง GL ที่ยืนยันได้ |
| `INV_POST_009` | Period close (ปุ่ม **Close period** → `PeriodEndService.closeCurrent`) | Gate ก่อนปิด (`validatePeriodEnd`): นับเอกสารที่ block ในช่วงวันที่ของงวด — PR/PO/SR ที่ยัง `in_progress` และ `workflow_next_stage ≠ '-'`; GRN ที่ `doc_status` **ไม่** อยู่ใน `{draft, committed, voided}` (GRN แบบ draft *ไม่* block); CN ที่ไม่อยู่ใน `{draft, completed, cancelled, voided}`; บวกทุก location ที่บังคับนับ (`location_type ∈ {inventory, consignment}`, `physical_count_type = yes`, active) ต้องมี `tb_physical_count` ที่ `completed` สำหรับงวด ถ้าผ่าน: รันการปิดภายใน transaction เดียวพร้อม lock `FOR UPDATE` — เขียน transactions carry-over `close`/`open` ตาม `INV_CALC_008`/`INV_CALC_009` (rows snapshot เฉพาะเส้นทาง average) set `tb_period.status = closed` และ mark rows `tb_physical_count_period` ของงวดเป็น `completed` |
| `INV_POST_010` | Period open (`enum_inventory_doc_type = open`) | Chain อยู่ภายใน transaction `closeCurrent` เดียวกัน — `ensureNextPeriod` find-or-create `tb_period` ถัดไป (`status = open`) จากนั้น `writeOpenTransaction` สร้างแต่ละ lot ที่ยังเหลือขึ้นใหม่ในงวดใหม่ (`OPEN-{YYMM}-{seq}`, `in_qty = remaining`, `cost_per_unit` เดิม, `parent_lot_no` = lot ที่ปิด) Layers ที่ยกเข้ามา (`open_period`, `eop_in`) ถูก lock มูลค่า: ถูกตัดออกจากการ re-price ของงวดปัจจุบัน (`CARRIED_IN_TRANSACTION_TYPES`) |
| `INV_POST_011` | Period lock (`closed → locked` บน `tb_period.status`) | **ไม่เป็นส่วนของโมดูลนี้** ไม่มี endpoint lock/reopen บน `period-end.controller.ts`; `locked` ถูก set โดย service `period` แยกต่างหากที่รองรับหน้าจอ [system-config/period](/th/inventory/system-config/period) `findCurrent` ปฏิบัติต่องวด `locked` เป็นงวดปัจจุบัน (`status ∈ {open, locked}`) ดังนั้นงวด locked ยังแสดงได้ — และปิดได้ — ผ่านโมดูลนี้ |
| `INV_POST_012` | Reversal (compensating transaction) | ไม่มี endpoint reversal ทั่วไปบน API ของ inventory transaction การแก้ไขทำผ่านโมดูล source (credit note ต่อ GRN, stock-out/stock-in ผ่าน [inventory-adjustment](/th/inventory/inventory-adjustment)); แต่ละอันเขียน transaction ใหม่ของตัวเอง `deleted_at` บน `tb_inventory_transaction` ไม่เคยถูก set โดย code path ใดปัจจุบัน |

State diagram (degenerate, single-state):

```
[*] → posted → (compensating reversal optional) → posted (with deleted_at set on original)
```

Transaction row เป็น immutable หลังเขียน; reversal คือ row ใหม่ ไม่ใช่การเปลี่ยนสถานะ
