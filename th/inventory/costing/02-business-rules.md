## 1. ภาพรวม

หน้านี้บันทึกกฎทางธุรกิจที่ดำเนินการกำกับ **โมดูล costing** — เอนจินที่เลือก `cost_per_unit` สำหรับทุก outbound stock movement, รีเฟรช `average_cost_per_unit` ทุก inbound, และ — เฉพาะ business unit ที่ใช้วิธี average — เขียน period-locked `closing_cost_per_unit` ที่ปลายงวด เนื่องจาก costing **ไม่ใช่** โมดูล document แยก — เป็นชั้นพฤติกรรมเหนือ ledger ของ [inventory](/th/inventory/inventory) — ชุดกฎตรงนี้ดูต่างจาก GRN / PR / SR catalogues: ไม่มี document lifecycle ของตัวเอง ไม่มี save / approve / commit progression ไม่มี `doc_status` แต่กฎข้างล่างอธิบาย **เอนจินอ่าน configuration อย่างไร เลือก cost อย่างไร ดำเนินการ arithmetic อย่างไร รีเฟรช average อย่างไร และ anchor ขอบเขตงวดอย่างไร** ทุกกฎ **invoke จาก** inventory transaction post หรือ period-end run ที่อยู่ในโมดูล inventory; โมดูล costing เป็นเจ้าของ logic ของกฎ ไม่ใช่ trigger ไม่มีชั้น RBAC authority แยกซ้อนทับ engine — ดู Section 4

โครงสร้างสองจุดให้สีแก่ทุกกฎข้างล่าง **ประการแรก** **วิธี costing ตั้งค่าที่ business unit ไม่ใช่ per product** (ตาม [costing/01-data-model](/th/inventory/costing/01-data-model) § 5 item 1) เอนจิน resolve วิธีผ่าน `tb_business_unit.calculation_method` (backstage schema, default `average`; `getCalculationMethod(bu_code)`, `inventory-transaction.service.ts:449-454`) ครั้งเดียวต่อการเรียก และ apply กับทุก detail line ใน transaction ไม่มี per-product override; mixed FIFO / WA ข้าม products ที่ business unit เดียวกัน **ไม่ใช่** การตั้งค่าที่รองรับ ภายใต้ **average** ค่าเฉลี่ยเคลื่อนที่ถูกรักษา **ต่อสินค้าข้ามทุก location** (`getNetTotals(tx, productId)`, `inventory/net-average-cost.helper.ts`) และประทับซ้ำลง layer ที่ยังมีชีวิตของสินค้านั้นในงวดที่ active; ภายใต้ **average_per_location** เก็บต่อ `(product, location)` (`resolveAverageLocationScope`) **ประการที่สอง** ทุก cost ที่เลือกตอน post คือ **immutable on write** — เมื่อเขียนไป `tb_inventory_transaction_cost_layer.cost_per_unit` ค่าเป็นส่วนหนึ่งของ historical ledger และไม่สามารถแก้ไขได้แม้วิธีที่ตั้งค่าจะเปลี่ยน มีข้อยกเว้นสองกรณีและทั้งคู่แทนที่แถวแทนการแก้: (a) credit-note-amount adjustment เขียน `diff_amount` และคำนวณ `cost_per_unit` ของ lot ต้นทางใหม่ตาม `INV_CALC_011`; (b) GRN บน BU แบบ average ที่โพสต์ตอน save แล้วถูก void, reject หรือแก้ไขก่อน commit จะจะถูก soft-delete การเคลื่อนไหว (void/reject) หรือ retire เฉพาะบรรทัดที่เปลี่ยนภายใต้ header ที่ void แล้วและโพสต์ใหม่ (แก้ไข) (`voidGrnLedger` / `repostGrnLedgerIfChanged`, `good-received-note.ledger.ts:516-873`) และถูกปฏิเสธหาก lot ที่รับเข้ามาถูกใช้ไปแล้ว คุณสมบัติเหล่านี้ — วิธีเดียวต่อ business unit, immutable cost บน layer row — คือสิ่งที่ทำให้ audit trail ของ costing ป้องกันได้ข้ามงวด

## 2. กฎการตรวจสอบ (Validation Rules)

Rule IDs ตาม `COST_VAL_NNN` Validation ทำงาน **ตอน cost-pick** — เมื่อ inventory transaction post invoke costing engine เพื่อเติม `cost_per_unit` / `average_cost_per_unit` บน cost-layer row ที่จะเขียน ไม่มี save-time หรือ commit-time split; engine ถูกเรียกครั้งเดียวต่อ cost-layer row และคืน valid cost หรือ fail parent transaction

## 3. กฎการคำนวณ (Calculation Rules)

ค่าการเงินทั้งหมด store เป็น `Decimal(20, 5)` บน cost-layer และ detail rows แต่ **เอนจินปัดต้นทุนต่อหน่วยทุกค่าที่เขียนเป็น 2 ตำแหน่ง** (`Math.round(x × 100) / 100` ใน `inventory-transaction.service.ts:1054,1302`, `calculateNewAverageCost`, `getCurrentAverageCost`) และกระทบยอดรวมของ layer ให้ตรงความละเอียดนั้น (`splitFifoCost(qty, total, 2)`) สาย money chain ของ GRN ที่ป้อนเข้ามาเป็น 5 ตำแหน่ง Display rounding เป็น 2 ตำแหน่งสำหรับ currency amounts และ 3 ตำแหน่งสำหรับปริมาณ กฎข้างล่างคือ arithmetic ของเอนจิน; ถูก invoke โดยกฎใน Section 2 (validation) และ Section 5 (posting)

Rule IDs ตาม `COST_CALC_NNN` กฎเหล่านี้ **delegate ไป** หรือ **align กับ** inventory-module rules `INV_CALC_001`–`INV_CALC_012`

| Rule ID | สูตร |
| ------- | ------- |

| `COST_CALC_009` (Standard cost — recipe baseline) | `tb_product.standard_cost` อ่านโดย recipe costing และโดยตัวเลือก `standard` ของการตั้งค่า BU `si.cost-from` (`enum_physical_count_costing_method = standard` เดิมไม่ถูกอ่านแล้ว) **ไม่** อ่านโดย FIFO / WA cost-pick การอัปเดต `standard_cost` เป็น prospective |
| `COST_CALC_010` (Rounding) | **แก้ไข 2026-09-22** ต้นทุนต่อหน่วยบน ledger (`cost_per_unit`, `average_cost_per_unit`) ปัดเป็น **2 ตำแหน่ง** ด้วย JavaScript `Math.round` (half away from zero สำหรับค่าบวก); ค่า `total_cost` ของ layer ถูกกระทบยอดให้รวมเท่ากับยอดเอกสาร 2 ตำแหน่งพอดี (`splitFifoCost`); ส่วนแบ่ง `extra_cost_amount` มาจาก `splitByWeight` ที่ความละเอียดเดียวกัน ยอดฝั่งเอกสาร (`base_net_amount`, เปอร์เซ็นต์ deviation) เป็น 5 ตำแหน่ง คอลัมน์ยังคง `Decimal(20, 5)` Display: 2 ตำแหน่งสำหรับ currency, 3 ตำแหน่งสำหรับปริมาณ |

### 3.1 ตัวอย่างที่ทำงาน (FIFO, business unit `BU-A` พร้อม `calculation_method = fifo`)

Products สองตัวที่ business unit เดียวกันเป็น FIFO ทั้งคู่ (วิธีเป็น per business unit ไม่ใช่ per product) พิจารณา product `P-1` ที่ location `LOC-A` (code `LA`) ในงวด `2609` ไม่มี on-hand ก่อน:

- **Inbound 1** (GRN commit, `good_received_note`): `in_qty = 100`, landed `cost_per_unit = ฿10.00`, `lot_seq_no = 1` → `lot_no = LA26090001`, `lot_index = 1`
  - Cost-layer row: `in_qty = 100, cost_per_unit = ฿10.00, total_cost = ฿1,000.00, extra_cost_amount = 0, average_cost_per_unit = 0` (ไม่มี shadow average ภายใต้ FIFO)
- **Inbound 2** (GRN commit, บรรทัดเดียว, สินค้า `base_net_amount = ฿650.00` สำหรับ 50 หน่วย บวก extra cost ค่าขนส่ง `฿50.00` ที่จัดสรรให้บรรทัดนั้น): `stock_cost = 700.00`, `cost_per_unit = Round2(700.00 / 50) = ฿14.00`, `lot_seq_no = 2` → `lot_no = LA26090002`
  - Cost-layer row: `in_qty = 50, cost_per_unit = ฿14.00, total_cost = ฿700.00, extra_cost_amount = ฿50.00, average_cost_per_unit = 0`
- **Outbound** (SR issue): `out_qty = 80` FIFO consume `LOT-1` ก่อน (`lot_seq_no = 1`)
  - Cost-layer row: `out_qty = 80, cost_per_unit = ฿10.00, total_cost = ฿800.00, from_lot_no = LOT-1` ตาม `COST_CALC_001`
  - `LOT-1` remaining: `100 − 80 = 20`; `LOT-2` ไม่ถูกแตะที่ `50`
  - On-hand valuation: `20 × 10.00 + 50 × 14.00 = ฿900.00`
- **Outbound** (SR issue): `out_qty = 30` FIFO consume `LOT-1` ที่เหลือ (`20 units at ฿10.00`) บวก `10 units` จาก `LOT-2 (at ฿14.00)`
  - Cost-layer row 1: `out_qty = 20, cost_per_unit = ฿10.00, total_cost = ฿200.00, from_lot_no = LOT-1`
  - Cost-layer row 2: `out_qty = 10, cost_per_unit = ฿14.00, total_cost = ฿140.00, from_lot_no = LOT-2`
  - นี่คือ **two-row FIFO outbound** — SR detail line เดียวผลิต cost-layer rows หลายแถว
  - On-hand valuation: `LOT-2: 40 × 14.00 = ฿560.00`

### 3.2 ตัวอย่างที่ทำงาน (WA, business unit `BU-B` พร้อม `calculation_method = average`)

Product `P-1` เดียวกันที่ `LOC-A` movements ทางกายภาพเดียวกัน แต่ที่ business unit ต่างที่ตั้ง WA หมายเหตุว่าบน BU นี้การเคลื่อนไหวของ GRN ถูกเขียนตอน **save** ไม่ใช่ commit (`postsInventoryAtSave`) และค่าเฉลี่ยเป็นระดับสินค้า — location ที่สอง `LOC-B` ที่ถือ `P-1` จะใช้ค่าเฉลี่ยร่วมกัน:

- **Inbound 1**: `in_qty = 100, cost_per_unit = ฿10.00`
  - Cost-layer row: `in_qty = 100, cost_per_unit = ฿10.00, total_cost = ฿1,000.00, average_cost_per_unit = ฿10.00`
- **Inbound 2**: `in_qty = 50, cost_per_unit = ฿14.00`
  - `new_average = Round2((1,000.00 + 700.00) / 150) = Round2(11.33333) = ฿11.33` ตาม `COST_CALC_003`; เขียนบน layer ใหม่ **และประทับซ้ำบน layer ของ Inbound 1**
- **Outbound** (SR issue): `out_qty = 80` WA อ่านค่าเฉลี่ยของสินค้า `฿11.33` ตาม `COST_CALC_002`
  - Cost-layer row (single): `out_qty = 80, cost_per_unit = ฿11.33, total_cost = ฿906.40`
  - Average ไม่ถูกประทับซ้ำโดย outbound; ตอนนี้ `getNetTotals` รวมสุทธิ `(100×10 + 50×14 − 80×11.33) / (150 − 80) = 793.60 / 70 = ฿11.34` สำหรับการ recompute ของการรับ *ครั้งถัดไป* (รวมสุทธิที่ต้นทุนของแต่ละ layer เอง, `inventory-cost.formula.ts` `sumNetTotals`)
  - On-hand: `70 units × ฿11.33 = ฿793.10` ที่ค่าเฉลี่ยที่ประทับไว้
- **Outbound** (SR issue): `out_qty = 30`
  - Cost-layer row (single): `out_qty = 30, cost_per_unit = ฿11.33, total_cost = ฿339.90`
  - On-hand: `40 × 11.33 = ฿453.20`

Physical flow เดียวกัน COGS total ต่าง (FIFO ผลิต `฿800 + ฿200 + ฿140 = ฿1,140`; WA ผลิต `฿906.40 + ฿339.90 = ฿1,246.30`) ความต่างคือ **เพียง** cost-pick rule; qty ledger เหมือนกัน ในสถานการณ์ราคาขาขึ้น FIFO COGS ต่ำกว่าและ ending-inventory value สูงกว่า — ดู [`calculation-methods.md`](./calculation-methods.md) § 5 **แก้ไข 2026-09-22:** เวอร์ชันก่อนของตัวอย่างนี้ถือค่าเฉลี่ยที่ 5 ตำแหน่ง (`฿11.33333`); เอนจินปัดเป็น 2 ตำแหน่ง

### 3.3 ตัวอย่างที่ทำงาน (Credit-note-amount revaluation)

ต่อจาก § 3.1 (FIFO): vendor ลดราคา `฿100.00` หลังรับการซื้อ `LOT-2` (เดิม `50 units at ฿14.00, total ฿700.00`) Credit note post เป็น `enum_transaction_type = credit_note_amount`:

- Cost-layer row: `in_qty = 0, out_qty = 0, diff_amount = −฿100.00, transaction_type = credit_note_amount, lot_no = LOT-2`
- `LOT-2` revalued ตาม `COST_CALC_005`: `new_cost_per_unit = (700.00 + (−100.00)) / 50 = ฿12.00`
- Outbound ถัดไปที่ consume จาก `LOT-2` หยิบ `cost_per_unit = ฿12.00` (ไม่ใช่ `฿14.00`); portions ที่บริโภคแล้ว (10 units ที่บริโภคใน outbound ที่สองของ § 3.1 ที่ `฿14.00`) **ไม่** ถูกปรับย้อนหลัง — variance ไหลผ่าน `diff_amount` บน cost-layer ledger เท่านั้น ไม่มีการ post general ledger เกิดขึ้นเลยในเส้นทางนี้ (ไม่มีโค้ด journal-entry อยู่ใน backend); `diff_amount` คือบันทึกถาวรทั้งหมดของการ revalue นี้

## 4. กฎการกำหนดสิทธิ์ (Authorization Rules)

**แก้ไข (ยืนยันแล้ว 2026-07-22):** ฉบับก่อนหน้าของ section นี้กำหนดกฎ `COST_AUTH_NNN` สิบข้อบน RBAC split แบบ Finance / Finance Manager / Inventory Controller / Auditor ซึ่งไม่มีอยู่จริงสำหรับโมดูลนี้ การตรวจสอบกับซอร์สพบว่า: `enum_stage_role` (enum role เดียวใน tenant schema) คือ `{create, approve, purchase, issue, view_only}` — ไม่มีสมาชิก `finance` หรือ `auditor`; `constant/permissions.ts` ใน frontend ไม่มี key เฉพาะ finance หรือ auditor เลย; permission key เดียวที่แตะโมดูลนี้คือ `inventory_management.period_end.view` / `.execute` ทั่วไป (เปิด/ปิดงวด ดู [inventory/period-end](/th/inventory/inventory/period-end)) และ permission CRUD ทั่วไปของแต่ละ source document เอง (เช่น `procurement.credit_note`) ไม่มี tier การอนุมัติ cost-impact ไม่มีการแยก "requester vs. executor" สำหรับการเปลี่ยน configuration และ — ตามการแก้ไขใน Section 2 — ไม่มีการบล็อกที่ code บังคับสำหรับการเปลี่ยน `calculation_method` สอดคล้องกับข้อค้นพบ Finance/Auditor เดียวกันที่ยืนยันแล้วบน [inventory/02-business-rules](/th/inventory/inventory/02-business-rules) § 4

Authorization บนโมดูล costing **บางจริง** — engine เป็น system service ที่ invoke โดย inventory transaction posts gate ด้วย permission ที่ action ที่เรียกมันต้องมีอยู่แล้วเท่านั้น:

| ผู้กระทำ | ทำอะไรได้ | Gate |
| -------- | ---------- | ---- |
| ผู้ถือ `inventory_management.period_end.execute` | จุดชนวนการปิดงวด ซึ่งรัน logic FIFO lot-carry หรือ Average close-and-snapshot ตามที่อธิบายใน Section 5 | `AppIdGuard('period_end.close')` ที่ backend; ไม่มีการตรวจชื่อ role |
| ผู้ถือ `inventory_management.period_end.view` | ดูงวดปัจจุบันและ pre-close review checklist | `AppIdGuard('period_end.findOne' / 'findReview')` |
| ผู้มี permission save/commit GRN (`procurement.goods_received_note.commit` — key เดียวครอบคลุมทั้งคู่), อนุมัติ SR issue, commit inventory adjustment, หรืออนุมัติ credit-note | จุดชนวน cost-pick engine โดยอ้อมเป็นผลข้างเคียงของ permission gate ของเอกสารนั้นเอง (`procurement.*`, `inventory_management.*`) — ไม่มีการตรวจ authorization เพิ่มเติมเฉพาะ costing บนนี้ | ตาม permission ของ source document นั้น ดูหน้า business-rules ของโมดูลนั้นเอง |

## 5. กฎการ Posting (Posting Rules)

"Posting" ของโมดูล costing คือ cost-layer row write ที่ engine ทำในขณะที่ inventory transaction post กฎข้างล่างอธิบาย **engine เขียนอะไร** บน cost-layer row สำหรับแต่ละ `enum_transaction_type`

Rule IDs ตาม `COST_POST_NNN`

| Rule ID | Trigger | Costing-engine effect |
| ------- | ------- | --------------------- |
| `COST_POST_001` | Inbound ไป inventory-type location (`enum_transaction_type ∈ {good_received_note, adjustment_in, transfer_in}`) | Engine เลือก inbound cost (จาก source document — GRN **landed** cost ตาม `COST_CALC_011` ยืนยันว่าใช้งานจริง 2026-09-22; unit cost ของ stock-in; transfer-in cost จาก `transfer_out` คู่กัน) เขียน `tb_inventory_transaction_detail` หนึ่งแถวและ cost-layer row หนึ่งแถวขึ้นไป: `in_qty > 0`, `cost_per_unit = Round2(picked_cost)`, `lot_no = <location_code><YYMM><run>`, `lot_index` ต่อแถวที่แยก, `lot_seq_no` นับตามงวดตาม `COST_CALC_004`, `extra_cost_amount` (GRN เท่านั้น), `period_id` / `at_period` จากวันที่เอกสาร **Average units** (`average`, `average_per_location`): รีเฟรชและประทับซ้ำ `average_cost_per_unit` ตาม `COST_CALC_003` **FIFO units:** เขียน `average_cost_per_unit = 0` — **แก้ไข 2026-09-22** ไม่มี shadow WA **จังหวะของ GRN:** การเขียนเกิดที่ `commit()` บน BU แบบ FIFO และตั้งแต่ `save()` บน BU แบบ average (`postsInventoryAtSave`, `good-received-note.ledger.ts:55-57`); ส่วนหัวการเคลื่อนไหวบันทึก `info.posted_at_save` เพื่อให้ commit ไม่โพสต์ซ้ำ |
| `COST_POST_002` | Outbound จาก inventory-type location (`enum_transaction_type ∈ {issue, adjustment_out, transfer_out}`) | Engine resolve `calculation_method` ของ business unit **FIFO branch** ตาม `COST_CALC_001`: iterate layer ที่ใช้ได้เก่าสุดก่อนตาม transaction clock (`COST_CALC_001`) เขียน cost-layer row หนึ่งแถวต่อ layer ที่ consume พร้อม `out_qty`, `cost_per_unit = consumed_lot.cost_per_unit`, `from_lot_no = consumed_lot.lot_no` **WA branch** ตาม `COST_CALC_002`: เขียน cost-layer row เดียวที่ `out_qty = total`, `cost_per_unit = current_average`, `from_lot_no` เว้นว่างหรือตั้ง sentinel "WA pool" หากจำเป็น Average **ไม่** รีเฟรช (outbound ไม่ blend ใหม่) |
| `COST_POST_003` | Credit-note-amount adjustment (`enum_transaction_type = credit_note_amount`) | Engine เขียน cost-layer row พร้อม `in_qty = 0`, `out_qty = 0`, `diff_amount = signed_amount`, `transaction_type = credit_note_amount`, `lot_no = originating_lot` อัปเดต `cost_per_unit` ของ lot ต้นทางตาม `COST_CALC_005` |
| `COST_POST_004` | Credit-note-quantity adjustment (`enum_transaction_type = credit_note_quantity`) | Engine ปฏิบัติเป็น outbound: เขียน cost-layer row พร้อม `out_qty = credit_qty`, `cost_per_unit = originating_lot.cost_per_unit`, `from_lot_no = originating_lot` |
| `COST_POST_005` | Receipt ไป direct-cost location | **แก้ไขแล้ว:** engine **ไม่** skip layer — `createFifoTransaction` / `createAverageTransaction` เขียนแถว cost-layer ขาเข้าตามปกติ แล้วเขียนแถวขาออกชดเชยอัตโนมัติทันที (`createDirectExpenseOut`) ที่ต้นทุนเดียวกันภายใต้ transaction header เดียวกัน เพื่อให้ยอดคงเหลือสุทธิของ location เป็นศูนย์ Direct receipt ถูกยกเว้นจากการคำนวณ weighted-average (ไม่มีผลต่อ `average_cost_per_unit`) ไม่มีผลกับ GL จาก inventory (โมดูล GL ไม่ถูกเรียกจากโค้ด inventory) |
| ~~`COST_POST_006`~~ | **ลบออก — ไม่มี posting branch เฉพาะ consignment** (ดู `COST_VAL_012` ที่ถูกลบด้านบน) Consignment-location receipt ถูก cost เหมือน inventory-type receipt ทั่วไป | — |

| `COST_POST_009` | Count-variance posting (`enum_inventory_doc_type ∈ {stock_in, stock_out}` ที่มาจากการนับที่เสร็จแล้ว) | Engine resolve แหล่งต้นทุนการนับจากการตั้งค่า BU `si.cost-from` และเลือก cost ส่วนเกินตาม `COST_CALC_008` (ส่วนที่ขาดใช้ต้นทุนของ lot ที่ consume / ค่าเฉลี่ยปัจจุบัน ณ ตอนโพสต์) เขียน cost-layer row ผ่าน `COST_POST_001` ปกติ (ส่วนเกิน → adjustment_in) หรือ `COST_POST_002` (ส่วนขาด → adjustment_out) โดยส่งต้นทุนที่เลือกผ่านไป แหล่ง valuation ของ count variance ถูกเก็บใน activity log เพื่อ audit |

### 5.1 Cost Method × Trigger Mapping — เอกสารวางแผน vs Code

Costing ไม่มี per-document status lifecycle Engine cost ถูก invoke โดย inventory-affecting transactions ตารางข้างล่าง map แต่ละ trigger transaction กับผล Average (AVCO) และ FIFO คอลัมน์ "Notes / Source" อ้างเอกสารวางแผนจริงที่ `../carmen-frontend-e2e/docs/persona-doc/System Process/*.md` เมื่อมี บวก code path ที่รอบนี้ตรวจสอบแต่ละแถวใหม่ — ฉบับร่างก่อนหน้าอ้างเอกสารชุดเดียวกันนี้ด้วย path ที่ไม่มีอยู่จริง (`Test_case/System_Process/...`) พร้อม "capture date" ที่กุขึ้นเอง path และการตรวจสอบ code ที่ถูกต้องอยู่ด้านล่าง "AVCO" คือคำที่เอกสารวางแผนใช้เรียกสิ่งเดียวกับที่ Prisma schema เรียก `average`

|---|---|---|---|

### 5.2 Discrepancy Callouts — เอกสารวางแผน vs Code

> ⚠️ **SR cost-pick เป็น pass-through — ไม่มี AVCO re-average, ไม่มี FIFO layer ใหม่** Store Requisition ย้ายสินค้าจาก inventory location ไป Direct หรือ Consignment destination ที่ existing unit cost Engine cost ถูก invoke (ตาม `COST_POST_002`) เพื่อเลือก existing layer cost แต่ AVCO ไม่ re-average และ FIFO ไม่สร้าง layer ใหม่ ยืนยันกับ `inventory-transaction.service.ts` โดยตรง; เหตุผลการออกแบบ ("internal movement at book value, no value gained or lost") ระบุอยู่ในเอกสารวางแผน `proc-03-cost-calculation.md` § "SR Exception — Why No Recalc" (`../carmen-frontend-e2e/docs/persona-doc/System Process/`)

> ⚠️ **Costing method ไม่มีการล็อกที่ code บังคับ แม้จะมีเจตนาออกแบบ** เอกสารวางแผนบันทึก "costing method ล็อกที่ implementation ไม่สามารถเปลี่ยนหลัง go-live" เป็น **requirement ที่ stakeholder ยืนยัน** — แต่ไม่ใช่สิ่งที่ code ปัจจุบันทำ ดู `COST_VAL_009` ที่ถูกลบใน Section 2: ไม่มีการตรวจ on-hand ไม่มี drain precondition และไม่มี rejection path ใด ๆ ใน write path ของ `tb_business_unit.calculation_method` (`backstage_business-units.controller.ts`) ถือว่านี่เป็นช่องว่างจริงระหว่างเจตนาการออกแบบกับ implementation ไม่ใช่กฎที่บังคับใช้

> ⚠️ **Physical Count cost source ตั้งค่าได้ ไม่ใช่ fixed — และกลไกเปลี่ยนไปแล้ว (2026-10)** Count-surplus posts ใช้ BU config key `si.cost-from` (`standard`, `last_cost`, `last_receiving`, `average`) เพื่อเลือก unit cost; `enum_physical_count_costing_method` เดิม (`standard`, `last`, `average`, `last_receiving`) ไม่ถูกอ่านแล้ว — แยกจาก AVCO/FIFO cost-pick บนธุรกรรมปกติ ทั้ง `carmen/docs` และเอกสารวางแผนชุด `System Process` ไม่ได้ระบุ enum นี้โดยชื่อ Source: [01-data-model](/th/inventory/costing/01-data-model) § 2.6; `COST_CALC_008`

> ⚠️ **เส้นทาง CRN lot cost reversal — ต้องตรวจสอบซ้ำกับรอบ resync ของโมดูล credit-note เอง** ว่า CRN กลับ lot cost ของ GRN เดิมหรือใช้ cost ปัจจุบันถูกบันทึกเป็น "TBC" ในเอกสารวางแผน (`proc-03-cost-calculation.md` P4 Q5) ตอนที่เขียน Prisma engine มีสอง code path แยกกัน — `credit_note_quantity` (คืนที่ต้นทุน lot ต้นทาง) และ `credit_note_amount` (revalue ผ่าน `diff_amount`) — ยืนยันว่าทั้งคู่มีอยู่ใน `inventory-transaction.service.ts` ส่วน UX flow ไหน trigger path ไหนยังไม่ได้ตรวจสอบซ้ำในรอบนี้

> ✅ **การเก็บ cost multi-currency — ยืนยันแล้ว 2026-09-22: สกุลเงินฐานเท่านั้น** GRN feed ส่ง `base_net_amount` และแปลงส่วนแบ่ง extra cost ด้วย `calcBase(share, grn.exchange_rate)` (`good-received-note.ledger.ts:75,131`); แถว ledger ไม่มีคอลัมน์สกุลเงินหรืออัตรา คำถาม "TBC" ของเอกสารวางแผน (`proc-03-cost-calculation.md` P4 Q6) มีคำตอบแล้ว: การตีมูลค่าเป็นสกุลเงินฐานของ business unit ที่อัตราแลกเปลี่ยนของเอกสาร ตัวอย่างที่ทำงานทั้งหมดในหน้านี้ใช้ Thai Baht `฿` ที่อัตรา 1
>
> ⚠️ **จังหวะการโพสต์ GRN ต่างกันตามวิธี** บน BU แบบ average การเคลื่อนไหวมีอยู่ตั้งแต่ GRN ยังเป็น `saved` และถูกถอนออกหาก GRN ถูก void / reject / แก้ไข (`COST_POST_011`); บน BU แบบ FIFO ไม่มีอะไรเกิดขึ้นจนกว่าจะ commit ผู้ทดสอบที่ตรวจ "สต๊อกหลัง save" ต้องรู้วิธีของ BU ก่อน

## 6. กฎข้ามโมดูล (Cross-Module Rules)

| Rule ID | โมดูลที่เกี่ยวข้อง | กฎ |
| ------- | -------------- | ---- |
| `COST_XMOD_001` | [inventory](/th/inventory/inventory) | Cost-layer ledger `tb_inventory_transaction_cost_layer` เป็นของโมดูล inventory; costing engine คือ **ชั้นพฤติกรรม** ที่อ่านและเขียน ledger ทุก cost-pick ในโมดูลนี้ invoke จาก `INV_POST_001`–`INV_POST_010` event |
| `COST_XMOD_002` | [good-receive-note](/th/inventory/good-receive-note) | GRN invoke `COST_POST_001` สำหรับแต่ละเหตุการณ์รับที่มีปริมาณสต็อก (`received_base_qty + foc_base_qty`) > 0 — ตอน **commit** (`saved → committed`) บน BU แบบ FIFO, ตอน **save** (`draft → saved`) บน BU แบบ average `cost_per_unit` ที่เขียนลง cost layer คือ **landed** cost: `(base_net_amount + extra cost ที่จัดสรร) / (received + FOC)` (`COST_CALC_011`; extra cost จาก `tb_extra_cost` / `tb_extra_cost_detail` ด้วยโหมด `by_qty` = เท่ากัน, `by_value` = ตามปริมาณ, `manual` = ไม่แบ่ง — ยืนยันว่าใช้งานจริง 2026-09-22 ก่อนหน้านี้ "ยังไม่ยืนยัน") แถว ledger ชี้กลับไปยังเหตุการณ์รับ (`good_received_note_detail_item_id`) และ `GET …/stock-movements` ของ GRN อ่านมัน |

| `COST_XMOD_005` | [inventory-adjustment](/th/inventory/inventory-adjustment) | Manual `tb_stock_in` / `tb_stock_out` adjustments invoke `COST_POST_001` (inbound — พบสต๊อก, นับเกิน) หรือ `COST_POST_002` (outbound — แตกหัก, write-off หมดอายุ, นับขาด) **เมื่อ commit** (`PATCH …/stock-ins/:id/commit`, `…/stock-outs/:id/commit`; create เขียน `draft` — อัปเดต 2026-09-22) `cost_per_unit` มาจากเอกสาร (สำหรับ stock-in lot ใหม่ ผู้ใช้ระบุต้นทุน; `tb_stock_in_detail` ยังมี `expired_at` ตั้งแต่ `20260731120000`) หรือเอนจินเลือกให้ (สำหรับ outbound, FIFO หรือ WA ตามวิธีที่ตั้งค่า) |
