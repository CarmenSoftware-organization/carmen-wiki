# ใบรับสินค้า (Goods Receive Note) — Test Scenarios — Receiver

> **At a Glance**
> **Persona:** Receiver (Store Keeper / Receiving Clerk + Inventory Manager) &nbsp;·&nbsp; **โมดูล:** [good-receive-note](/th/inventory/good-receive-note) &nbsp;·&nbsp; **จำนวน scenario:** ~24
> **หมวด:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **ความครอบคลุม E2E:** map ไปยัง `501-grn.spec.ts` ใน `../carmen-inventory-frontend-e2e/`
> **แก้ไขในรอบนี้ (2026-07-15):** ตัด `accepted_qty` ออก (ไม่มีฟิลด์นี้อยู่ — ดู [01-data-model.md](./01-data-model.md)), scenario batch-commit และ end-of-period auto-commit (ไม่พบโค้ดที่ตรงกัน) และ scenario "post-commit reversal พร้อม elevated co-authorisation" (endpoint `/void` ไม่มี gate เช่นนั้น) แก้ไขจังหวะการเปลี่ยนแปลงระบบ: **save** (`draft → saved`) ไม่ใช่ commit คือสิ่งที่ post inventory และเลื่อน PO

หน้านี้จับ test scenario ที่ persona Receiver (**Store Keeper / Receiving Clerk** ที่ dock บวก **Store Manager / Inventory Manager** ที่ commit) ขับเคลื่อนโดยตรงในโมดูล `good-receive-note` ความเกี่ยวข้องของ Receiver เริ่มเมื่อ PO มาถึงที่ `po_status ∈ {sent, partial}` (หรือสำหรับ `doc_type = manual` เมื่อเกิดการรับ ad-hoc) และจบเมื่อ GRN ออกจากโซน receiver — ผ่าน `committed` (ล็อกแล้ว ไม่พบ handoff โมดูลเพิ่มเติม), `voided` จาก `draft` / `saved`, หรือ variance ที่ flag ส่งต่อไปยัง Purchaser Scenario จัดกลุ่มเป็น **happy path** (การเดินสถานะ `draft → saved → committed`, GRN manual, GRN บางส่วน, การจับ lot/expiry, variance การรับของขาด), **RBAC** (ขอบเขต Store Keeper เทียบ Inventory Manager), **validation** (test เชิงลบเทียบกับ `GRN_VAL_001`–`GRN_VAL_014`), และ **edge case** เล็กน้อย (tolerance boundary, ความละเอียดทศนิยม, การ save พร้อมกัน, การรวมหลาย PO)

## 2. Permission / Authorization

| # | Scenario | พฤติกรรมที่คาด (allow/deny + เหตุผล) |
| - | -------- | --------------------------------------- |
| RCV-PERM-01 | Store Keeper สร้าง GRN ที่ `doc_status = draft` และ save เป็น `saved` | **Allow** Store Keeper เป็นเจ้าของ transition `draft → saved` ที่แก้ไขได้ ซึ่งเป็นขั้นตอน posting ด้วย Map ไปยังครึ่ง create / save ของ TC-GRN-030001 / TC-GRN-070001 |
| RCV-PERM-02 | Inventory Manager commit GRN ที่ `saved` (`saved → committed`) | **Allow** Inventory Manager ล็อกเอกสาร; `commit()` ฝั่ง server ต้องการ `doc_status = saved` |
| RCV-PERM-03 | Store Keeper พยายาม commit GRN ที่ `saved` | **Deny — ต้องการ Inventory Manager** ปุ่ม **Commit** ถูกซ่อน / ปิดสำหรับบทบาท Store Keeper; เรียก API โดยตรง return `"Commit from status saved requires the Inventory Manager role."`; เอกสารยังที่ `saved` Map ไปยัง TC-GRN-110002 |
| RCV-PERM-04 | ผู้ใช้ใดพยายามแก้ไข GRN ที่ `committed` | **Deny — สถานะ terminal** `committed` ถูกล็อกจากการแก้ไข header / บรรทัด / lot / attachment (comment ยังอนุญาต) endpoint แก้ไข reject ด้วย `"GRN at status committed is locked."` Map ไปยัง TC-GRN-080005 และ TC-GRN-090003 |
| RCV-PERM-05 | การแยกหน้าที่ — Receiver (ผู้ post GRN) เทียบ Purchaser (ผู้ซื้อบน PO) | **ยังไม่ยืนยัน** เวอร์ชันก่อนหน้าของแถวนี้ระบุ deny แบบเข้มเมื่อผู้ใช้เดียวกันเป็นทั้ง PO buyer และผู้ post GRN (กฎแบบ `PO_AUTH_010`) ไม่พบการตรวจ `buyer_id` cross-check ใน `good-received-note.service.ts` หรือ `good-received-note.logic.ts` ในรอบนี้ — ให้ถือว่าการควบคุมนี้เป็นเจตนาการออกแบบ ไม่ใช่กฎที่บังคับใช้ |
| RCV-PERM-06 | Void GRN ที่ `draft` หรือ `saved` | **Allow โดยไม่มี guard สถานะฝั่ง server** frontend แสดง Void เฉพาะเมื่อ `doc_status ∉ {committed, voided}` แต่ endpoint `/void` เอง (`voidGrnById`) บล็อกเฉพาะการ void ซ้ำ GRN ที่ `voided` แล้ว — ไม่ตรวจ `doc_status` อื่นใด **แก้ไขในรอบนี้:** เวอร์ชันก่อนหน้าของแถวนี้บรรยาย "post-commit reversal ที่ต้องการ co-authorisation ระหว่าง Inventory Manager + Finance" — ไม่พบ gate หรือการกลับด้านชดเชยใดๆ ใน `voidGrnById()` |

## 3. Validation / Error

| # | Scenario | Trigger | ข้อผิดพลาดที่คาด |
| - | -------- | ------- | -------------- |
| RCV-VAL-01 | ไม่มี vendor ตอน commit (`GRN_VAL_001`) | GRN ที่ `doc_status = saved` โดย `vendor_id IS NULL` (ปล่อยว่างระหว่างการรวมหลาย PO ที่ไม่ resolve vendor); Inventory Manager คลิก **Commit** | **Reject** — `GRN_VAL_001` Server return `"Vendor is required and must be from the approved vendor list."` Map ไปยัง TC-GRN-030003 และ TC-GRN-050003 |
| RCV-VAL-02 | ไม่มี PO reference เมื่อ `doc_type = purchase_order` (`GRN_VAL_004`) | GRN สร้างผ่านเส้นทาง PO-anchored ดังนั้น `doc_type = purchase_order`; ผู้ใช้ล้าง `purchase_order_detail_id` ของบรรทัดด้วยมือระหว่างแก้ไข; พยายาม save บรรทัด | **Reject ตอน save** — `GRN_VAL_004` clause แรก Server return `"PO reference is required for PO-sourced GRNs and must be absent for manual GRNs."` Map ไปยัง TC-GRN-030004 |
| RCV-VAL-03 | `received_qty = 0` และ `foc_qty = 0` บนบรรทัด (`GRN_VAL_007`) | Receiver เพิ่มบรรทัด ปล่อยทั้ง `received_qty` และ `foc_qty` เป็นศูนย์ คลิก **Save** | **Reject ตอน save** — `GRN_VAL_007` Server return `"Each line must record either a received quantity or a free-of-charge quantity greater than zero."` Map ไปยัง TC-GRN-070002 |
| RCV-VAL-04 | ไม่มีข้อมูล lot สำหรับสินค้าที่ติดตาม lot / perishable ตอน save (`GRN_VAL_012`) | GRN ที่ `draft` มีสินค้า perishable ที่ติดตาม lot บนบรรทัด `L1`; Store Keeper พยายาม save โดยไม่กรอกข้อมูล lot | **Reject** Server return `"Lot information is required for inventory items; line <seq> is missing lot data."` Receiver ต้องกลับไปที่บรรทัด เปิด sub-form lot (RCV-HP-06) และกรอก `lot_no` (auto หรือ manual) และ `expiry_date` ก่อนลอง save ใหม่ **หมายเหตุ:** หน้านี้แก้ไข "ตอน commit" เป็น "ตอน save" ตามจังหวะ posting จริง; call site ที่บังคับใช้กฎนี้ยังไม่ได้ตรวจสอบซ้ำอย่างอิสระในรอบนี้ |
| RCV-VAL-05 | รับจาก PO ที่ `voided` (`GRN_VAL_013`) | PO `PO-V` ที่ `po_status = voided`; Receiver พยายาม save GRN ที่บรรทัดอ้างอิง PO นั้น | **Reject** Server return `"Cannot receive against PO <po_no>: PO status voided does not permit receiving."` block เท่ากันสำหรับ `closed`, `completed`, `draft`, และ `in_progress` |
| RCV-VAL-06 | หน่วยรับไม่ valid / conversion factor ≤ 0 (`GRN_VAL_008`) | Receiver กรอก `received_qty = 10` แต่ `received_unit_conversion_factor = 0`; พยายาม save | **Reject ตอน save** — `GRN_VAL_008` Server return `"Each receipt event must specify a valid receiving UoM with a positive conversion factor."` |
| RCV-VAL-07 | รับเกินโดยไม่เปิด tolerance (`GRN_VAL_009`) | บรรทัด PO `L1`: pending qty = 10; tolerance การรับเกินของ tenant ปิด (`0%`); Receiver กรอก `received_qty = 12` บนบรรทัดที่ anchor กับ PO | **Reject ตอน save** — `GRN_VAL_009` Server return `"Receipt quantity exceeds the pending quantity on PO line <po_no>:<seq>; over-receipt tolerance not enabled."` |
| RCV-VAL-08 | `(invoice_no, vendor_id)` ซ้ำข้าม GRN ที่ไม่ถูก soft-delete (`GRN_VAL_005`) | Receiver กรอก `invoice_no = INV-001` บน GRN ที่ `vendor_id` มี GRN ที่ไม่ voided ซึ่ง `invoice_no` เดียวกันอยู่แล้ว | **Reject ตอน commit** — `GRN_VAL_005` Server return `"An invoice with this number has already been received from this vendor."` |

## 4. Edge Case
