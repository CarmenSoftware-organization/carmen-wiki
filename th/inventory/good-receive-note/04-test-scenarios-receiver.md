# ใบรับสินค้า (Goods Receive Note) — Test Scenarios — Receiver

> **At a Glance**
> **Persona:** Receiver (Store Keeper / Receiving Clerk + Inventory Manager) &nbsp;·&nbsp; **โมดูล:** [good-receive-note](/th/inventory/good-receive-note) &nbsp;·&nbsp; **จำนวน scenario:** ~24
> **หมวด:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **ความครอบคลุม E2E:** map ไปยัง `501-grn.spec.ts` ใน `../carmen-inventory-frontend-e2e/`
> **ตรวจสอบซ้ำ 2026-09-22:** จังหวะการเปลี่ยนแปลงระบบถูกแก้ไขอีกครั้ง — **commit** (`saved → committed`) โพสต์ inventory และเลื่อน PO; บน **business unit แบบ average** save โพสต์ inventory ไว้แล้ว (PO ยังเลื่อนตอน commit); void/reject ถอนการเคลื่อนไหวล่วงหน้านั้นออก rule ID ด้านล่างเดินตาม [02-business-rules.md](./02-business-rules.md) §2 ที่เขียนใหม่ (`GRN_VAL_002`, `006`–`014`)

> **ความครอบคลุมที่รันได้:** spec `../carmen-inventory-frontend-e2e/tests/501-grn.spec.ts` (76 case; 57 case ไม่มี assertion ตาม `docs/test-cases/SPEC-HEALTH.md`); gap report `docs/test-cases/gaps/501-grn-core-gap.md` (62 case ที่มี oracle ที่ fail ได้) และ `docs/test-cases/gaps/501-grn-from-po-gap.md` (24 case ของ wizard) ไม่มีหน้า catalog `501-grn-core.md` scenario ด้านล่างไม่ได้ mirror ไว้ที่นั่น

หน้านี้จับ test scenario ที่ persona Receiver (**Store Keeper / Receiving Clerk** ที่ dock บวก **Store Manager / Inventory Manager** ที่ commit) ขับโดยตรงในโมดูล `good-receive-note` การมีส่วนร่วมของ Receiver เริ่มเมื่อ PO มาถึงที่ `po_status ∈ {approved, sent_or_print, partial}` (หรือสำหรับ `doc_type = manual` เมื่อเกิดการรับแบบ ad-hoc) และจบเมื่อ GRN ออกจากโซนของ receiver — ผ่าน `committed` (โพสต์และล็อกแล้ว), `voided` จาก `draft` / `saved` หรือ variance ที่ถูกทำเครื่องหมายส่งต่อไปยัง Purchaser scenario จัดกลุ่มเป็น **happy path** (การเดินสถานะ `draft → saved → committed` บน BU แบบ FIFO และ average, GRN แบบ manual, GRN บางส่วน, การบันทึก expiry, การรับของขาด, void พร้อมถอนการเคลื่อนไหว), **RBAC** (permission key), **validation** (negative test เทียบ checklist จริงของ save / commit / void) และ **edge case** (boundary ของ deviation, ความแม่นยำทศนิยม, commit พร้อมกัน, การรวมหลาย PO)

## 2. Permission / Authorization

| # | Scenario | พฤติกรรมที่คาด (allow/deny + เหตุผล) |
| - | -------- | --------------------------------------- |
| RCV-PERM-01 | ผู้ใช้ที่มี `procurement.goods_received_note.create` + `.update` สร้าง GRN และ save draft | **Allow** `POST …/good-received-notes` (guard `goodReceivedNote.create`) และ `PATCH …/:id` (`goodReceivedNote.update`); Save-draft เก็บเอกสารที่ไม่ครบได้ Maps to TC-GRN-030001 / TC-GRN-070001 |
| RCV-PERM-02 | ผู้ใช้ที่มี `procurement.goods_received_note.commit` save (`draft → saved`) และ commit (`saved → committed`) | **Allow** ทั้ง `PATCH …/save` และ `PATCH …/commit` อยู่หลัง gateway guard **เดียวกัน** `goodReceivedNote.commit` (`good-received-notes.controller.ts:1369,1626`) |
| RCV-PERM-03 | ผู้ใช้ที่**ไม่มี** สิทธิ์ commit พยายาม save หรือ commit | **Deny — 403 จาก `AppIdGuard('goodReceivedNote.commit')`**; ปุ่ม **Save** และ **Commit** ถูกซ่อนโดยการตรวจสิทธิ์ของ frontend ไม่มีข้อความ "Inventory Manager role" — การปฏิเสธเป็นการปฏิเสธด้วย permission key **แก้ไข 2026-09-22:** เพราะ save และ commit ใช้ key เดียวกัน ผู้ใช้ที่ save ได้จึง commit ได้ด้วย; การแยก "Store Keeper save ได้แต่ commit ไม่ได้" ตั้งค่าไม่ได้ในวันนี้ Maps to TC-GRN-110002 |
| RCV-PERM-04 | ผู้ใช้ใดพยายามแก้ GRN ที่ `committed` | **Deny** endpoint detail คืน `GRN_NON_DRAFT_NO_*_DETAIL`; UI ซ่อน affordance แก้ไขทั้งหมด (`canEdit` false); comment และไฟล์แนบยังทำได้ Maps to TC-GRN-080005 และ TC-GRN-090003 |
| RCV-PERM-05 | Segregation of duties — Receiver (ผู้โพสต์ GRN) เทียบ Purchaser (ผู้ซื้อ PO) | **ยังไม่ implement** (ตรวจซ้ำ 2026-09-22): ไม่มีการตรวจ `buyer_id` ไขว้ใน `good-received-note.service.ts` / `.logic.ts` |
| RCV-PERM-06 | Void GRN ที่ `draft` หรือ `saved`; พยายาม void ที่ `committed` | **Allow** สำหรับ `draft` / `saved` ด้วย `procurement.goods_received_note.delete` (`DELETE …/void`, guard `goodReceivedNote.delete`) **Deny** สำหรับ `committed`: server คืน `GRN_COMMITTED_NOT_VOIDABLE` (400) และ UI ซ่อน Void / Commit เมื่อ committed แล้ว (`grn-footer-action.tsx:27`) **แก้ไข 2026-09-22:** guard ตอนนี้อยู่ฝั่ง server (รอบ 2026-07-15 พบเพียง guard ฝั่ง UI) |
| RCV-PERM-07 | client มือถือ list GRN | request ที่ `x-app-id` resolve เป็น app `mobile` ได้ตัวกรอง `doc_status = draft` แบบบังคับ (`applyMobileGrnDocStatusFilter`); สถานะอื่นไม่ถูกคืนแม้จะร้องขอ client desktop เห็นทุกสถานะ |

## 3. Validation / Error

| - | -------- | ------- | -------------- |
| RCV-VAL-01 | reference ที่ resolve ไม่ได้ตอน create (`GRN_VAL_001` / `GRN_VAL_003`) | `POST …/good-received-notes` ด้วย `vendor_id`, `purchase_order_detail_id` หรือ unit id ที่ไม่มีอยู่ | **Reject 404** พร้อมข้อความ reference ที่ resolve ไม่ได้ ("Purchase order detail not found: …"); `POST …/verify` `{verify_state: "create", body}` แสดง `GRN_REFERENCE_NOT_FOUND` ต่อ id (และ `GRN_UNIT_NOT_ALLOWED_FOR_PRODUCT` เมื่อหน่วยไม่ใช่ order unit ของสินค้า) Maps to TC-GRN-030003 / 030004 / 050003 |

| RCV-VAL-07b | ราคาเกินเพดานราคาของสินค้า (`GRN_VAL_007`) | สินค้า `price_deviation_limit = 10`; `order_price = ฿100` ต่อหน่วยฐาน; `received_price = ฿115` | **Reject ตอน save** — `GRN_DEVIATION_LIMIT_EXCEEDED`, `kind = price`, `field = received_price` `received_price = ฿90` (ถูกกว่า) ถูกยอมรับ; GRN แบบ manual (ไม่มี `order_price`) ไม่ถูกตรวจเลย |
| RCV-VAL-07c | ส่วนลดหรือภาษีมากกว่าบรรทัด (`GRN_VAL_008`) | บรรทัด `received_price × received_qty = ฿1,000`, `discount_amount = ฿1,200` | **Reject ตอน save** — `GRN_DISCOUNT_EXCEEDS_LINE_AMOUNT` (หรือ `GRN_TAX_EXCEEDS_LINE_AMOUNT`) แสดง `<product> (line n)` |
| RCV-VAL-08 | Void / reject หลังสต๊อกจากการรับถูกเบิกแล้ว (`GRN_VAL_013`) | BU แบบ average; GRN ที่ `saved` ที่การเคลื่อนไหวโพสต์ตอน save; store requisition ใช้ไป 3 จาก 10 หน่วยที่รับ | **Reject 409** — `GRN_RECEIPT_ALREADY_CONSUMED` ("This receipt cannot be revised — stock received on it has already been issued"); เอกสารคงเป็น `saved`; PATCH header ที่จะเปลี่ยนปริมาณถูกปฏิเสธแบบเดียวกัน (`repostGrnLedgerIfChanged`) |
| RCV-VAL-09 | `(invoice_no, vendor_id)` ซ้ำ | GRN สองใบของ vendor เดียวกันที่มี `invoice_no` เดียวกัน | **ยอมรับ** ไม่มีกฎ uniqueness ใน schema หรือโค้ด (ตรวจซ้ำ 2026-09-22; unique index เดียวคือ `(grn_no, deleted_at)`) ควรทดสอบเพราะ PRD อ้างตรงกันข้าม |

## 4. Edge Case

| # | Scenario | เงื่อนไข | ผลที่คาด |
| - | -------- | --------- | -------- |
| RCV-EDGE-01 | Boundary พอดีของเพดาน deviation ปริมาณ | สินค้า `qty_deviation_limit = 5`; บรรทัด PO `order_base_qty = 10`; Receiver กรอก `received_qty = 10.5` (เกิน 5 % พอดี) | **ยอมรับ** — `deviation (5.00000) ≤ limit (5)`; `received_qty = 10.501` ถูกปฏิเสธตาม RCV-VAL-07 การเปรียบเทียบเกิดที่ 5 ตำแหน่ง (`DEVIATION_SCALE = 100000`) จึงไม่มี float noise มาทำให้พลาด ตอน commit `tb_purchase_order_detail.received_qty = 10.5 ≥ 10 − 0` → `po_status = completed` |
| RCV-EDGE-02 | ความแม่นยำทศนิยมและการปัดเศษตลอดสาย | `received_qty = 5.123`, `received_price = ฿33.333`, conversion factor `1.234567`, extra cost ฿7 `by_qty` บนบรรทัดเดียว | `sub_total_price = 170.65946` (5 ตำแหน่ง, `calcGrnItemPrices`); `received_base_qty = 5.123 × 1.234567`; ledger `cost_per_unit = Round2((base_net + 7) / stock_qty)`; cost layer กระทบยอดเป็น `total_cost` ที่แม่นยำ (`splitFifoCost(…, 2)`); `extra_cost_amount` บน layer รวมกันเป็น ฿7 |
| RCV-EDGE-03 | commit พร้อมกันบนบรรทัด PO เดียวกันจากสอง session | GRN-A (`received_qty = 6`) และ GRN-B (`received_qty = 4`) ต่าง `saved` กับ `PO-X` บรรทัด `L1` (`order_qty = 10`); ผู้ใช้ทั้งสองคลิก **Commit** ภายในวินาทีเดียวกัน | commit ทั้งสองสำเร็จ: `updatePurchaseOrderReceiving` row-lock junction row (`lockJunctionRows`) และเพิ่มค่าแบบ atomic ดังนั้น `received_qty` จบที่ 10 พอดีและ `po_status = completed`; ไม่นับซ้ำ การ commit GRN เดิมซ้ำเป็น idempotent (`postReceipt` เห็น `inventory_transaction_id` และ `po_receiving_applied`) การ commit ด้วย `doc_version` เก่าใน body คืน `409` |
| RCV-EDGE-04 | การรวมหลาย PO เข้า GRN เดียวด้วยผู้ขาย / สกุลเงินเดียวกัน | ผู้ขายเดียวกัน สกุลเงินเดียวกันข้าม `PO-A` (หนึ่งบรรทัด pending 4) และ `PO-B` (สองบรรทัด pending 6 แต่ละบรรทัด); ผู้ขายส่งรถคันเดียวครอบคลุมทั้งสอง PO | **GRN เดียวสามบรรทัด span สอง PO** wizard ขั้น 2 เลือกทั้งสอง PO (การเลือกที่มีสกุลเงินต่างกันถูกปฏิเสธด้วย toast `mixedCurrencyError`, `from-po-content.tsx:93-95`); header สืบทอด vendor, สกุลเงิน และอัตราแลกเปลี่ยนที่ใช้ร่วม; detail สามแถวแต่ละแถวบรรจุ `purchase_order_detail_id` ของตน **Commit** เลื่อน `received_qty` บน `tb_purchase_order_detail` สามแถวในธุรกรรมเดียว; `PO-A` → `completed`, `PO-B` → `completed` หรือ `partial` Maps to TC-GRN-040002 / 040004 (stub) และ gap case `TC-GRN-040005`–`040028` |
| RCV-EDGE-05 | บรรทัด FOC ล้วน เทียบ เอกสาร FOC ล้วน | (a) GRN ที่มีบรรทัดจ่ายเงินหนึ่งบรรทัดและอีกบรรทัด `received_qty = 0, foc_qty = 5`; (b) GRN ที่บรรทัดเดียวคือ `received_qty = 0, foc_qty = 5` | (a) ทั้งสองบรรทัดโพสต์ — แถว ledger ของบรรทัด FOC มี `qty = 5`, `cost_per_unit = 0` (บวกส่วนแบ่ง extra cost ถ้ามี) และตัวนับ FOC ที่รับของ junction PO เพิ่ม 5 (b) `createFromGoodReceivedNote` ตัดทุกรายการที่ `received_base_qty = 0` ออกก่อนโพสต์ (`inventory-transaction.service.ts:849`) → **ไม่มีการเขียนการเคลื่อนไหว** และไม่มีการตั้ง `inventory_transaction_id` แต่เอกสารยังไปถึง `committed` และตัวนับ FOC ของ PO ยังเพิ่ม ให้บันทึกความไม่สอดคล้องนี้ใน bug tracker แทนที่จะเป็น expectation ของ test |
| RCV-EDGE-06 | แก้ GRN ที่ `saved` ของ BU แบบ average ผ่าน API | BU แบบ average; GRN ที่ `saved` และการเคลื่อนไหวโพสต์ตอน save; `PATCH …/:id` เปลี่ยน `received_qty` ของบรรทัดจาก 10 เป็น 12 (server ยอมรับ — ไม่มี guard สถานะบน PATCH แบบครอบคลุม) | `repostGrnLedgerIfChanged`: การเคลื่อนไหวเก่าถูก soft-delete โพสต์อันใหม่ (`posted_at_save = true` PO ยังไม่ถูกแตะ) average ของสินค้าถูกประทับใหม่ หาก lot เก่าถูกใช้ไปแล้ว → 409 และ PATCH ถูก rollback |
