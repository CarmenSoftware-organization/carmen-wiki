## 1. ภาพรวม

หน้านี้จับกฎทางธุรกิจในการใช้งานที่ครอบคลุมเอกสาร Goods Receive Note (GRN) ตลอดวงจรชีวิต: input validation ตอน create / edit / save / commit, การคำนวณตัวเงิน (บรรทัดและ header รวม tag โหมดการกระจาย extra-cost), ประตู authorization ตามบทบาทและสถานะเอกสาร, ผลของ posting ในการเปลี่ยนแต่ละครั้งของ `enum_good_received_note_status`, และกฎข้ามโมดูลกับ [purchase-order](/th/inventory/purchase-order), [inventory](/th/inventory/inventory), [vendor-pricelist](/th/inventory/vendor-pricelist) และ [costing](/th/inventory/costing)

> ⚠️ **ตรวจสอบซ้ำ 2026-09-22 — เหตุการณ์โพสต์กลับมาเป็น `saved → committed` อีกครั้ง พร้อมข้อยกเว้นหนึ่งข้อ** รอบ 2026-07-15 เอกสาร `save()` เป็นเหตุการณ์โพสต์; ระหว่าง 2026-08 ถึง 2026-09 backend ย้ายการโพสต์ไปที่ **`commit()`** (`c815d67ce`) แล้วทำให้ **business unit แบบ average โพสต์การเคลื่อนไหวสต๊อกตอน `save()`** โดยยังปล่อย PO ไว้ให้ commit (`7d6556dd0`) โค้ดปัจจุบัน: `GoodReceivedNoteLogic.save()` (`good-received-note.logic.ts:78-147`) ตรวจสอบ ออกเลข `grn_no` จริง และ — เฉพาะเมื่อ `postsInventoryAtSave(method)` (`good-received-note.ledger.ts:49-51`) — เขียน ledger พร้อม `posted_at_save = true`; `commit()` (`:165-203`) และ `approve()` (`:289-320`) ต่างรัน `postReceipt()` (`:228-270`) ซึ่งเขียน ledger ถ้ายังไม่ได้เขียนและเลื่อน PO ส่วน 5 เขียนใหม่ตามนี้; rule ID คงเดิม
>
> ⚠️ **Three-way match / การโพสต์ AP — ยังไม่ implement; โมดูล GL มีอยู่แต่ไม่ได้เชื่อมกับ GRN** ไม่มี vendor-invoice entity หน้าจอบันทึก หรือ match algorithm (ตรวจซ้ำ 2026-09-22) ตอนนี้มีโมดูล GL แล้ว (`apps/micro-business/src/gl/`) แต่ไม่มีอะไรนอก `src/gl/` เรียกมัน — `GlPostingService.post()` (`gl-posting.service.ts:293`) โพสต์เฉพาะ journal voucher ที่สร้างโดยเส้นทาง JV/template/reversal/closing และ `enum_gl_jv_source.inventory` / `.ap` ไม่มีผู้เขียน `GRN_POST_006`–`GRN_POST_009` และ `GRN_XMOD_007` ยังคงเป็น "ยังไม่ implement"

มีสองประเด็นเชิงโครงสร้างที่ทาบทับทุกกฎด้านล่าง **อันแรก** หมายเลข lot และ cost layer อยู่บน inventory ledger ซึ่งตั้งแต่ 2026-08-10 ชี้ **กลับ** มายังเหตุการณ์รับ (`tb_inventory_transaction_detail.good_received_note_detail_item_id`); วันหมดอายุตอนนี้อยู่บนเหตุการณ์ GRN (`tb_good_received_note_detail_item.expired_at`) ไม่มีการกรอกหมายเลข lot บน GRN เลย — lot ถูกสร้างตอนโพสต์เป็น `<location_code><YYMM><ลำดับ 4 หลัก>` (`common/helpers/lot-number.helper.ts:27-35`) **อันที่สอง** การจัดสรร extra cost **ใช้งานจริงแล้ว** (`f8cd9f0d9`, 2026-09-10): `allocateExtraCost()` (`good-received-note.extra-cost.ts:40-61`) แบ่งยอดรวม extra cost ไปยังบรรทัดที่นำสต๊อกเข้าคลัง — `by_qty` = ส่วนเท่ากันต่อบรรทัด, `by_value` = ถ่วงตามปริมาณสต๊อกของแต่ละบรรทัด, `manual` = ไม่จัดสรร — และส่วนแบ่งเข้าสู่ landed cost ของบรรทัดและ `extra_cost_amount` ของ cost layer แต่ละชั้น enum ของ Prisma ยังมีเพียงสามโหมดนั้น; `by_weight` / `by_volume` ไม่มีอยู่ ตัวอย่างในส่วน 3.1 ตอนนี้แสดงสิ่งที่โค้ดทำ รวมถึงชื่อโหมดที่สวนทางกับความรู้สึก

## 2. กฎ Validation

## 3. กฎการคำนวณ

ค่าเงินทั้งหมดเก็บเป็น `Decimal(20, 5)` ที่ระดับแถว; **อัตรา** ภาษีและส่วนลดเก็บเป็น `Decimal(15, 5)`; อัตราแลกเปลี่ยนเป็น `Decimal(15, 5)` บน header GRN **เขียนใหม่ 2026-09-22 จากโค้ด** server derive ทุกฟิลด์เงินของเหตุการณ์รับจาก `received_price` ใน `calcGrnItemPrices()` (`good-received-note.pricing.ts:40-60` ปัดเป็น **5 ตำแหน่ง**) และไม่เคยเชื่อถือ `sub_total_price` / `net_amount` / `total_price` / `base_*` ที่ client ส่งมา `discount_amount` และ `tax_amount` ถูกรับ **เป็นจำนวนเงินจาก request** — backend ไม่คำนวณใหม่จาก `discount_rate` / `tax_rate` (อัตราถูกเก็บเป็น snapshot; frontend ทำให้จำนวนและอัตราสอดคล้องกันใน `grn-item-cells/computed-sync.tsx`) landed cost สำหรับ ledger คำนวณในสกุลฐานตอนโพสต์ (`stockQtyOf` / `stockCostOf`, `inventory-transaction.service.ts:73-92`) และต้นทุนต่อหน่วยที่เขียนลง ledger ปัดเป็น **2 ตำแหน่ง** (`Math.round(x × 100) / 100`, `:941,1134`)

| `GRN_CALC_013` (landed cost — feed costing) | ต่อเหตุการณ์รับ: `stock_qty = received_base_qty + foc_base_qty`; `stock_cost = base_net_amount + calcBase(share, exchange_rate)`; `cost_per_unit = Round2(stock_cost / stock_qty)`; `tb_inventory_transaction_detail.{qty, cost_per_unit, total_cost} = {stock_qty, cost_per_unit, stock_cost}` จากนั้น cost layer ถูกสร้างโดย `splitFifoCost(stock_qty, stock_cost, 2)` (กระทบยอดทศนิยมแบบแม่นยำข้ามแถว layer หนึ่งแถวขึ้นไป) และส่วนแบ่ง extra cost ถูกแบ่งข้าม layer เดียวกันตามปริมาณลง `extra_cost_amount` (`inventory-transaction.service.ts:965-1002`) เหตุการณ์ที่ `received_base_qty = 0` ถูกตัดออกก่อนโพสต์ (`:849`) |

### 3.1 ตัวอย่างคำนวณ (สกุลธุรกรรม ฿ THB)

สองบรรทัด vendor ใน THB, `exchange_rate = 1.00000` (ไม่มี FX), สินค้าทั้งสองอยู่ในหน่วยฐานที่ conversion factor เท่ากับ 1, หนึ่งบรรทัด extra-cost จัดสรร `by_value`

- **บรรทัด 1** (หนึ่งเหตุการณ์รับ): `received_qty = 10.000`, `received_price = ฿125.50`, client ส่ง `discount_amount = ฿62.75` (5%), `tax_amount = ฿83.46` (7% ของ net)
  - `sub_total_price = 125.50 × 10.000 = ฿1,255.00`
  - `net_amount = 1,255.00 − 62.75 = ฿1,192.25`
  - `total_price = 1,192.25 + 83.46 = ฿1,275.71`
- **บรรทัด 2** (หนึ่งเหตุการณ์รับ): `received_qty = 4.000`, `received_price = ฿89.00`, `discount_amount = ฿0.00`, `tax_amount = ฿24.92`
  - `sub_total_price = ฿356.00`; `net_amount = ฿356.00`; `total_price = ฿380.92`
- **Extra cost** (`Σ tb_extra_cost_detail.amount = ฿200.00`, `allocate_extra_cost_type = by_value` → ถ่วงตามปริมาณสต๊อก 10 : 4):
  - ส่วนแบ่งบรรทัด 1: `200.00 × 10 / 14 = ฿142.85714`
  - ส่วนแบ่งบรรทัด 2: `200.00 × 4 / 14 = ฿57.14286` (`splitByWeight` กระทบยอดให้ส่วนแบ่งรวมกันเท่ากับ ฿200.00 พอดี)
  - หากโหมดเป็น `by_qty` แต่ละบรรทัดจะได้ `฿100.00` โดยไม่สนปริมาณ; หากเป็น `manual` ไม่มีบรรทัดใดได้เลย
- **Header roll-up**: `net_amount = ฿1,548.25`; `total_amount = ฿1,656.63` (ไม่รวม extra cost)
- **Ledger feed** (บรรทัด 1, `foc_qty = 0`): `stock_cost = 1,192.25 + 142.85714 = ฿1,335.10714`; `cost_per_unit = Round2(1,335.10714 / 10) = ฿133.51`; cost layer: `in_qty = 10`, `total_cost ≈ ฿1,335.11`, `extra_cost_amount ≈ ฿142.86`

ถ้าบรรทัด 1 มี `foc_qty = 1.000` บนเหตุการณ์เดียวกันด้วย `stock_qty = 11` และ `cost_per_unit = Round2(1,335.10714 / 11) = ฿121.37` — หน่วย FOC เข้าสต๊อกที่ landed cost ที่ถูกเจือจาง และ (เพราะน้ำหนักคือปริมาณสต๊อก) ส่วนแบ่ง extra cost ของบรรทัด 1 เพิ่มเป็น `200 × 11/15 = ฿146.67`

State diagram (Prisma-canonical):

```
[*] → draft ──save──► saved ──commit / approve──► committed
        │  (AVG: ledger)        (ledger ถ้ายังไม่มี + เลื่อน PO)
        ├──void/reject──► voided
        └──delete (soft)
                saved ──void/reject──► voided   (AVG: ถอน ledger ออก เว้นแต่ lot ถูกใช้แล้ว → 409)
```

`committed` และ `voided` เป็น terminal; `committed` void ไม่ได้ (`GRN_COMMITTED_NOT_VOIDABLE`) `draft` ยอมรับ soft-delete

### 5.1 วงจรชีวิตสถานะ — การแมพ Live UI กับ BRD

Prisma enum `enum_good_received_note_status` ที่เอกสารไว้ข้างต้นคือสิ่งที่ live UI ใช้ ไม่มี BRD `FR-XXX` identifier ทางการที่กำหนดสำหรับ specification สถานะ GRN ในเอกสาร source ที่มีอยู่ — reference ที่ใกล้ที่สุดคือ model 3 สถานะของ `grn-master-prd.md` และ enum 5 สถานะของ `GRN-Technical-Specification.md` ทั้งสองแตกต่างจาก Prisma (ดู [good-receive-note/01-data-model](/th/inventory/good-receive-note/01-data-model) § 5 รายการ 1) ตารางด้านล่างแมพทุกสถานะ live-UI ที่สังเกตได้กับ PRD / Technical Spec equivalent เพื่อให้ tester และ developer reconcile ทั้งสองโดยไม่กำกวม Source: `Test_case/System_Process/tx-01-grn.md` (วันที่จับ 2026-04-27)

| Live UI status | PRD / Technical Spec equivalent | ต่าง | หมายเหตุ |
|---|---|---|---|
| `draft` | _(ไม่อยู่ใน tx-01-grn.md)_ | 🔴 ใหม่ใน live UI | PRD บรรยาย `Received → Committed`; ไม่มีสถานะ Draft ปรากฏ Prisma default คือ `draft` แก้ไขได้ (เก็บแบบไม่ครบได้); เลข placeholder `draft-{seq}`; ไม่มีผลกระทบสต๊อกหรือ PO |
| `saved` | `Received` (model 3 สถานะของ grn-master-prd.md) | 🟡 เปลี่ยนชื่อ | PRD ติด label สถานะนี้เป็น `Received` Live UI เรียกว่า `saved` (ผ่านการตรวจสอบ มีเลขแล้ว read-only บน UI) **บน BU แบบ average การเคลื่อนไหวสต๊อกถูกโพสต์แล้วที่สถานะนี้**; บน BU แบบ FIFO ยังไม่ PO ยังไม่ถูกเลื่อนในทั้งสองกรณี |
| `committed` | `Committed` | ✅ ตรง | สถานะล็อก terminal และ **เหตุการณ์โพสต์** (`GRN_POST_003`–`GRN_POST_005`): ledger ถูกเขียน (ถ้ายังไม่ได้เขียนตอน save) และ PO ถูกเลื่อน ไม่มี GL accrual — โมดูล GL มีอยู่แต่ไม่ถูกเรียก void ไม่ได้ |
| `voided` | _(ไม่อยู่ใน tx-01-grn.md)_ | 🔴 ใหม่ใน live UI | การยกเลิกบริหารก่อน commit ไม่ปรากฏใน status flow string ของ `Test_case/System_Process/tx-01-grn.md` |
