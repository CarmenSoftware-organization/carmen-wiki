## 1. ภาพรวม

หน้านี้จับกฎทางธุรกิจในการใช้งานที่ครอบคลุมเอกสาร Goods Receive Note (GRN) ตลอดวงจรชีวิต: input validation ตอน create / edit / save / commit, การคำนวณตัวเงิน (บรรทัดและ header รวม tag โหมดการกระจาย extra-cost), ประตู authorization ตามบทบาทและสถานะเอกสาร, ผลของ posting ในการเปลี่ยนแต่ละครั้งของ `enum_good_received_note_status`, และกฎข้ามโมดูลกับ [purchase-order](/th/inventory/purchase-order), [inventory](/th/inventory/inventory), [vendor-pricelist](/th/inventory/vendor-pricelist) และ [costing](/th/inventory/costing)

> ⚠️ **ตรวจสอบซ้ำ 2026-10-27 — เหตุการณ์โพสต์ยังคงเป็น `saved → committed` พร้อมข้อยกเว้นของ BU แบบ average; สิ่งที่เปลี่ยนคือวิธีที่ GRN สถานะ `saved` หรือ `committed` แก้ไขได้** โค้ดปัจจุบัน: `GoodReceivedNoteLogic.save()` (`good-received-note.logic.ts:77-152`) ตรวจสอบ ออกเลข `grn_no` จริง และ — เฉพาะเมื่อ `postsInventoryAtSave(method)` (`good-received-note.ledger.ts:55-57`, จริงสำหรับ `average` **และ** `average_per_location`) — เขียน ledger พร้อม `posted_at_save = true`; `commit()` (`:170-215`) และ `approve()` (`:313-349`) ต่างรัน `postReceipt()` (`:240-294`) ซึ่งเขียน ledger ถ้ายังไม่ได้เขียนและเลื่อน PO ใหม่ตั้งแต่ 2026-09-22: GRN สถานะ `saved` **แก้ไขได้** (ผู้ขายและ `grn_date` ตายตัว บรรทัดที่ถูกอ้างอิงถูกล็อก — `GRN_VAL_021`–`GRN_VAL_023`), GRN ที่ `committed` รับเฉพาะการแก้ฟิลด์ส่วนหัวของใบกำกับผู้ขายจนกว่า AP invoice จะดึงไป (`GRN_VAL_024`), ใบรับ FIFO ต้องไม่ลงวันที่ย้อนก่อนใบรับล่าสุดของสินค้าและ location เดียวกัน (`GRN_VAL_020`) และบรรทัด FOC ล้วนโพสต์แล้ว (`GRN_VAL_019`) ส่วน 5 เขียนใหม่ตามนี้; rule ID คงเดิม
>
> ⚠️ **Three-way match / การโพสต์ AP — ตอนนี้มีอยู่นอกโมดูลนี้; GRN ยังไม่โพสต์ journal** เอกสาร **AP Invoice** (backend `apps/micro-business/src/ap/ap-invoice`; หน้าจอ AP ของ frontend เป็น mock ในเบราว์เซอร์ ดู [AP Invoice from GRN](/th/inventory/general-ledger/ap-invoice-from-grn)) มีแถว `tb_ap_invoice_detail_source` ที่จับคู่ detail item ของ GRN ด้วย `matched_qty` พร้อม `grn_unit_price`, `matched_amount` และ `variance_amount`; GRN ต้นทางต้องยังใช้งานอยู่, `committed` และ `post_type = ap` และปริมาณที่จับคู่รวมข้ามเอกสาร AP ที่ไม่ void ต้องไม่เกิน `received_qty` ของรายการ (`AP_GRN_NOT_COMMITTED`, `AP_GRN_OVER_MATCHED`, `ap-invoice.posting.ts:152-230,1100-1130`) การโพสต์ AP เขียน GL journal ด้วย `source = ap` (`ap-invoice.posting.ts:291`) ไม่มีอะไรใน `good-received-note.*.ts`, `inventory-transaction.service.ts` หรือ `period-end.*` เรียกโมดูล GL และ `enum_gl_jv_source.inventory` ไม่มีผู้เขียน แถว "ยังไม่ implement" เดิม `GRN_POST_006`–`GRN_POST_009` และ `GRN_XMOD_007` จึงถูกเขียนใหม่ด้านล่างเป็น *อยู่นอกโมดูลนี้*

มีสองประเด็นเชิงโครงสร้างที่ทาบทับทุกกฎด้านล่าง **อันแรก** หมายเลข lot และ cost layer อยู่บน inventory ledger ซึ่งตั้งแต่ 2026-08-10 ชี้ **กลับ** มายังเหตุการณ์รับ (`tb_inventory_transaction_detail.good_received_note_detail_item_id`); วันหมดอายุตอนนี้อยู่บนเหตุการณ์ GRN (`tb_good_received_note_detail_item.expired_at`) ไม่มีการกรอกหมายเลข lot บน GRN เลย — lot ถูกสร้างตอนโพสต์เป็น `<location_code><YYMM><ลำดับ 4 หลัก>` (`common/helpers/lot-number.helper.ts:27-35`) **อันที่สอง** การจัดสรร extra cost **ใช้งานจริงแล้ว** (`f8cd9f0d9`, 2026-09-10): `allocateExtraCost()` (`good-received-note.extra-cost.ts:40-61`) แบ่งยอดรวม extra cost ไปยังบรรทัดที่นำสต๊อกเข้าคลัง — `by_qty` = ส่วนเท่ากันต่อบรรทัด, `by_value` = ถ่วงตามปริมาณสต๊อกของแต่ละบรรทัด, `manual` = ไม่จัดสรร — และส่วนแบ่งเข้าสู่ landed cost ของบรรทัดและ `extra_cost_amount` ของ cost layer แต่ละชั้น enum ของ Prisma ยังมีเพียงสามโหมดนั้น; `by_weight` / `by_volume` ไม่มีอยู่ ตัวอย่างในส่วน 3.1 ตอนนี้แสดงสิ่งที่โค้ดทำ รวมถึงชื่อโหมดที่สวนทางกับความรู้สึก

## 2. กฎ Validation

Rule ID เป็น `GRN_VAL_NNN` **เขียนใหม่ 2026-09-22 จากโค้ด** ไม่ใช่จาก PRD: กฎด้านล่างคือสิ่งที่ `create()` / `update()` (`good-received-note.service.ts`), `POST …/verify` (`verify/good-received-note.verify-create.ts`, `good-received-note.validate.ts`), `save()`, `commit()`, `approve()`, `reject()` และ `voidGrnById()` บังคับใช้จริง ทุกการตรวจสอบเรียกได้โดยไม่มีผลข้างเคียงผ่าน `POST /api/:bu_code/good-received-notes/verify` ด้วย `verify_state ∈ {create, save, commit}` (`logic.ts:369`); ฟังก์ชันเดียวกันรันอีกครั้งเมื่อเรียก transition จริง แถวที่มีในเวอร์ชันก่อนแต่ **ไม่มีโค้ด** รองรับถูกขีดฆ่าและอธิบายไว้แทนการลบ เพื่อให้ cross-reference ยัง resolve ได้

## 3. กฎการคำนวณ

ค่าเงินทั้งหมดเก็บเป็น `Decimal(20, 5)` ที่ระดับแถว; **อัตรา** ภาษีและส่วนลดเก็บเป็น `Decimal(15, 5)`; อัตราแลกเปลี่ยนเป็น `Decimal(15, 5)` บน header GRN **เขียนใหม่ 2026-09-22 จากโค้ด** server derive ทุกฟิลด์เงินของเหตุการณ์รับจาก `received_price` ใน `calcGrnItemPrices()` (`good-received-note.pricing.ts:40-60` ปัดเป็น **5 ตำแหน่ง**) และไม่เคยเชื่อถือ `sub_total_price` / `net_amount` / `total_price` / `base_*` ที่ client ส่งมา `discount_amount` และ `tax_amount` ถูกรับ **เป็นจำนวนเงินจาก request** — backend ไม่คำนวณใหม่จาก `discount_rate` / `tax_rate` (อัตราถูกเก็บเป็น snapshot; frontend ทำให้จำนวนและอัตราสอดคล้องกันใน `grn-item-cells/computed-sync.tsx`) landed cost สำหรับ ledger คำนวณในสกุลฐานตอนโพสต์ (`stockQtyOf` / `stockCostOf`, `inventory-transaction.service.ts:92-111`) และต้นทุนต่อหน่วยที่เขียนลง ledger ปัดเป็น **2 ตำแหน่ง** (`Math.round(x × 100) / 100`, `:1054,1302`)

Rule ID เป็น `GRN_CALC_NNN`

| Rule ID | สูตร |
| ------- | ------- |
| `GRN_CALC_001` (line subtotal) | `sub_total_price = Round5(received_price × received_qty)` ในสกุลธุรกรรม FOC qty ไม่มีส่วนร่วมกับเงินเลย (`foc_qty` ไม่มีราคา) |
| `GRN_CALC_002` (line discount) | `discount_amount` คือจำนวนที่ client ส่งมา (ต้อง `≤ received_price × received_qty`, `GRN_VAL_008`); `discount_rate` / `is_discount_adjustment` ถูกเก็บแต่ไม่ถูกใช้โดยสายการคำนวณฝั่ง server |
| `GRN_CALC_003` (line net) | `net_amount = Round5(sub_total_price − discount_amount)` |
| `GRN_CALC_004` (line tax) | `tax_amount` คือจำนวนที่ client ส่งมา (ต้อง `≤ received_price × received_qty`); `tax_rate` / `is_tax_adjustment` เป็น snapshot **ไม่มี branch แบบ tax-inclusive ใน backend** — variant tax-inclusive ของ PRD ยังไม่ implement |
| `GRN_CALC_005` (line total) | `total_price = Round5(net_amount + tax_amount)` |
| `GRN_CALC_006` (variance) | deviation วัดเป็นเปอร์เซ็นต์ **ส่วนเกิน** เท่านั้น: `qty: (received_base_qty − order_base_qty) / order_base_qty × 100`; `price: (received_price/received_factor − order_price/order_factor) / (order_price/order_factor) × 100`; การขาดให้คะแนน `0` (`percentOverage`, `deviation.ts:62-63` เทียบที่ 5 ตำแหน่ง) ป้อน `GRN_VAL_006` / `GRN_VAL_007`; ไม่มีอะไรถูกเขียนกลับลงแถว |
| `GRN_CALC_007` (header roll-up) | `tb_good_received_note.net_amount / base_net_amount / total_amount / base_total_amount` ถูกคำนวณใหม่จากเหตุการณ์รับที่มีอยู่โดย `recalculateGrnTotals()` (`service.ts:3269`) หลังทุก create / update และบังคับได้ด้วย `POST …/good-received-notes/:id/regenerate-totals` (หรือ `…/regenerate-totals` สำหรับทั้งหมด) จำนวน extra cost **ไม่** อยู่ใน header totals |
| `GRN_CALC_008` (base conversion) | `base_price = calcBase(received_price, exchange_rate)`; `base_sub_total_price`, `base_net_amount`, `base_total_price` ในทำนองเดียวกันจากคู่สกุลธุรกรรมของมัน (`pricing.ts:55-58`); `base_discount_amount` / `base_tax_amount` จากจำนวนที่ client ส่ง |
| `GRN_CALC_009` (extra-cost total) | `extra_cost_total = Σ tb_extra_cost_detail.amount` เหนือ header extra cost ที่มีอยู่ของ GRN (สกุลเอกสาร **ไม่รวม** `tax_amount` ของ detail เอง) โดยใช้โหมดของ header ที่ **เก่าที่สุด** (`applyExtraCostShares`, `ledger.ts:100-133`) |
| `GRN_CALC_010` (extra-cost — `by_value`) | `share_i = splitByWeight(extra_cost_total, weights = stock_qty_i)` โดย `stock_qty_i = received_base_qty_i + foc_base_qty_i`; บรรทัดที่ `stock_qty = 0` ไม่ได้ส่วนแบ่ง (`allocateExtraCost`, `extra-cost.ts:49-58`) **แม้ชื่อจะเป็น `by_value` แต่ถ่วงตามปริมาณ ไม่ใช่มูลค่าบรรทัด** |
| `GRN_CALC_011` (extra-cost — `by_qty`) | `share_i = extra_cost_total / n` — ส่วนแบ่ง **เท่ากัน** หนึ่งส่วนต่อบรรทัดที่นำสต๊อกเข้าคลัง โดยไม่สนขนาด **แม้ชื่อจะเป็น `by_qty` แต่ไม่สนปริมาณ** |
| `GRN_CALC_012` (extra-cost — `manual`) | ไม่มีการจัดสรร (`allocation = ∅`); extra cost ถูกเก็บแต่ไม่ถึง ledger ยังไม่มีฟิลด์กรอกด้วยมือต่อบรรทัด |
| `GRN_CALC_013` (landed cost — feed costing) | ต่อเหตุการณ์รับ: `stock_qty = received_base_qty + foc_base_qty`; `stock_cost = base_net_amount + calcBase(share, exchange_rate)`; `cost_per_unit = Round2(stock_cost / stock_qty)`; `tb_inventory_transaction_detail.{qty, cost_per_unit, total_cost} = {stock_qty, cost_per_unit, stock_cost}` จากนั้น cost layer ถูกสร้างโดย `splitFifoCost(stock_qty, stock_cost, 2)` (กระทบยอดทศนิยมแบบแม่นยำข้ามแถว layer หนึ่งแถวขึ้นไป) และส่วนแบ่ง extra cost ถูกแบ่งข้าม layer เดียวกันตามปริมาณลง `extra_cost_amount` (FIFO `createFifoTransaction`, `inventory-transaction.service.ts:1006-1150`; average `postAverageReceiptLines`, `:1205-1400`) เหตุการณ์ที่ `stock_qty` เป็น 0 ถูกตัดออกก่อนโพสต์ (`:927`) |
| `GRN_CALC_014` (rounding mode) | สายการคำนวณเงิน: 5 ตำแหน่ง (`ROUNDING_SCALE = 100000`) เปอร์เซ็นต์ deviation: 5 ตำแหน่ง `cost_per_unit` ของ ledger: 2 ตำแหน่ง การแสดงผล: สกุลเงิน 2 ตำแหน่ง ปริมาณ 3 ตำแหน่ง อัตราแลกเปลี่ยน 5 ตำแหน่งเสมอ (FE `35391bf5`) |

### 3.1 ตัวอย่างคำนวณ (สกุลธุรกรรม ฿ THB)

สองบรรทัด vendor ใน THB, `exchange_rate = 1.00000` (ไม่มี FX), สินค้าทั้งสองอยู่ในหน่วยฐานที่ conversion factor เท่ากับ 1, หนึ่งบรรทัด extra-cost จัดสรร `by_value`

- **บรรทัด 1** (หนึ่งเหตุการณ์รับ): `received_qty = 10.000`, `received_price = ฿125.50`, client ส่ง `discount_amount = ฿62.75` (5%), `tax_amount = ฿83.46` (7% ของ net)
  - `sub_total_price = 125.50 × 10.000 = ฿1,255.00`
  - `net_amount = 1,255.00 − 62.75 = ฿1,192.25`
  - `total_price = 1,192.25 + 83.46 = ฿1,275.71`
- **บรรทัด 2** (หนึ่งเหตุการณ์รับ): `received_qty = 4.000`, `received_price = ฿89.00`, `discount_amount = ฿0.00`, `tax_amount = ฿24.92`
  - `sub_total_price = ฿356.00`; `net_amount = ฿356.00`; `total_price = ฿380.92`
- **Extra cost** (`Σ tb_extra_cost_detail.amount = ฿200.00`, `allocate_extra_cost_type = by_value` → ถ่วงตามปริมาณสต๊อก 10 : 4):
  - ส่วนแบ่งบรรทัด 1: `200.00 × 10 / 14 = ฿142.85714`
  - ส่วนแบ่งบรรทัด 2: `200.00 × 4 / 14 = ฿57.14286` (`splitByWeight` กระทบยอดให้ส่วนแบ่งรวมกันเท่ากับ ฿200.00 พอดี)
  - หากโหมดเป็น `by_qty` แต่ละบรรทัดจะได้ `฿100.00` โดยไม่สนปริมาณ; หากเป็น `manual` ไม่มีบรรทัดใดได้เลย
- **Header roll-up**: `net_amount = ฿1,548.25`; `total_amount = ฿1,656.63` (ไม่รวม extra cost)
- **Ledger feed** (บรรทัด 1, `foc_qty = 0`): `stock_cost = 1,192.25 + 142.85714 = ฿1,335.10714`; `cost_per_unit = Round2(1,335.10714 / 10) = ฿133.51`; cost layer: `in_qty = 10`, `total_cost ≈ ฿1,335.11`, `extra_cost_amount ≈ ฿142.86`

ถ้าบรรทัด 1 มี `foc_qty = 1.000` บนเหตุการณ์เดียวกันด้วย `stock_qty = 11` และ `cost_per_unit = Round2(1,335.10714 / 11) = ฿121.37` — หน่วย FOC เข้าสต๊อกที่ landed cost ที่ถูกเจือจาง และ (เพราะน้ำหนักคือปริมาณสต๊อก) ส่วนแบ่ง extra cost ของบรรทัด 1 เพิ่มเป็น `200 × 11/15 = ฿146.67`

| `GRN_POST_013` | PATCH บน GRN สถานะ `saved` ของ BU แบบ average | `repostGrnLedgerIfChanged()` (`ledger.ts:807-873`) เรียกตอนท้ายของ `update()` (`service.ts:1996-2010`) หลังการตรวจ stock-lock และเนื้อหา: ถ้าการเคลื่อนไหวที่มีอยู่บรรจุ `posted_at_save = true` และ `po_receiving_applied != true` (`isLedgerRevisable`) ให้วางแผนการแก้ไขต่อบรรทัดเหตุการณ์ (`planLedgerRevision`, `ledger.ts:650`): แถวที่สินค้า location ปริมาณสต๊อก หรือต้นทุนต่างกัน (epsilon 5 ตำแหน่ง) ถูก **retire** — cost layer ถูก soft-delete และแถวถูกย้ายไปใต้ header ใหม่ที่ void แล้ว (`info.revised_from`, `retireLedgerRows`, `:699`) — และเฉพาะบรรทัดเหล่านั้นถูกโพสต์ใหม่ใต้ header เดิม (`appendToGoodReceivedNoteTransaction`) บรรทัดที่ไม่แตะจึงคงเลข lot เดิม; จากนั้นประทับ average ของสินค้าที่ได้รับผลกระทบใหม่ หากไม่เหลืออะไรของใบรับบน ledger header จะถูกลบและใบรับอ่านได้เหมือนไม่เคยโพสต์ GRN `saved` ที่ไม่เคยโพสต์ (ปริมาณเป็น 0 ทั้งหมด) จะโพสต์ทันทีที่มีปริมาณ (`postSavedReceiptIfDue`, `:768`) การเคลื่อนไหวที่ไม่มี link ต่อบรรทัด (เขียนก่อนมีคอลัมน์) ถูกแทนที่ทั้งก้อน GRN ที่ committed แล้วไม่ถูกโพสต์ซ้ำเลย |

State diagram (Prisma-canonical):

```
[*] → draft ──save──► saved ──commit / approve──► committed
        │  (AVG: ledger)        (ledger ถ้ายังไม่มี + เลื่อน PO)
        ├──void/reject──► voided
        └──delete (soft)
                saved ──void/reject──► voided   (AVG: ถอน ledger ออก เว้นแต่ lot ถูกใช้แล้ว → 409)
```

`committed` และ `voided` เป็น terminal; `committed` void ไม่ได้ (`GRN_COMMITTED_NOT_VOIDABLE`) `draft` ยอมรับ soft-delete

> ⚙️ **กฎฝั่ง server — list บน mobile เป็น `draft` เท่านั้น:** Endpoint รายการ GRN ใช้ตัวกรองมุมมองที่ขึ้นกับอุปกรณ์ `applyMobileGrnDocStatusFilter(paginate, appId)` โดยอุปกรณ์ที่เรียกถูก resolve จาก request header `x-app-id` เทียบกับ app allowlist เมื่ออุปกรณ์เป็น `mobile` รายการถูกบังคับให้เป็น `doc_status = draft` เท่านั้น — ตัวกรอง `doc_status` อื่นใดบน request จะถูกถอดออกและแทนที่ด้วย `doc_status|enum = draft` บนอุปกรณ์ที่ไม่ใช่ mobile (desktop) รายการไม่เปลี่ยน: ส่งคืนทุกสถานะ (`draft`, `saved`, `committed`, `voided` ตามที่มี) นี่คือ **การจำกัดมุมมอง (VIEW) ไม่ใช่กฎสถานะเอกสาร** — GRN ที่ไม่ใช่ `draft` ยังคงมีอยู่ในฐานข้อมูลและเข้าถึงได้โดยตรง เพียงแต่ไม่ปรากฏในมุมมอง list บน mobile บังคับใช้ฝั่ง server ที่ backend gateway (`carmen-turborepo-backend`, helper `apps/backend-gateway/src/common/helpers/mobile-grn-doc-status-filter.ts`); **ไม่ปรากฏใน PRD หรือ Technical Spec ดั้งเดิม**
