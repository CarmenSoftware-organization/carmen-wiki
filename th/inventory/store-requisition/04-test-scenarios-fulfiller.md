# ใบเบิกของสโตร์ (Store Requisition) — Test Scenarios — Fulfiller

> **At a Glance**
> **Persona:** Fulfiller (Store Keeper / Warehouse Supervisor ที่ต้นทาง) &nbsp;·&nbsp; **โมดูล:** [store-requisition](/th/inventory/store-requisition) &nbsp;·&nbsp; **Scenarios:** ~27
> **หมวดหมู่:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **E2E coverage:** map ไปยัง `tests/701-sr.spec.ts` (TC-SR-120001..120004+ Issuance) ใน `../carmen-inventory-frontend-e2e/`

หน้านี้จับ scenario test ที่ persona Fulfiller (ผู้ที่ถือขั้น workflow ที่ tag `enum_stage_role.issue` โดยทั่วไปมีตำแหน่ง Store Keeper / Warehouse Supervisor) ขับเคลื่อนโดยตรงในโมดูล `store-requisition` การมีส่วนร่วมของ Fulfiller เริ่มเมื่อ SR ไปถึงขั้น tag issue ของ `in_progress` (หลังขั้น tag approve ที่อยู่ก่อนหน้าเสร็จสิ้น) และจบที่การเดินขั้น workflow สุดท้าย — การเรียก `POST .../approve` ทั่วไปเดียวกับที่ Approver ใช้ (`useIssueStoreRequisition` และ `useApproveStoreRequisition` เรียก endpoint เดียวกัน ต่างกันเพียง tag `stage_role`) Scenarios จัดกลุ่มเป็น **happy path** (การ issue เต็มตรงกับ `approved_qty`, การ issue บางส่วนตอน stock-out ที่ issue, `sr_type = transfer` ที่เพิ่ม on-hand ปลายทาง, `sr_type = issue` เข้าปลายทาง `direct` ที่ on-hand ปลายทางไม่เปลี่ยน), **RBAC** (authorization ที่ gate ตามขั้น, สิทธิ์ fulfiller scope ตาม location), **validation** (test เชิงลบกับ `SR_VAL_008` — `issued_qty > approved_qty`, `SR_VAL_011`/`SR_VAL_013` — gate ที่การเดินขั้นสุดท้าย) และ **edge case** เรื่อง optimistic concurrency และผลผสมหลายบรรทัด (บางบรรทัด issue เต็ม อื่น issue บางส่วน อื่นเป็นศูนย์) **แก้ไขรอบนี้:** การเลือก lot ไม่ใช่ action ของ Fulfiller — `createFifoConsumption()` ใน `inventory-transaction.service.ts` กำหนด lot อัตโนมัติแบบ FIFO; ไม่มี lot-selection UI ใน SR frontend Segregation of duties (Approver ≠ Fulfiller), การ block commit ในงวดปิด (`SR_VAL_014`) และการ post GL/journal-entry ถูกตรวจสอบกับ source ปัจจุบันแล้วพบว่ายังไม่ยืนยัน — scenarios ที่สร้างจากข้อกล่าวอ้างเหล่านั้นถูกแก้ไขด้านล่าง Handoff ข้าม persona ที่ pivot จาก Fulfiller (Scenarios 1, 2, 6, 8 ในภาพรวมแม่) อยู่ใน [04-test-scenarios.md](./04-test-scenarios.md) ไม่ใช่ที่นี่

## 2. Permission / Authorization

| FUL-PERM-01 | Fulfiller ใน `user_action.execute` ที่ขั้น tag issue กระทำบน SR ที่ต้นทางของตน | **Allow** การป้อน `issued_qty` และคลิก **Issue** enable ขณะ `doc_status = in_progress` และ `workflow_current_stage` tag ด้วย `enum_stage_role.issue` ตาม `SR_AUTH_007` |

| FUL-PERM-04 | ~~Approver พยายาม fulfil SR ที่ตนอนุมัติเหนือ threshold SoD~~ — แก้ไขรอบนี้ | — | **ถูกลบ** ไม่มี check segregation-of-duties และไม่มี threshold การผ่อนคลายอยู่ใน source ปัจจุบัน — ผู้ใช้คนเดียวกันสามารถ approve แล้ว issue SR เดียวกันได้ทุกมูลค่าโดยไม่มี block ระดับ code ใด ๆ |
| FUL-PERM-05 | Fulfiller พยายามกระทำบน SR `completed` | **Deny — สถานะจุดสิ้นสุด** ตามกฎกลาง `completed` ล็อกข้าม persona การแก้หลัง commit ผ่าน `[inventory-adjustment](/th/inventory/inventory-adjustment)` |

## 3. Validation / Error

| # | Scenario | Trigger | Error ที่คาดหวัง |
| - | -------- | ------- | --------------- |
| FUL-VAL-01 | `issued_qty > approved_qty` บนบรรทัด | Fulfiller ป้อน `issued_qty = 12` บนบรรทัดที่ `approved_qty = 10` | **Reject** — `SR_VAL_008` Server คืน `"Quantities must satisfy 0 ≤ issued_qty ≤ approved_qty ≤ requested_qty."` สาเหตุพบบ่อย: typo / ข้อผิดพลาดการป้อนข้อมูล |
| FUL-VAL-02 | `issued_qty < 0` บนบรรทัด | Fulfiller ป้อนปริมาณติดลบโดยบังเอิญ | **Reject** — `SR_VAL_008` Server คืน invariant error เดียวกัน |
| FUL-VAL-03 | การเดินขั้นสุดท้ายโดยไม่มีบรรทัดที่อนุมัติ | บรรทัดทั้งหมดมี `approved_qty = 0` (เช่น ทุกบรรทัดถูก reject ในการเรียก `/approve` ก่อนหน้า แต่ไม่เคยเรียก `/reject` ทั้งเอกสาร) | **Reject** — `SR_VAL_011` Server คืน `"SR must contain at least one approved line (approved quantity > 0) before it can be committed."` **แก้ไขรอบนี้:** นี่เป็น state ที่เป็นไปได้ ไม่ใช่ bug — การ reject ทุกบรรทัดไม่ทำให้เอกสาร void อัตโนมัติ ต้องมีการเรียก reject ทั้งเอกสารแยกต่างหากเพื่อยุติเอกสาร |
| FUL-VAL-04 | ~~ขาดข้อมูล lot บน inventory transaction ที่ลิงก์~~ — แก้ไขรอบนี้ | — | **ไม่ใช่ scenario ที่ Fulfiller trigger ได้** การกำหนด lot เป็น FIFO อัตโนมัติ; ไม่มีขั้นการเลือก lot ที่ Fulfiller ข้ามหรือทำไม่ครบได้ |
| FUL-VAL-05 | On-hand ต้นทางต่ำกว่า `issued_qty` ที่การเดินขั้นสุดท้าย (check live) | check `SR_VAL_013` live: SR อื่น consume on-hand ต้นทางระหว่างที่ Fulfiller ป้อน `issued_qty` กับคลิก Issue; on-hand ตอนนี้ < `issued_qty` | **Reject** — `SR_VAL_013` Server คืน `"Source stock-out at issue: line <seq> requires <issued_qty> but only <on_hand> is available at <from_location_name>."` Fulfiller ลด `issued_qty` เป็น on-hand live และ re-submit (รูปแบบ partial-issuance ของ FUL-HP-04) |
| FUL-VAL-06 | ~~การพยายาม commit ในงวดปิด~~ — แก้ไขรอบนี้ | — | **ถูกลบ** การค้นหาทั่ว repo ใน `store-requisition.service.ts`, `store-requisition.logic.ts` และ SR DTOs สำหรับ `period` ไม่พบผลลัพธ์เลย; ให้ถือ `SR_VAL_014` ว่ายังไม่ยืนยัน |
| FUL-VAL-07 | Optimistic-concurrency ไม่ตรงตอนการเดินขั้นสุดท้าย | ผู้ใช้อื่น (แท็บพร้อมกัน หรือระบบ background) ได้อัปเดต `doc_version` บน SR ระหว่างอ่านกับการเรียก Issue | **Reject** — optimistic-concurrency ทั่วไป Server reject ด้วย `409`; frontend fetch `doc_version` ใหม่ก่อน retry (`fetchFreshSr()` ใน `use-sr-form-actions.ts`) |

## 4. Edge Cases
