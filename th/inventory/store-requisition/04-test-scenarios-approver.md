# ใบเบิกของสโตร์ (Store Requisition) — Test Scenarios — Approver

> **At a Glance**
> **Persona:** Approver (Department Head + approver ระดับสูงขึ้น) &nbsp;·&nbsp; **โมดูล:** [store-requisition](/th/inventory/store-requisition) &nbsp;·&nbsp; **Scenarios:** ~27
> **หมวดหมู่:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **E2E coverage:** map ไปยัง `tests/701-sr.spec.ts` (TC-SR-060001..060005, 070001..070003, 080001..080002, 090001+, 100001+, 110001+) ใน `../carmen-inventory-frontend-e2e/`

หน้านี้จับ scenario test ที่ persona Approver (ผู้ที่ถือขั้น workflow ที่ tag `enum_stage_role.approve` โดยทั่วไปมีตำแหน่ง Department Head) ขับเคลื่อนโดยตรงในโมดูล `store-requisition` การมีส่วนร่วมของ Approver เริ่มเมื่อ SR transition เป็น `in_progress` และ workflow ลงที่ขั้นที่ Approver อยู่ใน `user_action.execute`; จบเมื่อบรรทัดทั้งหมดถูก action (เดิน workflow ไปขั้นถัดไป) หรือเมื่อ Approver เรียกการ reject ทั้งเอกสารแยกต่างหาก (`voided`) Scenarios จัดกลุ่มเป็น **happy path** (approve เต็มต่อบรรทัด, ตัดลงพร้อม `approved_message`, reject รวมอยู่ในการเรียก `/approve` เดียวกัน, send-back พร้อม `review_message` ผ่านการเรียก `/review` แยกต่างหาก), **RBAC** (authorization ที่ gate ตามขั้นตาม `SR_AUTH_014`; segregation of duties ระหว่าง Requester กับ Approver **ยังไม่ยืนยัน** — ไม่พบ check ระดับ code ใด ๆ), **validation** (test เชิงลบกับ `SR_VAL_010` — `approved_qty > requested_qty`) และ **edge case** เรื่อง approver พร้อมกันบนบรรทัดต่างกันและขอบเขตการ reject ทั้งเอกสาร **แก้ไขรอบนี้:** approval delegation, SLA time-out escalation และการเชื่อมโมดูล budget ถูกตรวจสอบกับ `store-requisition.service.ts`, `store-requisition.logic.ts` และ workflow orchestrator แล้วพบว่ายังไม่ยืนยัน (ค้นหาแล้วไม่พบ `delegat` หรือ route ของ budget เลย) — scenarios ที่สร้างจากข้อกล่าวอ้างเหล่านั้นถูกลบหรือระบุว่ายังไม่ยืนยันด้านล่าง **แต่ multi-tier value-threshold escalation ยืนยันแล้วว่ามีจริง** (การค้นหาติดตามผลพบว่า check "ผลศูนย์รายการ" ก่อนหน้าค้นหาเฉพาะคำตรงตัว `threshold`; กลไกที่ใช้งานจริงคือ `routing_rules` ของ workflow ที่ assign ให้ ซึ่ง route ตาม `total_amount` ได้ — ดู `SR_XMOD_008` ใน [02-business-rules.md](./02-business-rules.md)) — APR-HP-06 และ APR-EDGE-05 ด้านล่างถูกแก้ไขให้ถูกต้องแทนที่จะลบทิ้ง Handoff ข้าม persona ที่ pivot จาก Approver (Scenarios 1, 3, 4, 5 ในภาพรวมแม่) อยู่ใน [04-test-scenarios.md](./04-test-scenarios.md) ไม่ใช่ที่นี่

## 2. Permission / Authorization

| # | Scenario | พฤติกรรมที่คาดหวัง (allow/deny + เหตุผล) |
| - | -------- | --------------------------------------- |
| APR-PERM-01 | Approver ใน `user_action.execute` ที่ขั้นปัจจุบันกระทำบน SR | **Allow** Action approve / trim / reject / send-back ล้วน enable บนบรรทัดขณะ `doc_status = in_progress` และ `workflow_current_stage` ตรงกัน ตาม `SR_AUTH_005` |
| APR-PERM-02 | ผู้ใช้ที่ **ไม่** อยู่ใน `user_action.execute` พยายามอนุมัติ | **Deny — workflow-stage gating** ตาม `SR_AUTH_014` ผู้ใช้เห็น SR ใน activity feed แต่ปุ่ม **Approve** ถูกซ่อน / disable; การเรียก API โดยตรง reject ด้วย `"You are not assigned to act on this requisition at the current stage."` ไม่เขียน `approved_qty` Map ไปยัง TC-SR-070002 (Unauthorized User Attempts to Approve) |
| APR-PERM-03 | Requester พยายามอนุมัติ SR ของตน | **ยังไม่ยืนยันว่าถูก block หรือไม่** ไม่พบการ cross-check `requestor_id` ใด ๆ ใน `store-requisition.service.ts` หรือ `store-requisition.logic.ts` ที่ action approve อย่าระบุ block SoD ใน test expectation จนกว่าจะได้รับการยืนยันอย่างเป็นอิสระกับ tenant ที่ใช้งานจริง |
| APR-PERM-04 | Approver พยายามตั้ง `approved_qty > requested_qty` | **Deny — value cap** ตาม `SR_VAL_010` หน้าจอ block การป้อนฝั่ง client; server reject ผ่าน `"Approved quantity cannot exceed requested quantity; to grant more, the requester must amend and resubmit."` Approver ต้องตัดเป็น `requested_qty` หรือส่งบรรทัดกลับขอ requester แก้ |
| APR-PERM-05 | Approver reject บรรทัดโดยไม่มี `reject_message` | **Deny — เหตุผลบังคับ** ตาม `SR_VAL_010` ส่วนสอง Dialog Reject ต้องการ `reject_message` ไม่ว่าง; server reject submission ว่างด้วย `"Rejection reason is required."` |
| APR-PERM-06 | Approver พยายามแก้ `requested_qty` บนบรรทัด | **Deny — ขอบเขต Approver** Approver ตั้ง `approved_qty` (และคอลัมน์ลายเซ็น) ได้ แต่ไม่ใช่ `requested_qty` (ซึ่งเป็นขอบเขต requester และล็อกตอน submit) ฟิลด์ `requested_qty` ของบรรทัด read-only บนหน้าจออนุมัติ การเปลี่ยน requested quantity ต้องส่งบรรทัดกลับเพื่อแก้ (APR-HP-04) |
| APR-PERM-07 | Approver พยายามกระทำบน SR `completed` | **Deny — สถานะจุดสิ้นสุด** ตามกฎกลาง `completed` ล็อกข้าม persona Approver อาจตรวจสอบลายเซ็นเชิงประวัติศาสตร์สำหรับ audit แต่ re-approve หรือ revoke ไม่ได้ |

## 3. Validation / Error

| # | Scenario | Trigger | Error ที่คาดหวัง |
| - | -------- | ------- | --------------- |
| APR-VAL-01 | `approved_qty > requested_qty` ต่อบรรทัด | Approver พยายาม `approved_qty = 30` บนบรรทัดที่ `requested_qty = 25` | **Reject** — `SR_VAL_010` ส่วนแรก Server คืน `"Approved quantity cannot exceed requested quantity; to grant more, the requester must amend and resubmit."` |
| APR-VAL-02 | `approved_qty < 0` | Approver พยายามปริมาณที่อนุมัติติดลบ (ข้อผิดพลาดการป้อนข้อมูลหรือ API mis-use) | **Reject** — `SR_VAL_008` (quantity invariant reject ติดลบทุกขั้น) Server คืน `"Quantities must satisfy 0 ≤ issued_qty ≤ approved_qty ≤ requested_qty."` |
| APR-VAL-03 | Reject บรรทัดด้วย `reject_message` ว่าง | Approver คลิก Reject และ submit โดยไม่ป้อนเหตุผล | **Reject** — `SR_VAL_010` ส่วนสอง Server คืน `"Rejection reason is required."` |
| APR-VAL-04 | Send-back ด้วย `review_message` ว่าง | Approver คลิก Send Back และ submit โดยไม่ป้อนเหตุผล | **Reject** — กลุ่มเดียวกันกับ VAL-03 Server คืน `"Review message is required when sending an SR back for correction."` |
| APR-VAL-05 | Approver กระทำบนบรรทัดนอกขั้นของตน | Approver อยู่ใน `user_action.execute` สำหรับขั้น 1 แต่พยายามกระทำบนบรรทัดที่ `current_stage_status` อยู่ที่ขั้น 2 (ผ่านขั้น 1 แล้ว — ลำดับผิดปกติ) | **Reject** — `SR_AUTH_014` Server คืน `"You are not assigned to act on this requisition at the current stage."` |
| APR-VAL-06 | ~~Warning เกินงบประมาณตอนอนุมัติ~~ — แก้ไขรอบนี้ | — | **ยังไม่ยืนยัน** `TC-SR-070003` ใน `701-sr.spec.ts` มี test-plan annotation บรรยาย warning เกินงบประมาณ แต่ไม่พบ route, field หรือการเชื่อมโมดูล budget เข้ากับหน้าจออนุมัติ SR ใน `carmen-inventory-frontend-react` หรือ `carmen-turborepo-backend-v2` ให้ถือ annotation นี้เป็น test-plan copy เชิงตัวอย่าง ไม่ใช่พฤติกรรมที่ยืนยันแล้ว จนกว่าจะพบการเชื่อมโมดูล budget |

## 4. Edge Cases

| # | Scenario | เงื่อนไข | คาดหวัง |
| - | -------- | -------- | ------- |
| APR-EDGE-01 | Approver พร้อมกันบนบรรทัดต่างกัน | สอง approver (ทั้งคู่ใน `user_action.execute` สำหรับขั้นเดียวกัน) เปิด SR เดียวกันและแต่ละคลิก approve บนบรรทัดต่างกันพร้อมกัน | **Locking ระดับบรรทัด** ระบบล็อกที่ระดับบรรทัดผ่าน optimistic concurrency (`doc_version` บน detail) แต่ละบรรทัดยอมรับ approver แรกที่กระทำ; approver ที่สองกระทำบนบรรทัดเดียวกันได้รับ message "line already actioned" และถูกขอให้ refresh ไม่มี double-write ไม่มีลายเซ็นสูญ Workflow เดินเมื่อบรรทัดทั้งหมดถูก action โดย approver บางคน |
| APR-EDGE-02 | การ reject ทั้งเอกสารหลังทุกบรรทัดถูก mark reject | Approver mark ทุกบรรทัด active เป็น reject (แต่ละบรรทัดมี `reject_message` ของตน) จากนั้นเรียก action reject ทั้งเอกสารแยกต่างหาก | **`doc_status = voided` ไม่ใช่ `cancelled`** **แก้ไขรอบนี้:** ไม่มีการ cancel อัตโนมัติ — `StoreRequisitionService.reject()` เป็นการเรียกแยกที่ approver ต้องเรียกเอง; `cancelled` ไม่เคยถูกกำหนดโดย service method ใดในปัจจุบัน Requester ถูกแจ้ง |
| APR-EDGE-03 | ~~Time-out / SLA escalation~~ — แก้ไขรอบนี้ | — | **ถูกลบ** ไม่พบ logic SLA-timeout หรือ auto-escalation ใด ๆ ใน workflow orchestrator หรือโมดูลนี้; ให้ถือข้อกล่าวอ้าง "stale-approval auto-escalation" ใด ๆ ว่ายังไม่ยืนยัน |
| APR-EDGE-04 | Approver ตัดเป็น on-hand ต้นทางพอดีตอนอนุมัติ | On-hand ต้นทางที่ Approver เห็น = 15; Approver ตัด `approved_qty = 15` (ตรงกับ on-hand) | **อนุมัติยอมรับ** ตอนการเดินขั้น workflow สุดท้าย on-hand ต้นทางอาจขยับ (การบริโภคอื่น) `SR_VAL_013` run อีกครั้งที่จุดนั้นเทียบกับ on-hand live — ถ้า on-hand ตกต่ำกว่า 15 ขั้น issue short-issue; ถ้าเพิ่มขึ้น ไม่กระทบ (การ issue cap ที่ `approved_qty = 15` อยู่แล้ว) Approver **ไม่** เห็นความเสี่ยง stock-out ตอน issue ที่อนุมัติ |
| APR-EDGE-05 | Multi-tier ที่ขั้นสองตัดเพิ่ม | `tb_workflow` ของ tenant กำหนดขั้น tag `approve` ที่สองซึ่งเข้าถึงได้ผ่าน routing rule ตาม `total_amount` (APR-HP-06); approver ขั้นสองตัดบรรทัดที่ approver ขั้นแรกอนุมัติเต็มไปแล้วเพิ่มเติม | **กลไกยืนยันแล้ว แต่ยังไม่ verify อย่างเป็นอิสระกับ tenant แบบ multi-stage ที่ใช้งานจริงในรอบนี้** กลไก approve ทั่วไปเดียวกัน apply ที่ขั้นสองด้วย (`SR_AUTH_005`/`SR_AUTH_006`) และ JSON `history` ต่อบรรทัดจับ action ของทั้งสองขั้นตามลำดับ; routing rule ที่พา SR ไปถึงขั้น 2 (`SR_XMOD_008`) ยืนยันแล้วว่ามีจริง แต่ scenario เฉพาะนี้ (ตัดซ้อนตัดข้ามสองขั้นที่ route มา) ไม่ได้ถูก exercise อย่างเป็นอิสระกับ tenant แบบ multi-stage ที่ใช้งานจริงในรอบนี้ — ถือรายละเอียดการผสมการตัดนี้ว่าเป็นไปได้ ไม่ใช่ยืนยันแล้ว |
| APR-EDGE-06 | Approver กระทำแล้วแก้ทันทีใน session เดียวกัน | Approver อนุมัติบรรทัด 1 ที่ 25 จากนั้นรู้ตัวว่าตั้งใจตัด; พยายาม re-set `approved_qty = 20` | **อนุญาตการตัดสินใจใหม่ใน session ก่อน workflow เดิน** ตราบเท่าที่ขั้น workflow ยังไม่เดิน (โดยทั่วไปเพราะบรรทัดอื่นบนขั้นยังไม่ถูก action) Approver อาจอัปเดตลายเซ็นของตนบนบรรทัด; `approved_date_at` อัปเดต, `approved_qty` ล่าสุดคือค่า canonical, JSON `history` บันทึกการเปลี่ยน เมื่อ workflow เดิน (บรรทัดทั้งหมดถูก action submit decision) บรรทัดถูกล็อกที่ขั้นนี้ |
| APR-EDGE-07 | ~~Bulk approve จาก approvals list~~ — แก้ไขรอบนี้ | Approver เลือก SR หลายตัวใน list | **ยังไม่ยืนยันในฐานะ action ระดับ list** action bulk ระดับ list ที่ยืนยันได้เดียวคือ **Export Selected** (`TC-SR-060003`, ปุ่ม bulk-actions ของ `sr-component.tsx`) Bulk approve/reject/review มีอยู่เฉพาะ *ภายใน* line table ของ SR เดียว (`handleBulkApprove` / `handleBulkReject` / `handleBulkReview` ของ `sr-item-fields.tsx` ที่ apply การตัดสินใจกับหลายบรรทัดที่เลือกบนเอกสารเดียว) — ไม่ใช่ข้าม SR หลายตัวจาก list อย่า test หา action bulk-approve ข้ามเอกสาร |
| APR-EDGE-08 | Bulk-select บรรทัดภายใน SR เดียวและ apply การตัดสินใจเดียว | SR มี 5 บรรทัด; Approver เลือก 3 บรรทัดผ่าน row checkbox และคลิก action bulk-approve ที่แสดงเมื่อมีการเลือกอยู่ | **ยืนยันจริง** — `sr-item-fields.tsx` แสดง control bulk approve / reject / review เมื่อ `selectedRows.length > 0` และ `canBulkAction` เป็นจริง; action apply `stage_status` ที่เลือกกับทุกบรรทัดที่เลือก จากนั้นกฎ `SR_VAL_010` ต่อบรรทัดตามปกติ apply ตอน submission นี่คือ action bulk ภายในเอกสารเดียว ต่อบรรทัด ไม่ใช่ข้ามเอกสาร (ดู APR-EDGE-07) |
