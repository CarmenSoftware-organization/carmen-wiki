# ใบเบิกของสโตร์ (Store Requisition) — Test Scenarios — Requester

> **At a Glance**
> **Persona:** Requester (Outlet Manager ที่ปลายทางบริโภค) &nbsp;·&nbsp; **โมดูล:** [store-requisition](/th/inventory/store-requisition) &nbsp;·&nbsp; **Scenarios:** ~29
> **หมวดหมู่:** Happy Path &nbsp;·&nbsp; Permission &nbsp;·&nbsp; Validation &nbsp;·&nbsp; Edge Case
> **E2E coverage:** `tests/701-sr.spec.ts` (TC-SR-01xxxx..05xxxx) ใน `../carmen-inventory-frontend-e2e/`; case ที่มี oracle รองรับใน `docs/test-cases/gaps/701-sr-gap.md` section 01–05 (ฟอร์ม, กฎส่วนหัว, เพิ่ม/ลบบรรทัด, dialog สต๊อก, save/discard, dialog Submit)
> **Re-sync 2026-09-22:** ไม่มีตัวเลือก `sr_type`, `sr_no`/`sr_date` ถูกกำหนดขั้นสุดท้ายตอน submit, ไม่มีการตรวจความพร้อมต้นทาง, ไม่มี auto-save, ลบเดี่ยว/batch เฉพาะเจ้าของ, dialog date-pattern, การตรวจสินค้าที่ปลายทาง — แถวด้านล่างแก้ไข in place

หน้านี้จับ scenario test ที่ persona Requester (**Outlet Manager** ที่ปลายทางบริโภค) ขับเคลื่อนโดยตรงในโมดูล `store-requisition` การมีส่วนร่วมของ Requester เริ่มเมื่อความต้องการสต๊อกถูกระบุที่เอาท์เลต (event ผลิตที่วางแผน, การละเมิด par-level, ใบ event banquet หรือ auto-create ที่ขับโดย recipe จาก `[recipe](/th/inventory/recipe)`) และจบเมื่อ SR ออกจาก requester zone — ผ่าน submit (handoff ไปยังผู้ที่ถือขั้น workflow แรก) หรือผ่านการ soft-delete `draft` ของตนเอง (เส้นทางลบก่อน submit เดียวที่ยืนยันได้; ไม่มีเส้นทางถอน `in_progress` ที่ยืนยันได้) Scenarios จัดกลุ่มเป็น **happy path** (เดิน `draft`: create / ป้อนบรรทัด / submit; auto-create จาก recipe; resubmit หลัง send-back), **RBAC** (Requester ไม่ได้กำหนดให้ department; requester จะ approve SR ของตนเองได้หรือไม่นั้น **ยังไม่ยืนยัน** — ไม่พบ check ระดับ code ใด ๆ), **validation** (test เชิงลบกับ `SR_VAL_001`–`SR_VAL_009` ที่ Requester trigger ได้ที่ save หรือ submit) และชุดเล็ก ๆ ของ **edge case** เรื่องโหมด soft vs hard ของความพร้อมต้นทาง บรรทัด cost-dimension split ความแม่นยำทศนิยมบน `requested_qty` และการ submit พร้อมกันบนเอาท์เลตเดียวกัน Handoff ข้าม persona ที่ pivot จาก Requester (Scenarios 1, 2, 3, 4 ในภาพรวมแม่) อยู่ใน [04-test-scenarios.md](./04-test-scenarios.md) ไม่ใช่ที่นี่

## 2. Permission / Authorization

| # | Scenario | พฤติกรรมที่คาดหวัง (allow/deny + เหตุผล) |
| - | -------- | --------------------------------------- |
| REQ-PERM-01 | Outlet Manager สร้าง SR ที่ `doc_status = draft` และ submit | **Allow** Requester เป็นเจ้าของ transition `draft → in_progress` ที่แก้ไขได้สำหรับ SR ของ department ของตน `New SR`, ป้อนบรรทัด, upload attachment และ `Submit` ล้วน enable บน SR ที่ยังไม่ submit Approver และ Fulfiller เห็นเอกสารใน `in_progress` หลัง submit แต่ Requester ไม่อาจแก้ได้อีก Map ไปยัง TC-SR-010001 + TC-SR-050001 |
| REQ-PERM-02 | ผู้ใช้ที่ไม่มี SR workflow ที่อนุญาตให้ create เปิด `/new` | **Deny — workflow gate ไม่ใช่ RBAC** `/new` ถูกห่อด้วย `CreateWorkflowGate`; ผู้ใช้เห็น `AccessDeniedBlock` (`None of the approval flows let you start a store requisition.`) แทนฟอร์ม ไม่มี error สมาชิกภาพแผนกตอน create (create DTO บังคับเพียงว่าต้องมี `department_id`) Map ไปยัง TC-SR-010002 (`test.fixme`) |
| REQ-PERM-03 | Requester แก้ SR `draft` ของตน | **Allow** การแก้ส่วนหัวและบรรทัด upload attachment ลบ — ล้วน enable ขณะ `doc_status = draft` ตาม `SR_AUTH_002` |
| REQ-PERM-08 | Requester อีกคนลบ draft ที่ตนไม่ได้เป็นเจ้าของ — **เพิ่ม 2026-09-22** | **Deny — ownership** `DELETE .../store-requisitions/:id` → `SR_DELETE_FORBIDDEN` (403, `You are not the owner of this store requisition`); ใน batch call รายการถูกรายงานด้วย `reason = not_owner` และไม่มีอะไรถูกลบ platform super-admin ข้าม check นี้ได้ |
| REQ-PERM-04 | Requester พยายามแก้ SR `in_progress` ของตน (หลัง submit) | **Deny — เอกสารออกจากมือ requester แล้ว** Endpoint แก้ reject ด้วย `"SR at status in_progress is not editable by the requester; the document is under approval / fulfilment."` ข้อยกเว้น: ถ้า workflow ได้ route SR กลับมาขั้น requester (send-back จาก approver) การแก้ enable อีกครั้งที่ขั้น requester เท่านั้น ตาม `SR_AUTH_002` ส่วนสอง |
| REQ-PERM-05 | Requester พยายามอนุมัติ SR ของตน | **ยังไม่ยืนยันว่าถูก block หรือไม่** การค้นหาทั่ว repo ใน `store-requisition.service.ts` และ `store-requisition.logic.ts` ไม่พบการ cross-check `requestor_id` ใด ๆ ที่ action approve ถ้าผู้ใช้คนเดียวกันถือทั้ง role ของ Requester และ role assignment ของขั้นที่ tag approve, source ปัจจุบันดูเหมือนจะไม่ block ไม่ให้เขา approve SR ของตนเอง — ควรยืนยันกับ tenant ที่ใช้งานจริงก่อนที่จะระบุใน test assertion ว่าถูก block หรือ allow |
| REQ-PERM-06 | Requester พยายามถอน SR ที่ submit แล้ว (`in_progress`) | **Deny — ไม่มี action แบบนี้อยู่จริง** `store-requisition.service.ts` ไม่มี endpoint `cancel` / `withdraw` สำหรับเอกสาร `in_progress`; action **Delete** จำกัดเฉพาะ `doc_status = draft` เมื่อ submit แล้ว เส้นทางเดียวของ requester ที่จะยุติเอกสารคือขอให้ผู้ที่ถือขั้น workflow ปัจจุบันเรียกการ reject ทั้งเอกสาร (ซึ่งตั้งเป็น `voided`) |
| REQ-PERM-07 | Requester พยายามแก้ SR `completed` | **Deny — สถานะจุดสิ้นสุด** การแก้ส่วนหัวและบรรทัดถูก block ข้าม persona ทั้งหมด (ไม่ใช่แค่ Requester) บน SR `completed`; เส้นทางแก้หลัง commit เดียวคือ `[inventory-adjustment](/th/inventory/inventory-adjustment)` Map ไปยัง permission-denial ข้าม persona |

| REQ-VAL-07 | สินค้า inactive / discontinued บนบรรทัด | Requester เลือกสินค้าที่ถูก mark inactive ตั้งแต่นั้น (active ใน catalog cache แต่ inactive ใน master) | **Reject ตอน save line / submit** — `SR_VAL_006` Server คืน `"Product is required and must be active for issue from the source location."` |
| REQ-VAL-08 | product+dimension ซ้ำบน SR เดียวกัน | Requester เพิ่ม `Rice-1kg` ด้วย `dimension = [{cost_centre: 'Banquet'}]` สองครั้ง (แทนที่จะแก้บรรทัดที่มี) | **Reject ตอน save line** — `SR_VAL_007` Server คืน `"This product is already on the SR with the same cost-dimension allocation; edit the existing line or use a different dimension to split."` ตาม unique index `SRT1_*` |
| REQ-VAL-09 | `requested_qty = 0` หรือติดลบบนบรรทัด | Requester ทิ้งปริมาณที่ default 0 หรือพิมพ์ `-25` | ติดลบ: ฟอร์ม flag เซลล์ (`requested_qty ≥ 0` ขอบแดง ไม่มีข้อความ) และ Save/Submit ถูก block ด้วย toast `{n} items are still incomplete` ศูนย์: **Save สำเร็จ** (create DTO รับตัวเลขใดก็ได้); **Submit ปฏิเสธ** ด้วย 400 `Store requisition is not ready to submit — store_requisition_detail.<n>.requested_qty: …` (`ValidateSRBeforeSubmitSchema` `positive()`, `SR_VAL_008`) Map ไปยัง TC-SR-020002 |
| REQ-VAL-10 | สินค้าไม่ได้เปิดใช้ที่ปลายทาง — **แทนที่กรณีความพร้อมต้นทาง (ไม่มี check แบบนั้น `SR_VAL_009`)** | สินค้าของบรรทัดไม่มีแถว `tb_product_location` สำหรับ `to_location_id` | **Reject ตอน submit** — `SR_VAL_015` Server คืน 400 `The following products are not allowed in the destination location: <product names>`; SR คงเป็น `draft` TC-SR-020003 / 030002 ("insufficient stock" ตอน submit) บรรยายพฤติกรรมที่ไม่มีอยู่จริง |
| REQ-VAL-11 | วันนี้อยู่นอกทุก inventory period ที่เปิดตอน submit — **เพิ่ม 2026-09-22** | Inventory period ของเดือนปัจจุบันถูกปิด | Submit คืน 422 `SR_DATE_PATTERN_REQUIRED`; client เปิด dialog date-pattern *วันที่ใน open period* → `sr_date` = วันสุดท้ายของ open period ปัจจุบัน submit ถูก retry และยอมรับ; *วันนี้* → ยอมรับแต่ SR issue ไม่ได้จนกว่า period นั้นจะเปิด; **Cancel** ทิ้ง draft ไว้ไม่แตะต้อง ถ้าไม่มี open period เลย: 422 `SR_NO_OPEN_PERIOD` (`SR_VAL_014`, `SR_VAL_016`) |

## 4. Edge Cases

| # | Scenario | เงื่อนไข | คาดหวัง |
| - | -------- | -------- | ------- |
| REQ-EDGE-01 | คำขอเกิน on-hand ต้นทาง | `requested_qty = 100`; on-hand ต้นทาง = 60 | **Submit อนุญาต ไม่มี warning** ไม่มีการตรวจความพร้อมหรือ reservation ตอน submit (`SR_VAL_009` ยังไม่ยืนยัน); requester เห็น on-hand ได้เฉพาะใน dialog Inventory Information การขอเกินจะปรากฏตอน approver ตัดหรือที่ขั้น issue (`SR_VAL_013`) |
| REQ-EDGE-02 | Cost-dimension split บนสินค้าเดียวกัน | การป้อนสินค้าเดียวกันสองแถวตาม REQ-HP-03; สองแถวมีค่า JSON `dimension` ต่างกัน | สองแถว persist (unique index `SRT1_*` รวม `dimension`); ไหลอย่างอิสระผ่านการอนุมัติ (แต่ละสามารถ trim / reject แยก) และ fulfillment (แต่ละเขียน inventory transaction แยก) การแยกต้นทุนข้าม cost-centre ผ่าน GL/journal-entry ยังไม่ยืนยัน — ไม่พบ code การ post journal สำหรับโมดูลนี้ Edge: product+dimension เหมือนกันเป็น duplicate ตาม REQ-VAL-08 |
| REQ-EDGE-03 | ความแม่นยำทศนิยมบน `requested_qty` | Outlet manager ป้อน `requested_qty = 12.345` (3 ทศนิยม อยู่ใน `Decimal(20, 5)` พอดี) | **ยอมรับที่ storage** ปริมาณถูกเก็บที่ความแม่นยำ 5dp; แสดงผลปัด half-up 3dp ("12.345"); ไหลผ่านการอนุมัติและ issue ไม่เปลี่ยน; `received_base_qty` / `cost_per_unit` ของ inventory transaction ที่ลิงก์ใช้สัญญาความแม่นยำเดียวกัน ตาม `SR_CALC_007` |
| REQ-EDGE-04 | การ submit พร้อมกันบนเอาท์เลตเดียวกัน (สอง requester, สอง SR กับต้นทางเดียวกัน) | เอาท์เลตมีสอง requester (Outlet Manager และรอง); ทั้งคู่ submit SR กับ `WH-Central` พร้อมกัน ทั้งคู่ขอ `Rice-1kg` ปริมาณที่รวมกันเกิน on-hand ต้นทาง | **การ submit ทั้งสองสำเร็จแยกกัน** แต่ละ SR ผ่าน `SR_VAL_009` บน snapshot ของตน (check ต่อ SR ไม่ aggregate ข้าม submit พร้อมกัน) race ถูก resolve ที่อนุมัติ (Approver เห็นทั้งคู่และตัดได้) และที่ fulfillment (`SR_VAL_013` check live ตอน commit จับการ over-commit) SR หนึ่ง commit เต็ม; อีกตัว commit บางส่วนหรือเจอ stock-out Variance บันทึกบนส่วน |
| REQ-EDGE-05 | `description` ยาวและ attachment จำนวนมาก | Requester เขียน `description` 4,000 ตัวอักษรและแนบไฟล์ PDF / รูป 10 ไฟล์ผ่าน `tb_store_requisition_comment.attachments` | **ยอมรับใน Prisma limits** `description` เป็น `VarChar` (ไม่มี cap ความยาว); `attachments` JSONB array มี file ref 10 ตัว (`{originalName, fileToken, contentType}`) Storage backend (S3) ถือไฟล์; SR ถือเฉพาะ token Approver / Fulfiller เห็น attachment ใน activity log |
| REQ-EDGE-06 | ออกจากฟอร์มโดยมีการเปลี่ยนแปลงที่ยังไม่บันทึก — **แก้ไข 2026-09-22: ไม่มี auto-save** | Requester อยู่ระหว่างป้อนบรรทัดและนำทางออก (Back, sidebar) โดยไม่บันทึก | `useNavigationGuard` แสดง dialog *Discard changes?* พร้อม **Keep editing** / **Discard**; ไม่มีสิ่งใดถูก persist จนกว่าจะ **Save** `grep setInterval\|autosave routes/store-operation/store-requisition/` ไม่คืนอะไรเลย ดังนั้น TC-SR-040003 ("Auto-Save Draft Every 60 Seconds") ไม่มีพฤติกรรมให้ assert (gap `TC-SR-040105`) |
| REQ-EDGE-07 | Duplicate SR ที่มีอยู่ — **เพิ่ม 2026-09-22** | SR ที่บันทึกแล้วใด ๆ เปิดในโหมด view | **Duplicate** ในส่วนหัวนำทางไป `/new?duplicate_id=<id>`; ส่วนหัวและบรรทัดถูกเติมไว้ล่วงหน้า (`buildSrDuplicateValues`) ฟอร์ม dirty ตั้งแต่ต้น (baseline คือฟอร์มว่าง) และ **Save** สร้างเอกสาร `draft-<hex>` ใหม่; SR ต้นฉบับไม่เปลี่ยนแปลง |
