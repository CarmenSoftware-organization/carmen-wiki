# ใบรับสินค้า (Goods Receive Note)

> **At a Glance**
> **วัตถุประสงค์ของโมดูล:** บันทึกการรับสินค้าจริงตามใบ PO โพสต์การเคลื่อนไหวสต๊อกเข้า และอัปเดต costing แบบ FIFO / average (`draft` → `saved` → `committed` หรือ `voided`) &nbsp;·&nbsp; **ผู้ใช้:** Store Keeper / Receiver, Inventory Manager, Purchaser &nbsp;·&nbsp; **เอนทิตี/ตารางหลัก:** `tb_good_received_note`, `tb_good_received_note_detail`, `tb_good_received_note_detail_item`, `tb_inventory_transaction`, FIFO / average-cost layers &nbsp;·&nbsp; **หน้าย่อย:** 13
>
> **ตรวจสอบซ้ำ 2026-10-27 กับ `carmen-turborepo-backend` `c9d788829` และ `carmen-frontend` `391062b5`** โมเดลการโพสต์ของ 2026-09-22 ยังคงใช้ได้: สต๊อกโพสต์ที่ **`commit()`** (`saved → committed`, `good-received-note.logic.ts:170-215` → `postReceipt()` `:240-294`) และบน **business unit แบบ average `save()` จะโพสต์การเคลื่อนไหวสต๊อกล่วงหน้า** (`postsInventoryAtSave()` → `isAverageMethod()`, `good-received-note.ledger.ts:55-57`, เรียกจาก `logic.ts:104-149`); PO ถูกเพิ่มยอดตอน commit เท่านั้น ข้อค้นพบสองข้อจากรอบก่อนถูกตรวจซ้ำ: **"BU แบบ average โพสต์ตอน save" — ยังจริง** (และตอนนี้กฎนี้ครอบคลุมวิธี costing ใหม่ `average_per_location` ด้วย) และ **"GRN ที่เป็น FOC ล้วน commit โดยไม่มีการเคลื่อนไหว" — ไม่จริงอีกต่อไป** (แก้เมื่อ 2026-10-24 โดย `fc03b5718`; บรรทัดที่มีเฉพาะของแถมตอนนี้โพสต์แล้ว ดู §3 FOC) สิ่งใหม่ตั้งแต่ 2026-09-22: **(a)** GRN สถานะ `saved` **แก้ไขได้เหมือน draft** ยกเว้นผู้ขาย `grn_date` และบรรทัดใดที่เอกสารอื่นพึ่งพาอยู่ (*stock lock*); บน BU แบบ average การแก้ไขจะโพสต์ใหม่เฉพาะบรรทัดที่เปลี่ยน (`repostGrnLedgerIfChanged`, `ledger.ts:807-873`); GRN ที่ `committed` แก้ไขได้เฉพาะฟิลด์ส่วนหัวของใบกำกับผู้ขาย และถูกตรึงเมื่อ AP invoice ที่ยังใช้งานอยู่ดึงมันไป (`good-received-note.ap-link.ts`); **(b)** `tb_good_received_note.commit_date` ถูกประทับทุกครั้งที่ย้ายไป `committed` (`updateGrnStatus`, `service.ts:3429-3445`; migration `20261016130000_grn_commit_date`); **(c)** ภายใต้ FIFO ใบรับห้ามลงวันที่ก่อนใบรับล่าสุดของสินค้าและ location เดียวกันในงวด (`GRN_DATE_BEFORE_LATEST_RECEIPT`); **(d)** ตอนนี้มีโมดูล **Accounts Payable** (`apps/micro-business/src/ap/ap-invoice`; หน้าจอ AP ของ React ยังทำงานบน mock ในเบราว์เซอร์, `routes/accounting/accounts-payable/shared/ap-mock-repository.ts`) ที่จับคู่บรรทัด GRN ที่ `committed` และ `post_type = ap` แล้วโพสต์เข้า GL — ข้อความ "ไม่มี AP / ไม่มี three-way match" ในหน้านี้เวอร์ชันก่อนถูกยกเลิก (§1, §2, ดู [AP Invoice from GRN](/th/inventory/general-ledger/ap-invoice-from-grn)); ตัว GRN เองยังไม่เขียน journal `approve()` (`POST …/approve`, `logic.ts:313-349`) เป็นจุดเข้าที่สองสำหรับการโพสต์ `saved → committed` แบบเดียวกัน การ void / reject GRN สถานะ `saved` บน BU แบบ average จะถอนการเคลื่อนไหวล่วงหน้านั้นออก (`voidGrnLedger()`, `ledger.ts:516-580`) และถูกปฏิเสธหาก lot ที่รับเข้ามาถูกใช้ไปแล้วหรือการ void จะทำให้ location ติดลบ

## 1. ภาพรวม

**ใบรับสินค้า (Goods Receive Note — GRN)** คือเอกสารที่บันทึกการรับสินค้าจริงจากผู้ขายอย่างเป็นทางการและเขียนเข้าคลังสินค้า แต่ละ GRN ประกอบด้วยส่วนหัว — เลข GRN, **วันที่รับ `grn_date` ที่บังคับกรอก** (คอลัมน์ `received_at` แยกต่างหากถูกลบโดย migration `20260907153500_drop_grn_received_at`; ตอนนี้ `grn_date` รับหน้าที่นั้นแทนและเป็น `NOT NULL`), ผู้ขาย, หมายเลขใบกำกับและวันที่, สกุลเงินและอัตราแลกเปลี่ยน, snapshot ของเงื่อนไขเครดิต, ฟิลด์ `post_type` (`ap` / `consignment` / `cash`) และส่วนหัวค่าใช้จ่ายเพิ่มเติม (extra cost) — และรายการสินค้าหนึ่งรายการขึ้นไป แต่ละบรรทัดระบุสินค้าและคลังจัดเก็บ ส่วนปริมาณ/ราคา/ภาษีจริงอยู่บนแถวเหตุการณ์รับของลูก (`tb_good_received_note_detail_item`) ทำให้หนึ่งบรรทัดครอบคลุมได้หลายเหตุการณ์การรับ (ส่งแยกรอบ, ของแถม FOC พ่วงกับของที่จ่ายเงิน) แต่ละเหตุการณ์รับมีปริมาณที่สั่งและ **`order_price`** (ราคาต่อหน่วยตาม PO, เป็น `NULL` บน GRN แบบ manual), ปริมาณที่รับและ **`received_price`** (ราคาต่อหน่วยที่รับจริง — แหล่งเดียวของสายการคำนวณเงินของบรรทัด: `sub_total_price = received_price × received_qty`, `good-received-note.pricing.ts:40-60`), ปริมาณ FOC, ส่วนลด, ภาษี และยอดรวมต่อบรรทัดที่ระบบคำนวณให้; ส่วนหัวจะรวบยอดเป็นยอด net และยอดรวมทั้งในสกุลเงินธุรกรรมและสกุลฐาน เหตุการณ์รับยังมี **`expired_at`** แบบไม่บังคับ (migration `20260731120000_add_inflow_price_expiry`) หมายเลข lot **ไม่ได้** เก็บบนแถว GRN — lot อยู่บน `tb_inventory_transaction_detail` ซึ่งตั้งแต่ migration `20260810180000_move_grn_lot_link_to_ledger` จะชี้ **กลับ** มายังเหตุการณ์รับผ่าน `tb_inventory_transaction_detail.good_received_note_detail_item_id` (เป็น Prisma `@relation` จริง, `schema.prisma:1254,1269`); ส่วนคอลัมน์เดิม `detail_item.inventory_transaction_id` ตอนนี้เก็บเพียง id ของ **ส่วนหัว** การเคลื่อนไหวและทำหน้าที่เป็นธง "โพสต์แล้ว" (schema comment ที่ `schema.prisma:1142-1143`) ดู [01-data-model.md](/th/inventory/good-receive-note/01-data-model) §2.3 และ §5

GRN เดินตามวงจรชีวิต 4 สถานะบน `enum_good_received_note_status`: `draft` (แก้ไขได้; draft ถือเลข placeholder รูปแบบ `draft-{seq}`, `good-received-note.service.ts:105,2381`) → `saved` (ผ่านการตรวจสอบแล้ว ออกเลข `grn_no` จริง **ยังแก้ไขได้** ภายใต้ข้อจำกัดใน §3 "Editing a saved GRN") → `committed` (โพสต์แล้ว; แก้ไขได้เฉพาะฟิลด์ส่วนหัวของใบกำกับผู้ขาย จนกว่า AP invoice จะดึง GRN ไป) → และ `voided` ซึ่งเข้าได้จาก `draft` หรือ `saved` เท่านั้น: GRN ที่ `committed` ถูก server ปฏิเสธ (`GRN_COMMITTED_NOT_VOIDABLE`, `service.ts:2354`) และการ void/reject GRN ใดก็ตามที่ credit note ที่ยังใช้งานอ้างถึงจะถูกปฏิเสธ (`assertGrnFreeOfCreditNotes`, `good-received-note.stock-lock.ts`) **เหตุการณ์โพสต์คือ `saved → committed`** (`GoodReceivedNoteLogic.commit()` และ `approve()` ต่างเรียก `postReceipt()`, `logic.ts:240-294`): นี่คือจุดที่เขียนแถว `tb_inventory_transaction` และ FIFO / average cost layer (`postGrnLedger()` → `InventoryTransactionService.createFromGoodReceivedNote()`) และเป็นจุดที่เพิ่มยอด junction row ของ PO ต้นทาง, `tb_purchase_order_detail.received_qty` และ `po_status` (`partial` / `completed`) (`updatePurchaseOrderReceiving()`, `logic.ts:521-562`) ข้อยกเว้นเดียวคือ **business unit แบบ average** (`average` และ `average_per_location`): ที่นั่น `save()` เขียนการเคลื่อนไหวสต๊อกไว้ก่อนแล้ว (`logic.ts:104-149`, ทำเครื่องหมาย `posted_at_save` บน `tb_inventory_transaction.info`) เพื่อให้ average ของสินค้าขยับทันทีที่รู้ว่ารับของแล้ว; commit จะพบว่าการเคลื่อนไหวมีอยู่แล้วและทำเฉพาะครึ่งที่เกี่ยวกับ PO `save()`, `commit()` และ `approve()` แต่ละอย่างจะปฏิเสธ `grn_date` ที่อยู่นอกงวดสินค้าคงคลังสถานะ `open`/`locked` (`assertDateInOpenPeriod`, `GRN_DATE_OUTSIDE_OPEN_PERIOD`, HTTP 422; `save()` เฉพาะ BU แบบ average) และบน BU แบบ FIFO ยังปฏิเสธวันที่ก่อนใบรับล่าสุดของสินค้าเดียวกันที่ location เดียวกันในงวดนั้น (`assertGrnInReceiptOrder`, `GRN_DATE_BEFORE_LATEST_RECEIPT`, HTTP 422, `receipt-date-order.helper.ts:164`) เมื่อ `committed` แล้ว การแก้ไขต้องผ่าน `tb_credit_note` กับ GRN หรือการปรับปรุงชดเชยใน [inventory-adjustment](/th/inventory/inventory-adjustment)

GRN สามารถสร้างได้จาก PO หนึ่งใบหรือมากกว่าที่ `po_status ∈ {approved, sent_or_print, partial}` (`purchase-order.service.ts:836-846`) — รองรับการรวมหลาย PO เมื่อ PO ที่เลือกมี **ผู้ขายและสกุลเงินเดียวกัน** (`from-po-content.tsx:94-97` ปฏิเสธการเลือกที่มีสกุลเงินต่างกัน; ไม่มีการตรวจสอบเงื่อนไขเครดิต) — หรือสร้างด้วยมือสำหรับการรับของที่ไม่มี PO ต้นทาง (`doc_type = manual`) ตัวเลือก PO เสนอเฉพาะสิ่งที่ผู้เรียกรับได้: backend ทำเครื่องหมาย `can_use` บนทุก PO บรรทัด และ location ปลายทางตามสิทธิ์ location ของผู้ใช้ (บรรทัดที่ไม่มี location บันทึกไว้นับว่าใช้ไม่ได้, `purchase-order.service.ts:1636-1652`) และ frontend ปิดแถวที่ `can_use === false` (`grn-po-usable.ts`) การรับของบางส่วนถือเป็นเรื่องปกติ — GRN ติดตามปริมาณที่รับเทียบกับที่สั่งต่อบรรทัด และตอน commit จะส่ง `received_qty` (และปริมาณ FOC ที่รับ) กลับไปยัง PO ต้นทาง **แก้ไข 2026-10-27:** หน้านี้เวอร์ชันก่อนระบุว่าไม่มีการบันทึกใบกำกับผู้ขาย, การโพสต์ AP หรือ three-way match ตอนนี้เอกสาร **AP Invoice** มีอยู่ใน backend แล้ว (`apps/micro-business/src/ap/ap-invoice`, ตาราง `tb_ap_invoice*`; หน้าจอ AP ของ frontend เป็น mock ที่ไม่เรียก API — ดู [AP Invoice from GRN](/th/inventory/general-ledger/ap-invoice-from-grn)): แต่ละบรรทัด AP มีแถว `tb_ap_invoice_detail_source` ชี้ไปยัง detail item ของ GRN พร้อม `matched_qty`, `grn_unit_price`, `matched_amount` และ `variance_amount`; GRN ต้นทางต้องยังใช้งานอยู่, `committed` และ `post_type = ap` และปริมาณที่จับคู่รวมทุกเอกสาร AP ที่ไม่ void ต้องไม่เกิน `received_qty` ของรายการ (`AP_GRN_NOT_COMMITTED`, `AP_GRN_OVER_MATCHED`; `ap-invoice.posting.ts:152-230,1100-1130`) การบันทึกโมดูล AP เองอยู่นอกหน้านี้ พื้นที่ `routes/accounting` ทั้งหมด (AP, `documents`) ยังเป็น **ข้อมูล mock** ที่ไม่เรียก API

## 2. บริบททางธุรกิจ

GRN คือจุดควบคุมที่โลกของจริงพบกับบัญชี: จนกว่า commit (หรือ save บน BU แบบ average) จะเกิดขึ้น PO ยังเป็นเพียง commitment เมื่อโพสต์แล้ว สต๊อกคงคลังและ cost layer จะถูกอัปเดต และ — ตอน commit — `received_qty` ของ PO ต้นทางจะเพิ่มขึ้น ธุรกิจโรงแรมมีกำไรขั้นต้นจากต้นทุนอาหารที่บางเฉียบและต้องพึ่งพาจุดตรวจนี้เพื่อจับการส่งของขาด ส่งของเกิน และการคลาดเคลื่อนของราคาก่อนที่จะกลายเป็นความผิดพลาดของคลังสินค้า ตั้งแต่ 2026-08 backend บังคับใช้การควบคุมการรับของสองอย่างของตัวเองตอน save: **เพดาน deviation** ต่อสินค้า (`tb_product.price_deviation_limit` / `qty_deviation_limit` ทั้งคู่เป็นเปอร์เซ็นต์; ควบคุมเฉพาะฝั่ง *เกิน* — การส่งขาดคือการรับบางส่วน, `good-received-note.deviation.ts:57-134`) และ **เพดานจำนวนเงิน** (ส่วนลดและภาษีต่อบรรทัดต้องไม่เกิน `received_price × received_qty`, `good-received-note.validate.ts:42-69`) การแยก `doc_type` PO/manual และสถานะล็อกหลัง commit มีอยู่เพื่อให้ทุกการรับของอธิบายได้ **แก้ไข 2026-09-22:** กฎ unique `(invoice_no, vendor_id)` ที่หน้านี้เวอร์ชันก่อนอ้างถึง **ไม่มี** constraint ใน schema และไม่มีการตรวจสอบในโค้ด — unique index เดียวบนส่วนหัวคือ `(grn_no, deleted_at)`

**การโพสต์ GL — สถานะที่แม่นยำ ณ 2026-10-27** โมดูล general ledger (`apps/micro-business/src/gl/`, ตาราง `tb_gl_jv*`, `tb_gl_balance`) ยังไม่มี hook ใน GRN: `good-received-note.*.ts`, `inventory-transaction.service.ts` และ `period-end.*` ไม่ import อะไรจาก `@/gl` และไม่มีโค้ดเขียน `enum_gl_jv_source.inventory` (`schema.prisma:4885`) สิ่งที่เปลี่ยนคือโมดูล **AP Invoice** และ **AP Payment** ตอนนี้โพสต์ journal เข้า GL ด้วย `source = ap` (`ap-invoice.posting.ts:291`, `ap-payment.posting.ts:228`) — นี่คือวิธีที่ GRN ที่รับแล้วไปถึง ledger: GRN `committed` → AP invoice ที่จับคู่กับมัน → การโพสต์ AP **external accounting-export API** แบบอ่านอย่างเดียวที่แยกต่างหาก (`inventory/accounting-export`, `GET /api/ext/v1/ap-invoices`) เผยแพร่ GRN ที่ `committed` (รวมถึงที่ void แล้วแต่เคยโพสต์) และ credit note เป็นเอกสาร vendor-invoice สำหรับระบบบัญชีภายนอก โดยข้าม GRN ที่ `post_type = consignment` และบรรทัดที่ location แบบ consignment (`export-core.service.ts:194-228`, `builders/grn.ap-builder.ts`) enum `post_type` ของส่วนหัว (`ap` | `consignment` | `cash`, ค่าเริ่มต้น `ap`) จึงมีผู้ใช้สองราย — คุณสมบัติสำหรับ AP invoice (เฉพาะ `post_type = ap`) และตัวกรอง export — แต่ยังไม่เปลี่ยนอะไรภายในโมดูล GRN เอง; `enum_transaction_type` ยัง resolve การรับ GRN ทุกรายการเป็นค่าเดียวคือ `good_received_note`

ความปลอดภัยของอาหารและการควบคุมคุณภาพ: การรับของทุกรายการที่โพสต์แล้วจะได้หมายเลข lot และวันหมดอายุแบบไม่บังคับ **แก้ไข 2026-09-22:** หมายเลข lot ถูกสร้างโดย `buildLotNo()` (`apps/micro-business/src/common/helpers/lot-number.helper.ts:27-35`) ในรูปแบบ **`<location_code><YYMM><ลำดับ 4 หลัก>`** — เช่น `MK-0126070246` — โดยเลขลำดับคือ `lot_seq_no` ของ cost layer ซึ่งเริ่มนับใหม่ที่ 1 ในทุกงวดสินค้าคงคลัง (`getNextLotSeqNo`, `common/helpers/lot-seq-no.helper.ts` — เลขลำดับถัดไปคือ `lot_seq_no` สูงสุดของงวด **รวม layer ที่ soft-delete** ดังนั้นการ void GRN จึงไม่ออกเลข lot ซ้ำ) รูปแบบเดิม `RC{YY}{MM}{seq}` ไม่มีอยู่แล้ว และไม่มีการเขียนทับหมายเลข lot ด้วยมือบนหน้าจอ GRN วันหมดอายุถูกเก็บบนเหตุการณ์รับ (`tb_good_received_note_detail_item.expired_at`, nullable, จงใจไม่ตรวจสอบเทียบกับ `grn_date` เพื่อให้ยังรับสินค้าใกล้หมดอายุหรือหมดอายุแล้วได้ — schema comment ที่ `schema.prisma:1196`) ไม่มีประตู "quality hold" ต่อบรรทัด, ฟิลด์ `accepted_qty` หรือกลไก accept/reject — ความคลาดเคลื่อนในการรับของถูกจัดการด้วยการกรอก `received_qty` ให้น้อยกว่าปริมาณที่สั่ง ความคลาดเคลื่อนของราคาถูกตรวจสอบเทียบกับ **ราคา PO** (`order_price` เทียบ `received_price` โดย normalise เป็นหน่วยฐาน) ไม่ใช่เทียบกับ vendor pricelist; ไม่มีการค้น pricelist ภายในโมดูล GRN

## 3. แนวคิดสำคัญ

- **Receiving Lot**: หมายเลข lot ที่กำหนดตอนโพสต์บน inventory ledger (ไม่ใช่บนแถว GRN) สร้างในรูปแบบ `<location_code><YYMM><ลำดับ 4 หลัก>` โดย `buildLotNo()` (`common/helpers/lot-number.helper.ts`); เลขลำดับคือ `lot_seq_no` ที่นับตามงวด (นับ layer ที่ soft-delete ด้วย) แถว ledger (`tb_inventory_transaction_detail`) ถือ `good_received_note_detail_item_id` ชี้กลับไปยังเหตุการณ์รับ ทำให้ FIFO consumption และการสืบย้อน recall resolve ไปยังบรรทัด GRN ต้นทางได้ **แก้ไข 2026-09-22:** รูปแบบไม่ใช่ `RC{YY}{MM}{seq}`, ตั้งค่าไม่ได้ และไม่มีการเขียนทับด้วยมือ
- **Partial Receipt**: GRN ที่ทำให้ PO ที่ค้างอยู่สำเร็จเพียงบางส่วน ปริมาณที่รับสามารถน้อยกว่าที่สั่งได้ และตอน commit PO ต้นทางจะเคลื่อนไปที่ `partial` (หรือ `completed` เมื่อทุกบรรทัดที่ active เข้าเงื่อนไข `received_qty ≥ order_qty − cancelled_qty`, `updatePoStatuses`, `logic.ts:564-590`) สามารถออก GRN หลายใบกับ PO เดียวกันได้จนกว่าจะครบ
- **Over/Under Receipt**: การรับขาดไม่มีวันไม่ผ่านการตรวจสอบ (`percentOverage` ให้คะแนน 0, `deviation.ts:62-63`) การรับเกินถูกควบคุมด้วย `qty_deviation_limit` ของสินค้า (เปอร์เซ็นต์ที่เกิน `order_base_qty`; `0`/`NULL` = ไม่มีเพดาน) และราคาเกินด้วย `price_deviation_limit` (เปอร์เซ็นต์ที่เกิน `order_price` ต่อหน่วยฐาน) — ทั้งคู่ประเมินตอน **save** และผ่าน `POST …/verify` ด้วย `verify_state = save` และทั้งคู่ปฏิเสธ **ทั้งเอกสาร** (`GRN_DEVIATION_LIMIT_EXCEEDED`, HTTP 400) ไม่มีการตั้งค่า "over-receipt tolerance" ระดับ tenant; เพดานอยู่ที่ product master ต่อสินค้า
- **Save (`draft → saved`)**: รัน checklist ของการ save (`findGoodReceivedNoteSaveIssues`, `validate.ts:91-103`: ต้องเป็น `draft`; แล้วกฎเนื้อหาที่ใช้ร่วมกับการแก้ไขภายหลัง — เพดาน deviation; ส่วนลด/ภาษี ≤ มูลค่าบรรทัด, `validate.ts:116-130`), ใช้เลข running จริง (`assignRunningGrnNo`, `service.ts:2400-2418`), ประทับ `received_by_*` ถ้ายังว่าง และ — **เฉพาะบน business unit แบบ average** (`average`, `average_per_location`) — โพสต์การเคลื่อนไหวสต๊อกล่วงหน้าพร้อม `posted_at_save = true` บนส่วนหัวการเคลื่อนไหว (เว้นแต่ใบรับลงวันที่ในงวดที่ใหม่กว่างวดปัจจุบัน ซึ่งจะรอการยกยอดของงวดนั้น — `isHeldUntilBroughtForward`) BU แบบ FIFO: ไม่กระทบสต๊อก PO ไม่ถูกแตะตอน save เลย
- **Editing a saved GRN** (เปลี่ยน 2026-10-24, `fc03b5718`, ก่อนหน้านั้น `a2218e077`): `PATCH` บน GRN สถานะ `saved` ทำได้ (`checkGrnUpdateAllowed`, `good-received-note.ap-link.ts:122`) โดยปฏิเสธ (i) การเปลี่ยน `doc_status` ใด ๆ (`GRN_STATUS_CHANGE_NOT_ALLOWED` — สถานะเปลี่ยนได้ผ่าน save / commit / void / approve / reject เท่านั้น), (ii) การเปลี่ยน `vendor_id` หรือ `grn_date` (`GRN_SAVED_IDENTITY_LOCKED`, HTTP 400) และ (iii) การเปลี่ยนบรรทัดที่เอกสารอื่นพึ่งพา — `lot` ของมันถูก issue ดึงไปแล้ว, หรือมี credit note ที่ยังใช้งานอ้างถึงสินค้าที่ location นั้น, หรือการเคลื่อนไหวของใบรับเป็นแบบ legacy ที่การแก้ไขโพสต์ใหม่ไม่ได้ (`legacy_posting`) (`GRN_LINE_STOCK_LOCKED`, HTTP 409; และ `GRN_COST_STOCK_LOCKED`, HTTP 409 สำหรับการเปลี่ยน extra cost / สกุลเงิน / อัตราแลกเปลี่ยนขณะที่มีบรรทัดใดถูกล็อก) — ผ่าน `findGrnStockLocks()` (`good-received-note.stock-lock.ts:186`) / `assertStockLocksHeld()` (`:281`) กฎเนื้อหาที่ save บังคับจะถูกรันซ้ำบนเอกสารที่แก้ไข และบน BU แบบ average `repostGrnLedgerIfChanged()` จะ retire แถว ledger ของบรรทัดที่เปลี่ยน (เก็บไว้ใต้ header ที่สร้างมาแบบ void แล้ว, `info.revised_from`) และโพสต์เฉพาะบรรทัดเหล่านั้นใหม่; บรรทัดที่ไม่เปลี่ยนคงเลข lot เดิม response รายละเอียดมี `has_stock_lock` และ `stock_lock_reasons` ต่อบรรทัด (`stock_consumed`, `credit_note`, `legacy_posting`) ซึ่ง frontend แปลงเป็นแถวที่ถูกล็อก (`grn-form.tsx:52-61`) ฝั่ง frontend: input ผู้ขายและวันที่ถูกปิดบน `saved`, สกุลเงิน / อัตราแลกเปลี่ยน / extra cost ล็อกทั้งเอกสารเมื่อมีบรรทัดใดถูกล็อก, ไม่มีปุ่ม *Save draft* และไม่มี Delete (backend ลบได้เฉพาะ `draft`) และ Save ส่งเฉพาะ `PATCH` (`grn-header.tsx:56-67,150-179`)
- **Editing a committed GRN**: เปลี่ยนได้เฉพาะ `post_type`, ฟิลด์ credit-term, `invoice_no`, `invoice_date`, `invoice_f`, `payment_due_date`, `description` และ `note` (`HEADER_EDITABLE_KEYS`, `ap-link.ts:19-33`; อย่างอื่น → `GRN_COMMITTED_HEADER_ONLY`) เมื่อ AP invoice ที่ไม่ void ใดมีบรรทัดที่มาจาก GRN แม้แต่นั้นก็ถูกปฏิเสธ (`GRN_AP_LINKED_NOT_EDITABLE` ซึ่งระบุเลขเอกสาร AP); response รายละเอียดแสดงรายการใน `ap_invoices` และ frontend แสดงปุ่ม *Edit* ที่ปิดพร้อมเหตุผล (`grn-header.tsx:60-65,167-175`) GRN ที่ `voided` แก้ไขไม่ได้เสมอ (`GRN_VOIDED_NOT_EDITABLE`)
- **Commit (`saved → committed`) — เหตุการณ์โพสต์**: `commit()` / `approve()` ตรวจกฎงวดเปิดบน `grn_date` อีกครั้ง (และบน FIFO ตรวจกฎลำดับการรับ) แล้ว `postReceipt()`: (1) เขียนส่วนหัว `tb_inventory_transaction` + `tb_inventory_transaction_detail` หนึ่งแถวและ cost layer ต่อเหตุการณ์รับที่เคลื่อนสต๊อก — เว้นแต่เขียนไปแล้วตอน save; (2) เพิ่ม `received_qty` และปริมาณ FOC ที่รับบน junction row ของ PO↔PR และ `tb_purchase_order_detail.received_qty` แล้วคำนวณ `po_status` ใหม่; (3) ประทับ `po_receiving_applied` บนส่วนหัวการเคลื่อนไหวเพื่อให้การ commit ซ้ำไม่นับซ้อน; การอัปเดตสถานะยังประทับ `commit_date` ด้วย (`service.ts:3441`) frontend ให้ commit **draft** ได้ในคลิกเดียว — ไล่เรียก `PATCH → /save → /commit` (`use-grn-form-actions.ts:550-565`) และหาก `grn_date` อยู่นอกงวดเปิดปัจจุบัน จะถามว่าจะคงวันที่เดิมหรือย้ายไปวันแรกของงวด (`PeriodDateChoice`, `components/share/period-date-choice.tsx`) ไม่มี batch commit และไม่มี auto-commit ตามกำหนดเวลา
- **Extra Cost Allocation — ยืนยันแล้วว่าใช้งานจริง (2026-09-10, commit `f8cd9f0d9`)**: `allocate_extra_cost_type` ของส่วนหัว extra cost ขับการแบ่งจริงใน `allocateExtraCost()` (`good-received-note.extra-cost.ts:40-61`) ตอนโพสต์: **`by_qty` = แบ่งยอดรวมเป็นส่วนเท่า ๆ กัน หนึ่งส่วนต่อบรรทัดที่นำสต๊อกเข้าคลัง**; **`by_value` = ถ่วงน้ำหนักตามปริมาณสต๊อกของแต่ละบรรทัด (`received_base_qty + foc_base_qty`)**; **`manual` = ไม่จัดสรรอะไรเลย** (ยังไม่มีฟิลด์กรอกต่อบรรทัด) ส่วนแบ่งถูกแปลงเป็นสกุลฐานและบวกเข้า landed cost ของบรรทัด (`stockCostOf() = base_net_amount + base_extra_cost_amount`, `inventory-transaction.service.ts:109-111`) และบันทึกบน cost layer ทุกชั้นเป็น `extra_cost_amount` (migration `20260910130000_add_cost_layer_extra_cost`) หมายเหตุว่าชื่อสวนทางกับความรู้สึก — `by_value` ถ่วงตามปริมาณ ส่วน `by_qty` แบ่งเท่ากัน — ให้บันทึกตามที่โค้ดทำ frontend เสนอเฉพาะ `by_qty` และ `by_value` (`grn-extra-cost-fields.tsx:201-202`) ไม่มีโหมด `by_weight` / `by_volume`
- **FOC (Free of Charge)**: `foc_qty` อยู่บนเหตุการณ์รับเดียวกับปริมาณที่จ่ายเงิน **FOC เข้าสต๊อก**: ปริมาณที่โพสต์คือ `received_base_qty + foc_base_qty` (`stockQtyOf()`, `inventory-transaction.service.ts:92-94`) ดังนั้นต้นทุนต่อหน่วยที่เขียนลง ledger จะถูกเจือจาง (`(base_net_amount + extra cost) / (received + FOC)` ปัดเป็น 2 ตำแหน่ง) **บรรทัดที่เป็น FOC ล้วน (ปริมาณที่จ่ายเป็น 0) โพสต์เข้าสต๊อกที่ต้นทุนสินค้าศูนย์** (บวกส่วนแบ่ง extra cost ถ้ามี) และเพิ่มตัวนับ FOC ที่รับของ PO (`logic.ts:530-535`) **แก้ไข 2026-10-27 (ข้อค้นพบของรอบก่อนถูกแก้แล้ว):** ฉบับ 2026-09-22 ของข้อนี้ระบุว่า `createFromGoodReceivedNote` ตัดรายการที่ `received_base_qty = 0` ออกก่อน ทำให้ *เอกสาร* ที่เป็น FOC ล้วน commit โดยไม่เขียนการเคลื่อนไหวแต่ยังเพิ่มตัวนับ FOC ของ PO `fc03b5718` (2026-10-24) เปลี่ยนตัวกรองเป็น `stockQtyOf(item) > 0` (`inventory-transaction.service.ts:927`; `isPostableReceipt()`, `ledger.ts:209-211`) เอกสาร FOC ล้วนจึงโพสต์แล้ว เอกสารที่ไม่มีปริมาณสต๊อกเลยยังไม่เขียนการเคลื่อนไหว (`createFromGoodReceivedNote` log warning และคืน `null`, `:929-939`)
- **`post_type` (ap / consignment / cash)**: enum ระดับส่วนหัว (`enum_good_received_note_post_type`, ค่าเริ่มต้น `ap`) ที่มาแทน boolean คู่ `is_consignment` / `is_cash` เดิม — สองฟิลด์นั้นไม่มีอยู่ใน schema แล้ว **แก้ไขได้บน GRN ที่ committed** (เป็นหนึ่งในฟิลด์ส่วนหัวของใบกำกับผู้ขาย) ภายในโมดูล GRN มันยังไม่เปลี่ยนอะไร (ประเภทการเคลื่อนไหวเดียวกัน ไม่มีการโพสต์ที่แตกต่าง) แต่มีผู้ใช้สองรายนอกโมดูลที่อ่านมัน: AP invoice จับคู่ได้เฉพาะ GRN ที่ `post_type = ap` (`ap-invoice.posting.ts:1118-1122`) และ external accounting export ข้าม GRN แบบ `consignment` (`export-core.service.ts:228`) `enum_transaction_type` (enum ประเภทของ ledger คงคลัง) ไม่มีสมาชิก "Stock In" / "Consignment In" / "Non-Inventory" — การรับ GRN จะโพสต์เป็นค่าเดียวคือ `good_received_note` เสมอ

## 4. บทบาทและ Persona

| Role | ความรับผิดชอบ |
|------|----------------|
| Store Keeper / Receiving Clerk | รับการส่งของจริงที่ dock นับสินค้าเทียบกับ PO และใบส่งของของผู้ขาย สร้าง GRN ในสถานะ `draft` (draft สามารถเก็บแบบไม่ครบได้ — ปุ่ม Save-draft ข้ามการ validate ฟอร์ม, `use-grn-form-actions.ts:425-440`) แนบใบส่งสินค้า บันทึกปริมาณที่รับต่อบรรทัด และ save (`draft → saved`: ตรวจสอบ ออกเลข GRN และโพสต์สต๊อกล่วงหน้าเฉพาะบน BU แบบ average เท่านั้น) |
| Store Manager / Inventory Manager | ตรวจสอบ GRN สถานะ `saved` และ commit (`saved → committed`) — ขั้นตอนที่โพสต์สต๊อก (BU แบบ FIFO) และเพิ่มยอด PO การที่คนเดียวกันจะทำทั้งสองขั้นได้หรือไม่เป็นเรื่องของสิทธิ์: gateway ใช้ guard key **เดียวกัน** ปกป้องทั้ง save และ commit (`AppIdGuard('goodReceivedNote.commit')` บนทั้ง `PATCH …/save` และ `PATCH …/commit`, `good-received-notes.controller.ts:1375,1632`) และ permission key ฝั่ง frontend คือ `procurement.goods_received_note.commit` (`constant/permissions.ts:89`) ไม่มีการตรวจสอบตามชื่อ role |
| Purchaser / Procurement Officer | เป็นเจ้าของ PO ต้นทางที่ GRN ถูกสร้างขึ้นมาเทียบด้วย ตรวจสอบข้อมูลการรับของสำหรับ PO ที่ตนออก และประสานกับผู้ขายเมื่อมีความคลาดเคลื่อน (ส่งขาด ผิดสินค้า) |
| Department Manager | ตรวจสอบ GRN ที่กระทบ cost-centre ของแผนก และยืนยันว่าสินค้าที่รับตรงกับที่สั่งสำหรับแผนก |
| System Administrator | ดูแล RBAC และการกำหนดลำดับ running-code (เลข GRN), รหัสภาษี และอัตราแลกเปลี่ยน; ดูแลการเชื่อมต่อกับโมดูล PO และ Inventory **ยังไม่ยืนยัน:** ไม่พบ "GRN configuration console" เฉพาะทาง (ตัวแก้ไขรูปแบบเลข lot, panel endpoint การเชื่อมต่อ) ในซอร์สปัจจุบัน — หน้าจอตั้งค่าภาษี สกุลเงิน และ running-code เป็นหน้าจอทั่วไปข้ามโมดูล ตามที่บันทึกไว้ใน [system-config](/th/inventory/system-config) และ [master-data](/th/inventory/master-data) ไม่ใช่ workspace เฉพาะของ GRN |

**Finance / AP persona — ตรวจซ้ำ 2026-10-27** บทบาท "Finance Team / AP Clerk" ที่ทำ three-way match จากโมดูล GRN ยังไม่ใช่หน้าจอหรือ role ของ GRN (`enum_stage_role` ไม่มีสมาชิก `finance`; หน้าจอ GRN ไม่มี action match หรือ journal) สิ่งที่มีตอนนี้คือพื้นที่ **Accounts Payable** แยกต่างหาก (`routes/accounting/accounts-payable`, backend `apps/micro-business/src/ap/`) ที่ AP clerk สร้าง AP invoice จากบรรทัด GRN ที่ `committed` และ `post_type = ap` (`ap-invoice.posting.ts:152-230`) — บันทึกไว้นอกโมดูลนี้ จากฝั่ง GRN ผลเพียงอย่างเดียวคือการตรึงเอกสารที่ committed ตามที่อธิบายใน §3 "Editing a committed GRN"

## 5. โมดูลที่เกี่ยวข้อง

**กระแสข้ามโมดูล:**
- [purchase-order](/th/inventory/purchase-order) — GRN ถูกสร้างจาก PO ที่สถานะ `approved` / `sent_or_print` / `partial`; commit เพิ่ม `received_qty` และ `po_status` ของ PO
- [inventory](/th/inventory/inventory) — commit (หรือ save บน BU แบบ average) โพสต์การเคลื่อนไหวสต๊อกเข้า; `GET …/good-received-notes/:id/stock-movements` (2026-08, `service.ts:2177`) คืน lot ที่โพสต์แล้วต่อบรรทัด และแท็บ Stock Movement บน frontend จะแสดงเฉพาะเมื่อ GRN เป็น `committed` แล้ว (`grnStockVisible()`, `grn-stock-table.tsx:35-45` — **committed หรือ `saved` บน BU ที่ใช้วิธี `average` / `average_per_location`** ซึ่งการเคลื่อนไหวมีอยู่แล้ว; ใบรับที่ถูกถือไว้ของงวดถัดไปจะกลับมาพร้อม `is_posted: false`)
- [costing](/th/inventory/costing) — landed cost ต่อบรรทัด (net + extra cost ที่จัดสรร หารด้วยปริมาณรับ + FOC) ป้อนเข้า FIFO lot record หรือ average ของสินค้า / ต่อ location (`average` เทียบ `average_per_location`); `GET …/cost/products/:product_id/last-receiving/unit/:unit_id` และ `…/last-cost` (Bruno `_uncategorized/cost/`) อ่านราคา GRN ล่าสุดกลับมา
- [vendor-pricelist](/th/inventory/vendor-pricelist) — **ไม่มีการเชื่อมต่อฝั่ง GRN**; price deviation ตรวจสอบเทียบกับ `order_price` ของ PO ไม่ใช่ pricelist
- [purchase-order/credit-note](/th/inventory/purchase-order/credit-note) — `GET …/good-received-notes/vendor/:vendor_id/cn` แสดง GRN สถานะ `saved`/`committed` ที่ยังมีสินค้าอย่างน้อยหนึ่งรายการที่ยังไม่ถูกออก credit note; ตั้งแต่ 2026-09-21 สินค้าหนึ่งรายการบน GRN ใบหนึ่งออก credit note ได้เพียงครั้งเดียว (`findFullyCreditedGrnIds`, `service.ts:561-617`)

**การตั้งค่า Master:**
- [master-data/vendor](/th/inventory/master-data/vendor) — vendor master ที่อ้างอิงโดยส่วนหัว GRN
- [master-data/currency](/th/inventory/master-data/currency) — สกุลธุรกรรมและอัตราแลกเปลี่ยนสำหรับการรับของที่ dual-post
- [master-data/tax-profile](/th/inventory/master-data/tax-profile) — รหัสภาษีที่ใช้กับบรรทัด GRN
- [master-data/credit-term](/th/inventory/master-data/credit-term) — เงื่อนไขการชำระเงินที่ copy จาก vendor master ลง GRN
- [master-data/extra-cost-type](/th/inventory/master-data/extra-cost-type) — ส่วนประกอบ landed cost (freight, duties, handling) ที่จัดสรรข้ามบรรทัด
- [master-data/delivery-point](/th/inventory/master-data/delivery-point) — สถานที่รับของที่สินค้าได้รับการรับจริง
- [master-data/unit](/th/inventory/master-data/unit) — หน่วยนับสำหรับปริมาณที่รับ
- [master-data/location](/th/inventory/master-data/location) — สถานที่จัดเก็บที่แต่ละบรรทัดเขียนการเคลื่อนไหวสต๊อกเข้า
- [system-config/workflow](/th/inventory/system-config/workflow) — workflow อนุมัติ / commit สำหรับการอนุญาต GRN
- [system-config/period](/th/inventory/system-config/period) — ประตูงวดสินค้าคงคลังสำหรับการโพสต์ GRN (`tb_inventory_period` เปลี่ยนชื่อจาก `tb_period` เมื่อ 2026-09-16; `grn_date` ต้องอยู่ในงวดสถานะ `open` หรือ `locked` ตอน create-verify, save (BU แบบ average), commit และ approve)
- [system-config/running-code](/th/inventory/system-config/running-code) — การกำหนดลำดับหมายเลขเอกสาร GRN
- [reporting-audit/activity](/th/inventory/reporting-audit/activity) — บันทึกการเปลี่ยนสถานะและการแก้ไข GRN สำหรับ audit
- [reporting-audit/attachment](/th/inventory/reporting-audit/attachment) — ใบส่งสินค้า ใบส่งของ และหลักฐานคุณภาพที่แนบกับแต่ละ GRN
