# ใบรับสินค้า (Goods Receive Note)

> **At a Glance**
> **วัตถุประสงค์ของโมดูล:** บันทึกการรับสินค้าจริงตามใบ PO โพสต์การเคลื่อนไหวสต๊อกเข้า และอัปเดต costing แบบ FIFO / average (`draft` → `saved` → `committed` หรือ `voided`) &nbsp;·&nbsp; **ผู้ใช้:** Store Keeper / Receiver, Inventory Manager, Purchaser &nbsp;·&nbsp; **เอนทิตี/ตารางหลัก:** `tb_good_received_note`, `tb_good_received_note_detail`, `tb_good_received_note_detail_item`, `tb_inventory_transaction`, FIFO / average-cost layers &nbsp;·&nbsp; **หน้าย่อย:** 13
>
> **ตรวจสอบซ้ำ 2026-09-22 กับ `carmen-turborepo-backend-v2` HEAD — โมเดลการโพสต์เปลี่ยนอีกครั้ง** รอบตรวจสอบ 2026-07-15 พบว่า `save()` โพสต์สต๊อกและ `commit()` เพียงล็อกเอกสาร ซึ่งถูกต้อง ณ ตอนนั้น แต่ **ไม่ใช่** สิ่งที่โค้ดทำอีกต่อไป commit `c815d67ce` ("ย้ายการลงสต๊อกจาก save() ไป commit()") ย้ายการโพสต์สต๊อก **และ** การเพิ่ม `received_qty` ของ PO ไปไว้ที่ **`commit()`** (`saved → committed`, `good-received-note.logic.ts:165-203` → `postReceipt()` `:228-270`) จากนั้น commit `7d6556dd0` เปิดข้อยกเว้นหนึ่งข้อกลับมา: บน business unit ที่ `calculation_method = average` **`save()` จะโพสต์การเคลื่อนไหวสต๊อกล่วงหน้า** (`postsInventoryAtSave()` ใน `good-received-note.ledger.ts:49-51` เรียกจาก `logic.ts:105-143`) เพื่อให้การเบิกจ่ายที่เกิดขึ้นระหว่างที่ GRN รออยู่ในสถานะ `saved` ถูกตีมูลค่าด้วย average ใหม่; ส่วน PO ยังคงถูกเพิ่มยอดเฉพาะตอน commit เท่านั้น ภายใต้ **FIFO** ไม่มีอะไรแตะสต๊อกจนกว่าจะ commit `approve()` (`POST …/approve`, `logic.ts:289-320`) เป็นจุดเข้าที่สองสำหรับการโพสต์ `saved → committed` แบบเดียวกัน การ void / reject GRN สถานะ `saved` บน BU แบบ average ตอนนี้ **จะ** ถอนการเคลื่อนไหวล่วงหน้านั้นออก (`voidGrnLedger()`, `ledger.ts:298-377`) และจะถูกปฏิเสธหาก lot ที่รับเข้ามาถูกใช้ไปแล้ว ข้อสรุป 2026-07-15 เรื่อง three-way match และการโพสต์ AP ยังคงใช้ได้กับโมดูลนี้: ไม่มีโค้ดบันทึกใบกำกับผู้ขายหรือ AP journal สิ่งใหม่คือ **โมดูล general ledger** (`apps/micro-business/src/gl/`, gateway `application/gl-posting`, `gl-jv`) — โพสต์เฉพาะ journal voucher แบบ manual / template / reversal / closing เท่านั้น; **ไม่มีส่วนใดในโค้ด GRN, inventory-transaction หรือ period-end เรียกใช้มัน** (ดู §2)

## 1. ภาพรวม

**ใบรับสินค้า (Goods Receive Note — GRN)** คือเอกสารที่บันทึกการรับสินค้าจริงจากผู้ขายอย่างเป็นทางการและเขียนเข้าคลังสินค้า แต่ละ GRN ประกอบด้วยส่วนหัว — เลข GRN, **วันที่รับ `grn_date` ที่บังคับกรอก** (คอลัมน์ `received_at` แยกต่างหากถูกลบโดย migration `20260907153500_drop_grn_received_at`; ตอนนี้ `grn_date` รับหน้าที่นั้นแทนและเป็น `NOT NULL`), ผู้ขาย, หมายเลขใบกำกับและวันที่, สกุลเงินและอัตราแลกเปลี่ยน, snapshot ของเงื่อนไขเครดิต, ฟิลด์ `post_type` (`ap` / `consignment` / `cash`) และส่วนหัวค่าใช้จ่ายเพิ่มเติม (extra cost) — และรายการสินค้าหนึ่งรายการขึ้นไป แต่ละบรรทัดระบุสินค้าและคลังจัดเก็บ ส่วนปริมาณ/ราคา/ภาษีจริงอยู่บนแถวเหตุการณ์รับของลูก (`tb_good_received_note_detail_item`) ทำให้หนึ่งบรรทัดครอบคลุมได้หลายเหตุการณ์การรับ (ส่งแยกรอบ, ของแถม FOC พ่วงกับของที่จ่ายเงิน) แต่ละเหตุการณ์รับมีปริมาณที่สั่งและ **`order_price`** (ราคาต่อหน่วยตาม PO, เป็น `NULL` บน GRN แบบ manual), ปริมาณที่รับและ **`received_price`** (ราคาต่อหน่วยที่รับจริง — แหล่งเดียวของสายการคำนวณเงินของบรรทัด: `sub_total_price = received_price × received_qty`, `good-received-note.pricing.ts:40-60`), ปริมาณ FOC, ส่วนลด, ภาษี และยอดรวมต่อบรรทัดที่ระบบคำนวณให้; ส่วนหัวจะรวบยอดเป็นยอด net และยอดรวมทั้งในสกุลเงินธุรกรรมและสกุลฐาน เหตุการณ์รับยังมี **`expired_at`** แบบไม่บังคับ (migration `20260731120000_add_inflow_price_expiry`) หมายเลข lot **ไม่ได้** เก็บบนแถว GRN — lot อยู่บน `tb_inventory_transaction_detail` ซึ่งตั้งแต่ migration `20260810180000_move_grn_lot_link_to_ledger` จะชี้ **กลับ** มายังเหตุการณ์รับผ่าน `tb_inventory_transaction_detail.good_received_note_detail_item_id` (เป็น Prisma `@relation` จริง, `schema.prisma:1135,1150`); ส่วนคอลัมน์เดิม `detail_item.inventory_transaction_id` ตอนนี้เก็บเพียง id ของ **ส่วนหัว** การเคลื่อนไหวและทำหน้าที่เป็นธง "โพสต์แล้ว" (schema comment ที่ `:1022-1024`) ดู [01-data-model.md](/th/inventory/good-receive-note/01-data-model) §2.3 และ §5

GRN เดินตามวงจรชีวิต 4 สถานะบน `enum_good_received_note_status`: `draft` (แก้ไขได้; draft ถือเลข placeholder รูปแบบ `draft-{seq}`, `good-received-note.service.ts:90,2333-2339`) → `saved` (ผ่านการตรวจสอบแล้ว ออกเลข `grn_no` จริง และล็อกการแก้ไขบน UI) → `committed` (โพสต์แล้วและล็อก) ส่วน `voided` เข้าได้จาก `draft` หรือ `saved`; GRN ที่ `committed` แล้วตอนนี้ถูก server ปฏิเสธเอง (`GRN_COMMITTED_NOT_VOIDABLE`, `service.ts:2254-2256`) **เหตุการณ์โพสต์คือ `saved → committed`** (`GoodReceivedNoteLogic.commit()` และ `approve()` ต่างเรียก `postReceipt()`, `logic.ts:228-270`): นี่คือจุดที่เขียนแถว `tb_inventory_transaction` และ FIFO / average cost layer (`postGrnLedger()` → `InventoryTransactionService.createFromGoodReceivedNote()`) และเป็นจุดที่เพิ่มยอด junction row ของ PO ต้นทาง, `tb_purchase_order_detail.received_qty` และ `po_status` (`partial` / `completed`) (`updatePurchaseOrderReceiving()`, `logic.ts:500-570`) ข้อยกเว้นเดียวคือ **business unit แบบ average**: ที่นั่น `save()` เขียนการเคลื่อนไหวสต๊อกไว้ก่อนแล้ว (`logic.ts:105-143`, ทำเครื่องหมาย `posted_at_save` บน `tb_inventory_transaction.info`) เพื่อให้ average ของสินค้าขยับทันทีที่รู้ว่ารับของแล้ว; commit จะพบว่าการเคลื่อนไหวมีอยู่แล้วและทำเฉพาะครึ่งที่เกี่ยวกับ PO ทั้ง `save()` (BU แบบ average), `commit()` และ `approve()` จะปฏิเสธ `grn_date` ที่อยู่นอกงวดสินค้าคงคลังสถานะ `open`/`locked` (`assertDateInOpenPeriod`, `GRN_DATE_OUTSIDE_OPEN_PERIOD`, HTTP 422) เมื่อ `committed` แล้ว การแก้ไขต้องผ่าน `tb_credit_note` กับ GRN หรือการปรับปรุงชดเชยใน [inventory-adjustment](/th/inventory/inventory-adjustment)

GRN สามารถสร้างได้จาก PO หนึ่งใบหรือมากกว่าที่ `po_status ∈ {approved, sent_or_print, partial}` (`purchase-order.service.ts:811-816`; enum ของ PO ถูกแยกเมื่อ 2026-09-14 — `sent` กลายเป็น `sent_or_print` และมีค่าใหม่ `approved` นำหน้า) — รองรับการรวมหลาย PO เมื่อ PO ที่เลือกมี **ผู้ขายและสกุลเงินเดียวกัน** (`from-po-content.tsx:93-95` ปฏิเสธการเลือกที่มีสกุลเงินต่างกัน; ไม่มีการตรวจสอบเงื่อนไขเครดิต) — หรือสร้างด้วยมือสำหรับการรับของที่ไม่มี PO ต้นทาง (`doc_type = manual`) การรับของบางส่วนถือเป็นเรื่องปกติ — GRN ติดตามปริมาณที่รับเทียบกับที่สั่งต่อบรรทัด และตอน commit จะส่ง `received_qty` (และปริมาณ FOC ที่รับ) กลับไปยัง PO ต้นทาง **ยังไม่พบ (ตรวจซ้ำ 2026-09-22):** ไม่มีการบันทึกใบกำกับผู้ขาย, การโพสต์ AP journal หรือ three-way match (PO ↔ GRN ↔ invoice) ใน frontend หรือ backend; ส่วน `routes/accounting` ที่เพิ่มใน frontend เมื่อ 2026-07-31 แสดง **แถว mock** ที่สร้างใน `routes/accounting/accounting-documents.ts` (`documentsFor()` ปั้นแถวขึ้นมา 8 แถวต่อประเภทเอกสาร) และไม่เรียก API ใดเลย

## 2. บริบททางธุรกิจ

GRN คือจุดควบคุมที่โลกของจริงพบกับบัญชี: จนกว่า commit (หรือ save บน BU แบบ average) จะเกิดขึ้น PO ยังเป็นเพียง commitment เมื่อโพสต์แล้ว สต๊อกคงคลังและ cost layer จะถูกอัปเดต และ — ตอน commit — `received_qty` ของ PO ต้นทางจะเพิ่มขึ้น ธุรกิจโรงแรมมีกำไรขั้นต้นจากต้นทุนอาหารที่บางเฉียบและต้องพึ่งพาจุดตรวจนี้เพื่อจับการส่งของขาด ส่งของเกิน และการคลาดเคลื่อนของราคาก่อนที่จะกลายเป็นความผิดพลาดของคลังสินค้า ตั้งแต่ 2026-08 backend บังคับใช้การควบคุมการรับของสองอย่างของตัวเองตอน save: **เพดาน deviation** ต่อสินค้า (`tb_product.price_deviation_limit` / `qty_deviation_limit` ทั้งคู่เป็นเปอร์เซ็นต์; ควบคุมเฉพาะฝั่ง *เกิน* — การส่งขาดคือการรับบางส่วน, `good-received-note.deviation.ts:57-134`) และ **เพดานจำนวนเงิน** (ส่วนลดและภาษีต่อบรรทัดต้องไม่เกิน `received_price × received_qty`, `good-received-note.validate.ts:22-61`) การแยก `doc_type` PO/manual และสถานะล็อกหลัง commit มีอยู่เพื่อให้ทุกการรับของอธิบายได้ **แก้ไข 2026-09-22:** กฎ unique `(invoice_no, vendor_id)` ที่หน้านี้เวอร์ชันก่อนอ้างถึง **ไม่มี** constraint ใน schema และไม่มีการตรวจสอบในโค้ด — unique index เดียวบนส่วนหัวคือ `(grn_no, deleted_at)`

**การโพสต์ GL — สถานะที่แม่นยำ ณ 2026-09-22** ตอนนี้มีโมดูล general ledger ใน backend แล้ว (`apps/micro-business/src/gl/{gl-jv,gl-posting,gl-period,gl-budget,…}`; gateway `application/gl-jv`, `gl-posting`, `gl-reports`; ตาราง `tb_gl_jv*`, `tb_gl_balance`, migration `20260909170000_gl_core_master`, `20260914030000_gl_core_jv_ledger`) `GlPostingService.post()` (`gl-posting.service.ts:293`) โพสต์ **journal voucher** (`tb_gl_jv`) ลง `tb_gl_balance` โค้ดเดียวที่สร้าง JV คือโมดูล JV เอง (`gl-jv.service.ts:214`, source `manual`), การรัน template (`gl-jv-template.service.ts:786`) และ voucher แบบ reversal / closing ของ posting service เอง (`gl-posting.service.ts:571,909,1116`) `enum_gl_jv_source` จองสมาชิก `inventory` และ `ap` ไว้ (`schema.prisma:4724-4736`) แต่ **ไม่มีโค้ดใดเขียนค่าเหล่านั้น**; การ grep `apps/micro-business/src` นอก `src/gl/` หา `GlPosting`, `gl-jv` หรือ `from '@/gl` เจอเพียง `app.module.ts` และชุด seed ของ tenant `good-received-note.logic.ts`, `inventory-transaction.service.ts` และ `period-end.service.ts` ไม่ได้ import อะไรจากโมดูล GL เลย **ข้อสรุป: ไม่มี GRN, inventory transaction หรือการปิดงวดใดโพสต์เข้า GL ledger ในวันนี้** มีหน้า wiki แยกต่างหากที่บันทึกโมดูล GL; ในหน้านี้ให้ถือว่า "Dr Inventory / Cr AP" ยังไม่ implement ต่อไป enum `post_type` ของส่วนหัว (`ap` | `consignment` | `cash`, ค่าเริ่มต้น `ap`) ยังถูกเก็บและ serialize แต่ไม่ขับ branch ใดใน backend; `enum_transaction_type` ยัง resolve การรับ GRN ทุกรายการเป็นค่าเดียวคือ `good_received_note`

ความปลอดภัยของอาหารและการควบคุมคุณภาพ: การรับของทุกรายการที่โพสต์แล้วจะได้หมายเลข lot และวันหมดอายุแบบไม่บังคับ **แก้ไข 2026-09-22:** หมายเลข lot ถูกสร้างโดย `buildLotNo()` (`apps/micro-business/src/common/helpers/lot-number.helper.ts:27-35`) ในรูปแบบ **`<location_code><YYMM><ลำดับ 4 หลัก>`** — เช่น `MK-0126070246` — โดยเลขลำดับคือ `lot_seq_no` ของ cost layer ซึ่งเริ่มนับใหม่ที่ 1 ในทุกงวดสินค้าคงคลัง (`getNextLotSeqNo`, `inventory-transaction.service.ts:1399-1406`) รูปแบบเดิม `RC{YY}{MM}{seq}` ไม่มีอยู่แล้ว และไม่มีการเขียนทับหมายเลข lot ด้วยมือบนหน้าจอ GRN วันหมดอายุถูกเก็บบนเหตุการณ์รับ (`tb_good_received_note_detail_item.expired_at`, nullable, จงใจไม่ตรวจสอบเทียบกับ `grn_date` เพื่อให้ยังรับสินค้าใกล้หมดอายุหรือหมดอายุแล้วได้ — schema comment ที่ `:1076`) ไม่มีประตู "quality hold" ต่อบรรทัด, ฟิลด์ `accepted_qty` หรือกลไก accept/reject — ความคลาดเคลื่อนในการรับของถูกจัดการด้วยการกรอก `received_qty` ให้น้อยกว่าปริมาณที่สั่ง ความคลาดเคลื่อนของราคาถูกตรวจสอบเทียบกับ **ราคา PO** (`order_price` เทียบ `received_price` โดย normalise เป็นหน่วยฐาน) ไม่ใช่เทียบกับ vendor pricelist; ไม่มีการค้น pricelist ภายในโมดูล GRN

## 3. แนวคิดสำคัญ

- **Receiving Lot**: หมายเลข lot ที่กำหนดตอนโพสต์บน inventory ledger (ไม่ใช่บนแถว GRN) สร้างในรูปแบบ `<location_code><YYMM><ลำดับ 4 หลัก>` โดย `buildLotNo()` (`common/helpers/lot-number.helper.ts`); เลขลำดับคือ `lot_seq_no` ที่นับตามงวด แถว ledger (`tb_inventory_transaction_detail`) ถือ `good_received_note_detail_item_id` ชี้กลับไปยังเหตุการณ์รับ ทำให้ FIFO consumption และการสืบย้อน recall resolve ไปยังบรรทัด GRN ต้นทางได้ **แก้ไข 2026-09-22:** รูปแบบไม่ใช่ `RC{YY}{MM}{seq}`, ตั้งค่าไม่ได้ และไม่มีการเขียนทับด้วยมือ
- **Partial Receipt**: GRN ที่ทำให้ PO ที่ค้างอยู่สำเร็จเพียงบางส่วน ปริมาณที่รับสามารถน้อยกว่าที่สั่งได้ และตอน commit PO ต้นทางจะเคลื่อนไปที่ `partial` (หรือ `completed` เมื่อทุกบรรทัดที่ active เข้าเงื่อนไข `received_qty ≥ order_qty − cancelled_qty`, `logic.ts:543-570`) สามารถออก GRN หลายใบกับ PO เดียวกันได้จนกว่าจะครบ
- **Over/Under Receipt**: การรับขาดไม่มีวันไม่ผ่านการตรวจสอบ (`percentOverage` ให้คะแนน 0, `deviation.ts:62-63`) การรับเกินถูกควบคุมด้วย `qty_deviation_limit` ของสินค้า (เปอร์เซ็นต์ที่เกิน `order_base_qty`; `0`/`NULL` = ไม่มีเพดาน) และราคาเกินด้วย `price_deviation_limit` (เปอร์เซ็นต์ที่เกิน `order_price` ต่อหน่วยฐาน) — ทั้งคู่ประเมินตอน **save** และผ่าน `POST …/verify` ด้วย `verify_state = save` และทั้งคู่ปฏิเสธ **ทั้งเอกสาร** (`GRN_DEVIATION_LIMIT_EXCEEDED`, HTTP 400) ไม่มีการตั้งค่า "over-receipt tolerance" ระดับ tenant; เพดานอยู่ที่ product master ต่อสินค้า
- **Save (`draft → saved`)**: รัน checklist ของการ save (`findGoodReceivedNoteSaveIssues`, `validate.ts:90-106`: ต้องเป็น `draft`; เพดาน deviation; ส่วนลด/ภาษี ≤ มูลค่าบรรทัด), ใช้เลข running จริง (`assignRunningGrnNo`, `service.ts:2392-2410`), ประทับ `received_by_*` ถ้ายังว่าง และ — **เฉพาะบน business unit แบบ average** — โพสต์การเคลื่อนไหวสต๊อกล่วงหน้าพร้อม `posted_at_save = true` บนส่วนหัวการเคลื่อนไหว BU แบบ FIFO: ไม่กระทบสต๊อก PO ไม่ถูกแตะตอน save เลย UI ถือว่า `saved` เป็น read-only (`grn-header.tsx:81-82`: `canEdit = !isCommitted && !isVoid && !isSaved`); `PATCH` ของ backend ไม่มี guard สถานะของตัวเอง แต่ endpoint เพิ่ม/แก้/ลบ detail เป็น `draft`-only (`GRN_NON_DRAFT_NO_*_DETAIL`) และการ PATCH GRN สถานะ `saved` บน BU แบบ average จะ void และโพสต์การเคลื่อนไหวใหม่หากปริมาณหรือต้นทุนเปลี่ยน (`repostGrnLedgerIfChanged`, `ledger.ts:434-459`)
- **Commit (`saved → committed`) — เหตุการณ์โพสต์**: `commit()` / `approve()` ตรวจกฎงวดเปิดบน `grn_date` อีกครั้ง แล้ว `postReceipt()`: (1) เขียนส่วนหัว `tb_inventory_transaction` + `tb_inventory_transaction_detail` หนึ่งแถวและ cost layer ต่อเหตุการณ์รับที่เคลื่อนสต๊อก — เว้นแต่เขียนไปแล้วตอน save; (2) เพิ่ม `received_qty` และปริมาณ FOC ที่รับบน junction row ของ PO↔PR และ `tb_purchase_order_detail.received_qty` แล้วคำนวณ `po_status` ใหม่; (3) ประทับ `po_receiving_applied` บนส่วนหัวการเคลื่อนไหวเพื่อให้การ commit ซ้ำไม่นับซ้อน frontend ให้ commit **draft** ได้ในคลิกเดียว — ไล่เรียก `PATCH → /save → /commit` (`use-grn-form-actions.ts:486-513`) และหาก `grn_date` อยู่นอกงวดเปิดปัจจุบัน จะถามว่าจะคงวันที่เดิมหรือย้ายไปวันแรกของงวด (`PeriodDateChoice`, `components/share/period-date-choice.tsx`) ไม่มี batch commit และไม่มี auto-commit ตามกำหนดเวลา
- **Extra Cost Allocation — ยืนยันแล้วว่าใช้งานจริง (2026-09-10, commit `f8cd9f0d9`)**: `allocate_extra_cost_type` ของส่วนหัว extra cost ขับการแบ่งจริงใน `allocateExtraCost()` (`good-received-note.extra-cost.ts:40-61`) ตอนโพสต์: **`by_qty` = แบ่งยอดรวมเป็นส่วนเท่า ๆ กัน หนึ่งส่วนต่อบรรทัดที่นำสต๊อกเข้าคลัง**; **`by_value` = ถ่วงน้ำหนักตามปริมาณสต๊อกของแต่ละบรรทัด (`received_base_qty + foc_base_qty`)**; **`manual` = ไม่จัดสรรอะไรเลย** (ยังไม่มีฟิลด์กรอกต่อบรรทัด) ส่วนแบ่งถูกแปลงเป็นสกุลฐานและบวกเข้า landed cost ของบรรทัด (`stockCostOf() = base_net_amount + base_extra_cost_amount`, `inventory-transaction.service.ts:90-92`) และบันทึกบน cost layer ทุกชั้นเป็น `extra_cost_amount` (migration `20260910130000_add_cost_layer_extra_cost`) หมายเหตุว่าชื่อสวนทางกับความรู้สึก — `by_value` ถ่วงตามปริมาณ ส่วน `by_qty` แบ่งเท่ากัน — ให้บันทึกตามที่โค้ดทำ frontend เสนอเฉพาะ `by_qty` และ `by_value` (`grn-extra-cost-fields.tsx:201-202`) ไม่มีโหมด `by_weight` / `by_volume`
- **FOC (Free of Charge)**: `foc_qty` อยู่บนเหตุการณ์รับเดียวกับปริมาณที่จ่ายเงิน **ตั้งแต่ 2026-09-10 FOC เข้าสต๊อก**: ปริมาณที่โพสต์คือ `received_base_qty + foc_base_qty` (`stockQtyOf()`, `inventory-transaction.service.ts:73-75`) ดังนั้นต้นทุนต่อหน่วยที่เขียนลง ledger จะถูกเจือจาง (`(base_net_amount + extra cost) / (received + FOC)` ปัดเป็น 2 ตำแหน่ง) บรรทัดที่เป็น FOC ล้วนยังโพสต์เข้าสต๊อกที่ต้นทุนศูนย์และยังเพิ่มตัวนับ FOC ที่รับของ PO (`logic.ts:508-523`) หมายเหตุว่า `createFromGoodReceivedNote` ตัดรายการที่ `received_base_qty = 0` ออกก่อน (`inventory-transaction.service.ts:849`) — *เอกสาร* ที่เป็น FOC ล้วนจึงไม่โพสต์อะไรเลย; บรรทัด FOC ล้วนภายในเอกสารที่มีบรรทัดจ่ายเงินอย่างน้อยหนึ่งบรรทัดยังถูกโพสต์โดย loop ต่อรายการ
- **`post_type` (ap / consignment / cash)**: enum ระดับส่วนหัว (`enum_good_received_note_post_type`, ค่าเริ่มต้น `ap`) ที่มาแทน boolean คู่ `is_consignment` / `is_cash` เดิม — สองฟิลด์นั้นไม่มีอยู่ใน schema แล้ว **ยังไม่ยืนยัน:** ไม่พบ logic แยกเงื่อนไขตาม `post_type` ใน backend (ไม่มีการจัดการ GL ที่ต่างกัน ไม่มี inventory-transaction type ที่แยกกัน) — ฟิลด์นี้ถูกเก็บและ expose ผ่าน API แต่ดูเหมือนจะไม่เปลี่ยนพฤติกรรมของระบบ `enum_transaction_type` (enum ประเภทของ ledger คงคลัง) ไม่มีสมาชิก "Stock In" / "Consignment In" / "Non-Inventory" — การรับ GRN จะโพสต์เป็นค่าเดียวคือ `good_received_note` เสมอ

## 4. บทบาทและ Persona

| Role | ความรับผิดชอบ |
|------|----------------|
| Store Keeper / Receiving Clerk | รับการส่งของจริงที่ dock นับสินค้าเทียบกับ PO และใบส่งของของผู้ขาย สร้าง GRN ในสถานะ `draft` (draft สามารถเก็บแบบไม่ครบได้ — ปุ่ม Save-draft ข้ามการ validate ฟอร์ม, `use-grn-form-actions.ts:400-411`) แนบใบส่งสินค้า บันทึกปริมาณที่รับต่อบรรทัด และ save (`draft → saved`: ตรวจสอบ ออกเลข GRN และโพสต์สต๊อกล่วงหน้าเฉพาะบน BU แบบ average เท่านั้น) |
| Store Manager / Inventory Manager | ตรวจสอบ GRN สถานะ `saved` และ commit (`saved → committed`) — ขั้นตอนที่โพสต์สต๊อก (BU แบบ FIFO) และเพิ่มยอด PO การที่คนเดียวกันจะทำทั้งสองขั้นได้หรือไม่เป็นเรื่องของสิทธิ์: gateway ใช้ guard key **เดียวกัน** ปกป้องทั้ง save และ commit (`AppIdGuard('goodReceivedNote.commit')` บนทั้ง `PATCH …/save` และ `PATCH …/commit`, `good-received-notes.controller.ts:1369,1626`) และ permission key ฝั่ง frontend คือ `procurement.goods_received_note.commit` (`constant/permissions.ts:73`) ไม่มีการตรวจสอบตามชื่อ role |
| Purchaser / Procurement Officer | เป็นเจ้าของ PO ต้นทางที่ GRN ถูกสร้างขึ้นมาเทียบด้วย ตรวจสอบข้อมูลการรับของสำหรับ PO ที่ตนออก และประสานกับผู้ขายเมื่อมีความคลาดเคลื่อน (ส่งขาด ผิดสินค้า) |
| Department Manager | ตรวจสอบ GRN ที่กระทบ cost-centre ของแผนก และยืนยันว่าสินค้าที่รับตรงกับที่สั่งสำหรับแผนก |
| System Administrator | ดูแล RBAC และการกำหนดลำดับ running-code (เลข GRN), รหัสภาษี และอัตราแลกเปลี่ยน; ดูแลการเชื่อมต่อกับโมดูล PO และ Inventory **ยังไม่ยืนยัน:** ไม่พบ "GRN configuration console" เฉพาะทาง (ตัวแก้ไขรูปแบบเลข lot, panel endpoint การเชื่อมต่อ) ในซอร์สปัจจุบัน — หน้าจอตั้งค่าภาษี สกุลเงิน และ running-code เป็นหน้าจอทั่วไปข้ามโมดูล ตามที่บันทึกไว้ใน [system-config](/th/inventory/system-config) และ [master-data](/th/inventory/master-data) ไม่ใช่ workspace เฉพาะของ GRN |

**ตัดออกในรอบนี้ (ไม่พบ route, component หรือ endpoint ที่ตรงกัน):** บทบาท "Finance Team / AP Clerk" ที่อธิบายว่าทำ three-way match ตรวจสอบการจัดสรรค่าใช้จ่ายเพิ่มเติมก่อนโพสต์ AP และเซ็นรับรองกิจกรรมการรับของที่สิ้นงวด การค้นหาทั่ว repo ของ `carmen-turborepo-backend-v2` และ `carmen-inventory-frontend-react` สำหรับ `three-way`, `vendor_invoice`, `VendorInvoice`, และ `tb_invoice` ให้ผลศูนย์รายการ และ `enum_stage_role` (enum บทบาท stage ของ workflow ที่ใช้ร่วมกับ PR/PO) ไม่มีสมาชิก `finance` — ตรงกับข้อสรุปเดียวกันที่ยืนยันแล้วในโมดูล `purchase-order`

## 5. โมดูลที่เกี่ยวข้อง

**กระแสข้ามโมดูล:**
- [purchase-order](/th/inventory/purchase-order) — GRN ถูกสร้างจาก PO ที่สถานะ `approved` / `sent_or_print` / `partial`; commit เพิ่ม `received_qty` และ `po_status` ของ PO
- [inventory](/th/inventory/inventory) — commit (หรือ save บน BU แบบ average) โพสต์การเคลื่อนไหวสต๊อกเข้า; `GET …/good-received-notes/:id/stock-movements` (2026-08, `service.ts:2082`) คืน lot ที่โพสต์แล้วต่อบรรทัด และแท็บ Stock Movement บน frontend จะแสดงเฉพาะเมื่อ GRN เป็น `committed` แล้ว (`grnStockVisible()`, `grn-stock-table.tsx:30-32`)
- [costing](/th/inventory/costing) — landed cost ต่อบรรทัด (net + extra cost ที่จัดสรร หารด้วยปริมาณรับ + FOC) ป้อนเข้า FIFO lot record หรือ average ของสินค้า; `GET …/cost/products/:product_id/last-receiving/unit/:unit_id` และ `…/last-cost` (Bruno `_uncategorized/cost/`) อ่านราคา GRN ล่าสุดกลับมา
- [vendor-pricelist](/th/inventory/vendor-pricelist) — **ไม่มีการเชื่อมต่อฝั่ง GRN**; price deviation ตรวจสอบเทียบกับ `order_price` ของ PO ไม่ใช่ pricelist
- [purchase-order/credit-note](/th/inventory/purchase-order/credit-note) — `GET …/good-received-notes/vendor/:vendor_id/cn` แสดง GRN สถานะ `saved`/`committed` ที่ยังมีสินค้าอย่างน้อยหนึ่งรายการที่ยังไม่ถูกออก credit note; ตั้งแต่ 2026-09-21 สินค้าหนึ่งรายการบน GRN ใบหนึ่งออก credit note ได้เพียงครั้งเดียว (`findFullyCreditedGrnIds`, `service.ts:494-552`)
