# เทมเพลตรายงาน (Report Templates)

> **At a Glance**
> **วัตถุประสงค์ของโมดูล:** หน้าจอ authoring ที่ผู้ดูแลภายในของ Carmen Blue ใช้สร้างและดูแลเทมเพลตรายงานแบบ XML ที่ขับเคลื่อนทุกเอกสารพิมพ์ของแพลตฟอร์ม และ (ตั้งแต่ 2026-07-23) เลือก default form template ต่อประเภทเอกสารด้วย &nbsp;·&nbsp; **กลุ่มผู้ใช้:** ผู้ดูแลภายในและวิศวกร support ของ Carmen Blue ที่ถือ grant permission `report_template.*` (ดู [Permissions](/th/platform/report-templates/permissions)) &nbsp;·&nbsp; **เอนทิตี/ตารางหลัก:** `tb_report_template` (ฟิลด์: `name`, `description`, `name_i18n`, `description_i18n`, `report_group`, `template_type`, `is_default`, `dialog`, `content`, `export_xml`, `allow_run`, `allow_export`, `source_type`, `source_name`, `source_params`, `orientation`, `signature_config`, `allow_business_unit`, `deny_business_unit`, `calculation_methods`, `is_standard`, `is_active`, `builder_key`, `doc_version`) และ `tb_report_template_version` (หนึ่ง snapshot ต่อการสร้าง/แก้ไข/กู้คืน/นำเข้า) &nbsp;·&nbsp; **หน้าย่อย:** 5

## 1. ภาพรวม

โมดูล Report Templates คือหน้าจอ authoring สำหรับนิยามรายงานของแพลตฟอร์ม แต่ละแถวใน `tb_report_template` อธิบายเอกสารที่พิมพ์/ส่งออกได้หนึ่งรายการ ได้แก่ ชื่อที่อ่านง่ายสำหรับมนุษย์ แท็ก `report_group` สำหรับการจัดกลุ่มใน picker ตอน runtime payload XML สองชุด (**Dialog XML** ที่นิยาม form ตัวกรองที่แสดงให้ผู้ใช้ปลายทาง และ **Content XML** ที่นิยามผลลัพธ์ที่ render ออกมา) การผูก data source (`source_type` + `source_name` + `source_params`) และฟิลด์ควบคุมการเข้าถึงที่จำกัดว่า business unit ใดจะรันได้ หน้ารายการที่ `/report-templates` (`ReportTemplateManagement.tsx`) เป็นแคตตาล็อกแบบ server-paginated ค้นหาได้ กรองได้ มี facet สำหรับ status/source-type/template-type/calculation-method ส่งออก CSV เลือกแถว ดาวน์โหลด backup แบบ JSON และนำเข้า JSON ได้ หน้าแก้ไขที่ `/report-templates/:id/edit` และ `/report-templates/new` (`ReportTemplateEdit.tsx`) เป็น layout สองคอลัมน์ คอลัมน์ซ้ายเป็นการ์ดเดียวที่มีข้อมูลเทมเพลต (ชื่อและคำอธิบาย EN/TH) ขอบเขต BU และวิธีคิดต้นทุน และการผูก data source ส่วนคอลัมน์ขวามีสี่แท็บ — Dialog XML, Content XML, Export XML และแท็บ Preview ที่กลายเป็น layout editor แบบลากวางของ Dialog ระหว่างแก้ไข แถบ data-lineage ใต้ชื่อหน้าสรุป ฟิลด์ Dialog → source → builder key และ sheet ประวัติเวอร์ชันแสดงรายการและกู้คืนการบันทึกก่อนหน้า

ตั้งแต่ 2026-07-23 โมดูลนี้ยังเป็นเจ้าของการเลือก "ชนิดเอกสาร → เทมเพลต" ซึ่งเดิมเป็นงานของโมดูลแยกชื่อ `print-template-mapping` ค่า `report_group` ที่จับคู่กับ `template_type = "form"` และ boolean ใหม่ `is_default` (unique ต่อกลุ่มในหมู่ form template ที่ live) ตอนนี้ตัดสินใจว่า layout เอกสารเดี่ยวตัวไหนที่ business unit จะได้เป็น default สำหรับ `report_group` หนึ่ง ๆ เมื่อยังไม่ได้เลือกเอง สิ่งนี้แสดงผลผ่านโมดูล Platform ระดับบนสุดของตัวเอง [กลุ่มฟอร์มรายงาน (Report Form Groups)](/th/platform/report-form-groups) (`/report-form-groups`, `ReportFormGroupManagement.tsx` มีรายการ sidebar ในกลุ่ม Content เป็นของตัวเอง) เป็นการ์ดหนึ่งใบต่อ `report_group` ที่ตายตัว แต่ละใบแสดง form template ของตนพร้อม action "set as default" — ดู [โมดูลที่เกี่ยวข้อง](#5-โมดูลที่เกี่ยวข้อง) สำหรับสิ่งที่มันแทนที่ หน้าย่อยเดิมที่ `report-templates/form-groups` ตอนนี้เป็น pointer สั้น ๆ ครอบคลุมเฉพาะส่วนที่ยังเฉพาะเจาะจงกับโมดูลนี้ (§7)

การผูก data source คือสัญญาตอน runtime เทมเพลตจะอ่านจาก **view** ของฐานข้อมูล (ไม่มีพารามิเตอร์ ตัวกรองทำงานผ่าน WHERE clause ตอน runtime) **function** (พารามิเตอร์แบบ positional ที่ได้จาก `source_params`) หรือ **procedure** (พารามิเตอร์ positional เหมือนกัน บวกกับ INOUT refcursor ต่อท้ายชื่อ `rs` และ procedure มีหน้าที่ใช้ตัวกรองภายในเอง) แต่ละแถวของ `source_params` จะ map ฟิลด์ filter หนึ่งฟิลด์จาก Dialog XML (เช่น `DateFrom`) เข้ากับ type ของ PostgreSQL และธง `nullable` ค่า `source_name` เป็น identifier แบบ plain ที่ไม่มี schema prefix และไม่มี quote — จะถูก resolve กับ schema ของแต่ละ tenant ตอน runtime ตัว probe "Browse in BU" ให้ผู้ดูแลเลือก business unit เป้าหมาย ดึงรายการ views/functions/procedures ที่มีอยู่จริงใน schema ของ tenant นั้น แล้วเลือกแทนที่จะพิมพ์ identifier จากความจำ

เทมเพลตถูกแบ่งเป็น **standard** (Carmen Blue ส่งมอบ/ดูแล) และ **custom** (ต่อลูกค้า) ผ่าน `is_standard` และเป็น **active**/**inactive** ผ่าน `is_active` ทั้งคู่สลับได้ต่อแถวจากหน้า Edit และใช้เป็น facet ของหน้ารายการ Chip-input list `allow_business_unit` และ `deny_business_unit` กำหนดขอบเขตของเทมเพลตให้กับ BU ที่ระบุ (`allow` ว่าง = ทุก BU; `deny` ทับ `allow`) การแก้ไขเทมเพลตแสดงการ validate XML แบบ inline (จำนวนบรรทัด จุดแสดง parse error ต่อแท็บ) และเตือนเรื่องการเปลี่ยนแปลงที่ยังไม่ได้บันทึกผ่านแถบ action ติดล่างและ hook `useUnsavedChanges` รายละเอียดพฤติกรรม UI และตัว schema XML เองอยู่ในหน้าย่อย — หน้า landing นี้เพียงปูทาง

## 2. บริบททางธุรกิจ

แพลตฟอร์มของธุรกิจโรงแรมพิมพ์และส่งอีเมลเอกสารปฏิบัติการจำนวนมาก — purchase order, ใบ GRN, รายการ pick ของ store requisition, รายงานมูลค่าสต็อก, สรุปต้นทุนอาหาร — และ layout ของแต่ละแบบไม่ค่อยเหมือนกันระหว่างลูกค้า กลุ่มแบรนด์ต้องการ logo และที่อยู่ของตน ทีมการเงินอยากให้ประทับอัตราแลกเปลี่ยนไว้ด้านบน บาง property ต้องการเวอร์ชันภาษาไทยควบคู่กับต้นฉบับภาษาอังกฤษ การ hard-code ความหลากหลายทุกแบบลงในโค้ดแอปพลิเคชันจึงไม่ยั่งยืน แพลตฟอร์มจึงแยกนิยามรายงานออกมาเป็นแถว XML ที่วิศวกร support ของ Carmen Blue (ไม่ใช่ลูกค้า) สามารถแก้ไขผ่านหน้าจอ admin นี้ได้

แถว `tb_report_template` จึงทำหน้าที่สองอย่าง ในด้านปฏิบัติการ มันคือ source ที่ runtime ของรายงานเรียกใช้เมื่อผู้ใช้คลิก "print" หรือเปิดรายงาน — Dialog XML render form พารามิเตอร์ Content XML render ผลลัพธ์ และ `source_name`/`source_params` ตัดสินใจว่าจะเรียก object ใดในฐานข้อมูล ในด้านเชิงพาณิชย์ มันคือหน่วยของการ customise การส่งมอบเอกสารพิมพ์ใหม่ให้ลูกค้าหมายถึงการเพิ่ม (หรือ clone) แถวที่นี่ ไม่ใช่การ deploy แอปพลิเคชันซ้ำ การเก็บการ authoring ไว้ใน Platform admin — โดย gate ด้วย permission key `report_template.*` ([rbac](/th/platform/rbac)) — ช่วยรักษาสัญญาการ customise นี้ไว้โดยไม่ต้องเปิดเผย XML เบื้องหลังให้ลูกค้าเห็น จนถึง 2026-07-23 เทมเพลตตัวไหนจะ render เอกสารประเภทหนึ่ง ๆ ตัดสินโดยโมดูลแยก print-template-mapping ซึ่งถูกลบออกจากผลิตภัณฑ์เมื่อ 2026-07-24 (carmen-backstage commit `de11377`); การตัดสินใจนั้นย้ายมาอยู่บนตารางนี้เองแล้ว ผ่าน `template_type = "form"` + `report_group` + `is_default` (ดู §1 และ §3)

## 3. แนวคิดสำคัญ

- **Report template**: หนึ่งแถวใน `tb_report_template` ที่อธิบายเอกสารที่พิมพ์/ส่งออกได้หนึ่งรายการอย่างครบถ้วน ประกอบด้วยฟิลด์ระบุตัวตน (`name`, `description`, `report_group`, `template_type`) payload XML สองชุด (`dialog`, `content`) การผูก data source (`source_type`, `source_name`, `source_params`) ฟิลด์ print-layout (`orientation`, `signature_config` — ยังไม่เปิดเผยในฟอร์มของ SPA) ขอบเขต BU (`allow_business_unit`, `deny_business_unit`, `calculation_methods`), ชื่อที่แปลแล้ว (`name_i18n`, `description_i18n`), สวิตช์ run/export และ Export XML และธง lifecycle (`is_standard`, `is_default`, `is_active`, `builder_key`, `doc_version`)
- **Dialog XML**: payload XML ที่เก็บในฟิลด์ `dialog` ซึ่ง runtime ของรายงานใช้ render form ตัวกรอง/พารามิเตอร์ที่แสดงให้ผู้ใช้ปลายทางก่อนรันรายงาน แก้ไขในแท็บ **Dialog XML** ของคอลัมน์ขวา พร้อมจำนวนบรรทัดและการ validate แบบ inline
- **Content XML**: payload XML ที่เก็บในฟิลด์ `content` ซึ่งกำหนดวิธี render ผลลัพธ์ของรายงาน แก้ไขในแท็บ **Content XML** ตัว editor รับการอัปโหลด `.frx`, `.xml` หรือ `.txt` ซึ่งสะท้อนว่ารายงานเดิม authored ด้วย `.frx` ของ FastReport แล้ว migrate เข้ามาเป็น XML ที่นี่
- **Export XML**: payload XML ชุดที่สามแบบ optional ใน `export_xml` (null = ไม่มี) เอกสาร `<Export>` ที่ map dataset ของรายงานเป็นคอลัมน์ CSV สำหรับ action "Export data" ของรายงาน; `ParseExportXML` ของ micro-report ต้องมี root `<Export>` อย่างน้อยหนึ่ง `<Column>` (แต่ละตัวมี `Header` และมีเพียงหนึ่งใน `Field` / `Value` / `Expression`) และรับ `<Sort>` key แบบ optional กับแอตทริบิวต์ `GroupBy`/`FileName` แท็บ Export XML แสดงคำเตือน lint แบบไม่บล็อก (`lintExportXml`) เช่น `Field` ที่ไม่ใช่คอลัมน์ใน Content XML รูปแบบเต็ม: [XML Spec](/th/platform/report-templates/xml-spec) §4
- **Preview / layout editor**: แท็บที่สี่ของคอลัมน์ขวา ในโหมดดู จะ render Dialog XML เป็น form แบบ disabled (พร้อม badge จำนวนคอลัมน์ จำนวนฟิลด์ และคำเตือนจาก parser) เมื่อหน้าอยู่ในโหมดแก้ไขบน viewport อย่างน้อย 768px มันกลายเป็น **Dialog layout editor** — ตัวเลือก Cols (1–4), stepper ColSpan ต่อเซลล์, ลากเพื่อเรียงใหม่หรือย้ายเข้า/ออก `<Group>`, เลือกหลายรายการเพื่อ group/ungroup, เมนู Add-field (Date, Lookup, Date range, Lookup range), ลบพร้อม toast Undo และ property panel ของฟิลด์ที่โฟกัส การแก้ไขถูกเขียนกลับตรงเข้า Dialog XML รายละเอียดที่ [UI Screens](/th/platform/report-templates/ui-screens) §4.8
- **สวิตช์ Run / Export (`allow_run`, `allow_export`)**: boolean สองตัว แสดงในฟอร์มเฉพาะ `template_type = "list"` (ค่าเริ่มต้น `true` / `false`) `allow_run` แสดงปุ่ม Run Report; `allow_export` แสดงปุ่ม Export data และต้องมี Export XML (ฟอร์มเตือนเมื่อเปิดโดยไม่มี) เมื่อปิดทั้งสอง เทมเพลตจะถูกซ่อนจาก Report List บังคับฝั่ง server โดย micro-report: การรันแบบโต้ตอบปฏิเสธ list template ที่ `allow_run` ปิด และ endpoint export ปฏิเสธเมื่อ `allow_export` ปิด ทั้งคู่เป็น `REPORT_TEMPLATE_UNAVAILABLE` (`run_disabled` / `export_disabled`) (`micro-report` `service/report_service.go`, `model/availability.go`)
- **Calculation methods (`calculation_methods`)**: array ของ `average` / `fifo` / `average_per_location` (Prisma `enum_calculation_method`) ค่าว่างหมายถึงเทมเพลตรองรับทุกวิธีคิดต้นทุน; มิฉะนั้น business unit ที่วิธีคิดต้นทุนไม่อยู่ในรายการจะใช้ไม่ได้ ฟอร์มแสดง checkbox เฉพาะ list template และล้างค่าสำหรับ form template micro-report ใช้กฎนี้ตอนรัน (`TemplateAvailability`, เหตุผล `calculation_method_unsupported`)
- **ชื่อและคำอธิบายหลายภาษา**: `name_i18n` / `description_i18n` (`{en?, th?}`) SPA เขียนทั้ง `name` / `description` ธรรมดาและ JSON `*_i18n` ทุกครั้งที่บันทึก; `name` ยังเป็น unique key (ไม่ซ้ำในหมู่แถวที่ live) และถูกเขียนคู่ให้เท่ากับ `name_i18n.en`
- **ประวัติเวอร์ชัน**: ทุกการสร้าง แก้ไข กู้คืน และนำเข้า เขียน snapshot `tb_report_template_version` (`version` = `doc_version` ของแถวหลังเขียน) ปุ่ม **Versions** บนหน้าแก้ไขเปิด sheet ที่แสดงรายการเวอร์ชัน diff ระดับฟิลด์ และ diff ของ XML (Dialog / Content / Export) เทียบกับเรคคอร์ดปัจจุบัน ดาวน์โหลด JSON ต่อเวอร์ชัน และ **Restore** (ดู §4 เรื่อง gate)
- **Backup และ import**: ดาวน์โหลดเทมเพลตเป็น JSON ได้ (`carmen.report-template-backup`, format version 1) ทีละตัวจากหน้าแก้ไข / เมนูของแถว สำหรับแถวที่เลือก หรือสำหรับทุกแถวที่ตรงกับ query ของรายการปัจจุบัน; dialog **Import** พรีวิวไฟล์ backup และให้ผู้สร้างเลือกสร้าง เขียนทับ หรือข้ามแต่ละแถว (§4)
- **Source type**: หนึ่งใน `view`, `function`, หรือ `procedure` view ไม่รับพารามิเตอร์ (runtime ใช้ตัวกรองผ่าน WHERE clause) function และ procedure ต้องประกาศพารามิเตอร์ positional ผ่าน `source_params` procedure ต้องรับ INOUT refcursor ต่อท้าย (ชื่อ default `rs`) เพิ่ม และต้องใช้ตัวกรองภายในเอง
- **Source name**: SQL identifier แบบ plain (ไม่มี schema prefix ไม่มี quote) ที่ระบุชื่อ view/function/procedure ใน schema ของแต่ละ tenant resolve ตอน runtime กับ schema ของ business unit ที่เรียก ต้องระบุเมื่อ `source_type` เป็น `function` หรือ `procedure`
- **Source params**: รายการแบบมีลำดับที่ map ฟิลด์ filter ของ Dialog (`filter` เช่น `DateFrom`) เข้ากับ type ของ PostgreSQL (เช่น `date`, `uuid`, `text`) พร้อมธง `nullable` เก็บเป็น `{ params: [...] }` ว่างสำหรับ source แบบ `view`
- **Allow / Deny business unit**: รายการรหัส BU แบบคั่นด้วย comma สองรายการที่รับผ่าน chip input รายการ `allow` ที่ว่าง แปลว่า "ทุก business unit รันเทมเพลตนี้ได้" รายการ `deny` ทับ `allow` เฉพาะ list template เท่านั้น — ฟอร์มบันทึกรายการว่างสำหรับ `template_type = "form"` และ micro-report ถือว่า form template พร้อมใช้เสมอ (`TemplateAvailability` คืน available สำหรับ `form` ก่อนอ่านรายการ) โค้ดถูกเทียบแบบตัวพิมพ์ใหญ่
- **Template Type (`list` vs. `form`)**: คอลัมน์ `template_type` (เปลี่ยนชื่อจาก `kind` เมื่อ 2026-07-23; ค่าก็เปลี่ยนจาก `"report"`/`"print"` เป็น `"list"`/`"form"`) แบ่งแคตตาล็อกเป็นรายงานเชิงวิเคราะห์แบบตารางสำหรับผู้ใช้ (`"list"`) และ layout เอกสารเดี่ยว (`"form"`) ต่างจาก `kind` เดิม `template_type` **ถูกเปิดเผย** และจำเป็นในฟอร์ม edit ของ SPA (select: List / Form) — มันยังเปลี่ยนว่า field อื่นใดที่ฟอร์มแสดง (`is_standard`/chip ขอบเขต BU สำหรับ list template; `is_default` + dropdown `report_group` แบบตายตัวสำหรับ form template)
- **Report group และ default (เฉพาะ form template)**: สำหรับ `template_type = "form"` SPA จำกัด `report_group` ไว้ที่รายการ code คงที่ 12 ตัว (`FORM_REPORT_GROUPS`: `PR, PO, GRN, SR, CN, SI, SO, IA, PC, SC, RFP, EOP`) และ `is_default` ทำเครื่องหมายเทมเพลตที่ live หนึ่งตัวต่อกลุ่มที่ใช้เมื่อ business unit ยังไม่ได้เลือกเอง — บังคับด้วย partial unique index ระดับฐานข้อมูล (`idx_report_template_default_per_group`) ไม่ใช่แค่ฝั่ง client หน้าจอ [Form Groups](/th/platform/report-templates/form-groups) (`/report-form-groups`) คือ surface เฉพาะสำหรับตั้งค่านี้
- **Standard vs. Custom**: ธง `is_standard` แยกเทมเพลตที่ Carmen Blue ส่งมอบ/ดูแล (`Standard`) จากของที่เพิ่มต่อลูกค้า (`Custom`) แสดงเป็น badge ของคอลัมน์ในหน้ารายการ
- **สถานะ Active / Inactive**: ธง `is_active` ควบคุมว่าเทมเพลตจะปรากฏใน picker ตอน runtime หรือไม่ เทมเพลตที่ inactive ยังแก้ไขได้ที่นี่ แต่ผู้ใช้ปลายทางมองไม่เห็น
- **Builder key**: identifier สั้น ๆ ที่ใส่หรือไม่ใส่ก็ได้ (เช่น `pr-summary`) ที่เชื่อมเทมเพลตกับ builder/registration ในโค้ดแอปพลิเคชัน เป็น free-text และยังไม่ได้ validate จาก Platform admin
- **Probe BU picker**: feature สำหรับการพัฒนาในส่วน Source ของหน้า Edit ที่โหลดรายการ views/functions/procedures จริงจาก schema ของ tenant ที่เลือก (`reportTemplateService.listDbObjects`) เพื่อให้ผู้ดูแลเลือก `source_name` จาก dropdown แทนที่จะพิมพ์

## 4. บทบาทและ Persona

การเข้าถึงถูกควบคุมด้วยโมเดล RBAC แบบ permission-based ของแพลตฟอร์ม ([rbac](/th/platform/rbac)): แต่ละ route ถือ key `requiredPermission` ของตัวเองบน `PrivateRoute` และ session ต้องมี grant `report_template.*` ที่ตรงกัน (หรือ flag super-admin) จึงจะผ่าน session ที่ไม่มี key จะเห็นหน้า `Forbidden` ภายใน shell `<Layout>` ปกติ

| Route | `requiredPermission` |
|---|---|
| `/report-templates` | `report_template.read` |
| `/report-templates/new` | `report_template.create` |
| `/report-templates/:id/edit` | `report_template.update` |

ภายในหน้าจอ action ที่แก้ไขข้อมูลมี gate `<Can>` ของตัวเอง: **Add Template** ห่อด้วย `report_template.create` (ทั้งปุ่ม header และปุ่ม empty-state — ไม่มีตัวใดที่ไม่ถูก gate), **Edit** ของ row ด้วย `report_template.update`, **Delete** ของ row ด้วย `report_template.delete` (มีเฉพาะภายในหน้า — ไม่มี route ใดต้องการ key delete) และ toggle **Edit** ของหน้า edit ด้วย `report_template.update` action ใหม่: sheet **Versions** และ **Download backup** ต่อเทมเพลต (header, เมนูของแถว) กับ **Download all** / **Download selected** ถูก gate ด้วย `report_template.read` (ปุ่ม **Restore** ใน sheet เองใช้ `report_template.update` และซ่อนขณะแก้ไข); **Import** ถูก gate ด้วย `report_template.create` และตัวเลือก **Overwrite** ต่อแถวปรากฏเฉพาะ session ที่ถือ `report_template.update` ด้วย ฝั่ง server gateway กั้น `GET .../versions` และ `GET .../versions/:version_no` ด้วย `report_template.read` และ `POST .../versions/:version_no/restore` ด้วย `report_template.update` (`backstage_report-templates.controller.ts`) การ probe Browse-in-BU เรียก `GET /api-system/report-templates/db-objects` ซึ่ง gateway กั้นด้วย **`sql_workbench.read`** ไม่ใช่ key `report_template.*` — ผู้สร้างที่มี `report_template.update` แต่ไม่มี grant SQL Workbench จะได้ toast error จาก probe และต้องพิมพ์ `source_name` เอง action **View History** (ใหม่ ข้ามโมดูล) ทั้งบน row และหน้า edit ถูก gate ด้วย `activity_log.read` พร้อม `clusterId={BACKSTAGE_SCOPED_RECORD}` — ฟีเจอร์ Activity Trail เดียวกับที่ document ไว้ใน [clusters](/th/platform/clusters)/[business-units](/th/platform/business-units)/[users](/th/platform/users)/[applications](/th/platform/applications) ไม่มี gate ใดส่ง `clusterId` จริง — เทมเพลตรายงานเป็น tenant-global การตรวจสอบจึง resolve โดยไม่จำกัดขอบเขตต่อ cluster

รายการ sidebar และ route ของทั้ง `/report-templates` และ `/report-form-groups` ถือ `permission: 'report_template.read'` เหมือนกัน (`../carmen-backstage/src/components/nav/backstageNav.ts`) — **key permission นี้ใช้ร่วมกันระหว่างโมดูลนี้กับรายการเมนู Form Groups** ไม่ใช่ของ Report Templates แต่ผู้เดียว แต่ **key feature ต่างกัน**: `feature: 'report_templates'` gate สาม route ของโมดูลนี้ ส่วน `feature: 'report_form_groups'` gate route และแถว sidebar ของ Form Groups แยกต่างหาก — การเปลี่ยน feature flag ของฝั่งหนึ่งไม่กระทบอีกฝั่ง ไม่มีแถว nav ใดถือ `superAdminOnly` เมทริกซ์ฉบับเต็ม ข้อยกเว้น bootstrap และกลไกของ gate อยู่ใน [Permissions](/th/platform/report-templates/permissions)

ลูกค้าปลายทางไม่เข้าถึงโมดูลนี้ — พวกเขาบริโภคผลลัพธ์ของรายงานผ่าน picker ตอน runtime ไม่ใช่ผ่านแคตตาล็อกเทมเพลต การ authoring ยังคงเป็นงานภายในของ Carmen Blue: การมอบสิทธิ์ให้ใครสักคนหมายถึงการ assign role ใน catalog ที่รวม key `report_template.*` (จนถึง 2026-06 surface นี้เคยถูก hardcode กับ role enum รุ่นเก่า `platform_admin` / `support_manager` / `support_staff` ซึ่งถูกถอดออกแล้ว — ตาราง mapping การ migrate อยู่ใน [rbac](/th/platform/rbac) §5)

## 5. โมดูลที่เกี่ยวข้อง

- [rbac](/th/platform/rbac) — โมเดล permission เบื้องหลัง key `report_template.*`: catalog, role, scoped assignment, bypass ของ super-admin; กลไกของ gate อยู่ใน [rbac permissions](/th/platform/rbac/permissions)
- **Print Template Mapping** — ถูกลบออกจากผลิตภัณฑ์เมื่อ 2026-07-24 (carmen-backstage commit `de11377`; ตามด้วย backend-gateway proxy และ permission key `print_template_mapping.*` ที่ถูกลบเมื่อ 2026-07-23 ใน carmen-turborepo-backend commit `c135bb21e`) เคยเป็นตาราง routing ที่ตัดสินว่าเทมเพลต `kind="print"` ตัวไหน render เอกสารแต่ละประเภท ตอนนี้การตัดสินใจนั้นทำบนตารางนี้โดยตรงผ่าน `template_type = "form"` + `report_group` + `is_default` แสดงผลผ่านโมดูล [กลุ่มฟอร์มรายงาน (Report Form Groups)](/th/platform/report-form-groups) แบบ standalone ความสามารถหนึ่งอย่างที่ไม่ได้ย้ายมาด้วยคือการกำหนด default ต่อ business unit — โมดูลเดิม route เทมเพลต default ต่างกันได้ต่อ BU แต่กลไก `is_default` ปัจจุบันไม่มีสิ่งทดแทน
- [business-units](/th/platform/business-units) — เป็นแหล่งของรหัส BU ที่ใช้ใน chip input `allow_business_unit` / `deny_business_unit` และการค้นหา schema ของ tenant ของ "Probe BU" picker
- [clusters](/th/platform/clusters) — อธิบายลำดับชั้น cluster/BU เหนือระดับ BU; เทมเพลตรายงานเป็น tenant-global และไม่มี FK ไปยัง cluster
- [users](/th/platform/users) — row identity ของ user ที่ role assignment ของ RBAC ชี้ไป; การมอบสิทธิ์ report-template หมายถึงการ assign role ที่รวม key `report_template.*`
