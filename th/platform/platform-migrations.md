# การย้ายระบบแพลตฟอร์ม (Platform Migrations)

**Platform Migrations** คือหน้าจอเดียว `PlatformMigrationManagement` ที่ `/platform/migrations` ซึ่งรัน operation สองแบบต่อ **ฐานข้อมูลแพลตฟอร์มเดียวที่ทุก cluster และทุก business unit ใช้ร่วมกัน** — ไม่ใช่ฐานข้อมูลของ tenant ใดตัวหนึ่ง แบบแรกคือ Prisma schema migration (Deploy, Resolve) แบบที่สองคือทะเบียนสคริปต์ seed 8 ตัว บวกกับ drift check 6 ตัว — 5 ใน 6 ตัวเป็น read-only ตัวที่หกเขียนข้อมูลจริงและถูกซ่อนจากคอนโซลนี้ (§3.3) — ซึ่งเติมหรือตรวจข้อมูลอ้างอิงระดับแพลตฟอร์ม เช่น สกุลเงิน, permission, platform role, license feature และ operation รายบริษัทหนึ่งตัวที่กล่าวถึงใน §3.4 เพราะทุกการเขียนที่นี่ลงไปในตารางที่ทุก tenant อ่าน หน้านี้จึงบอกทีละ operation ว่าอันไหนกดซ้ำได้และอันไหนไม่ได้ แทนที่จะพูดรวบยอดว่า "idempotent" คำเดียว

> **At a Glance**
> **Component:** `PlatformMigrationManagement` &nbsp;·&nbsp; **Route:** `/platform/migrations` กั้นด้วย `<PrivateRoute requireSuperAdmin feature="platform_migrations">` (`../carmen-platform/src/App.tsx:434-441`) &nbsp;·&nbsp; **Nav:** `superAdminOnly: true` — **ธงตัวนี้ ไม่ใช่การไม่มี permission key ต่างหากที่กั้นเมนูนี้** — `feature: 'platform_migrations'`, `groupKey: 'navGroup.database'`, ไม่มีฟิลด์ `permission` เลย (`platformNav.ts:53`) &nbsp;·&nbsp; **สองผู้มีสิทธิ์ฝั่ง backend:** header `x-deploy-token` ที่ตรงกัน (ตรวจ**ก่อน**) หรือ session ของ super-admin (ทางเลือกสำรอง) — ทั้งสองอยู่หลังสวิตช์เปิด/ปิดเดียวกัน `platform_migration.api_enabled` (§3.1, §4) &nbsp;·&nbsp; **ทะเบียน:** 2 การกระทำระดับ migration (Deploy, Resolve) + 14 operation ของ seed/check เห็นในคอนโซลนี้ 13 ตัว &nbsp;·&nbsp; **e2e suite:** **ไม่มี** — `../carmen-platform-e2e/tests/` ไม่มีโฟลเดอร์ `platform-migrations` &nbsp;·&nbsp; **หน้าย่อย:** 0

## 1. ภาพรวม

`PlatformMigrationManagement.tsx` (696 บรรทัด) render การ์ดซ้อนกัน 4 ใบ บวก run console ที่ใช้ร่วมกัน การ์ด **Status** (`PlatformMigrationManagement.tsx:361-442`) บอกว่าฐานข้อมูลแพลตฟอร์มมี migration ค้างอยู่ไหม มีปุ่ม **Apply migrations** ปุ่มเดียวที่รัน Deploy และมีสวิตช์ **Raw Prisma output** แบบยุบได้ที่โชว์ข้อความ CLI ที่ผ่านการปิดบังแล้วเบื้องหลังคำตัดสินนั้น ถัดลงมาคือการ์ด **Resolve a stuck migration (advanced)** ที่ยุบไว้เป็นค่าเริ่มต้น (`:444-518`) ให้ผู้ดูแลทำเครื่องหมาย migration หนึ่งโฟลเดอร์ว่า `applied` หรือ `rolled-back` ใน `_prisma_migrations` โดยระบุชื่อ โดยไม่รัน SQL ของมันจริง ถัดลงไปอีกคือการ์ดทะเบียนสองใบ — **Seed data** (ขอบซ้ายสีอำพัน มี badge "Writes data") กับ **Drift checks** — แต่ละใบ render หนึ่งแถวต่อหนึ่ง operation ผ่าน `OpRow` (`pages/platformMigration/OpRow.tsx`) ดึงมาจากทะเบียนเดียวกัน `platformSeedService.getCatalog()` (`:167-169`) ด้านล่างสุดมี `RunConsole` (`pages/platformMigration/RunConsole.tsx`) ที่โชว์ผลลัพธ์ของทุกการกระทำ — deploy, resolve และทุกการรัน seed/check — ในสมุดบันทึกเล่มเดียวที่จำกัดไว้ 20 รายการ (`useRunLog`, `runLog.ts:32`) เพราะงานจริงบนหน้านี้เป็นลำดับ (deploy แล้ว seed แล้วเช็คว่าเปลี่ยนอะไรไป) ไม่ใช่การกดทีละครั้งแบบแยกกัน (`runLog.ts:6-9`)

ทุกคำขอจากหน้านี้เดินทางจาก frontend → `backend-gateway` (ที่ authorization guard ทำงาน, §3.1) → เรียก RPC ภายใน → `micro-business` ซึ่งเป็นโปรเซสที่เรียก `prisma` จริงหรือ spawn โปรเซสลูก `bun <script>` เข้าฐานข้อมูลแพลตฟอร์ม `PlatformMigrationsService`/`PlatformSeedsService` ของฝั่ง gateway เองเป็นแค่ตัวส่งต่อ RPC บาง ๆ ไม่มี logic ของตัวเอง (`../carmen-turborepo-backend-v2/apps/backend-gateway/src/platform/platform-migrations/platform-migrations.service.ts:1-47`, `platform-seeds/platform-seeds.service.ts:1-65`) ส่วน controller ของ `micro-business` เอง (`apps/micro-business/src/authen/platform_migration/platform_migration.controller.ts`, `platform_seed/platform_seed.controller.ts`) **ไม่มีการตรวจสิทธิ์ซ้ำรอบที่สอง** — เชื่อ guard ของ gateway เต็มที่

ผู้ดูแลที่ต้องระบุ business unit สำหรับ operation หนึ่งตัว (§3.4) จะถูกถามผ่าน `BuSwitcher` (`PlatformMigrationManagement.tsx:662-685`) ส่วนแผง debug สำหรับ dev เท่านั้น (`DevDebugSheet`) โชว์ payload ดิบของ `/api-system/platform/migrations/status` แต่โชว์เฉพาะ dev build เท่านั้น — ตัวคอมโพเนนต์เองคืน `null` ถ้า `import.meta.env.DEV` ไม่จริง (`../carmen-platform/src/components/ui/dev-debug-sheet.tsx:18`) จึง**ไม่ใช่ด่าน RBAC**

## 2. บริบททางธุรกิจ

ตารางข้อมูลอ้างอิงระดับแพลตฟอร์มทุกตาราง — permission, role, สกุลเงิน, license feature — ถูกนิยามไว้ในซอร์ส (`prisma-shared-schema-platform/prisma/seed.*.data.ts`) แต่จะกลายเป็นข้อมูลจริงก็ต่อเมื่อรันสคริปต์ตัวใดตัวหนึ่งที่คอนโซลนี้เรียก ก่อนที่คอนโซลนี้จะมี สคริปต์เหล่านี้เป็นคำสั่ง `bun run db:seed.*`/`db:check.*` ที่รันได้เฉพาะคนมี shell บนโฮสต์ที่เข้าถึงฐานข้อมูลแพลตฟอร์มได้โดยตรง หน้านี้คือเปลือกฝั่งผู้ใช้ที่ครอบสคริปต์ชุดเดียวกันนั้นเป๊ะ ๆ (§3.3 อ้างถึงทุกตัว) บวกสิ่งหนึ่งที่ CLI ไม่เคยมี: run console แบบสตรีมสด ให้ผู้ดูแลที่กำลังดูสคริปต์ seed ที่แตะแถว permission หลักร้อยแถว (`seed.permission.data.ts` มีประมาณ 278 รายการ) เห็นความคืบหน้าแทนที่จะรอหน้าจอดำเปล่า ๆ

เดิมพันคือเหตุผลที่หน้านี้ต้องมีรูปแบบแบบนี้: ทุกสคริปต์ที่นี่เขียนลงฐานข้อมูลแพลตฟอร์ม**เดียว** ไม่ใช่ของ tenant ใดตัวหนึ่ง การรัน `seed-platform-role-permission` ที่พลาดไปไม่ได้กระทบลูกค้ารายเดียว — มันกระทบ permission catalog ที่หน้า role ของทุก cluster อ่าน นี่ยังเป็นเหตุผลที่คอนโซลนี้จงใจ**ไม่**เปิดให้กดสคริปต์ CLI ตัวหนึ่งที่ยังมีอยู่ในซอร์ส: `db:seed.platform-super-admin` อ่าน environment variable `SUPER_ADMIN_USER_ID` แล้วมอบสิทธิ์ super-admin แบบไม่มีเงื่อนไขให้ user id นั้น — ผู้กดจากหน้าเว็บเลือกไม่ได้ว่าจะให้ใคร และจากการอ่านสคริปต์เองยืนยันว่าไม่มีการเขียน `created_by_id` ที่ไหนเลย (`seed.platform-super-admin.ts:8-39`) — จึงไม่มี audit trail ว่าใครถูกมอบสิทธิ์หรือใครเป็นคนมอบ คอมเมนต์ของทะเบียนเองระบุเหตุผลของการตัดออกว่า [Super Admins](/th/platform/super-admins) ทำงานนี้อยู่แล้วอย่างถูกต้อง ผ่านหน้าจอที่บันทึกไว้จริงว่าใครเป็นคนกระทำ (`PLATFORM_SEED_CATALOG`, `platform_seed.catalog.ts:25-29`); การอ่านสคริปต์ที่ถูกตัดออกยืนยันว่าคอมเมนต์นี้ถูกต้องจริง ไม่ใช่แค่มีอยู่เฉย ๆ

## 3. แนวคิดสำคัญ

### 3.1 สองผู้มีสิทธิ์หลังสวิตช์เดียว — และแต่ละทางบันทึก actor เป็นใคร

`PlatformMigrationGuard.canActivate()` (`../carmen-turborepo-backend-v2/apps/backend-gateway/src/auth/guards/platform-migration.guard.ts:118-140`) เป็นด่านตรวจสิทธิ์เดียวสำหรับ**ทุก** route ในโมดูลนี้ — ทั้ง migrations controller และ seeds controller ประกาศ `@UseGuards(PlatformMigrationGuard)` เหมือนกัน (`platform-migrations.controller.ts:59`, `platform-seeds.controller.ts:36`) มันทำงานตามลำดับนี้เป๊ะ ๆ:

1. **สวิตช์ ตรวจก่อนเสมอ** `isApiEnabled()` อ่านฟิลด์ `api_enabled` ของแถว `platform_migration` จาก `tb_platform_config` แคชไว้ 60 วินาที; แถวที่ไม่มี, แถวที่อ่านไม่ได้ หรือฟิลด์ที่เป็นค่าอื่นนอกจาก `true` เป๊ะ ๆ ล้วนอ่านเป็น**ปิด** (`platform-migration.guard.ts:69-94`) ถ้าสวิตช์ปิด ทุก route ในโมดูลนี้ตอบ `403 Platform migration API is disabled` ไม่ว่าใครจะเป็นคนเรียก — deploy token กับ session ของ super-admin ถูกปฏิเสธเท่ากัน (`:119-121`)
2. **Deploy token ตรวจก่อนในบรรดาสองผู้มีสิทธิ์** ถ้าสวิตช์เปิด guard จะเทียบ header `x-deploy-token` ของคำขอกับ `envConfig.PLATFORM_DEPLOY_TOKEN` ด้วยการเปรียบเทียบแบบใช้เวลาเท่ากัน (`isTokenEqual`, `:103-110`, `timingSafeEqual`) ถ้าตรงกันจะตั้ง `request.deployActor = 'ci:deploy-token'` แล้วคืน `true` ทันที — **ไม่มีการเรียก Keycloak ไม่มีการค้นหา super-admin เลย** สำหรับเส้นทางนี้ (`:122-128`) `PLATFORM_DEPLOY_TOKEN` มีค่า default เป็นสตริงว่าง (`apps/backend-gateway/src/libs/config.env.ts:219`) และ token ที่ตั้งไว้เป็นค่าว่างไม่มีทางเท่ากับ token ที่ส่งมาได้เลยในการเปรียบเทียบของ guard เอง (`presentedToken && configuredToken && ...`, `:125`) เส้นทางนี้จึงไม่มีผลใด ๆ ในสภาพแวดล้อมที่ไม่เคยตั้งค่า token ไว้อย่างชัดเจน
3. **Super-admin ทางเลือกสำรอง** เฉพาะเมื่อไม่มี token ใดตรงกัน guard ถึงจะรัน `KeycloakGuard` แล้วต่อด้วย `PlatformSuperAdminGuard` (`:129-134`) ตัวหลังเรียก RPC (`platform-permissions.effective`) แล้วอนุญาตเฉพาะเมื่อ `is_super_admin` ในผลลัพธ์เป็น `true` เป๊ะ ๆ โดย fail-closed (ปฏิเสธ) เมื่อ RPC ผิดพลาด (`platform-super-admin.guard.ts:40-70`) เมื่อสำเร็จ guard จะตั้ง `request.deployActor = 'super-admin:<user_id>'` (`platform-migration.guard.ts:135-139`)

ทั้ง migrations controller และ seeds controller บันทึก audit log แบบมีโครงสร้างที่ระบุ `deployActor` ตัวเดียวกันนี้ทุกครั้งที่เรียก (`executeAuditLog`, `platform-migrations.controller.ts:81-88`; seeds controller สตรีมข้อมูลแทนที่จะรอผลลัพธ์ก้อนเดียว จึงไม่มีบรรทัด audit แบบเดียวกัน — ดู §6); controller ของ `micro-business` เองห่อทุกการเรียกที่เขียนข้อมูลด้วย `runWithAuditContext` โดยใช้ `user_id`/`tenant_id` ของผู้เรียกจาก payload ของ RPC (`platform_migration.controller.ts:59-64,76-78`) **นี่คือเรื่องเต็ม ๆ ที่หน้า [Platform Config](/th/platform/platform-config) เองใน §3.2 พาดพิงถึง**: การย้าย `PLATFORM_MIGRATION_API_ENABLED` มาเป็นคีย์นี้ทำให้ *ตัวคีย์ config เอง* ต้องเป็น super-admin เท่านั้นถึงจะแก้ได้ แต่ไม่ได้ตัดเส้นทาง deploy token ของ CI ที่เข้าสู่ endpoint การ migration ที่คีย์นี้กั้นออกไปเลย — เส้นทางนั้นถูกตรวจก่อน ไม่ใช่ตรวจทีหลัง และไม่มีผลก็ต่อเมื่อ `PLATFORM_DEPLOY_TOKEN` ถูกปล่อยว่างไว้เท่านั้น

### 3.2 สองคอนโซลใช้ lock เดียวกัน คนละ transport คนละ timeout

**Deploy/Resolve** (`PlatformMigrationService` ของ `micro-business`) เรียก Prisma CLI ด้วย `execFile` ไม่ผ่าน shell และมี timeout ตายตัว (`PLATFORM_MIGRATION_TIMEOUT_MS` default `120000` มิลลิวินาที / 2 นาที — `apps/micro-business/src/libs/config.env.ts:146`) บัฟเฟอร์ผลลัพธ์ทั้งก้อนก่อนตอบกลับ (`platform_migration.service.ts:154-171`) **Seed/Check** (`PlatformSeedService`) แทนที่ด้วยการ `spawn` `bun <script>` แล้วสตรีม stdout/stderr ทีละบรรทัดเป็น NDJSON ผ่าน HTTP response ของ gateway มี timeout ของตัวเองที่ยาวกว่า (`PLATFORM_SEED_TIMEOUT_MS` default `300000` มิลลิวินาที / 5 นาที — `config.env.ts:149`) เพราะสคริปต์ seed รันนานกว่า schema migration ได้มาก (`platform_seed.service.ts:224-241`) ทั้งสองปิดบัง connection string และ `SYSTEM_(DATABASE|DIRECT)_URL` จากทุกบรรทัดที่ส่งออก (`sanitize()` มีในทั้งสอง service) และทั้งสองสร้าง environment แบบ allowlist ให้โปรเซสลูกเพื่อไม่ให้อ่านความลับของบริการอื่นได้ (`buildChildEnv()` ทั้งสอง service)

ทั้งสอง service ใช้ lock **ตัวเดียวกัน** คือ `PlatformDbLock` (`apps/micro-business/src/authen/platform_db/platform_db.lock.ts`) — ตัวแปร boolean `running` ธรรมดาในหน่วยความจำ ถูกยกออกมาจาก `PlatformMigrationService` โดยเจตนา เพื่อไม่ให้ `migrate deploy` กับการรัน `seed.permission` วิ่งพร้อมกันเข้าฐานข้อมูลเดียวกันได้ (`:16-21`) การเรียกครั้งที่สองระหว่างที่มีงานค้างอยู่จะได้ `409 A platform database operation is already running` (`PlatformDbBusyError` แสดงเป็น `ErrorCode.ALREADY_EXISTS`) ซึ่ง frontend โชว์เป็น `toast.warning` ไม่ใช่ error (`errorText()`/`notifyError()`, `PlatformMigrationManagement.tsx:46-57`) **คอมเมนต์ของ lock เองระบุขอบเขตไว้ชัดเจน: หนึ่งโปรเซส ไม่ใช่ทั้งคลัสเตอร์ของ replica** (`platform_db.lock.ts:25-27`) — ถ้า `micro-business` รันมากกว่าหนึ่ง instance โค้ด 409 นี้ป้องกันสอง instance ไม่ให้รัน operation ที่ขัดแย้งกันพร้อมกันไม่ได้เลย ดู §6

การปิดแท็บเบราว์เซอร์หรือหลุดการเชื่อมต่อระหว่างรันจะ**ไม่**หยุดโปรเซสที่กำลังทำงานอยู่ในทั้งสองเส้นทาง: teardown ของสตรีม seed แค่ตั้งธง `cancelled` เพื่อไม่ส่งอีเวนต์ต่อไปยังการเชื่อมต่อที่ตายแล้ว และจงใจไม่เรียก `child.kill()` — คอมเมนต์ในโค้ดระบุว่าเป็นความตั้งใจ สอดคล้องกับพฤติกรรมของ tenant migration เพราะ seed ที่ถูกฆ่ากลางคันทิ้งข้อมูลค้างครึ่ง ๆ ไว้ได้ (`platform_seed.service.ts:289-296`) lock จะถูกปล่อยก็ต่อเมื่อโปรเซสลูกจบจริงเท่านั้น

### 3.4 ตัวเลือกหลาย BU ของ `seed-role-permission` เขียน tenant app-role — ไม่ใช่ platform RBAC

`seed-role-permission` เป็น operation เดียวในทะเบียนที่มีพารามิเตอร์ประกาศไว้ (`bu_id` บังคับ ชนิด `uuid` — `platform_seed.catalog.ts:42-44`) และตั้งแต่ commit `157a65e` (`../carmen-platform` HEAD — "feat(platform-migrations): เลือกได้หลาย BU ตอน seed role permissions (#281)") คอนโซลนี้ให้ผู้ดูแลเลือก BU **หลายตัว**พร้อมกันสำหรับ operation นี้ ผ่าน dialog `BuSwitcher` ตัวเดียวที่ตั้งเป็น `multiple` (`PlatformMigrationManagement.tsx:662-685`) ตัวตรวจว่า op ไหนต้องถามค่านี้เป็นแบบทั่วไป ไม่ได้ hardcode ที่ id ของ op นี้โดยเฉพาะ — `buParamOf()` มองหาพารามิเตอร์ชนิด `uuid` ที่ประกาศไว้และชื่อมีคำว่า `bu` op รายบริษัทตัวใหม่ในอนาคตจึงได้ dialog เดียวกันนี้อัตโนมัติ (`:78-83`) BU ที่เลือกจะถูกรัน**เรียงทีละตัว ทีละคำขอ ไม่มีการรันพร้อมกัน** — `runOpBatch` await `runOnce` ทีละตัวใน loop `for` (`:296-326`) เพราะ target ทุกตัวยิงสคริปต์ฐานข้อมูลเดียวกัน และคอมเมนต์ในโค้ดเองระบุตรง ๆ ว่าการรันพร้อมกันจะเชิญ deadlock มาเองและทำให้ log ที่สตรีมมาสลับกันอ่านไม่ออก (`:287-295`) ตัวที่ล้มเหลวหนึ่งตัวไม่หยุดตัวที่เหลือ ผู้ดูแลที่เลือกห้า BU จึงยังได้ครบทั้งห้าที่ถูกรัน (`:293-295`)

สิ่งที่ตัวเลือกนี้รันจริงต่อ BU คือสคริปต์เดี่ยวเดียวกันที่อธิบายไว้ใน §3.3: มันเขียนแถวลง **`tb_application_role`** และ **`tb_application_role_tb_permission`** ผูกกับ `business_unit_id` แต่ละตัว (`seed.role-permission.ts:452-543`) **นี่คือระบบ application-role รายผู้เช่า ตารางคนละคู่กับตาราง platform RBAC — `tb_platform_role`, `tb_platform_permission`, `tb_platform_role_tb_permission` — ที่ [Platform RBAC](/th/platform/rbac) เป็นผู้อธิบาย** ตัวเลือกหลาย BU บนหน้านี้ไม่แตะสิ่งที่ RBAC ดูแลเลยแม้แต่นิดเดียว การอ่าน "seed role permissions หลาย BU พร้อมกัน" ว่าเป็น operation ของ RBAC จะเป็นความเข้าใจผิดโดยสิ้นเชิง (`seed-platform-role-permission` ในทางกลับกัน เขียนลงตาราง link ของ platform RBAC จริง — ดู §3.3 — แต่ไม่รับ `bu_id` และรันรายบริษัทไม่ได้)

## 4. บทบาทและสิทธิ์

ไม่มีสตริง `permission` เลยในโมดูลนี้ — การเข้าถึงอิงตัวตนล้วน ๆ ผ่านสามชั้นที่เป็นอิสระจากกันและต้องเห็นตรงกันทั้งหมด:

1. **แถวเมนู:** `superAdminOnly: true` ใน `platformNav.ts:53`; ตัวกรองของ `buildPlatformNav()` จะเก็บแถวนี้ไว้เฉพาะเมื่อ `!item.superAdminOnly || opts.isSuperAdmin` (`:91-98`) — ผู้ที่ไม่ใช่ super-admin จะไม่เห็นเมนูนี้เลย แม้แต่เป็นแถวที่ปิดใช้งาน
2. **Route:** `<PrivateRoute requireSuperAdmin feature="platform_migrations">` (`App.tsx:434-441`) render `<Forbidden />` ให้ผู้ที่ล็อกอินแล้วแต่ไม่ใช่ super-admin ที่พิมพ์ URL ไปที่ `/platform/migrations` โดยตรง — ตรวจ*ก่อน*ด่านฟีเจอร์แฟล็ก ผู้ถูกปฏิเสธจึงเห็น 403 ไม่ใช่ 404 ที่มาจากแฟล็ก (`PrivateRoute.tsx:87-103`)
3. **ทุก endpoint ฝั่ง backend:** `PlatformMigrationGuard` (§3.1) — สวิตช์ก่อน แล้วค่อย deploy-token-หรือ-super-admin ตรวจซ้ำทุกครั้งที่เรียกไม่ว่า frontend จะโชว์อะไรไปแล้วก็ตาม

ชั้นที่ 3 เป็นชั้นเดียวจากสามชั้นที่การเรียก API ตรง ๆ ข้ามไม่ได้; ชั้น 1 กับ 2 เป็นความสะดวกฝั่ง frontend ไม่ใช่ด่านความปลอดภัย `PlatformSuperAdminGuard` เองตัดสินสถานะ super-admin ด้วยการเรียก RPC ไปที่ `platform-permissions.effective` แล้วเช็ค `is_super_admin === true` โดย fail-closed (ปฏิเสธการเข้าถึง) เมื่อ RPC ผิดพลาด แทนที่จะอนุญาตเป็นค่าเริ่มต้น (`platform-super-admin.guard.ts:40-70`) — ทิศทาง fail-closed แบบเดียวกับที่ตัวสวิตช์เองใช้ (§3.1) ต่างจาก default แบบ *fail-open* ที่สวิตช์บังคับใช้ license ของ [Platform Config](/th/platform/platform-config) เองใช้อยู่

## 7. คำแนะนำ

มองทุกแถวบนการ์ด **Seed data** เป็นการเขียนข้อมูลที่ทุก cluster ใช้ร่วมกันโดยเจตนา ไม่ใช่การกดตามปกติ — ข้อความยืนยันของคอนโซลเองสำหรับการเขียนแบบ BU เดียวระบุตรง ๆ ว่า "cannot be interrupted once started" (`en.ts:3319`) และ §3.3 แสดงให้เห็นว่า seed operation ส่วนใหญ่เพิ่มเติมได้อย่างเดียว: มันสร้างและอัปเดต แต่ไม่ลบแถวที่ซอร์สไม่ได้นิยามไว้แล้ว การรัน `check-*` ที่คู่กันทั้งก่อนและหลังการรัน `seed-*` ที่เกี่ยวข้องเป็นวิธีเดียวที่คอนโซลนี้ให้ผู้ดูแลเห็น drift ทิศทางเดียวแบบนี้ได้ เพราะ `seed-platform-role-permission` และ `seed-role-permission` โดยเฉพาะไม่เคยถอนลิงก์ที่ตกยุคคืนเองเลย (§3.3) ก่อนใช้ **Resolve** ทุกครั้ง ให้ยืนยันด้วยตัวเองนอกคอนโซลนี้ว่า SQL ของ migration ที่ระบุชื่อนั้นรันจริงหรือไม่ — การกระทำนี้บันทึกตามที่ผู้ดูแลยืนยันมาเท่านั้น ไม่มีการตรวจสอบไขว้กับสถานะจริงของฐานข้อมูล (§3.3, §6) เพราะ lock การทำงานพร้อมกันเป็นแบบต่อโปรเซส ไม่ใช่ต่อคลัสเตอร์ (§3.2, §6) สภาพแวดล้อมที่รัน `micro-business` มากกว่าหนึ่ง instance ควรถือว่า "ทีละคนต่อครั้ง" ที่นี่เป็นข้อตกลงที่ต้องทำเอง ไม่ใช่การรับประกันที่ระบบบังคับใช้ และเพราะ `seed-report-template-upload` ขึ้นกับระบบภายนอกที่ยังใช้งานอยู่และ credential ที่ hardcode ไว้ในสคริปต์นั้นโดยตรง (§3.3) ความล้มเหลวที่เฉพาะเจาะจงกับ operation ตัวนั้นตัวเดียวควรตรวจกับระบบภายนอกก่อนที่จะสรุปว่าคอนโซลนี้พัง

## 8. โมดูลที่เกี่ยวข้อง

- [Platform Config](/th/platform/platform-config) — เจ้าของ `platform_migration.api_enabled` สวิตช์เดียวที่ทุก route ในโมดูลนี้อยู่หลังมัน §3.2 ของหน้านั้นครอบคลุมฝั่งคีย์ config ของสวิตช์นี้ ส่วน §3.1 ข้างต้นครอบคลุมสองผู้มีสิทธิ์ที่สวิตช์นี้กั้นอยู่
- [Platform RBAC](/th/platform/rbac) — เจ้าของ `tb_platform_role`, `tb_platform_permission` และ `tb_platform_role_tb_permission` ตารางที่ `seed-platform-role`, `seed-platform-permission` และ `seed-platform-role-permission` เติมข้อมูลให้ และยังเป็นสิ่งที่ตาราง tenant app-role ของ `seed-role-permission` ต้องไม่ถูกสับสนด้วย (§3.4)
- [Super Admins](/th/platform/super-admins) — วิธีที่ถูกต้องและมี audit ในการมอบสิทธิ์ที่การตรวจสิทธิ์ของโมดูลนี้ตรวจหาอยู่ในที่สุด และยังเป็นเหตุผลที่ `db:seed.platform-super-admin` ถูกตัดออกจากทะเบียนของคอนโซลนี้โดยเจตนา (§2, §6)
- [Business Units](/th/platform/business-units) — เจ้าของ `tb_business_unit` entity ที่ตัวเลือกหลาย BU (§3.4) เลือกจาก และที่ `check-seat-pool-view` (§3.3) ยืมมาหนึ่งแถวสำหรับการทดสอบที่ rollback ของมัน
- [Licenses](/th/platform/licenses) — ผู้บริโภคของ view `v_business_unit_seat` ที่ `check-seat-pool-view` ตรวจความหมายให้
- [Tenant Migrations](/th/platform/tenant-migrations) — คอนโซลเทียบเท่าสำหรับฐานข้อมูล tenant รายบริษัท; โมดูลนี้กลับรันต่อฐานข้อมูลแพลตฟอร์มเดียวที่ทุก cluster ใช้ร่วมกันแทน
